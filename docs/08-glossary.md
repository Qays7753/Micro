# قاموس Micro

| المصطلح | المعنى المعتمد |
|---|---|
| SaaS | خدمة يملكها المطور ويستضيفها ويبيعها؛ صاحب المشروع يستخدم الأداة ولا يدير SaaS داخل التطبيق. |
| Problem Statement | وصف الضرر المتكرر الذي نعالجه والنتيجة التي يحتاجها المستخدم. |
| Vertical Slice | مسار قيمة كامل من الإدخال حتى النتيجة والفعل التالي، لا مجموعة شاشات منفصلة. |
| Prototype المرحلة 2 | نموذج هاتف RTL محلي محدود لإثبات أول قيمة، وليس MVP التجاري أو SaaS مركزيًا. |
| MVP التجاري اللاحق | نسخة تأتي بعد Prototype وPilot، وقد تضيف Auth وworkspace والعزل والتخزين المركزي والمزامنة حسب الدليل. |
| محاكاة Pre-build | فحص مكتبي حتمي للقواعد والنصوص والتغطية، لا يثبت فهم مستخدم حقيقي أو العودة أو الدفع. |
| Domain Core | منطق المجال المالي والتشغيلي المستقل عن الواجهة والتخزين والمزود. |
| Activity Profile | اختلاف منظم للفئة فوق النواة المشتركة، مثل الحرفة أو الطعام أو الخدمة. |
| Cost snapshot | نسخة ثابتة من مدخلات التكلفة وقت اعتماد السعر أو تأكيد الطلب. |
| Knowledge state | درجة معرفة التكلفة: معروفة، مقدرة، جزئية، ناقصة، قديمة، أو متغيرة. |
| Price floor | أدنى سعر حماية مبني على التكلفة والهامش الاحتياطي، وليس بالضرورة السعر التجاري النهائي. في الشريحة الحالية يضاف `safetyBufferMinor` لكل وحدة. |
| Recognized revenue | الإيراد الذي اعترف به المنتج وفق سياسة صريحة؛ لا يساوي القبض تلقائيًا. |
| نتيجة الطلب | مؤشر ناتج عن طلب واحد مع درجة معرفة؛ لا يساوي تلقائيًا ربح المشروع التراكمي. |
| Cash | المال المقبوض والمتاح وفق الأحداث المسجلة؛ لا يساوي الربح. |
| Deposit | عربون مقبوض مرتبط بطلب، لا يظهر ربحًا نهائيًا تلقائيًا قبل التسليم أو التسوية. |
| `depositCollectedMinor` | إجمالي تاريخي للعربون المقبوض عبر أحداث الطلب، وليس بالضرورة الكاش الحالي القابل للرد. |
| `collectedMinor` | مجموع الكاش المقبوض الحالي الذي يدخل في حساب المتبقي؛ قد ينخفض عند رد عربون صريح. |
| Receivable / Debt | مبلغ مستحق لم يُقبض؛ لا يزيد الكاش حتى التحصيل. |
| Order event | حدث تاريخي في دورة الطلب؛ لا يُحذف بصمت. |
| Revision | نسخة تعديل للمواصفات أو التكلفة بعد تغير الطلب. |
| Idempotency key | مفتاح غير فارغ يمنع تكرار أثر العملية عند إعادة إرسالها؛ يفسر ضمن نوع العملية حتى لا يمنع عملية مختلفة بصمت. |
| Local-only | بيانات محفوظة على الجهاز فقط ولم تُثبت مركزيًا. |
| Pending sync | عملية تنتظر الإرسال أو التأكيد المركزي؛ حالة مستهدفة خارج Domain Core المحلي الحالي. |
| Conflict | اختلاف بين نسختين يحتاج دمجًا أو قرارًا بشريًا؛ لا توجد SyncQueue مركزية منفذة في Domain Core الحالي. |
| Entitlement | حالة وصول المستخدم إلى الخدمة، منفصلة عن مالية مشروعه. |
| Workspace | حيز بيانات مشروع معزول عن المشاريع الأخرى. |
| Modular Monolith | تطبيق واحد مقسم إلى وحدات مجال وحدود واضحة، دون microservices مبكرة. |
| Port / Adapter | حد يفصل منطق المجال عن مزود التخزين أو الشبكة أو الواجهة. |
| RLS | سياسات عزل صفوف قاعدة البيانات حسب المستخدم أو Workspace. |
| Pilot | تجربة محدودة مع مستخدمين حقيقيين لقياس السلوك والقيمة، لا إطلاق تجاري عام. |

## قاعدة المصطلح

عند استخدام مصطلح جديد في وثيقة أو كود، أضفه هنا إذا كان يؤثر على القرار أو المجال. لا تستخدم المصطلح نفسه بمعنيين مختلفين في الواجهة والمنطق.

| المصطلح | المعنى المعتمد |
|---|---|
| System Definition | تعريف Micro كنظام كامل: المستخدم والمشكلة والقيمة والمداخل والحدود والمخرجات. |
| Financial Operating Model | النموذج الذي يحدد كيف تتحول أحداث المشروع إلى تكلفة ومبيعات ومخزون وكاش وربح وذمم وتقارير. |
| User Operating Model | وصف كيفية استخدام صاحب المشروع للنظام يوميًا وأسبوعيًا وشهريًا وفي يوم بلا طلب. |
| Guidance Interaction Policy | قواعد التوجيه والسؤال والتفسير داخل سير العمل دون تحويل المنتج إلى دورة تعليمية. |
| Scenario Test Set | عائلة اختبار اصطناعية من شخصيات وحالات وأسئلة تمثل أنماطًا مختلفة لاكتشاف فجوات المفهوم قبل البناء. |
| Scenario Coverage Matrix | ربط المشكلة والقدرة بالحالات والأسئلة ومعيار القبول وحالة التنفيذ. |
| Canonical document | المرجع الرسمي الحالي لموضوع محدد؛ لا تُنشأ نسخة منافسة منه دون قرار. |
| Result explanation | تفسير سبب النتيجة المالية ودرجة المعرفة والفعل التالي، وليس عرض رقم مجرد. |
| Guidance state | حالة تفضيل أو مساعدة سياقية اختيارية؛ لا تعني تقدمًا في دورة تعليمية. |
