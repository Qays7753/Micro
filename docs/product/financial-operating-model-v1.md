# Micro — النموذج المالي التشغيلي v1

## حالة الوثيقة

هذه الوثيقة تحدد كيف يفكر Micro ماليًا في الداخل، وكيف يحول الأحداث اليومية إلى صورة مفهومة للمستخدم. لا تعني أن كل الطبقات ستُبنى في مرحلة واحدة، ولا تستبدل عقود Domain Core الحالية؛ بل تحدد النموذج الذي يجب أن تتوافق معه مراحل البناء.

عند التنفيذ الحالي، يقيّد [`docs/contracts/05-financial-p0-policies.md`](../contracts/05-financial-p0-policies.md) و`docs/implementation/02-domain-contract-coverage.md` ما يدخل Prototype وما هو مؤجل؛ لا تُفهم الجداول المستقبلية هنا على أنها قدرات منفذة في Domain Core.

## Major Discussion Points

## 1. الغرض

Micro نظام إدارة مالية عملي للمشروع وصاحب المشروع. لذلك لا يكفي أن يحفظ حركة مالية أو يحسب مجموعًا؛ يجب أن يربط الحدث بسياقه، ويبين أثره على التكلفة والمخزون والربح والكاش والذمم ومال المالك، ثم يوضح للمستخدم ما يعرفه وما ينقصه وما القرار القريب.

المعالجة الداخلية يمكن أن تكون عميقة ومحاسبية، لكن تجربة المستخدم تبدأ من واقعة يعرفها:

```text
اشترى، باع، قبض، دفع، استهلك، اقترض، استثمر، سحب، سلّم، ألغى، أو يريد التسعير
```

ثم يحول النظام هذه الواقعة إلى أثر مترابط بدل إجباره على إنشاء قيود منفصلة في دفاتر متعددة.

## 2. طبقات الحقيقة المالية

| الطبقة | السؤال | مثال |
|---|---|---|
| الحدث | ماذا حدث؟ | دفع 30 دينارًا لمورد |
| السياق | لماذا حدث ولمن؟ | خامات للمشروع أو لطلب محدد |
| التصنيف | ما طبيعته؟ | شراء مخزون، تشغيلي، شخصي أو أصل |
| الأثر | ماذا تغير؟ | نقص الكاش وزاد المخزون أو نشأ دائن |
| النتيجة | ماذا يعني ماليًا؟ | لا تظهر التكلفة كاملة قبل الاستهلاك |
| المعرفة | ما درجة اليقين؟ | معروفة أو مقدرة أو ناقصة |
| الفعل | ماذا أفعل؟ | أطلب عربونًا أو أراجع السعر أو أحصل دينًا |

لا يجوز أن تُعرض النتيجة كأنها حقيقة كاملة إذا كانت طبقة الحدث أو السياق أو التصنيف ناقصة.

## 3. الكيانات المالية المشتركة

| الكيان | الوظيفة |
|---|---|
| المشروع | السياق المالي العام والعملة والفترة |
| المنتج أو الخدمة | ما يبيعه المشروع وطريقة تكلفته |
| الطلب أو البيع | الاتفاق أو عملية البيع ونسخة التكلفة |
| الحدث المالي | قبض أو دفع أو شراء أو سحب أو استثمار أو تسوية |
| المادة أو المخزون | كمية وقيمة ومصدر واستهلاك وتلف |
| المصروف | طبيعة ومصدر وفترة وعلاقة بالطلب أو المشروع |
| الحساب أو المحفظة | مكان وجود الكاش أو الحركة النقدية |
| العميل أو المورد | طرف له مبلغ أو عليه مبلغ |
| الأصل | منفعة طويلة لا تحمل كلها على عملية واحدة |
| مال المالك | استثمار وسحب وحقوق مرتبطة بالمشروع |
| التقرير | نتيجة مجمعة لسؤال ووقت وافتراضات واضحة |

## 4. تصنيف المصروف والحدث

لا نستخدم كلمة «مصروف» لكل خروج مال. يرشح النظام التصنيف بناءً على إجابات قصيرة ويتيح التعديل:

| البعد | الخيارات الأساسية |
|---|---|
| العلاقة | للمشروع، شخصي، مشترك، غير محدد |
| الطبيعة | تشغيلي، أصل/استثمار، تمويل، سحب، تحويل، تسوية |
| السلوك | ثابت، متغير، مختلط، غير معروف |
| العلاقة بالتكلفة | مباشر، غير مباشر، عام، غير منطبق |
| العلاقة بالعمل | طلب، منتج، حملة، فترة، المشروع عمومًا |
| حالة الدفع | مدفوع، مستحق، جزئي، غير معروف |

الأبعاد ليست بدائل متعارضة دائمًا. قد تكون فاتورة الكهرباء تشغيلية وعامة ومشتركة ومدفوعة نقدًا. وقد تكون الماكينة أصلًا واستثمارًا ومدفوعة نقدًا. وقد تكون الخامات شراء مخزون لم تُستهلك بعد.

## 5. المبيعات والطلبات والنتيجة

الطلب هو كيان تشغيلي ومالي يبدأ عند الاتفاق أو المسودة، وليس عند القبض فقط. يجب الاحتفاظ بالسعر ونسخة التكلفة والموعد والعربون والمتبقي والحالة والأحداث والتعديلات.

يجب التفريق بين:

- عرض أو تقدير لم يتحول إلى بيع.
- طلب متفق عليه ولم يُسلّم.
- تسليم تم مع مبلغ متبقٍ.
- بيع نقدي أو آجل.
- عربون قبل اكتمال الالتزام.
- إلغاء يحتاج ردًا أو احتفاظًا أو مراجعة.
- نتيجة نهائية أو تقديرية أو ناقصة.

القبض يغير الكاش، لكنه لا يساوي الربح تلقائيًا. والتسليم لا يساوي قبضًا كاملًا. والدين يظل مستحقًا حتى يتم تحصيله.

## 6. نموذج التكلفة

تبنى تكلفة المنتج أو الطلب تدريجيًا من البنود المعروفة والمقدرة:

```text
تكلفة المواد
+ وقت العمل
+ التغليف
+ التوصيل
+ العمولات
+ الهدر
+ حصة المصاريف العامة
= التكلفة المخططة أو الفعلية
```

في Prototype الحرفة لا تدخل حصة المصاريف العامة تلقائيًا؛ عناصر التكلفة المنفذة هي المواد والوقت والتغليف والتوصيل والهدر، وفق عقد P0. أما المصاريف العامة والتكلفة الفعلية فتحتاج سياسة Ledger وتوزيعًا لاحقًا.

يحسب النظام تكلفة الوحدة عند وجود كمية أو yield صحيح، ويحتفظ بنسخة التكلفة عند اعتماد السعر أو تأكيد الطلب أو إتمام العمل. لا يجوز أن تغير أسعار المواد الحالية نتيجة طلب تاريخي بصمت.

يجب أن يميز المستخدم بين:

- التكلفة المباشرة المعروفة.
- التكلفة الكاملة المقدرة.
- التكلفة الفعلية بعد التنفيذ.
- بنود مؤثرة ناقصة تمنع تسمية النتيجة ربحًا نهائيًا.

## 7. المخزون والشراء والاستهلاك

شراء المادة قد يخرج كاشًا أو ينشئ دائنًا، لكنه لا يصبح كله تكلفة بيع لحظة الشراء إذا بقي في المخزون. عند استهلاك المادة، تنتقل قيمة الجزء المستهلك إلى تكلفة الطلب أو المنتج أو الهدر.

المسار الصحيح هو:

```text
شراء مادة
→ زيادة كمية وقيمة المخزون
→ دفع أو دائن للمورد
→ استهلاك أو بيع أو تلف أو مرتجع
→ تحميل الجزء المناسب على التكلفة أو الهدر
```

المخزون اختياري حسب النشاط في تجربة المستخدم، لكنه يجب أن يكون متاحًا للنواة عندما يكون مؤثرًا. لا نفرض وصفات على الخدمة، ولا نطلب مخزونًا تفصيليًا إذا لم يغير القرار.

## 8. الوقت وموارد المنزل والمصاريف العامة

وقت صاحب المشروع ليس مجانيًا تلقائيًا في تحليل الجدوى. إذا لم يدخل قيمة للساعة أو مدة العمل، يظهر أثر النقص. وفي مسار الحرفة الحالي، غياب `time` أو إدخال وقت `known` بدقائق أو سعر ساعة صفري يجعل الحالة `incomplete` ويمنع عرض ربح نهائي؛ يمكن للسياسات المستقبلية تعريف نتيجة نقدية أو أولية فقط إذا وُسمت صراحة ولم تُعرض كربح كامل.

المصاريف المشتركة مثل الكهرباء والإنترنت والوقود واستخدام المنزل تحتاج قاعدة أو نسبة أو تقديرًا. إذا لم توجد قاعدة موثوقة، يسجل النظام المصروف بصورة واضحة ويخفض درجة المعرفة بدل تحميله كاملًا أو استبعاده كاملًا بصمت.

## 9. الربح والكاش والذمم ومال المالك

يعرض Micro صورًا منفصلة ومترابطة:

| الصورة | ماذا تعني؟ |
|---|---|
| الربح أو الخسارة | نتيجة الاعتراف بالمبيعات والتكلفة والمصاريف خلال فترة |
| الكاش | النقد الموجود والتدفقات الداخلة والخارجة |
| ما لي | مبالغ مستحقة عند العملاء أو أطراف أخرى |
| ما علي | مبالغ مستحقة للموردين أو أطراف أخرى |
| المخزون | قيمة المواد أو المنتجات غير المستهلكة وفق السياسة |
| الأصول | معدات أو أدوات ذات منفعة ممتدة |
| مال المالك | استثمار وسحب لا يسجلان كمبيعات أو مصروف تشغيل |
| النتيجة التراكمية | هدف لاحق بعد Ledger عام وفترات وأحداث متعددة، مع الفترة والسياسة ودرجة المعرفة |

لا نختصر كل ذلك في رقم واحد باسم «ما أملك». يمكن عرض ملخص بسيط، لكن يجب أن يشرح مكوناته وعلاقته بالكاش والربح والالتزامات.

## 10. نقطة التعادل والسيولة والاستمرارية

نقطة التعادل ليست رقمًا ثابتًا مستقلًا. تعتمد على الفترة والتكاليف الثابتة وهامش المساهمة ومزيج المنتجات والأسعار والافتراضات. يجب أن يعرض Micro:

- التكاليف الثابتة المعروفة خلال الفترة.
- الهامش المستخدم ومصدره.
- حجم المبيعات أو الوحدات المطلوب للتعادل.
- ما الذي يتغير إذا تغير السعر أو التكلفة أو المزيج.
- درجة المعرفة وما لم يدخل في الحساب.

السيولة تجيب عن سؤال مختلف: هل يستطيع المشروع دفع التزاماته والاستمرار؟ قد يكون المشروع رابحًا على الورق ولا يملك كاشًا كافيًا للمواد أو الموردين. لذلك تعرض نقطة التعادل مع الكاش والالتزامات لا بدلًا منهما.

## 11. التقارير والتحليل

كل تقرير يجب أن يجيب عن سؤال عملي ويبين الفترة ومصدر البيانات ودرجة المعرفة:

| التقرير | سؤال المستخدم |
|---|---|
| الوضع الحالي | ماذا أملك، وما لي، وما علي؟ |
| الربح والخسارة | كم ربحت أو خسرت ولماذا؟ |
| الكاش | كم لدي، وما الذي سيدخل أو يخرج؟ |
| المبيعات | ماذا بعت وبأي اتجاه؟ |
| تكلفة الطلب أو المنتج | هل السعر يغطي التكلفة والوقت؟ |
| المصاريف | أين تذهب الأموال وما الذي ارتفع؟ |
| المخزون | ماذا أملك وما الذي راكد أو ينقص؟ |
| الذمم | من عليه لي ومن يجب أن أدفع له؟ |
| ربحية المنتجات | ما الأكثر ربحًا، لا الأكثر مبيعًا فقط؟ |
| نقطة التعادل | كم أحتاج لأغطي التكاليف؟ |
| منذ البداية | هدف لاحق يحتاج Ledger عام؛ لا يجيب عنه `CraftOrder` الحالي |

يجب أن يستطيع التحليل تفسير السبب، مثل ارتفاع المواد أو التوصيل أو التسويق أو الوقت أو الهدر أو ضعف التحصيل. إذا لم تكن البيانات تكفي، يقول ذلك.

## 12. المعرفة وعدم اليقين

لكل نتيجة مالية حالة معرفة:

- `known`: البنود المؤثرة موجودة ومحدثة.
- `estimated`: بعض البنود تقديرية.
- `partial`: نتيجة أولية لا تسمى ربحًا نهائيًا.
- `incomplete`: بند مؤثر مفقود.
- `stale`: السعر أو المدة قديمة وفق سياسة حداثة.
- `variable`: التخصيص أو الطلب يغير النتيجة.

«غير متأكد» خيار صحيح. يسجل النظام ما هو معروف، يوضح الافتراض، ويضع ما ينقص في المتابعة. لا يضع صفرًا لمجرد أن المستخدم لم يعرف القيمة.

## 13. التاريخ والتصحيح والتدقيق

لا يمحو Micro حدثًا ماليًا حساسًا بصمت. التصحيح يكون بعكس أو تسوية أو حدث تعديل يحمل سببًا ووقتًا ومصدرًا. إعادة إرسال العملية لا تضاعف الأثر بفضل `idempotency_key`. تحديث سعر مادة أو تصنيف مصروف لا يغير نتيجة تاريخية بصمت.

التخزين الدائم والـLedger العام ونسخ البيانات ليست مكتملة في Domain Core الحالي؛ هذه الوثيقة تحدد الحاجة المستقبلية ولا تدعي أنها منفذة الآن.

## 14. التدرج في التنفيذ

الصورة النهائية كاملة، لكن التنفيذ مرحلي:

1. تثبيت الأحداث والتصنيفات والنتيجة ودرجة المعرفة.
2. ربط الطلب بالتكلفة والسعر والعربون والتسليم والتحصيل.
3. إضافة المصاريف والكاش والذمم والمخزون الانتقائي.
4. إضافة التقارير الأساسية والربح التراكمي ونقطة التعادل.
5. إضافة تفسير الأسباب والتحليل ومقارنة المتوقع بالفعلي.
6. توسيع Activity Profiles والتخزين وSaaS بعد اختبار القيمة.

هذا التدرج لا يلغي اكتمال تعريف النظام؛ بل يقلل المخاطر ويمنع بناء طبقات بلا اختبار.
