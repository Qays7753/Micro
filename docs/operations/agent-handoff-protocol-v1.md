# بروتوكول استلام وتسليم Agent — Micro

**الحالة:** `CURRENT / REQUIRED FOR ALL FUTURE SLICES`

## 1. المشكلة التي يحلها البروتوكول

قد تتغير المحادثة أو الحساب أو الوكيل، بينما يجب ألا تتغير الحقيقة المالية أو حالة الكود. الخطر ليس فقط أن يبدأ Agent من الصفر؛ بل أن يقرأ وثيقة قديمة، فيدعي أن قدرة مؤجلة منفذة، أو يعيد بناء Slice موجودة، أو يوسع ميزة قبل بوابتها، أو يرفع تغيرًا لا يمكن للوكيل التالي تفسيره.

لهذا يصبح المستودع هو دفتر تسليم العمل: **العقود تحدد السلوك، `main` يثبت ما دمج، `current-state.md` يشرح اللحظة الحالية، وPR يثبت ما تغير ولماذا وكيف اختبر.**

## 2. سلم السلطة

| السؤال | المصدر الحاكم |
|---|---|
| ما معنى المال أو النتيجة أو الكاش؟ | العقد والسياسة المالية ذات الصلة |
| هل القدرة منفذة فعليًا؟ | `main` + الاختبارات + PR المدمج + `current-state.md` |
| ما المسموح بدءه الآن؟ | طلب المالك الحالي + `current-state.md` + `todo.md` |
| كيف تبنى الشريحة؟ | العقد، `AGENTS.md`، المهارة ذات الصلة، وقالب الشريحة |
| ماذا نؤجل أو نرفض؟ | خارطة القدرات وقرارات `docs/decisions/` |

لا يتغلب `todo.md` أو وصف PR أو ذاكرة محادثة على عقد مالي. ولا يجوز لملف الحالة أن يعلن قدرة منفذة إذا لم يوجد كود وفحص ودمج على `main`.

## 3. بروتوكول الاستلام

يطبق الوكيل الجديد الخطوات التالية قبل أي تعديل:

1. يستنسخ المستودع، يثبت على `main`، ويشغّل `git pull --ff-only origin main`.
2. يقرأ `AGENTS.md` و`docs/operations/current-state.md` و`docs/operations/micro-thinking-charter-v1.md` و`docs/operations/agent-handoff-protocol-v1.md`.
3. يطابق `git log -5 --oneline` مع commit المذكور في الحالة؛ إن اختلفا، يحدّث فهمه من `main` ولا يعتمد الحالة القديمة.
4. يقرأ العقد المحدد للشريحة فقط، مع الوثائق المتخصصة المطلوبة في جدول الحالة.
5. يراجع `todo.md` و`git status --short`؛ لا يبدأ فوق تغييرات مجهولة أو ملف مولد مضاف بالخطأ.
6. ينشر بطاقة فهم وفق ميثاق التفكير، ثم يكتب بطاقة بدء الشريحة وفق القالب: السؤال، النطاق، ما لن يتغير، الملفات، الاختبارات، وشرط الإيقاف.

إذا وجد تناقضًا بين `main` والوثائق، لا يخمن. يفتح PR توثيقيًا صغيرًا أو يطلب قرار المالك بحسب أثر التناقض.

## 4. بروتوكول التنفيذ

| المرحلة | الحد الأدنى المطلوب |
|---|---|
| قبل الكود | بطاقة فهم مكتملة، عقد أو قرار نطاق معتمد، اختبار قبول، ومسار استعادة إن تغير التخزين |
| أثناء الكود | شريحة واحدة فقط؛ لا React مباشر إلى IndexedDB؛ لا خلط قدرة لاحقة «لأنها سهلة» |
| قبل PR | `pnpm check` و`git diff --check`، واختبار UI حي وLight/Dark عند تعديل واجهة، مع حذف بيانات QA التجريبية |
| PR | عنوان محدد، حدود صريحة، اختبارات منفذة، حدود لم تتغير، migration/export إن وجدت |
| دمج | CI ناجح ثم merge إلى `main`؛ لا تبدأ الشريحة التالية قبل ذلك |

## 5. بروتوكول التسليم

لا يعني التسليم رسالة في محادثة. يعني أن PR نفسه يجعل الوكيل التالي قادرًا على الاستمرار. عند إغلاق Slice يجب أن يتضمن نفس PR:

1. تحديث `docs/operations/current-state.md` بالواقع الجديد.
2. تحديث `todo.md` للبنود المكتملة فقط، مع ترك ما لم ينفذ غير مكتمل.
3. تحديث العقد أو مصفوفة التغطية إذا تغيرت الحقيقة التنفيذية.
4. سجل QA موجز تحت `docs/quality/` عند وجود QA حي أو هجرة تخزين أو قرار واجهة مهم.
5. وصف PR مطابقًا للقالب، وCI ناجحًا.

## 6. معيار التوقف

يتوقف الوكيل ويسأل المالك بدل البناء عند: تعارض عقدين، تغيير معنى مالي، أثر قانوني/ضريبي، قدرة تحتاج Pilot، طلب يخالف بوابة التوقف في الحالة، أو فحص لا ينجح بعد محاولات إصلاح متعقلة. لا يحل هذا التوقف بإضافة «افتراض» صامت إلى الكود.

## 7. منع تضارب الوكلاء

لا يعمل وكيلان على نفس Slice أو نفس migration في الوقت نفسه. إذا طُلب عمل متوازٍ، يفصل إلى عقود/بحث/QA لا تلمس الملفات نفسها، ثم يحدد المالك الوكيل الذي يدمج. لا يبني وكيل جديد فوق فرع Agent آخر؛ يبدأ من `main` المدمج فقط ما لم يطلب المالك صراحة مراجعة PR مفتوح.
