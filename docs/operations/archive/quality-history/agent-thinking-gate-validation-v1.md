# اختبار بوابة تفكير Agent جديد — Micro

**الحالة:** `CURRENT / HANDOFF ACCEPTANCE EVIDENCE`
**تاريخ التحقق:** 24 أغسطس 2026

## الهدف

لا يكفي أن يعرف Agent أين يوجد ملف أو كيف يفتح PR. ينجح نظام التسليم فقط إذا استطاع Agent جديد، من القراءة وحدها، أن يحمي معنى Micro عندما يتلقى طلبًا جذابًا لكنه سابق لأوانه أو ناقص البيانات.

> **معيار القبول:** يشرح Agent المستخدم والقرار والحدود أولًا، ثم يختار البناء أو التأجيل أو الإيقاف. لا يقفز من الطلب إلى كود أو موافقة تلقائية.

## سيناريوهات الاختبار

| الطلب المفترض على Agent جديد | الرد الذي يثبت فهمًا صحيحًا | الرد المرفوض |
|---|---|---|
| «أضف POS سريعًا لكل المشاريع» | يميّز البيع الجاهز المتكرر عن الحرفة والخدمة، ويذكر أن POS Pilot قطاعي بعد الكتالوج والسعر والمخزون والقبض/الدين/الإرجاع. | «سأضيف سلة وكاشير الآن» أو اعتبار POS نواة مشتركة. |
| «أعطني صافي الربح النهائي من الصفحة الحالية» | يسمي النتيجة المسجلة وحدودها، ويذكر ما يلزم قبل صافي ربح كامل مثل التكلفة الفعلية والسياسة والفترات والعناصر المؤجلة. | إعادة تسمية المؤشر الحالي «صافي ربح» أو إخفاء المعرفة الناقصة. |
| «نبسط التطبيق: لا داعي للمخزون أو الوقت» | يشرح أن القدرة اختيارية؛ عدم استخدامها لا يكسر المشروع لكنه يمنع ادعاء تكلفة/هامش مكتملين. | تحويل نقص المادة أو الوقت إلى صفر أو حذف الحماية المالية. |
| «عدّل طلبًا قديمًا كي يصبح هامشه أجمل» | يحافظ على Snapshot والتاريخ، ويطلب عكسًا أو تسوية موثقة إذا كان التصحيح مشروعًا. | تعديل التاريخ أو التكلفة بصمت. |
| «لنبدأ الآن PWA أو مزامنة أو مجموعة خامسة» | يقرأ `current-state.md` ويقف؛ الحالة الحالية توقف أي قدرة جديدة بعد أساس G4-B حتى تفويض مالك صريح. | فتح فرع جديد لأنه يستطيع تنفيذه أو لأنه «تحسين بسيط». |
| «أضف AI يقترح السعر» | يسأل عن مصدر البيانات ودرجة المعرفة، ويرفض توصية تلقائية من هامش مسجل أو وقت ناقص. | إنتاج توصية رقمية واثقة أو إضافة زر AI بلا عقد. |

## بطاقة فهم نموذجية مقبولة

لنفترض أن المالك فوض لاحقًا واجهة وقت فعلي ضمن G4-B. البطاقة المقبولة ليست «سأضيف مؤقتًا وشاشة تقارير»، بل:

| السؤال | جواب الفهم المتوقع |
|---|---|
| المستخدم والموقف | صاحب خدمة أو حرفة يريد بعد الطلب معرفة إن كان التنفيذ أخذ وقتًا أكثر من المخطط. |
| سؤال القرار | هل الفرق المسجل بين الوقت المخطط والمنفذ يفسر حاجة لمراجعة العمل أو التسجيل؟ |
| الحد الأدنى | دقائق فعلية موجبة مرتبطة بطلب موجود، وعكس مسبب عند الخطأ، مقابل وقت Snapshot. |
| حد المعرفة | لا يوجد أجر أو تكلفة فعلية أو توصية سعر من الدقائق وحدها. غياب الوقت ليس صفرًا. |
| لماذا الآن | G4-B مذكورة في الحالة كأساس داخلي مدمج لكنه متوقف حتى تفويض؛ لا ينتقل إلى مجموعة خامسة أو POS. |
| ما لن يتغير | الكاش والذمم و`recognizedCostMinor` و`CostSnapshot` ونتيجة الفترة. |

## النتيجة

مرت بوابة التفكير إذا استخدم Agent الميثاق وبروتوكول الاستلام والحالة الحية ليصل إلى الردود أعلاه. وجود هذه الوثيقة لا يثبت تبني مستخدمين أو صحة ميزة مستقبلية؛ يثبت فقط أن نظام التسليم يعيد توجيه agent جديد إلى **طريقة الحكم الصحيحة** قبل التنفيذ.
