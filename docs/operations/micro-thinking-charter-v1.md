# ميثاق تفكير Micro قبل التنفيذ

**الحالة:** `CURRENT / REQUIRED BEFORE ANY PRODUCT OR CODE WORK`

## 1. لماذا يوجد هذا الميثاق؟

يمكن لوكيل أن يقرأ ملف الحالة والعقد ويطبق الكود تقنيًا، ومع ذلك يفقد جوهر Micro: فيضيف شاشة صحيحة شكليًا لكنها لا تحل قرارًا لصاحب المشروع، أو يحذف عمقًا ماليًا بحجة البساطة، أو يبني ERP عامًا لأن الميزة مألوفة، أو يعرض رقمًا جذابًا لا يملك حق ادعائه. هذا الميثاق يجعل **طريقة الحكم** قابلة للانتقال بين الوكلاء، لا مجرد قائمة ملفات قابلة للقراءة.

> Micro عميق ماليًا وتشغيليًا في الداخل، لكنه عملي وخفيف في لحظة الاستخدام. لا نبني «نظامًا مبسطًا» ولا برنامج محاسبة ثقيلًا؛ نبني شريك إدارة يجعل الحدث اليومي مفهومًا ويقود إلى قرار أفضل.

## 2. الحقيقة التي يجب أن يبدأ منها كل Agent

| السؤال | الإجابة الملزمة |
|---|---|
| لمن نبني؟ | لصاحب مشروع صغير أو منزلي يدير المال والطلبات والمواد والالتزامات بنفسه أو بفريق محدود، وليس لمحاسب أو سلسلة متاجر افتراضية. |
| ما ألمه اليومي؟ | الأحداث موجودة لكن معناها منفصل: بيع أو شراء أو مصروف أو كاش أو دين أو مادة لا تتحول تلقائيًا إلى صورة مالية وقرار. |
| ما وعد Micro؟ | ربط الحدث بالتكلفة والكاش والمخزون والذمم والنتيجة وحد المعرفة، ثم عرض معنى وفعل تالٍ بلغة صاحب المشروع. |
| ما ليس Micro؟ | ليس تطبيقًا تعليميًا، ولا CRM أو POS أو ERP عامًا، ولا لوحة تقارير تزين رقمًا لا يملك مصدرًا. |
| ما معنى البساطة؟ | أقل إدخال وأقل مصطلح في الواجهة، مع منطق مالي عميق وصادق في الخلفية؛ ليست حذف الفروق المالية. |
| ما معنى الاكتمال؟ | صورة مالية أوسع تبنى تدريجيًا بعقود صحيحة. لا تعني حشد الميزات أو ادعاء كل التقارير قبل بياناتها. |

## 3. طريقة التفكير الإلزامية

يتبع الوكيل السلسلة التالية قبل اقتراح ميزة أو تعديل:

```text
موقف فعلي لصاحب مشروع
→ سؤال قرار واحد
→ حدث/بيانات دنيا قابلة للتسجيل
→ معنى مالي أو تشغيلي صحيح
→ ما نعرفه وما لا نعرفه
→ سطح قرار أو فعل تالٍ بسيط
→ اختبار سيناريو وحدود صريحة
```

لا تبدأ السلسلة من: «أي شاشة سنضيف؟» أو «ما الميزة التي يملكها المنافس؟». تبدأ من سؤال مثل: «هل يغطي السعر ما عرفناه من تكلفة هذا العمل؟»، أو «هل بقي للمشروع كاش بعد التزامه؟»، أو «هل هذا العمل المتكرر يأكل وقتًا أكثر من المخطط؟».

## 4. المبادئ التي لا يحق للوكيل كسرها

| المبدأ | التطبيق العملي |
|---|---|
| **الحدث لا يساوي معناه المالي** | شراء مادة يخفض الكاش ويرفع المخزون؛ لا يصبح COGS تلقائيًا. قبض عربون ليس ربحًا. دين العميل ليس كاشًا. |
| **المجهول ليس صفرًا** | عدم تسجيل الوقت أو حصة مصروف مشترك أو تاريخ تحصيل لا يعطي رقمًا مكتملًا؛ يظهر حد المعرفة وفعل المراجعة. |
| **التاريخ لا يعاد كتابته بصمت** | Snapshot والطلب والحدث الحساس يحفظون الحقيقة في لحظتها؛ التصحيح بعكس أو تسوية موثقة، لا تعديل خفي. |
| **الاختيارية لا تكسر النظام** | المخزون والوقت والكتالوج ووضع التشغيل قدرات بحسب الحاجة؛ عدم تفعيلها لا يمنع العمل، بل يحدد السؤال الذي لا يمكن الجواب عنه بدقة. |
| **العمق داخل النظام، لا الحمل على المستخدم** | لا يطلب مخطط حسابات أو timesheet أو إعدادات طويلة ما لم تغير قرارًا متكررًا. النظام يترجم السؤال القصير إلى معالجة صحيحة. |
| **التقرير ليس زينة** | كل رقم يذكر المصدر والفترة والافتراض والحد؛ ولا يعرض «أفضل» أو «خسارة» أو «نقطة تعادل» بلا معنى قابل للتفسير. |
| **المرحلية تحمي المعنى** | لا تضاف القدرة لأن تنفيذها سهل أو مألوف؛ تضاف بعد العقد والبيانات وبوابة الحاجة/Pilot إن كانت قطاعية. |
| **واجهة Micro لا تبدو مولدة أو عامة** | RTL وphone-first، لغة مهنية مباشرة، أرقام قابلة للقراءة، تباين Light/Dark، وقرار واضح؛ لا لغة تسويقية عامة أو emoji أو لوحات موحدة بلا هرمية. |

## 5. أسئلة النقد قبل الموافقة على أي قدرة

على الوكيل أن يسأل نفسه ويجيب كتابةً قبل الكود:

| السؤال النقدي | إذا غابت الإجابة |
|---|---|
| ما موقف المستخدم المتكرر الذي يحله هذا؟ | لا تبنِ الميزة. |
| ما قرار أفضل سيتخذه بفضلها؟ | لا تبنِ واجهة تجميع أو تقريرًا عامًا. |
| ما أقل بيانات لازمة؟ وهل يملكها المستخدم في لحظة العمل؟ | خفّض النطاق أو أجّل القدرة. |
| ما الذي لا يمكن للنظام ادعاؤه بعد البناء؟ | اكتبه كحد معرفة في العقد والواجهة والاختبار. |
| هل هذه نواة مشتركة أم قطاعية أم تحتاج Pilot؟ | لا تفتحها لكل المستخدمين تلقائيًا. |
| هل توسعها الآن يدفع Micro نحو ERP أو POS أو CRM أو تطبيق تعليمي؟ | أوقفها أو اعزلها خلف بوابة واضحة. |
| هل يمكن أن تغير حدثًا قديمًا أو نتيجة سابقة بصمت؟ | صمم عكسًا أو تسوية موثقة أولًا. |

## 6. بوابة فهم Agent جديدة

قبل إنشاء branch أو تعديل ملف، ينشر الوكيل في Issue أو أول تعليق PR **بطاقة فهم** من سبع فقرات قصيرة:

1. من هو المستخدم المحدد وما موقفه اليومي في هذه الشريحة؟
2. ما السؤال الإداري/المالي الواحد الذي ستساعده الشريحة على الإجابة عنه؟
3. ما الأحداث أو البيانات الدنيا، وما المعالجة الصحيحة خلفها؟
4. ما الذي سيبقى غير معروف ولن يتحول إلى صفر أو نتيجة مكتملة؟
5. لماذا هذه الشريحة الآن وفق `current-state.md`، ولماذا لا نبني القدرة المجاورة معها؟
6. ما العقد الحاكم والسيناريو الذي قد يكشف خطأ في الفرضية؟
7. ما الذي سيتغير، وما الذي يلتزم الوكيل بعدم تغييره؟

إذا لم يستطع الوكيل الإجابة بوضوح، فهو **غير جاهز للتنفيذ**. يعيد القراءة أو يسأل المالك؛ لا يعوض النقص بتخمين أو كود استكشافي على `main`.

## 7. ما يعنيه «فكر مثلنا»

التفكير المطلوب ليس الموافقة التلقائية على كل فكرة ولا رفضها لمجرد أنها كبيرة. هو توازن مهني محدد:

| عند سماع طلب | الاستجابة الصحيحة |
|---|---|
| «نريد نظامًا كاملًا» | نحافظ على العمق المالي النهائي، لكن نقسمه إلى قدرات لا تكسر المعنى ولا تثقل الاستخدام. |
| «أضف ميزة شائعة» | نسأل: أي ضرر متكرر تحله هنا، ولمن، وما الذي يلزم قبلها؟ قد تكون قطاعية أو مؤجلة لا مرفوضة. |
| «اجعلها أبسط» | نبسط التجربة لا الحقيقة: لا نخفي الفرق بين الكاش والربح أو الشراء والاستهلاك. |
| «أعط المستخدم ربحه» | نعرض النتيجة المسجلة وحدودها؛ لا نصنع صافي ربح من بيانات ناقصة. |
| «لا نريد تعقيدًا محاسبيًا» | نبقي المحاسبة منضبطة داخل التطبيق، ونستخدم سؤالًا عمليًا بدل المصطلح في الواجهة. |
| «نريد أسرع تنفيذ» | نسرع بالشرائح الواضحة والاختبارات، لا بدمج قدرات مختلفة أو تجاوز migration/QA/CI. |

## 8. مقياس قبول الشريحة

لا تقبل الشريحة بأنها «تعمل» فقط. تقبل عندما يثبت الوكيل أن صاحب المشروع يستطيع تسجيل الحدث بأقل حمل، وفهم أثره وحدوده، واتخاذ خطوة تالية أو معرفة سبب عدم وجود خطوة يقينية. ويثبت أيضًا أن البيانات القديمة لم تتشوه، وأن التغيير لا يدعي COGS أو ربحًا نهائيًا أو تنبؤًا أو قدرة مستقبلية من دون عقد ودليل.
