## 3. الحدود غير القابلة للتفاوض

لا تصف أي سطح حالي بأنه COGS كاملة أو صافي ربح نهائي أو قيمة مشروع أو توقع نقدي. في G3، COGS اختيارية؛ تظهر فقط من استهلاك ذي قيمة تكلفة محفوظة وارتباط صالح بطلب مكتمل وغير معكوس. عند غياب الدليل تستخدم قراءة الفترة Snapshot كبديل معلن ولا تحول الغياب إلى صفر، ويظل صافي الربح التشغيلي المسجل ظاهرًا ضمن نطاقه مع حالة وأسباب المراجعة. لا يغير أي تعديل `CostSnapshot` أو طلبًا تاريخيًا بصمت. لا توزع مصروفًا مشتركًا أو استهلاكًا عامًا على طلب أو منتج بلا عقد وأساس معلن، ولا تخصم المصدر غير المحمل خفية من نتيجة الفترة. لا تحول الوقت الفعلي إلى أجر أو تكلفة فعلية أو سعر مقترح. لا تحذف حدثًا حساسًا؛ صححه بعكس أو تسوية موثقة.

## 4. الحالة المتوقفة عمدًا

**لا تبدأ Profile أو قدرة مالية/بنية جديدة تلقائيًا.** التسلسل المالي المعتمد على Bridge هو G3 → O1 → G4-A → G4-B → G5. G3 الأساسية وتصحيحها مدمجان على Bridge عبر PR #98 وPR #99، وPR #100 صححت التوثيق فقط. لا تبدأ O1 إلا بعد قرار القبول النهائي لـG3 من Manus Agent 1 وموافقة المالك على Prompt O1؛ وبعد ذلك تكون كل شريحة PR مستقلة إلى Bridge. G15/G16 لقبول الجهاز وPilot ما زالا غير منفذين ولا يوقفان هذا التسلسل المالي على Bridge. لا PR إلى `main` قبل اكتمال الحزمة كلها ومراجعة قبول مستقلة وتفويض تجميعي صريح من المالك. القدرات التاريخية G4-B وG5 وG6-A وG6-B وG7-A وبرنامج إصلاح القرار البصري V1–V6 مدمجة على `main` وفق سجلاتها السابقة، ولا تُخلط مع برنامج Bridge الجديد. لا يصرح قرار النواة العامة وActivity Profiles بطعام/خدمات/زراعة/سياحة أو mixed schema. لا توسع G6-B إلى daily/RRULE/reminders أو التقويم الخارجي أو الحجز أو الموارد. لا توسع G7-A إلى CRM أو رسائل أو تذكيرات تلقائية. لا تنتقل إلى POS أو مزامنة أو Auth أو أي معنى سحابي قبل قرار ما بعد Pilot. لا توسّع الوقت الفعلي إلى أجر أو تكلفة أو توصية سعر، ولا توسّع G5 إلى صافي ربح نهائي أو COGS كاملة/قانونية أو تنبؤ/توصية من دون عقد مستقل.

C2 مدمج عبر PR #77 كمذكرة قرار فقط: لا يغير Review أو Finance ولا يبني Dashboard؛ يحدد معنى الملخص وبطاقة الطلب وأولوية سؤال الكاش/الذمم/الالتزامات وبوابة Pilot.

QA/Pilot مدمج عبر PR #78 كتقرير وبروتوكول قبول وفجوات فقط؛ لا يضيف وظيفة ولا يرفع نتيجة sandbox إلى قبول جهاز أو إنتاج أو Pilot بشري.

## 6. حالة مساحة العمل المقبولة

ملف `apps/prototype-web/client/public/__manus__/version.json` مولد محليًا وقد يظهر كتغيير؛ **لا يضاف إلى Git**. يجب أن يكون أي تغيير آخر مفسرًا في PR أو مُزالًا قبل التسليم.

## 7. ما يجب تحديثه عند الإغلاق القادم

عند إغلاق/دمج شريحة جديدة، يعدل الوكيل هذا الملف في نفس PR ليحدث: commit/PR، جدول «ما هو منفذ»، جدول «الحالة المتوقفة عمدًا»، إصدارات schema/export إن تغيرت، ومسار القراءة التالي. PWA مدمجة على `main` عبر PR #54 وG5 عبر PR #53 وG6-B/G7-A عبر PR #60، وA1 عبر PR #70، وA2 عبر PR #71، وA3 عبر PR #72، وB1 عبر PR #73، وB2 عبر PR #74، وB3 عبر PR #75، وC1 عبر PR #76، وC2 عبر PR #77، وQA/Pilot عبر PR #78. برنامج إصلاح القرار البصري V1–V6 مدمج على `main` عبر PR #96 بعد تصحيح PR #95؛ لا يوجد فعل مسح محلي في المنتج. **G3 الأساسية وتصحيح قبولها مدمجان على Bridge عبر PR #98 وPR #99، أما PR #100 فتوثيقية فقط لتحديث الرأس وتسلسل Bridge ولا تنسب إليها أي ميزة مالية.** يدعم برنامج Bridge تسلسل G3 → O1 → G4-A → G4-B → G5، ولا تبدأ O1 إلا بعد قبول G3 النهائي من Manus Agent 1 وموافقة المالك على Prompt O1. كل شريحة لاحقة PR مستقلة إلى Bridge، ولا PR إلى `main` قبل اكتمال الحزمة كلها ومراجعة قبول مستقلة وتفويض تجميعي صريح من المالك. يبقى `main` عند `76bd42116dcaf454bafa594d3d77852d1ce48439` خارج التغيير. يظل اختبار iOS الفعلي وAndroid وstandalone وOffline وCloudflare Pages production وPilot البشري مطلوبًا قبل إعلان قبول PWA الإنتاجي متعدد المنصات. ثم يحدث `todo.md` فقط بما يطابق الواقع المندمج.

## 8. قرار G8.1 — الثقة والاستعادة المحلية

أثبتت مراجعة `main` أن طبقة PWA والاستعادة المحلية المطلوبة في G8.1 موجودة جزئيًا في البناء المحلي: التثبيت اختياري وصادق، والتحديث بقرار المستخدم، وservice worker وWorkbox precache تفعلا في built preview. لكن محاولة reload مع الخادم متوقف عادت بعلامات `ERR_` ولم تعرض App Shell؛ لذلك تسجل QA/Pilot الحالة `OFFLINE_SHELL_NOT_VERIFIED` ولا ترفع cache observation إلى PASS. يظل السجل المالي محليًا على الجهاز، ولا يَعِد Micro بنقل البيانات بين الأجهزة؛ يجب تصدير ملف محلي قبل حذف بيانات المتصفح أو تغيير الجهاز. لم يتغير Domain أو `CostSnapshot` أو schema/export أو LocalStore في هذه المرحلة.

القبول المتاح هو قبول مصدر/بناء/محاكاة محلية فقط. لا يُعلن قبول Android أو iOS أو Cloudflare Pages الإنتاجي قبل اختبار جهاز فعلي وعنوان الإنتاج. يبقى `iOS physical acceptance pending` و`Cloudflare Pages production verification pending` حدّين صريحين.

يوجد في التفويض مرجع إلى `docs/decisions/remaining-capabilities-review-v2.md`، لكنه غير موجود في `main`؛ المرجع الموجود هو v1 وأقدم من الحالة الحية. لذلك اتُّبعت الحالة الحية والعقود، وسُجل هذا الفرق بدل اختلاق ملف أو حالة جديدة.

## 9. قرار G8.3 — الاستيراد الافتتاحي الموجّه

أصبح في فرع G8.3 معالج Application مستقل يقرأ ملفًا افتتاحيًا محدودًا، يتحقق منه كاملًا قبل الكتابة، يبني سجلات Domain افتتاحية للكاش والمادة، ويستخدم `replaceSnapshot` الذري على Store فارغ فقط. المعالج يرفض الملف الناقص أو التالف أو غير المدعوم، يرفض Store غير الفارغ، ويحافظ على التكرار الآمن عبر مفاتيح deterministic مرتبطة بـ`importId`. الواجهة تعرض معاينة عربية قبل التأكيد وتوضح أن الموقف الافتتاحي ليس مبيعات أو ربحًا.

لم تتغير schema/export العامة، ولم تُضف مزامنة أو حسابات أو تاريخ مالي مختلق. قبول هذه القدرة في `main` مشروط بمرور CI/Cloudflare في PR؛ QA الجهاز الفعلي وCloudflare الإنتاجي يظلان خارج بيئة sandbox.

## 10. قرار G9.2 — قراءة قيد السعة

تضيف طبقة Application دالة قرار صريحة فوق `ScheduleDay` القائم. تعيد `unknown` عند عدم تفعيل السعة، و`needs_review` عند مدد ناقصة، و`within_limit` أو `over_limit` عند وجود بيانات كاملة. يبقى التعارض منفصلًا، ولا ينتج القرار كتابة أو تغييرًا ماليًا أو تعديلًا للموعد.

## 11. قرار G9.3 — سطح قرار التشغيل

يستهلك `/schedule` الآن `buildCapacityDecisionViewModel` من طبقة Application ويعرض عبر `DecisionPanel` الحالة والحقيقة المعروفة والفعل التالي لليوم المختار أو اليوم الأول في الأسبوع. يعرض التعارض كتحذير مستقل؛ لا تحسب React السعة ولا تكتب إلى التخزين. الحالات الفارغة والناقصة منفصلة، والقرار النهائي يبقى للمالك.

تم اختبار الواجهة الحية ببيانات اصطناعية فقط لحالات عدم وجود سعة، وضمن الحد، وفوق الحد، والمدة المجهولة، والتعارض، وإزالة السعة، ثم أُفرغت مخازن IndexedDB. أضيفت لقطات smoke للأبعاد 360/390/430، وتحقق RTL وLight/Dark؛ لا يُعلن قبول جهاز فعلي أو Pilot أو إنتاج متعدد الأجهزة.

## 12. تصحيح قبول G9 — ربط القرار بالواجهة

صُحح نطاق G9.2/G9.3: القرار لم يعد دالة معزولة؛ صار مستهلكًا فعليًا في `/schedule` عبر view model و`DecisionPanel`. لا يغير الربط أي مال أو طلب أو Snapshot أو موعد عند القراءة أو التوجيه، ولا يضيف قدرة تشغيلية جديدة.

## 13. قرار G9.4/G9.5 — لا توسعة متابعة جديدة الآن

راجعت الشريحة الحالية فوق G7-A وسيناريوهات المتابعة المحلية. لم تثبت فجوة واحدة محددة ومدعومة تمنع قرارًا متكررًا؛ G7-A يعبر عن المصدر والملخص والموعد والسبب وتاريخ التغيير/الإزالة. لذلك لا تضاف وظيفة جديدة ولا حقول CRM، وتبقى G9.5 محققة بقرار عدم التوسعة. إعادة الفتح تحتاج دليل Pilot حقيقيًا على فقد معلومة محلية لا يمكن تمثيلها حاليًا.
