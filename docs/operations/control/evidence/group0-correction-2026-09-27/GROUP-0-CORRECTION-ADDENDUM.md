## 1. الحكم المصحح

مراجعة ChatGPT صحيحة في جوهرها: القائمة والخمس مجموعات صالحان كأساس، لكن ترتيب التنفيذ يحتاج تعديلًا واحدًا حاسمًا، مع فصل بعض أعمال التوثيق والحراس وتصحيح فهرس المعرفات.

التغيير الأساسي:

> `D-15` لا ينتظر انتهاء Group 1. يصبح **Safety Slice مالية مستقلة** بعد إغلاق بوابة القراءة وقبل Group 1، ولا تعمل بالتوازي افتراضيًا مع Group 1.

يمكن تنفيذ شريحة Group 1 غير المالية بالتوازي فقط بقرار منفصل، إذا ثبت فصل الملفات والعقود والـClaims وحدود الاختبار، لكن الترتيب الافتراضي يبقى متسلسلًا.

## 2. التصحيحات المعتمدة على التقرير

### 2.1 حالة التقرير

تبقى حالة Group 0:

`GROUP_0_READ_ONLY_COMPLETE / REPORT_CORRECTION_REQUIRED / WAITING_FOR_OWNER`

ويُحظر وصفها بأنها إغلاق نهائي قبل اعتماد النسخة المصححة.

### 2.2 إضافة D-15 كحاجز سلامة مستقل

يُضاف `D-15` كخطر سلامة مالية مستقل، وليس كإصلاح عرض أو قرار سياسة توصيل عام.

- **النطاق:** مسار `CraftOrder` الذي تكون فيه أجرة التوصيل قابلة للفوترة عبر المشروع وخارج سعر المنتج، وفق العقد الحالي.
- **المخاطر:** يمكن أن يشمل الدين المسجل أجرة التوصيل، بينما يظل سقف التحصيل أو إعادة حساب المتبقي مقيدًا بالسعر المتفق عليه فقط.
- **ما لا يعنيه:** لا يحسم تلقائيًا من يدفع التوصيل في كل السيناريوهات، ولا يحسم سياسة نتيجة الفترة، ولا يثبت صحة محاسبية رسمية.
- **الترتيب:** بطاقة إصلاح مستقلة، ثم Claim وPR مستقلان بعد اعتماد المالك.
- **مرجع البطاقة:** بطاقة التنفيذ الكاملة هي [`D15-REPAIR-CARD.md`](D15-REPAIR-CARD.md)، وهي معروضة للمراجعة فقط وليست تفويضًا للتنفيذ.
- **الأجرة المعلومة مقابل غير المسجلة:** الأجرة القابلة للفوترة تدخل المبلغ المستحق فقط عندما تكون مسجلة وفق العقد؛ `null` تعني «غير مسجلة بعد» ولا تُعامل كصفر. إذا كان معنى `shared` أو حصة العميل غير محدد، يتوقف التنفيذ ويُرفع قرار مستقل.

### 2.3 فصل Group 0 القراءة فقط عن التنفيذ

Group 0 نفسها لا تنفذ:

- `renderSmoke`.
- `ROUTE_TEMPLATES`.
- ESLint.
- CSS أو Tokens.
- أي Runtime.

بعد اعتماد Group 0 يمكن إنشاء شرائح منفصلة:

1. PR توثيقي للمراجع القديمة.
2. PR لحراس ومزامنة المسارات.
3. PR مستقل لـCSS إذا اعتمدت موجة UI وأثبتت الجرد أثره.
4. PR مستقل لـD-15.

لا تُخلط هذه الحدود في PR واحد.

### 2.4 Repair Card Index

جدول `S-01..S-14` في التقرير هو **فهرس بطاقات** وليس بطاقات تنفيذ مكتملة. قبل توجيه ZAI إلى التنفيذ، يجب أن تتضمن كل بطاقة منفذة:

1. العرض والدليل.
2. السبب المؤكد أو فرضية إعادة إنتاج واضحة.
3. السلوك المطلوب للمستخدم والبيانات.
4. المصدر الحاكم وجميع المستهلكين.
5. ما سيتغير وما لن يتغير.
6. الحالات الطبيعية والناقصة والخطأ والإلغاء والتاريخية عند اللزوم.
7. اختبار القبول.
8. حد الرجوع.

### 2.5 تصحيح فهرس المعرفات

يجب تصحيح الربط قبل اعتماد الفهرس التنفيذي:

- `F4-B` ليس هو `FI-004`؛ `FI-004` مرتبط بمسار `F14` في جدول المصالحة.
- `D-07` و`D-07A` يحتاجان معرفًا مرجعيًا واحدًا مع إبقاء الاسم الآخر كمرجع/مرادف تاريخي إن لزم.
- `AUD-000` يخص أداة عرض الأدلة، ولا يدخل في إصلاح Runtime؛ يجب ألا يظهر في قائمة التنفيذ ثم في قائمة خارج النطاق دون تفسير.
- كل معرف مكرر يُربط ببطاقة سبب جذري واحدة، ولا يُفتح له إصلاحان مستقلان.

### 2.6 F17 والتكبير

ينقسم `F17` إلى:

- إصلاح قابلية القراءة/التنقل في الكود ضمن شريحة الوصولية المبكرة إذا ثبتت المشكلة.
- تحقق Android/iOS والجهاز الحقيقي ضمن Group 3 للشاشات المرجعية ثم Group 4 للتغطية الأوسع.

لا يؤجل الإصلاح كله إلى Group 4، ولا يُعلن نجاح الجهاز من دون دليل جهاز فعلي.
