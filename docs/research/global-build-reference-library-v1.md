# مكتبة مراجع البناء العالمي لـMicro — الإصدار 1

**الحالة:** مرجع canonical للحزمة النهائية؛ يُستخدم مع بوابة Pre-build ومنطق البناء قبل التنفيذ

**تاريخ الفحص الأساسي:** 21–22 أغسطس 2026

**الغرض:** حفظ المعرفة العملية المستخلصة من البحث العالمي في مكان واحد قابل للرجوع، ثم تحويلها إلى قرارات بناء مستقلة داخل Micro

**المرجع الأعلى:** `Problem Statement v3` و`System Definition v1` والعقود والوثائق التشغيلية canonical

**قاعدة مهمة:** هذا الملف ليس قائمة Features، وليس مقارنة تسويقية، وليس إذنًا بنسخ كود خارجي.

> **الحكم المختصر:** لم نجد مشروعًا واحدًا يطابق Micro كاملًا. وجدنا سوابق قوية لمكونات منفصلة: المحاسبة، التكلفة، المخزون، الطلب، المواعيد، الوقت، التوجيه، Local-first، والأمان. القيمة المحتملة لـMicro ليست امتلاك كل هذه المكونات منفردة، بل ربطها حول قرار يومي مفهوم وصادق لصاحب المشروع المتناهي الصغر.

## 1. لماذا أُنشئت هذه المكتبة؟

كانت نتائج البحث العالمي موزعة بين تقارير سابقة، وملفات داخلية، وملاحظات صفحات GitHub، ومواقع منتجات تجارية، ومراجع UX وأمان. هذا التوزيع يخلق خطرين. الأول أن يقرأ Agent اسم مشروع فيظنه أساسًا جاهزًا للكود. والثاني أن تختفي الصفحة أو تتغير فيضيع المنطق الذي جعلها مفيدة.

لذلك تحفظ هذه المكتبة **المعلومة والمنطق والحدود**، لا الرابط وحده. لكل مرجع نسجل المشكلة التي يساعد على فهمها، والنمط الذي استخلصناه، وكيف يعمل ذلك النمط، وما الذي يمكن إعادة تنفيذه مستقلًا، وما الذي لا يدخل Micro، وحالة الترخيص، وقرار المرحلة.

هذه المكتبة لا تستبدل `docs/06-reference-library.md`؛ بل توسعها وتوثق أساسها. تصبح `docs/06-reference-library.md` فهرسًا تشغيليًا مختصرًا، بينما تكون هذه الوثيقة سجل المعرفة التفصيلي.

## 2. ما الذي تثبته المكتبة وما الذي لا تثبته؟

| المستوى | ما يمكن أن تثبته هذه المكتبة | ما لا يمكن أن تثبته |
| --- | --- | --- |
| Domain | أن نمطًا مثل cost snapshot أو تاريخ سعر المادة ظهر كحل عملي في مشاريع قريبة | أن كل صاحب مشروع أردني يحتاجه بنفس الشكل |
| UX | أن الوضوح، منع الخطأ، التوجيه السياقي، ورسالة الإصلاح أنماط موثقة | أن صياغة عربية بعينها ستفهم بلا اختبار بشري |
| Architecture | أن Local-first يحتاج حالة محلية وطابورًا ومزامنة وتعارضًا، لا cache فقط | أن WatermelonDB أو RxDB أو PocketBase هو الاختيار النهائي |
| Product | أن Micro يملك فرصة تركيبية مختلفة عن Accounting أو POS منفرد | عدم وجود منافس أو الجدة القانونية أو استعداد الدفع |
| Engineering | أن بعض المشاريع تملك اختبارات، نشاطًا، تقسيمًا طبقيًا، أو ترخيصًا واضحًا | سلامة كل سلوك مالي داخلي لمجرد وجود نجوم أو commits |
| License | أن الترخيص المعلن أو ملف LICENSE يعطي مستوى مخاطرة أوليًا | رأيًا قانونيًا نهائيًا في الاشتقاق أو التوزيع |

> **قاعدة الاستعمال:** وجود ميزة في مشروع خارجي يولد سؤالًا أو نمطًا للدراسة، ولا يتحول وحده إلى قرار بناء.

## 3. تعريفات ثابتة عند استخدام هذه المكتبة

| المصطلح | المعنى المعتمد في Micro |
| --- | --- |
| **نمط** | طريقة متكررة لتنظيم حدث أو بيانات أو تفاعل، مثل `cost snapshot` أو `next action` |
| **استلهام** | فهم الفكرة أو السلوك وإعادة صياغته داخل Micro دون نسخ كود أو نموذج بيانات حرفي |
| **Primitive** | جزء صغير قابل لإعادة التنفيذ مستقلًا، مثل تحويل الوحدات أو حالة حقل الخطأ |
| **مرجع Domain** | مشروع يساعد على فهم معنى اقتصادي أو تشغيلي، لا نظامًا يجب استيراده |
| **مرجع UX** | مصدر يوضح كيف يعرض النظام معلومة أو يمنع خطأ أو يوجه المستخدم |
| **مرجع معماري** | مصدر يوضح فصل الطبقات أو التخزين أو المزامنة أو الاختبارات |
| **Build independently** | نعيد تنفيذ النمط من عقود Micro ونختبره داخل Domain Core وPrototype |
| **Study** | نقرأ ونحلل ونستفيد من المنطق، لكن لا ندخله ككود أو dependency الآن |
| **Spike** | تجربة تقنية صغيرة تقيس سؤالًا محددًا دون التزام معماري نهائي |
| **Defer** | نضع حدًا معماريًا أو فرضية، ونؤجل التنفيذ حتى يظهر دليل |
| **Reject** | نقرر أن النمط أو النطاق لا يخدم Problem Statement أو يضيف ضررًا أكبر من قيمته |
| **Source snapshot** | ملخص محفوظ داخل هذه الوثيقة يظل مفهومًا حتى إن تغير المصدر الخارجي |

## 4. معيار إدخال أي مصدر جديد

لا يدخل مرجع جديد إلى التصميم أو الكود قبل تعبئة هذه البطاقة:

| الحقل | السؤال الإلزامي |
| --- | --- |
| `source_id` | كيف سنشير إليه بصورة ثابتة؟ |
| المشكلة | أي سؤال أو ضرر من Problem Statement يعالجه؟ |
| القطاع | هل يناسب الحرفة أو الطعام أو الخدمة أو نواة مشتركة؟ |
| النمط | ما الفكرة المحددة التي نأخذها؟ |
| المنطق | لماذا يعمل النمط؟ وما الأحداث والبيانات خلفه؟ |
| الفرق | ما الذي لا ينطبق على Micro؟ |
| المرحلة | Prototype أم Pilot أم MVP التجاري اللاحق؟ |
| الترخيص | SPDX أو ملف الترخيص الفعلي أو `other/NOASSERTION`؟ |
| الجودة | النشاط، الإصدارات، الاختبارات، التوثيق، الأمان، الاعتماديات؟ |
| القرار | Build / Study / Spike / Defer / Reject؟ |
| معيار القبول | كيف نعرف أن النمط نجح داخل Micro؟ |
| تاريخ المراجعة | متى نعيد فحص المصدر والقرار؟ |

## 5. مصفوفة المعرفة المستخلصة

| المجال | المعرفة المحفوظة | المرحلة الأولى | المرحلة اللاحقة | ما لا نفعله |
| --- | --- | --- | --- | --- |
| التكلفة | عناصر بوحدة وكمية وسعر وتاريخ ومصدر ودرجة معرفة، مع نسخة محفوظة | Build independently | actual cost وbatch وoverhead أكثر دقة | لا نستخدم markup وحده ولا نعيد حساب الماضي بصمت |
| الطلب | مصدر اتفاق، تفاصيل وعد، سعر، تكلفة، موعد، قدرة، حالة، فعل تالٍ، أحداث، تسوية | Build independently | قنوات وتكاملات | لا نجعل الطلب فاتورة أو حالة لون فقط |
| الحرفة | تخصيص، خامات، وقت، تعديل، cost snapshot مرتبط بالطلب | Build independently | BOM متعدد المستويات والدفعات | لا نبني ERP تصنيع |
| الطعام | وصفة، تحويل وحدات، دفعة، yield، حصص، هدر، تغليف، تاريخ سعر | Spike ثم Profile | دفعات واستهلاك مخزون متقدم | لا نفرض وصفة على كل الأنشطة |
| الخدمة | مدة، توفر، تعارض، مواد، تنقل، checklist، إتمام، تحصيل | Profile مبسط | actual time وتعدد مقدمي الخدمة | لا نفرض timesheet مؤسسيًا |
| المالية | القبض ليس ربحًا، العربون ليس نتيجة نهائية، الدين ليس كاشًا، السحب ليس مصروفًا | Mandatory constraint | دفتر داخلي وتقارير أوسع | لا نخلط subscription entitlement بمال المشروع |
| UX | حالة واضحة، لغة المستخدم، labels، منع خطأ، رسالة قابلة للإصلاح، توجيه سياقي | Build independently | personalization وanalytics | لا LMS ولا tour طويل |
| Local-first | LocalStore، queue، idempotency، sync state، conflict، export/restore | Spike محدود | Hybrid sync بعد الدليل | لا full sync أو CRDT تلقائيًا |
| الأمان | تخزين خاص، منع التسرب، عدم تسجيل الحساس، backup/restore وفقد الهاتف | Mandatory constraint | threat model أوسع وAuth | لا نطلق بيانات مالية حقيقية قبل بوابة الأمان |
| SaaS | entitlement مستقل عن Billing ومالية المستخدم | Boundary فقط | MVP التجاري اللاحق | لا Billing داخل Prototype |
| التراخيص | provenance، SPDX، notices، منع نسخ copyleft أو غير المرخص | Mandatory governance | dependencies معتمدة بعد المراجعة | لا copy-paste من مشروع مشابه |

# 6. بطاقات المصادر التفصيلية

## 6.1 SRC-DOMAIN-01 — Craftplan

**المصدر:** [1] و[2]

**المجال:** الأعمال الحرفية والتصنيع الحرفي D2C

**حالة الفحص:** صفحة GitHub وREADME وmetadata؛ نشاط حديث، نحو 1.1k نجمة وقت الفحص، وAGPL-3.0 بحسب metadata.

### المشكلة التي يساعد على فهمها

صاحب العمل الحرفي لا يبيع دائمًا منتجًا ثابتًا له وصفة واحدة. قد يغير الخامة، اللون، المقاس، التصميم، الكمية، والوقت بين طلب وآخر. إذا كان النظام يربط كل الطلبات بسعر المادة الحالي، فإنه يغير الحقيقة التاريخية ويجعل الربح القديم غير قابل للثقة.

### المفهوم المستخلص

المنتج الحرفي يحتاج بنية تجمع `catalog` ونسخة مكونات أو BOM ووقت العمل والدفعة والطلب. الأهم هو أن تكلفة الدفعة أو الطلب تصبح **snapshot** يمكن الرجوع إليه. تظهر في الوصف مفاهيم مثل versioned BOM، rollup للتكلفة، خطوات العمل، الوقت، الدفعات، استهلاك المواد، lot traceability، وper-lot unit cost.

### المنطق الاقتصادي والتشغيلي

1. يبدأ المستخدم بتعريف ما يبيع أو يصفه.

1. يحدد المواد والكمية والوحدة والسعر ومصدر السعر.

1. يضيف وقت التصميم والتنفيذ وأي تخصيص أو تغليف أو توصيل.

1. يحسب النظام تكلفة مخططة، ويبيّن ما هو معروف وما هو مقدر.

1. عند اعتماد السعر أو تأكيد الطلب تُحفظ نسخة من العناصر والافتراضات.

1. إذا تغير سعر المادة لاحقًا، تُستخدم النسخة الجديدة للطلبات الجديدة فقط.

1. إذا تغيرت مواصفات الطلب، ينشأ revision أو حدث واضح بدل تعديل صامت.

### ما يدخل Micro

يدخل `cost_structure` مبسط، تخصيص الطلب، الوقت المقدر، مصدر السعر، وحفظ `cost_snapshot` عند اعتماد السعر أو الطلب. يدخل أيضًا الفرق بين السعر الوقائي والنتيجة المالية بعد التسليم والتحصيل.

### ما نتركه ولماذا

نترك BOM متعدد المستويات، lot traceability، forecast، جدولة إنتاج متقدمة، CRM، الموردين المتعددين، ومصنع ERP. هذه مفاهيم مستقبلية قد تصبح مهمة، لكنها تضيف حالات وحقولًا قبل إثبات أول قيمة.

### قرار Micro

**Study + Build independently.** نعيد تنفيذ المنطق من عقود Micro، ولا ننسخ كود AGPL أو schema حرفية. معيار القبول هو أن تغير سعر مادة اليوم لا يغير نتيجة طلب قديم بصمت.

## 6.2 SRC-DOMAIN-02 — CostTable

**المصدر:** [3]

**المجال:** تكلفة وصفات الطعام والعمل المحلي

**حالة الفحص:** README يذكر Flutter وSQLite وProvider/Riverpod، وتاريخ أسعار، وتكاليف مباشرة وغير مباشرة، وسعر الوحدة والهامش؛ ظهر المشروع صغير النشاط، وذُكر MIT في README مع الحاجة إلى التحقق من ملف الترخيص الفعلي قبل النسخ.

### المشكلة التي يساعد على فهمها

سعر العبوة ليس تكلفة الوحدة. كيس مادة بسعر معين قد ينتج عددًا كبيرًا من الوحدات، وقد يدخل التغليف والعمل والهدر والمصاريف غير المباشرة في النتيجة. من دون تاريخ سعر ووحدة قابلة للتحويل قد يظهر رقم دقيق لكنه خاطئ المعنى.

### المفهوم المستخلص

يحتاج محرك التكلفة إلى `ingredients` أو مواد، `recipe`، كميات ووحدات، `price_history`، عناصر direct/indirect cost، yield أو servings، وتحديث جماعي أو سجل آخر تحديث. كما يفيد أن يرى المستخدم تكلفة الخام، تكلفة الوحدة، الهامش، وسعرًا مشتقًا من هدفه.

### المنطق

`material_cost = quantity × normalized_unit_price`، ثم تضاف عناصر العمل والتغليف والهدر والمصاريف المنطبقة، وبعدها تقسم التكلفة على yield أو عدد الوحدات. يجب أن تكون الوحدة والسعر والتاريخ مصدرًا للنتيجة، وأن يظهر نقص البيانات بدل أن يتحول إلى صفر.

### ما يدخل Micro

ندرس تاريخ السعر، تكلفة الوحدة، direct/indirect، yield، وحالة `known/estimated/incomplete/stale`. في الطعام نستخدمها داخل Activity Profile خاص بالوصفة والدفعة والحصة.

### ما نتركه

نترك واجهة food-only، والاعتماد على local-only، وأي schema حرفية، لأن المشروع لا يعالج الطلب أو العربون أو الدين أو التسليم أو نتيجة المشروع كاملة.

### القرار

**Study + Prototype spike.** لا ننسخ schema أو كودًا حتى نتحقق من الترخيص والاعتماديات. معيار القبول هو نجاح حالات تحويل الوحدة والدفعة والحصص مع نتائج يدوية متوقعة.

## 6.3 SRC-DOMAIN-03 — Recipe Costs

**المصدر:** [4] و[5]

**المجال:** وصفات المطاعم وتكلفة الحصة

**حالة الفحص:** تطبيق JavaScript أحادي الصفحة، مكونات ووصفات وتحويل وحدات، يتصل بـRails API؛ الواجهة MIT بحسب الملاحظات المحفوظة، والمشروع صغير وقديم، ويجب فحص API منفصلًا.

### المفهوم

فصل مدخلات المكونات عن الوصفة، وتحويل الوحدات قبل الحساب، ثم حساب تكلفة الدفعة أو الحصة. هذا يثبت أن أصغر وحدة مفيدة ليست «منتجًا بسعر»، بل كمية مادة موحدة مرتبطة بإنتاج متوقع.

### ما يدخل Micro

نأخذ `UnitConversion` كمكوّن مستقل قابل للاختبار، ونفصل حساب الدفعة عن حساب الوحدة، ونمنع تأكيد وصفة بوحدة مجهولة أو yield يساوي صفرًا.

### ما نتركه

نترك Rails API القديم، food-only UI، وعدم وجود الطلب والكاش والدين والمزامنة.

### القرار

**Primitive study.** يمكن إعادة تنفيذ الفكرة من الصفر، لكن لا ندخل كودًا خارجيًا قبل provenance وفحص الترخيص.

## 6.4 SRC-DOMAIN-04 — Craftybase

**المصدر:** [6] و[7]

**المجال:** makers والمنتجات اليدوية

**النوع:** منتج تجاري، ليس مصدر كود Micro.

### المفهوم

يعرض المنتج تتبع المواد، التكلفة الحقيقية، العمل، المصاريف العامة، COGS، ومزامنة الطلبات من قنوات مثل Etsy وShopify. تشرح الحاسبة الفرق بين `material cost` و`labor cost` و`markup` و`profit margin`، وتؤكد أن المادة تُحسب حسب الكمية المستخدمة لا سعر العبوة، وأن وقت صاحب المشروع تكلفة حقيقية.

### المنطق

الصيغة البسيطة للحاسبة قد تكون `selling_price = total_production_cost × (1 + markup)`، لكن ذلك لا يكفي كنظام Micro؛ لأن الربح والهامش والتغليف والرسوم والشحن والدفعات وتغير الأسعار تحتاج سياقًا. الـmarkup ليس margin، ولا ينبغي عرض نسبة تجارية جاهزة كقاعدة للأردن.

### ما يدخل Micro

نأخذ المسار المفاهيمي: مواد → وقت/عمل → تغليف/توصيل/رسوم → تكلفة مخططة → سعر حماية التكلفة → نتيجة بعد التسليم والتحصيل. نعرض الفرق بين markup وmargin، ودرجة المعرفة، ونسمح بتعديل الافتراضات.

### ما نتركه

نترك نسب التسعير التجارية الجاهزة، استيراد قنوات البيع، COGS الضريبي الكامل، والتحليلات الشاملة؛ لأنها ليست مثبتة محليًا ولا مطلوبة في أول Prototype.

### القرار

**Competitive reference + UX/Domain study.** لا كود ولا schema؛ نختبر المنطق مع أصحاب مشاريع حقيقيين.

## 6.5 SRC-DOMAIN-05 — Stocksmith

**المصدر:** [8]

**المجال:** الأعمال الصغيرة ذات الدفعات والتصنيع الخفيف

**النوع:** منتج تجاري.

### المفهوم

يربط المواد والمكونات والمنتجات النهائية، تصنيع الدفعة، تحديث المخزون، التكلفة الحقيقية للوحدة، وقنوات البيع. القيمة ليست في شاشة المخزون وحدها، بل في أن إنتاج دفعة يغير الكمية والتكلفة بطريقة مترابطة.

### ما يدخل Micro

نأخذ فكرة أن المخزون والحركة والتكلفة يجب أن تنتج من حدث واضح، ونصمم حدًا مستقبليًا لـ`inventory_movement` و`batch` من دون تنفيذ تصنيع كامل.

### ما نتركه

نترك ربط القنوات، المخزون اللحظي متعدد القنوات، والتصنيع الموسع إلى مرحلة تثبت فيها التجربة الحاجة.

### القرار

**Study / Defer.** لا يدخل Prototype إلا بقدر المادة المطلوبة للطلب والحالة التي يحتاجها السيناريو.

## 6.6 SRC-FIN-01 — Frappe Books

**المصدر:** [9]

**المجال:** محاسبة مبسطة، دفتر مزدوج، مخزون، فواتير وPOS

**حالة الفحص:** GitHub يصفه بأنه Modern Accounting Made Simple؛ ظهر فيه backend وmodels وreports وtests وtranslations، مع AGPL-3.0 ونشاط واسع وترجمة عربية ظاهرة في الملفات.

### ما يعلّمنا إياه

### ما نتركه

نترك Frappe كمنصة، POS العام، chart of accounts الظاهر، الفواتير والضرائب الكاملة، ولا ننسخ AGPL.

### القرار

**Study UX/Domain only.** معيار القبول هو أن يسجل المستخدم غير المحاسبي مصروفًا أو قبضًا ويفهم أثره دون فتح دفتر محاسبي.

تقدم PWA تجربة تطبيق مبنية ومنشورة على الويب، مع manifest وService Worker وApp Shell ومسارات للتثبيت والعمل دون اتصال وإدارة التنقل داخل التطبيق المثبت. القيمة ليست في تسمية التطبيق PWA، بل في جعل الويب سريعًا وقابلًا للاستمرار عند ضعف الاتصال.

### ما يدخل Micro

يدخل Web App بملء الشاشة، وApp Shell، وmanifest، وحالة Offline صادقة، وحفظ المسودة محليًا، ثم Service Worker بعد استقرار المسار. يجب أن يرى المستخدم «محفوظ على هذا الجهاز» بدل ادعاء المزامنة المركزية.

### ما نتركه

نترك الوعود العامة بأن PWA يساوي Native على كل جهاز، والإشعارات الخلفية المضمونة، والمزامنة السحابية، وأي API لا يثبت على المتصفح المستهدف.

### القرار

**Build independently ثم Defer بعض القدرات.** نعيد بناء الحد الأدنى من App Shell وOffline UX وفق Micro، ولا نضيف تعقيدًا قبل اختبار المتصفح والجهاز.

## 6.29 SRC-WEB-02 — Capacitor Web Native Runtime

**المجال:** تغليف Web App كتطبيق iOS/Android لاحقًا.

# 7. المنطق المشترك الذي يجمع هذه المصادر

## 7.1 من الحدث إلى النتيجة

المصادر المالية والتشغيلية المختلفة تلتقي في منطق واحد:

```
حدث واقعي
  ↓
تصنيف وسياق ومصدر وتاريخ
  ↓
أثر تشغيلي ومالي
  ↓
درجة معرفة أو نقص
  ↓
نتيجة مفهومة
  ↓
فعل تالٍ
  ↓
سجل تاريخي قابل للمراجعة
```

في Micro، الحدث قد يكون اتفاقًا، طلبًا، شراء مادة، مصروفًا، قبضًا، سحبًا، حقن رأس مال، تسليمًا، أو إلغاء. لا يكفي حفظ الحدث؛ يجب أن يعرف المستخدم ما الذي تغير وما الخطوة التالية.

## 7.2 من التكلفة إلى السعر إلى النتيجة

```
مواد/مكونات + كمية + وحدة + تاريخ سعر
+ وقت/عمل + تغليف + توصيل + هدر + مصروف منطبق
  ↓
planned_cost أو estimated_cost
  ↓
cost_status: known / estimated / partial / incomplete / stale / variable
  ↓
price_floor + required_buffer أو price_from_margin
  ↓
price decision + cost snapshot
  ↓
order agreement
  ↓
recognized result بعد التسليم/التسوية
```

`price_floor` يحمي من بيع أقل من تكلفة معروفة، لكنه ليس سعر السوق ولا يفرض قرار المستخدم. إذا كان بند مؤثر ناقصًا، لا نعرض ربحًا نهائيًا؛ نعرض نتيجة جزئية أو تقديرية مع سبب النقص.

## 7.3 من الطلب إلى التسوية

```
مصدر اتفاق خارجي أو داخلي
  ↓
اتفاق مبدئي
  ↓
سعر وتكلفة وموعد وعربون
  ↓
طلب مؤكد + snapshot
  ↓
تنفيذ/تحضير + قدرة + تذكير
  ↓
جاهز
  ↓
تم التسليم
  ↓
قبض/متبقي/دين/استرداد
  ↓
نتيجة الطلب + أثر الكاش + next action
```

التسليم ليس قبضًا، والعربون ليس ربحًا نهائيًا، والطلب المؤكد ليس بيعًا مكتملًا. هذه نقطة يجب ألا تضيع عند استلهام POS أو Accounting.

## 7.4 من البيانات المحلية إلى المزامنة

```
LocalStore
  ↓
SyncQueue لكل حدث قابل للمزامنة
  ↓
idempotency_key وإعادة محاولة
  ↓
RemoteStore عند وجوده
  ↓
حالة متزامن أو تعارض يحتاج مراجعة
  ↓
تصدير/استعادة وسجل تدقيق
```

لا يجوز أن يحل النظام تعارضًا ماليًا بصمت. إذا تغير طلب أو قبض في جهازين، يجب أن يحدد النظام ما الذي يحتاج مراجعة، ويحافظ على الأحداث بدل اختيار آخر كتابة فقط.

# 9. ما الذي حُفظ؟ وما الذي أُخرج من المرجع canonical؟

## ما حُفظ

حُفظت كل المعرفة التي تغير قرارًا أو تصميمًا: المفاهيم المالية، منطق التكلفة، تاريخ الأسعار، الوحدات والدفعات، cost snapshot، دورة الطلب، القدرة والموعد، مصدر الاتفاق، التوجيه داخل العمل، قواعد رسائل الخطأ، حالات Local-first، حدود المزامنة، entitlement، الأمان، والتراخيص. كما حُفظت المراجع التجارية التي لا تملك كودًا لأنها تكشف رحلة مستخدم أو نموذجًا اقتصاديًا مفيدًا.

## ما أُخرج من الجسم الأساسي

لم يُحذف أي ملف من المستودع. لكن المرجع الجديد لا يكرر كل نتيجة خام أو كل مستودع منخفض الصلة. أُخرجت من الجسم الأساسي القوائم التي لا تغير قرارًا، وأرقام النجوم والـforks إلا عند استعمالها كإشارة تاريخية، والصياغات التسويقية غير الضرورية، وواجهات المنتجات التي لا تخدم Micro، وأي schema أو snippet لا نملك حق استعماله.

السبب ليس إخفاء المعلومات؛ بل منع Agent من اعتبار الكثرة دليلًا أو قائمة المراجع backlog Features. الروابط تبقى في قسم المراجع، والمنطق المهم محفوظ داخل بطاقات المصادر، والملاحظات الخام تبقى كملفات بحث مساعدة خارج المرجع السلطوي.

## ما بقي مرجعًا مساعدًا لا سلطويًا

تبقى `docs/research/github-global-research.md` و`docs/research/github-global-research-round2.md` كتاريخ بحث سابق قابل للتتبع، ولا تُحذف. من الآن، عند اختلاف تفصيل بين تقرير قديم وهذه المكتبة، تكون هذه المكتبة هي المرجع التجميعي الأحدث للبحث العالمي، بينما تبقى Problem Statement والعقود أعلى منها.

# 10. قواعد الوضوح لأي Agent

يجب على أي Agent يقرأ هذه المكتبة أن يجيب قبل الاقتراح:

1. ما المشكلة المحددة التي يعالجها النمط؟

1. ما القطاع المتأثر: حرفة أم طعام أم خدمة أم نواة مشتركة؟

1. ما الحد الأدنى الذي نعيد تنفيذه دون نقل تعقيد المصدر؟

1. ما الحدث والمدخلات والنتيجة والفعل التالي؟

1. ما درجة معرفة النتيجة وما الذي ينقصها؟

1. هل سيغير النمط الحقيقة التاريخية أو يخلط الربح بالكاش؟

1. هل يحتاج تخزينًا محليًا أو مزامنة أو أمانًا أو تصديرًا؟

1. ما ترخيص المصدر، وهل نستفيد من الفكرة أم من كود؟

1. ما معيار القبول والفشل؟

1. في أي مرحلة يدخل النمط، وما الذي يؤجل عمدًا؟

إذا لم يمكن الإجابة عن هذه الأسئلة، لا يتحول المصدر إلى تصميم أو كود.

# 11. قرار المكتبة

**القرار:** تعتمد Micro هذه المكتبة كمرجع بناء عالمي تفصيلي، لكن لا تعتمد أي مصدر خارجي كنواة أو كبديل عن Domain Core أو العقود. كل استلهام يعاد صياغته داخل Problem Statement وActivity Profiles وFinancial Operating Model وGuidance Policy وScenario Test Set.

**قرار الكود:** لا يدخل كود خارجي من هذه الجولة إلى المستودع. أي dependency مستقبلية تمر عبر `external_code_policy.md` وتسجل الرابط والنسخة والملفات والترخيص والإسناد والاختبارات.

**قرار المرحلة:** تبدأ الأولوية بـPrototype الحرفة المخصصة، ثم Spike للطعام والخدمات، ثم اختبار مهام حقيقي. يبقى backend التجاري والمزامنة الكاملة وBilling وAuth التجاري والتكاملات خارج Prototype إلى أن تظهر حاجة مثبتة.
