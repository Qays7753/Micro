# G23 — تقرير قبول إعادة UX

## Major Discussion Points

بدأت G23 من `origin/main` عند رأس `16dfd5802ee3492da9d51b2872abcff8f8974bd6` بعد دمج G22 عبر PR #133. سؤال القبول هو: هل تعمل إصلاحات G20–G22 معًا في رحلة First-use واحدة، وهل ترفع Home الفعل الأكثر إلحاحًا بدل العودة إلى CTA عامة، مع إبقاء الحدود المالية والتخزينية صادقة؟

النطاق اقتصر على M-23 وM-25 والتحقق العام. لم تُضف Feature جديدة، ولم تُمس Market أو Delivery أو Services UI أو Auth أو Cloud أو API أو DB أو Profiles أو POS أو CRM أو AI. لم يتغير Domain أو الحساب المالي أو `CostSnapshot` أو `schema` أو `export` أو migration أو import/export semantics. بقي المسار المعماري UI → Application Service → Domain → `PrototypeLocalStore` كما هو.

كشف QA الحي Regression مباشرًا في M-23: بعد إنشاء طلب اصطناعي، حفظ اتفاق بقيمة `80.00` د.أ، تحصيل عربون `30.00`، تنفيذ وتسليم، ثم تحصيل المتبقي `50.00`، أصبح الطلب مغلقًا مع `resultStatus: incomplete`. كانت Home تعرض «فتح سجل الطلبات» كأولوية عامة، رغم أن بطاقة الطلب تعرض «راجع نتيجة الطلب» وأن التكلفة/الوقت الناقصين يمنعان النتيجة النهائية. هذه حالة Domain صحيحة وليست خللًا ماليًا.

عولج Regression بأصغر تغيير عرضي مباشر: أضيف نوع `result_review` في View Model، وتضيف Home attention مراجعة الطلب المغلق ذي `resultStatus` غير النهائي، ثم تجعل المراجعة الحرجة للتكلفة أو الدين أو النتيجة أولوية Hero قبل CTA التاريخ العامة. أضيف اختبار خدمة حتمي يغطي طلبًا مغلقًا بنتيجة ناقصة، ويتحقق من أن Hero يفتح `/orders/<id>` بعنوان «مراجعة النتيجة». لم تتغير transitions أو الحسابات أو التخزين.

نُفذت QA الحية بخادم واحد فقط على `http://localhost:3007` وبجلسة اصطناعية واحدة باسم «QA G23 إعادة قبول». نجح التأسيس، وبدء مسودة، وحفظها، والرجوع إلى القائمة، واستئناف المسودة مع استعادة الوصف والعميل والكمية والنص العربي الطويل. ظهرت التكلفة الناقصة وسعر الحماية «غير متاح بعد» دون تحويل المفقود إلى صفر.

نجح مسار الطلب الكامل: الاتفاق المحفوظ والعربون المنفصل، بدء التنفيذ، الجاهزية، التسليم المنفصل، ثم تحصيل المتبقي. لم يسجل التسليم قبضًا مخفيًا، وبقي العربون قبضًا لا ربحًا. بقيت النتيجة «غير مكتملة» بعد التحصيل بسبب نقص التكلفة والوقت، ولم يُعرض ربح نهائي.

في Finance ظهر الكاش المسجل `80.00` والتحصيلات المعلنة `0.00` والتوقع «غير متاح» لغياب إعلان مؤرخ، مع عدم وجود إعلانات فعالة أو أحداث عامة إضافية. بقي الطلب الناقص مستبعدًا من قراءة الهامش مع سبب ظاهر. وفي G5، محاولة الحفظ بمبلغ ومصدر اصطناعيين دون ملاحظة منعت الحفظ، وفتحت التفاصيل، وأظهرت رسالة عربية مفهومة دون إنشاء أثر مالي.

في Catalog ظهرت الحالة الفارغة ومسار الاسم الأساسي، وبقيت تفاصيل القياس والتحويل والقالب والقراءة مغلقة. وفي Schedule ظهرت أجندة فارغة صادقة، مع استبعاد الموعد المكتمل، وفعل «بدء طلب» بدل dead end، وبقيت التكرار والسعة خلف تفاصيل اختيارية. وفي Settings بقيت بيانات التصدير والاستيراد الحساسة خلف طبقة منفصلة مع وصف المراجعة قبل الاستبدال؛ لم يُشغّل Export/Import لأن أمر G23 يحظر تكرارهما في هذه الشريحة.

أكدت فحوص DOM أن RTL فعال في المسارات المختبرة، وأن Dark يعمل على Settings مع ثبات المحتوى. فُحص المسار المتأثر على 360 و390 و430 CSS px عبر إطارات من الخادم نفسه؛ بقي جذر التطبيق داخل العرض ولم يتجاوز `scrollWidth` عرض viewport. هذا فحص CSS/DOM محلي، وليس قبول Android أو iOS فعليًا.
