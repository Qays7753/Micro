```text
387 سطرًا  > 120 حرفًا
```

**المرحلة 1 — تنسيق خالص، بلا أي تغيير سلوكي.** أنشئ `.prettierrc.json` في الجذر:

| القاعدة | القيمة | السبب |
|---|---|---|
| `complexity` | `["error", 12]` | يمنع دالة سياسة واحدة تحمل عشرين فرعًا |
| `max-lines-per-function` | `["error", 60]` | يجبر تفكيك السياسات الطويلة |
| `@typescript-eslint/no-explicit-any` | `error` | المستودع نظيف اليوم — ثبّت ذلك |
| `no-restricted-syntax` | انظر `D-02` | يمنع `Math.round` خارج الوحدة المشتركة |

أضف `"lint": "eslint src tests"` إلى `scripts`، وأضفه إلى `check`، وإلى CI.

**معيار القبول.**

```bash

awk 'length>200' $(find src/domain -name '*.ts') | wc -l    # ← 0
```

### D-02 — سياستا تقريب في مستودع واحد

| الحقل | المحتوى |
|---|---|
| **الخطورة** | ملاحظة |
| **الموقع** | `src/domain/craft-order/policies.ts:146`، `src/domain/g5/policies.ts:56` |

**المشكلة.** `g5` يعرّف `roundHalfUp(numerator, denominator)` صراحةً كسياسة موثقة في العقد. `craft-order` — أقدم وأكثر الوحدات مركزية — يستخدم `Math.round` مباشرة. النتيجة متطابقة اليوم لأن كل المدخلات مؤكَّدة غير سالبة، لكن السياسة معرّفة في مكان ومضمرة في آخر. أول قيمة سالبة تدخل مسارًا يستخدم `Math.round` ستقرَّب نحو الصفر بدل نصف-لأعلى، بلا اختبار يكشفها.

كذلك `isValidLocalDate` و`assertId` و`assertPositiveMinor` و`addSafe` مكررة أو معرّفة في وحدة واحدة دون غيرها.

**القرار.** وحدة مشتركة واحدة، ومنع تقني للانحراف عنها.

**التنفيذ.**

1. أنشئ `src/domain/shared/` وضع فيها: `roundHalfUp`، `ceilRatio`، `addSafe`، `isValidLocalDate`، `isValidTimestamp`، `assertId`، `assertPositiveMinor`، `assertNonNegativeInteger`، ونوعَي `Currency` و`MoneyMinor` (انظر `D-05`).
2. انقل التعريفات من `g5/policies.ts` كما هي حرفيًا — **لا تعيد كتابتها ولا تحسّنها**.
3. بدّل كل موقع استخدام في الوحدات العشر ليستورد من `shared`.
4. ثبّت المنع في ESLint:

```jsonc
"no-restricted-syntax": ["error", {
  "selector": "MemberExpression[object.name='Math'][property.name=/^(round|ceil|floor)$/]",
  "message": "استخدم دوال التقريب من src/domain/shared — سياسة التقريب المالي لها تعريف واحد."
}]
```

مع استثناء `src/domain/shared/**` وحدها في `overrides`.

**معيار القبول.** الاختبارات الـ84 تمر بلا تعديل أي منها. هذا هو الدليل الحاسم على أن النقل لم يغيّر سلوكًا: أي تغيير في نتيجة حساب سيُسقط اختبارًا قائمًا.

**لا يشمل.** لا تغيّر `Math.ceil` في `unitCostMinor` — ذاك سلوك مقصود موثق في `D-03`، وتغييره قرار عقد لا تنظيف.

### P-03 — ترحيلات الـcursor بلا معالج أخطاء

| الحقل | المحتوى |
|---|---|
| **الخطورة** | مهم |
| **الموقع** | `apps/prototype-web/client/src/storage/local/IndexedDbLocalStore.ts:184–187, 192, 205, 219, 232` |

**المشكلة.** كل ترحيل يضبط `cursor.onsuccess` ولا يضبط `cursor.onerror`. إذا فشل أي cursor أثناء الترقية، تُجهض معاملة `versionchange` بصمت. النتيجة: مستخدم على `schemaVersion` قديم يشغّل كودًا يتوقع الحقول الجديدة — على بيانات مالية.

**الخيارات.**

| الخيار | الحكم |
|---|---|
| تجاهل — الاحتمال ضعيف | **مرفوض** — الضرر بيانات مالية تالفة صامتة، لا خطأ عابر |
| `try/catch` حول كتلة الترحيل | **مرفوض** — عمليات IndexedDB غير متزامنة؛ `try/catch` لا يلتقطها |
| `cursor.onerror` يرفع الخطأ إلى `openDatabase` | **معتمد** |

**التنفيذ.** أنشئ مساعدًا واحدًا داخل الملف بدل تكرار المعالج تسع مرات:

```ts
function migrateAll(
  store: IDBObjectStore | undefined,
  update: (value: Record<string, unknown>) => Record<string, unknown>,
  onFail: (error: DOMException | null) => void,
): void {
  if (!store) return;
  const cursor = store.openCursor();
  cursor.onerror = () => onFail(cursor.error);
  cursor.onsuccess = () => {
    const current = cursor.result;
    if (!current) return;
    current.update(update(current.value as Record<string, unknown>));
    current.continue();
  };
}
```

مرّر `onFail` يسجّل الخطأ ويستدعي `request.transaction?.abort()` صراحة، ثم اجعل `openDatabase` يرفض برسالة تفرّق بين «فشل الترقية» و«التخزين غير متاح» — لأن الفعل التالي للمستخدم مختلف تمامًا بينهما.

**معيار القبول.** أضف اختبارًا في `IndexedDbLocalStore.test.ts` يفتح قاعدة بنسخة قديمة، يزرع سجلًا تالفًا، ثم يتحقق أن `openDatabase` يرفض بالرمز الجديد بدل النجاح على schema ناقص.

**لا يشمل.** لا تغيّر منطق أي ترحيل قائم ولا ترفع `localSchemaVersion`. هذا إصلاح صلابة، لا ترحيل جديد.

### P-04 — تبويب ثانٍ يُعطّل التخزين

| الحقل | المحتوى |
|---|---|
| **الخطورة** | مهم |
| **الموقع** | `apps/prototype-web/client/src/storage/local/IndexedDbLocalStore.ts:50` |

**المشكلة.** `request.onblocked = () => reject(...)`. في PWA يفتحها المستخدم في تبويبين، أو يفتح التطبيق المثبّت والمتصفح معًا، تفشل كل عمليات التخزين برسالة «التخزين المحلي مفتوح في نافذة أخرى» — حالة يسهل الوقوع فيها ويصعب على صاحب مشروع فهمها أو الخروج منها.

**القرار.** اجعل التبويب القديم يفسح المجال تلقائيًا، وأبقِ `onblocked` كشبكة أمان أخيرة برسالة قابلة للتنفيذ.

**التنفيذ.**

1. عند نجاح فتح الاتصال، سجّل فورًا:

```ts
database.onversionchange = () => {
  database.close();
  // أبلغ طبقة التطبيق أن هذا التبويب صار قديمًا
};
```

هذا وحده يحل الحالة الشائعة: التبويب القديم يغلق اتصاله، فتكتمل ترقية التبويب الجديد بلا حجب.

2. عدّل رسالة `onblocked` لتصير فعلًا لا وصفًا: «Micro مفتوح في نافذة أخرى. أغلق النوافذ الأخرى ثم أعد المحاولة.»

3. عند وصول `onversionchange`، اعرض شاشة استرداد صريحة تطلب إعادة التحميل، ولا تسمح بإدخال مالي جديد على اتصال مغلق.

**معيار القبول.** اختبار يفتح اتصالين على نسختين مختلفتين ويتحقق أن الأول يُغلق وأن الثاني يكمل الترقية بلا رفض.

### P-01 — لا مسار نسخ احتياطي مستقل عن انضباط المستخدم

| الحقل | المحتوى |
|---|---|
| **الخطورة** | حاسم |
| **العقد المطلوب** | تحديث `docs/contracts/21-guided-opening-import-prototype-contract.md` أو عقد جديد للنسخ المحلي |

**المشكلة.** local-first + IndexedDB + بلا مزامنة. الحماية الوحيدة تصدير يدوي. مسح بيانات المتصفح، أو تغيير الهاتف، أو تنظيف تلقائي للتخزين تحت ضغط المساحة — أي منها يمحو كل السجل المالي. الضرر نهائي وغير قابل للتراجع، ويقع على البيانات التي بُني النظام كله ليحميها.

**الخيارات.**

| الخيار | يكسر حدًا معلنًا؟ | الحكم |
|---|---|---|
| مزامنة سحابية | نعم — «لا Cloud ولا Auth» | **مرفوض** في هذه المرحلة |
| تذكير تصدير داخل التطبيق | لا | **معتمد — الطبقة 1** |
| مؤشر «آخر نسخة منذ N يومًا» ظاهر | لا | **معتمد — الطبقة 2** |
| كتابة تلقائية عبر File System Access API | لا | **معتمد — الطبقة 3، بتحفظ** |
| `navigator.storage.persist()` | لا | **معتمد — الطبقة 0** |

**القرار.** أربع طبقات متدرجة، كل واحدة تعمل وحدها إن سقطت التي بعدها.

**الطبقة 0 — طلب تخزين دائم.** استدعِ `navigator.storage.persist()` مرة عند التأسيس. هذا يحمي من إخلاء المتصفح التلقائي تحت ضغط المساحة، وهو سطر واحد وأعلى عائد لكل جهد في القائمة كلها. اعرض نتيجته بصدق في الإعدادات: «التخزين الدائم: مفعّل / غير مفعّل».

**الطبقة 1 — مؤشر عمر النسخة.** خزّن `lastExportAt` في `LocalPreferences`. اعرض في الإعدادات وفي «مشروعي الآن» عند تجاوز عتبة: «آخر نسخة احتياطية قبل 12 يومًا». استخدم لغة الحقيقة القائمة، لا تحذيرًا مزعجًا.

**الطبقة 2 — تذكير مرتبط بالخطر لا بالوقت.** لا تذكّر كل سبعة أيام تلقائيًا. ذكّر عندما **يزيد ما يمكن فقدانه**: بعد N حدثًا ماليًا مسجلًا منذ آخر تصدير. التذكير المرتبط بالخطر يُقرأ، والمرتبط بالتقويم يُتجاهل.

**الطبقة 3 — كتابة تلقائية عند التوفر.** عبر File System Access API: يمنح المستخدم إذنًا لمجلد مرة واحدة، فيكتب التطبيق نسخة عند كل تغيير مهم. **تحفظ إلزامي:** هذه الواجهة غير متاحة على Safari/iOS، وهو منصة مستهدفة. لذلك الطبقة 3 **تحسين اختياري لا يُبنى عليه**، ولا يجوز أن تعرض الواجهة «محمي» بناءً عليها إلا على جهاز يدعمها فعلًا. الطبقات 0–2 هي الحماية الحقيقية.

**العقد قبل الكود.** يجب أن يحسم: أين يُخزَّن `lastExportAt`، وهل يدخل `export`، وما عتبة التذكير، وماذا يحدث عند تصدير فاشل أو ملغى، ونص كل حالة. لا يبدأ الكود قبل اعتماده.

**معيار القبول.** اختبارات لعتبة التذكير، ولحالة رفض `persist()`، ولتصدير ملغى (يجب ألا يُحدَّث `lastExportAt`)، ولمتصفح بلا File System Access (يجب أن تختفي الطبقة 3 لا أن تفشل).

**لا يشمل.** لا سحابة، لا حساب، لا مزامنة بين أجهزة، ولا ادعاء «بياناتك محمية» — الصياغة تصف ما حدث فعلًا: «آخر نسخة: 12/08/2026».

|---|---|
| **الخطورة** | حاسم |
| **الموقع** | `storage/local/types.ts:22`، `application/transfers/localTransferService.ts:112`، `application/transfers/guidedOpeningImportService.ts:14,43,85` |
| **القرار المرتبط** | `docs/decisions/25-multi-activity-core-profiles-v1.md` |

**المشكلة.** القرار 25 يقول «لا هوية مشروع واحدة مفروضة، والسياق على مستوى الواقعة». الكود يجسّد النموذج المرفوض: كائن مفرد على مستوى المشروع بنوع نشاط واحد ثابت. والأخطر أن `"custom_craft"` مثبّت كشرط **رفض** في مسارَي الاستيراد. ومع كون التصدير اليدوي هو النسخة الاحتياطية الوحيدة، فإن أول Profile ثانٍ يجعل كل ملف تصدير قائم غير قابل للاستيراد — أي مسار فقدان بيانات، لا خطأ نوع.

**القرار.** الترحيل يسبق أي عمل على Profiles، ويُنفَّذ وحده في شريحة مستقلة لا تضيف أي قدرة.

**التنفيذ — بهذا الترتيب حصرًا.**

1. **أعد التسمية أولًا.** `ActivityProfile` يعني اليوم «شاشة التأسيس» لا القطاع. أعد تسميته إلى `ProjectSetup` وحرّر الاسم للمعنى الجديد. تنفيذ هذا الآن رخيص؛ بعد شريحة واحدة يصير مكلفًا.
2. **ارخِ التحقق قبل أن توسّع البيانات.** بدّل `activityType !== "custom_craft" → reject` إلى قبول قيمة معروفة من مجموعة، مع `"custom_craft"` افتراضًا للملفات القديمة. **هذه الخطوة وحدها تفتح باب التوافق المستقبلي وهي غير كاسرة** — ملف قديم يبقى مستوردًا، وملف جديد يصير ممكنًا.
3. ارفع `localSchemaVersion` و`localExportVersion`، مع ترحيل يمنح كل سجل قديم `"custom_craft"` صراحة.
4. **اختبر الاتجاهين:** ملف بـ`exportVersion 17` يُستورد على البناء الجديد، وملف جديد يُرفض بوضوح على بناء قديم برسالة مفهومة لا بفشل صامت.

**معيار القبول.** ملف تصدير حقيقي من `main` الحالي يُستورد بنجاح على البناء الجديد بلا فقدان سجل واحد. هذا هو الاختبار الوحيد الذي يهم.

**لا يشمل.** لا تنشئ أي Profile قطاعي، ولا حقل سياق على الواقعة، ولا شاشة اختيار نشاط. هذه شريحة ترحيل بحتة تفتح الباب ولا تدخل منه.

### X-02 — قراءة التغطية قبل أي Profile

| **الوثيقة المطلوب تعديلها** | `docs/product/activity-profiles-and-hybrid-projects-v1.md` |

**المشكلة.** القاعدة 6.2 «عدم الاختيار ليس صفرًا» صحيحة ومتسقة مع `missing ≠ zero`. لكن نتيجتها غير مذكورة في الوثيقة: الحقل الاختياري يبقى فارغًا في أغلب الوقائع، وقاعدتك تمنع افتراض الصفر، فتعرض كل قراءة لكل Profile `غير متاح`. تكون قد بنيت آلة كاملة مخرجها الأصدق هو الامتناع عن الإجابة.

**القرار.** أضف مفهوم «قراءة التغطية» إلى الوثيقة **قبل** أي عقد Profile.

**التنفيذ.** بند جديد في القسم 6: أي سطح يعرض قراءة لكل نشاط يجب أن يعرض معه نسبة التغطية وفعلًا تاليًا — «7 من 12 مصروفًا في هذه الفترة بلا سياق نشاط · صنّفها الآن». التغطية ليست تحذيرًا بل معلومة أولى، لأنها تحدد كم تساوي القراءة المعروضة.

**لماذا هذا البند تحديدًا.** بدونه تقتل سياسة الصدق الميزة بصمت: المستخدم يرى `غير متاح` ولا يعرف أن السبب بيده ولا كيف يصلحه. هذا هو الفرق بين نظام صادق ونظام عاجز.

## 9. حواجز الحماية — تسري على كل بطاقة بلا استثناء

يُرفض أي PR يكسر واحدة منها مهما كانت جودته:

1. **لا يتغير معنى المال.** `collection ≠ profit`، `debt ≠ cash`، `purchase ≠ COGS`، `owner money ≠ sale/expense`، `missing ≠ zero`. إصلاح دين تقني لا يمس هذه أبدًا.
2. **لا يتغير رقم تاريخي.** أي `CostSnapshot` أو طلب أو حدث مالي مسجّل يبقى بقيمته نفسها بعد أي إصلاح. الترحيل يملأ حقولًا جديدة بقيم آمنة، ولا يعيد حساب قديم.
3. **لا حذف صامت.** كل تصحيح بعكس موثّق بسبب ومفتاح idempotency.
4. **لا رفع `schemaVersion` في مجموعة أ.** إن احتاج إصلاحك ترحيلًا فهو ليس دينًا تقنيًا — أعد تصنيفه إلى مجموعة ب.
5. **لا خلط تنسيق بمنطق.** PR إعادة التنسيق لا يحمل تغييرًا سلوكيًا واحدًا.
6. **لا توسيع نطاق.** إن وجدت مشكلة ثانية أثناء التنفيذ، سجّلها بمعرّف جديد ولا تصلحها في نفس PR.
7. **`pnpm check` يمر قبل كل push.** لا استثناء ولا «سأصلحه في التالي».
8. **لا ادعاء قبول ميداني.** نجاح CI أو sandbox لا يُرفع إلى ادعاء قبول على جهاز أو إنتاج أو Pilot.
