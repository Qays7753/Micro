# محاكاة تجارب ما قبل البناء — Micro v1

**نوع العمل:** محاكاة مكتبية حتمية مبنية على حالات مرجعية، وليست اختبارًا مع مستخدمين حقيقيين ولا دليلًا إحصائيًا أو تجاريًا.

## Major Discussion Points

تمت محاكاة التجارب الخمس الواردة في تقرير الجاهزية. أظهرت المحاكاة أن القواعد المالية والمسار المقترح قابلان للانتقال إلى Prototype محدود، لكنها لم تثبت أن صاحب مشروع حقيقي سيفهم أو يعود أو يدفع. هذه الحدود مقصودة وليست نقصًا في التقرير.

## 1. اختبار الحقيقة المالية

| الرمز | الحالة | النتيجة المكتبية | القيم المتوقعة | الفعل التالي |
|---|---|---|---|---|
| FT-01 | شراء مخزون ثم استهلاك جزء | PASS | `{"cash_after_purchase": 450, "inventory_value_after_purchase": 50, "recognized_cost_at_purchase": 0, "recognized_cost_after_consumption": 10, "inventory_value_after_consumption": 40}` | يظهر للمستخدم أن الشراء زاد المخزون وخفض الكاش، وأن الجزء المستهلك فقط دخل التكلفة. |
| FT-02 | عربون قبل التسليم | PASS | `{"cash_increase": 30, "recognized_revenue_before_delivery": 0, "final_profit_before_delivery": null, "remaining_receivable_after_deposit": 70}` | يُعرض العربون ككاش محصل مرتبط بطلب، لا كربح نهائي. |
| FT-03 | تسليم ثم تحصيل المتبقي | PASS | `{"recognized_revenue_at_delivery": 100, "recognized_cost_at_delivery": 60, "profit_indicator": 40, "cash_total_after_collection": 100, "receivable_after_collection": 0}` | بعد التحصيل، يراجع المستخدم نتيجة الطلب والفعل التالي. |
| FT-04 | تسليم بالدين | PASS | `{"cash_increase": 0, "receivable": 100, "profit_indicator": 40}` | يضع النظام الدين في المتابعة ولا يصفه بأنه كاش. |
| FT-05 | سحب شخصي | PASS | `{"cash_after": 400, "operating_profit_after": 200, "owner_equity_change": -100}` | يظهر أثر السحب على الكاش ومال المالك دون خفض ربح التشغيل. |
| FT-06 | مصروف مشترك للكهرباء | PASS | `{"cash_outflow": 100, "business_expense_for_result": 40, "knowledge_state": "estimated_or_known_by_policy"}` | يسأل النظام عن النسبة أو يقبل «غير متأكد»، ولا يحمل الفاتورة كاملة أو يستبعدها بصمت. |
| FT-07 | تغير سعر خامة بعد اعتماد الطلب | PASS | `{"old_order_cost": 20, "new_revision_cost": 30, "historical_order_changed_silently": false}` | ينشئ النظام Snapshot أو Revision جديدًا ويطلب مراجعة السعر والمواصفات. |
| FT-08 | إلغاء طلب ذي عربون | PASS | `{"status": "cancelled", "settlement": "needs_review", "automatic_refund": false, "automatic_retention": false}` | يعرض النظام خيار رد العربون أو الاحتفاظ به مع سبب، ولا يقرر بدل المستخدم. |
| FT-09 | نقطة التعادل مع الافتراضات | PASS | `{"contribution_per_unit": 20, "break_even_units": 6, "formula": "fixed_costs / contribution_margin"}` | يعرض الفترة والهامش والافتراضات، ويعيد الحساب عند تغير السعر أو التكلفة. |
| FT-10 | الأكثر مبيعًا مقابل الأكثر ربحًا | PASS | `{"best_seller": "A", "best_profit": "B", "profit_A": 50, "profit_B": 60}` | يفصل التقرير الكمية عن الهامش ولا يساوي بين الأكثر مبيعًا والأكثر ربحًا. |
| FT-11 | إعادة إرسال حدث قبض | PASS | `{"financial_effect_count": 1, "cash_increase": 30}` | لا يتضاعف الأثر المالي عند إعادة المحاولة. |
| FT-12 | يوم بلا طلب | PASS | `{"project_status": "needs_attention", "cash_known": 350, "receivables": 80, "next_action": "راجع التحصيل أو الالتزام القريب"}` | لا تظهر رسالة «لا يوجد طلب» فقط؛ تظهر صورة الوضع والفعل القريب. |

**الخلاصة:** 12 من 12 حالة حتمية نجحت على مستوى المحاكاة المكتبية. هذه النتيجة تثبت اتساق القواعد في الأمثلة المحددة، ولا تعني أن كل حالة أصبحت Use Case أو تقريرًا منفذًا في Domain Core.

### 1.1 مصفوفة ربط الحالات بالتنفيذ

الجدول التالي يمنع قراءة `PASS` بوصفها دليلًا على أن القدرة المقابلة منفذة. `DOMAIN-PARTIAL` يعني أن بعض القاعدة ممثل في `CraftOrder` واختباره، و`DEFERRED` يعني أن الحالة مكتبية أو تحتاج Ledger أو طبقة لاحقة.

| الرمز | حالة التنفيذ | الدليل الحالي أو سبب التأجيل |
|---|---|---|
| FT-01 | DEFERRED | شراء المخزون والاستهلاك وتقييمه غير منفذة؛ لا يوجد Ledger أو Inventory عام |
| FT-02 | DOMAIN-PARTIAL | اختبار `keeps deposit, delivery, collection, and profit separate` يغطي فصل العربون والنتيجة على مستوى الطلب |
| FT-03 | DOMAIN-PARTIAL | الاختبار نفسه يغطي التسليم والقبض والنتيجة لطلب واحد، لا سجلًا ماليًا عامًا |
| FT-04 | DOMAIN-PARTIAL | اختبار `registers a debt without increasing cash` يغطي الدين على مستوى الطلب |
| FT-05 | DEFERRED | السحب ومال المالك يحتاجان Ledger عام؛ غير موجودين في `CraftOrder` |
| FT-06 | DEFERRED | المصروف المشترك وتوزيعه يحتاجان سياسة تحميل ومصاريف عامة؛ مؤجلان في P0 |
| FT-07 | COVERED | اختبار `preserves the old cost snapshot when specifications change` يغطي حفظ النسخة والتعديل |
| FT-08 | COVERED | اختبارات الإلغاء وتسوية العربون بالرد أو الاحتفاظ تغطيان القرار الصريح ومنع التكرار |
| FT-09 | DEFERRED | نقطة التعادل تحتاج فترة وتكاليف ثابتة وهامش مساهمة ومزيج منتجات؛ لا تُحسب في Prototype |
| FT-10 | DEFERRED | مقارنة الأكثر مبيعًا والأكثر ربحًا تحتاج تقارير متعددة الطلبات؛ غير منفذة |
| FT-11 | COVERED | اختبار `does not duplicate a financial event when retried` يغطي idempotency المحلي |
| FT-12 | DEFERRED | صورة يوم بلا طلب تحتاج بيانات مشروع وLedger وفترة؛ تبقى نتيجة محاكاة فقط |

## 2. محاكاة Prototype الورقي أو القابل للنقر

الحالة: **DESK_PASS**. فحص مكتبي لتسلسل المسار، وليس إثباتًا لفهم مستخدم حقيقي.

| الخطوة | الحد الأدنى للإدخال | الناتج | الفعل التالي |
|---|---|---|---|
| إنشاء قطعة | اسم القطعة، المواصفات، الكمية | مسودة قطعة | أدخل الخامات والوقت |
| إدخال التكلفة | الخامات، الوقت، التغليف، التوصيل، الهدر إن عرف | تكلفة وحالة معرفة | راجع النقص أو اعتمد السعر |
| اعتماد السعر | سعر متفق أو سعر حماية مقترح | سعر وSnapshot | سجل الاتفاق والموعد |
| تسجيل الاتفاق | الزبون، الموعد، العربون إن وجد | طلب بحالة واضحة | ابدأ التنفيذ أو راجع التحذير |
| التسليم والتحصيل | تسليم، قبض أو دين | نتيجة الطلب والذمم | راجع النتيجة والفعل التالي |

نجحت المحاكاة في التحقق من أن كل خطوة لها إدخال أدنى ونتيجة وفعل تالٍ، وأن المسار لا يحتاج درسًا مستقلًا. هذا لا يقيس زمن المهمة أو الفهم أو الإرباك؛ لذلك تبقى جلسات المستخدمين إلزامية.

## 3. محاكاة جلسات المهام الواقعية

الحالة: **SCRIPT_READY_NOT_USER_EVIDENCE**. هذه محاكاة لبروتوكول المهمة والناتج المتوقع؛ لا يمكن للبرنامج محاكاة فهم أو تردد أو ثقة إنسان حقيقي.

| الرمز | المهمة | ما يجب ملاحظته | نتيجة المحاكاة |
|---|---|---|---|
| US-01 | تسعير طلب حرفة مخصص | يحدد المستخدم إن كان السعر يغطي التكلفة والوقت | PASS_DESK |
| US-02 | تسجيل شراء خامات للمخزون | يفهم أن الشراء ليس كله تكلفة بيع فورية | PASS_DESK |
| US-03 | تفسير عربون مقابل ربح | يفصل الكاش المحصل عن الربح النهائي | PASS_DESK |
| US-04 | تسجيل مصروف مشترك | يختار نسبة أو غير متأكد ويعرف أثر النقص | PASS_DESK |
| US-05 | قراءة يوم بلا طلب | يحدد فعلًا قريبًا بدل اعتبار اليوم بلا قيمة | PASS_DESK |

**التحويل إلى اختبار حقيقي:** 5–8 أصحاب مشاريع، تسجيل الزمن والأخطاء، وطلب شرح ماذا حدث وما أثره وما الفعل التالي.

## 4. اختبار يوم بلا طلب

الحالة: **DESK_PASS**. محاكاة مخرجات يوم بلا طلب، وليست قياسًا لعودة المستخدم.

| الحالة | صورة الوضع | الفعل التالي |
|---|---|---|
| يوم بلا طلب مع تحصيل متأخر | كاش معروف 350 د.أ، ما لي 80 د.أ، خطر المخزون: لا يوجد | راجع التحصيل |
| يوم بلا طلب مع التزام مواد | كاش معروف 350 د.أ، ما لي 0 د.أ، خطر المخزون: شراء مطلوب | قيّم الالتزام قبل الشراء |
| يوم بلا طلب مع منتج جديد | كاش معروف 350 د.أ، ما لي 0 د.أ، خطر المخزون: تقدير أولي | احسب تكلفة المنتج الجديد |

نجحت المحاكاة في منع مخرج فارغ من نوع «لا يوجد طلب». لكنها لا تثبت أن المستخدم سيعود في اليوم بلا مبيعات؛ ذلك يحتاج قياسًا سلوكيًا.

## 5. محاكاة Pilot لمدة 30 يومًا

الحالة: **DESIGN_READY_NOT_EXECUTED**. لا توجد بيانات بشرية يمكن توليدها بأمان؛ المحاكاة هنا تجهز التصميم ولا تختلق نتائج.

| الفترة | النشاط |
|---|---|
| قبل البدء | موافقة، تعريف المشروع، baseline، ومهمة مالية قصيرة |
| اليوم 1 | أول قيمة ومسار الحرفة أو حالة واقعية |
| اليوم 7 | عودة ومراجعة فهم النتيجة |
| اليوم 14 | مراجعة تكرار التسجيل والفعل التالي |
| اليوم 30 | مقابلة قرار الاستمرار والقيمة والتكلفة |

| مقياس | ما الذي يثبته؟ |
|---|---|
| زمن أول قيمة | من البدء إلى أول تكلفة/نتيجة مفهومة — يُقاس لكل مشروع |
| إكمال أول تكلفة | هل اكتملت دون مساعدة زائدة؟ — نعم/لا + سبب |
| فهم الربح والكاش | شرح المستخدم الفرق بلسانه — مهمة فهم |
| الفعل التالي | هل نفذ قرارًا أو متابعة بعد النتيجة؟ — حدث قابل للملاحظة |
| العودة | هل عاد في اليوم 7 و14 و30؟ — سجل استخدام |
| الثقة والأخطاء | ما الذي لم يصدقه أو سجله خطأ؟ — مقابلة + سجل |
| الالتزام التجاري | استمرار أو استعداد دفع لاحق — لا يقاس بالمجاملة |

قاعدة القرار: **لا نقرر العودة أو الدفع أو التوسع من المحاكاة؛ نقررها من Pilot حقيقي.**

## النتيجة العامة

| المجال | نتيجة المحاكاة | القرار |
|---|---|---|
| الحقيقة المالية | PASS مكتبي للحالات الاثنتي عشرة | يمكن تثبيت سياسات P0 وتحويلها إلى Golden Cases واختبارات لاحقة |
| مسار Prototype | DESK_PASS | صمّم Prototype RTL محليًا لمسار الحرفة فقط |
| تجربة المستخدم | SCRIPT_READY_NOT_USER_EVIDENCE | نفّذ جلسات مع أصحاب مشاريع حقيقيين؛ لا تدّعي الفهم من المحاكاة |
| يوم بلا طلب | DESK_PASS | ادخل الحالة في Prototype، ثم اختبر العودة الواقعية لاحقًا |
| Pilot | DESIGN_READY_NOT_EXECUTED | لا قرار تجاري قبل Pilot 5–8 مشاريع/30 يومًا |

## Action Points

1. تثبيت هذه النتائج في بوابة Pre-build وعدم تسميتها اختبار مستخدم أو Pilot.
2. اعتماد الحالات المالية الاثنتي عشرة كـGolden Financial Cases أولية قبل كتابة Adapter.
3. بناء Prototype محلي صغير على المسار المحدد، ثم اختبار المهام الخمس مع أصحاب مشاريع حقيقيين.
4. تسجيل أي فشل أو ارتباك في مصفوفة السيناريوهات بدل تعديل الحالة لتناسب الحل.
5. تأجيل قرار SaaS وAuth والمزامنة والدفع إلى ما بعد Prototype وPilot، كما هو مثبت في خارطة التنفيذ.

## حدود المحاكاة

المحاكاة لم تولد مستخدمين أو بيانات سوق أو احتمالات عشوائية. الحسابات حتمية ومبنية على افتراضات معلنة، ولذلك تصلح لاختبار الاتساق فقط. لا يمكنها قياس الفهم، زمن الإدخال، الثقة، العودة، الاستعداد للدفع، أو الأثر الفعلي على قرار صاحب المشروع.
