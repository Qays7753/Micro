# نتائج مراجعة Cloud Code الفعلية — الإصدار 1

**الحالة:** CURRENT / سجل مراجعة فعلي بعد استلام تقرير Cloud Code من مالك المشروع.

**المصدر:** تقرير القراءة الأولى المرفق في جلسة 22 أغسطس 2026. لا يمثل هذا الملف نص Cloud Code كاملًا؛ بل يلخص ملاحظاته ويضيف تحققًا مستقلًا وتنفيذ الإصلاحات التي لا تتطلب قرارًا منتجيًا جديدًا.

**الحد:** لا تُفهم نتائج هذه المراجعة على أنها تعني أن Prototype أو SaaS بُنيا. هي مراجعة جودة للنواة والوثائق قبل Prototype.

## 1. الحكم التنفيذي

كان تقرير Cloud Code دقيقًا ومفيدًا؛ فقد قرأ المستودع كاملًا، شغّل `typecheck` و18 اختبارًا قبل الإصلاحات، وأنشأ probes خارج المستودع. أُعيدت ملاحظاته C-01 إلى C-07 بصورة مستقلة على Domain Core، ثم عولجت العيوب السلوكية والوثائقية الآمنة في فرع إصلاح مستقل. ارتفع عدد الاختبارات الدائمة إلى 22، ونجحت بعد الإصلاحات.

لم يتغير مفهوم Micro أو أول Vertical Slice أو حدود Prototype. ما تغير هو رفع صرامة النواة: لا تراجع صامت بعد التسليم، ولا وقت معروف صفري ينتج تكلفة مكتملة، ونقص الوقت لا يُحجب بسبب مادة `variable` أو `stale`، وكل تسوية مباشرة إلى `settled` تسجل حدث حالة.

## 3. ما تم التحقق منه فعليًا

أُعيد إنتاج C-01 إلى C-07 في probe مؤقت خارج المستودع. ثبتت التجربة أن الطلب المسلّم كان يستطيع سابقًا العودة إلى `in_progress` مع `resultStatus: final`، وأن الوقت المعروف الصفري كان ينتج `known`، وأن نقص الوقت كان يختفي خلف `variable` أو `stale`، وأن التسوية بالدين أو القبض الكامل لم تكن تصدر `status_changed`، وأن السعر الصفري غير قابل للتمثيل، وأن سجل العربون التاريخي يبقى بعد الرد.

بعد الإصلاح، شغّل المستودع `pnpm typecheck` و`pnpm test` بنتيجة **22/22 اختبارًا ناجحًا**. الاختبارات الجديدة تغطي منع التراجع بعد التسليم، الوقت الصفري المعروف، تقاطع الوقت المفقود مع مادة مقدرة أو قديمة، وأحداث التسوية. حُذف probe المؤقت ولم يدخل في الاختبارات الدائمة.

## 4. القرارات المحافظة التي اتخذت ولماذا

### 4.1 الوقت الصفري المعروف

اعتُبر الوقت المعلن `known` مع `minutes === 0` أو `hourlyRateMinor === 0 غير كافٍ لنتيجة حرفة نهائية. هذا قرار حماية من الربح الوهمي وليس حكمًا بأن كل نشاط يحتاج وقتًا موجبًا إلى الأبد. إذا أثبت نشاط مستقبلي أنه لا يملك عملًا بشريًا أو يريد حذف وقت العمل عمدًا، يجب أن يضاف له حقل أو عقد صريح مثل `labor_not_applicable`؛ لا نستنتج ذلك من صفر صامت.

### 4.2 مراجعة طلب مسلّم

لا نضيف `correctDelivery` الآن لأن سياسة العكس والتسليم الجزئي والإرجاع والخصم لم تُحسم. الإصلاح الحالي دفاعي: يتيح وضع الطلب في `needs_review`، يحجب مؤشر الربح، ويمنع العودة إلى التنفيذ أو التأكيد حتى توجد عملية تصحيح موثقة. هذا يمنع فسادًا ماليًا ولا يخترع سياسة عكس.

### 4.3 حالة on_hold

العقد الكامل يحتاج حالة توقف بسبب مادة أو قدرة، لكن Domain Core الحالي لا يملك بيانات قدرة أو مخزونًا عامًا كافيًا. لذلك سُجلت الحالة مؤجلة، ولم تُستخدم `needs_review` كبديل؛ فالخلط بين توقف تشغيلي وتعارض مالي سيشوّه التقارير والفعل التالي.

## 5. ما بقي مفتوحًا بعد المراجعة

| الموضوع | سبب بقائه مفتوحًا | متى يعود؟ |
|---|---|---|
| `correctDelivery` | يحتاج سياسة تصحيح وإلغاء اعتراف وتسليم جزئي وإرجاع وخصم | قبل دعم تصحيح مالي بعد التسليم أو أي Ledger عام |
| `on_hold` | يحتاج عقد قدرة ومواد وفعل متابعة وانتقالات واختبارات | عند بناء Use Case تشغيلي يتطلب الحجز أو الإيقاف |
| السعر غير المكتمل | يحتاج تعريفًا يسمح بطلب بلا سعر وحدود التأكيد والعربون | عند تصميم مسار التسعير قبل الاتفاق |
| `partial` | يحتاج سياسة إدخال ونتيجة مستقلة عن `incomplete` و`estimated` | عند إضافة قدرة تكلفة جزئية فعلية |
| `depositCollectedMinor` | الاسم يحمل معنى تاريخيًا وليس كاشًا حاليًا | عند بناء نموذج أحداث أو View Model؛ لا يغير الآن دون توافق |
| مخرجات FT المؤجلة | تحتاج Ledger ومخزون وتقارير وفترات حقيقية | بعد Prototype وقرار طبقة مالية لاحقة |

## 6. أثر التقرير على قرار البدء

أثبت التقرير أن القراءة الأولى من Agent جيد لا ينبغي أن تكتفي بفهم المفهوم. يجب أن تعيد إنتاج الحالات الحدية، وتقارن العقود بالأنواع والدوال، وتبحث عن مسارات تغيّر الحالة دون أحداث، وتفصل نتائج المحاكاة المكتبية عن القدرات المنفذة. هذه إضافة إلى بروتوكول Micro وليست تغييرًا في المنتج.

بعد هذه الإصلاحات لا يزال القرار الصحيح هو بناء Prototype المرحلة 2 فقط: Adapter محلي، LocalStore، Use Cases، وواجهة هاتف RTL لمسار الحرفة، ثم اختبار المهام مع أصحاب مشاريع حقيقيين. لا تُفتح Auth أو Supabase أو RLS أو Ledger عام أو نقطة تعادل أو Billing بناءً على هذا التقرير.

## 7. بروتوكول القراءة التالي

عند مراجعة Cloud Code أو Agent جديد، يجب البدء بـ`AGENTS.md` ثم `docs/00-document-index.md`، وقراءة عقد P0 ومصفوفة التغطية، ثم فحص `src/domain/` والاختبارات. يجب إعادة إنتاج حالات الحافة خارج المستودع أولًا، وعدم إضافة probes أو أدوات تشخيصية إلى الاختبارات الدائمة إلا إذا أصبحت قاعدة منتج مستقرة.

يجب أن يسلّم Agent جدولًا من أربعة أعمدة: الملاحظة، هل هي مؤكدة، الدليل في الكود أو الوثائق، والإجراء أو القرار المطلوب. كما يجب أن يذكر بوضوح ما قرأه وما لم يقرأه، وألا يعدل قاعدة مالية تحتاج قرار مالك المنتج قبل عرض أثرها.
