# Micro — مصفوفة تغطية السيناريوهات v1

## الغرض

تربط هذه المصفوفة بين مشكلات أصحاب المشاريع، وقدرات Micro، ومجموعة الشخصيات والحالات والأسئلة. وهي لا تعني أن القدرة منفذة في التطبيق؛ بل تميز بين التغطية المفهومية والحاجة إلى Prototype أو كود أو Pilot.

## معيار الحالة

| الحالة | المعنى |
|---|---|
| `concept_pass` | المفهوم موصوف وقابل للاختبار، دون تنفيذ واجهة |
| `prototype_required` | يحتاج اختبار تجربة هاتفية قبل الحكم |
| `domain_required` | يحتاج عقدًا أو منطقًا في Domain Core |
| `pilot_required` | يحتاج استخدامًا مع أصحاب مشاريع حقيقيين |
| `deferred` | خارج النطاق الحالي بقرار واضح |

## التغطية التي لا تعني تنفيذًا

السيناريوهات تثبت أن النموذج يحتاج إلى هذه القدرات، لكنها لا تثبت أن واجهة أو قاعدة بيانات أو مزامنة معينة هي الحل. يجب نقل كل قدرة إلى Prototype واختبارها على الحالات ذات الصلة قبل اعتبارها قرارًا تنفيذيًا.

## الفجوات التي يجب إضافتها في v2

ينبغي أن تضيف النسخة التالية حالات التصحيح والعكس، التكرار، الدفعات الجزئية للمورد، القروض، أجرة المالك أو العامل، الضرائب المؤرخة، المرتجع الجزئي بعد التحصيل، افتتاح مشروع بسجلات ناقصة، المقارنة بين فترات متعددة، واستيراد البيانات من دفتر أو Excel أو WhatsApp عند إثبات الحاجة.

## نتيجة محاكاة Pre-build

أُجريت محاكاة مكتبية حتمية على 12 حالة مالية، وتسلسل Prototype، وثلاث حالات ليوم بلا طلب، وخمس مهام جلسات مستخدم، وجدول Pilot. نجحت الحالات المالية الاثنتا عشرة وتسلسل المسار ويوم بلا طلب على مستوى الاتساق المكتبي. لا تُغيّر هذه النتيجة حالات المصفوفة من `prototype_required` أو `pilot_required` إلى نجاح سلوكي؛ فهي تثبت قابلية الفحص فقط، لا فهم المستخدم أو عودته أو استعداده للدفع. التفاصيل في `pre-build-experiment-simulation-v1.md` وملف JSON المرافق.

## بوابة القبول

لا يجوز أن ينتقل أي قرار منتج أو ميزة إلى Prototype أو كود إذا لم يذكر:

1. مشكلة أو سؤالًا من هذه المصفوفة.
2. الحالات والشخصيات المتأثرة.
3. أقل إدخال ونتيجة وفعل تالٍ.
4. الأثر على الربح والكاش والمخزون والذمم ودرجة المعرفة.
5. معيار القبول والفشل وما قد يغير القرار.
