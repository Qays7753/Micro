# مراجعة القراءة الأولى المحاكية لـCloud Code — الإصدار 1

**الحالة:** CURRENT / مراجعة محاكية مرجعية؛ القراءة الفعلية موثقة في `cloud-code-first-read-findings-v1.md`.

**الحد المنهجي:** هذا التقرير ليس نتيجة قراءة فعلية من Cloud Code، ولا ينسب رأيًا إلى Agent خارجي. هو محاكاة مهنية لما يمكن أن يفهمه Agent جديد إذا بدأ من نقطة الدخول الموصى بها وراجع الوثائق والكود والاختبارات. بعد تنفيذ القراءة الفعلية، راجع [`cloud-code-first-read-findings-v1.md`](cloud-code-first-read-findings-v1.md) لفصل الملاحظات المحاكية عن النتائج المؤكدة.

**الغرض:** اختبار قابلية فهم المستودع من أول قراءة، وكشف أي فرق بين تعريف Micro في الوثائق وما ينفذ فعليًا في Domain Core، قبل بدء Prototype الهاتف.

## 1. طريقة المحاكاة

اتبعت المحاكاة ترتيب القراءة في `AGENTS.md` و`docs/00-document-index.md`: بدأت بهوية المنتج والـBlueprint، ثم بوابة Pre-build، ومكتبة المصادر ومنطق البناء، ووثائق المشكلة والاستخدام والنموذج المالي والتوجيه، ثم العقود وخصوصًا عقد السياسات المالية P0، ومصفوفة تغطية Domain Core، والسيناريوهات والمحاكاة. بعد ذلك قارنت الادعاءات التنفيذية بملفات `src/domain/` والاختبارات.

هذا الترتيب مهم لأن قراءة README أو ملفات الكود وحدها ستعطي صورة أصغر من Micro، بينما قراءة كل الوثائق دون مصفوفة التغطية قد تجعل Agent يظن أن الهدف التجاري منفذ بالفعل.

## 2. ما الذي سيفهمه Agent جديد بوضوح؟

### 2.1 هوية Micro

سيفهم Agent أن Micro **نظام إدارة مالية وتشغيلية كامل في الهدف** لصاحب المشروع المنزلي أو المتناهي الصغر، عميق ماليًا ومحاسبيًا في الداخل، لكنه بسيط وعملي في تجربة المستخدم. النظام لا يختزل المشروع في الطلبات، ولا يهدف إلى تعليم المستخدم كمقرر، بل يحول الأحداث اليومية إلى تكلفة ونتيجة وكاش والتزامات وقرار تالٍ.

سيفهم كذلك أن المنتج يملك SaaS تجاريًا في الهدف، لكن هذا لا يعني أن Prototype الحالي SaaS. طبقات Auth وworkspace وRLS والتخزين المركزي والمزامنة وBilling ليست جزءًا من Domain Core المحلي الحالي.

### 2.2 المستخدم والمشكلة والقيمة

المستخدم المباشر هو صاحب مشروع يدير البيع والتنفيذ والتحصيل بنفسه وليس محاسبًا محترفًا ولا مدير SaaS. المشكلة المركزية ليست غياب دفتر معاملات فقط، بل عدم القدرة على تكوين صورة سريعة وموثوقة عن تكلفة العمل ونتيجته والكاش والالتزامات والطلبات القادمة عندما يحتاج إلى التسعير أو قبول طلب أو تنفيذ أو تحصيل أو سحب مال.

القيمة المميزة هي ربط الاتفاق والتكلفة والوقت والموعد والعربون والتنفيذ والتسليم والتحصيل والنتيجة في مسار واحد، مع إظهار ما هو معروف ومقدر وناقص، والفصل الصريح بين الربح والكاش والدين والعربون. التوجيه يظهر داخل لحظة العمل وبشرح قصير وفعل مباشر، ولا يتحول إلى LMS أو دورة مالية.

### 2.3 أول Vertical Slice

سيفهم Agent أن الحرفة اليدوية المخصصة هي نقطة الإثبات الأولى، لا تعريف Micro الكامل ولا القطاع الوحيد مستقبلًا. أول مسار يتعامل مع مواصفات وكمية ومواد ووقت وتغليف وتوصيل وهدر وتكلفة وسعر حماية وموعد واتفاق وعربون وتنفيذ وتسليم وتحصيل أو دين ونتيجة طلب وفعل تالٍ.

الحرفة هي اختيار لاختبار العمق، ثم يمكن توسيع النواة إلى الأطعمة والخدمات عبر اختلافات الوصفة أو الدفعة أو الوقت أو التوفر أو المخزون، لا عبر نسخ ثلاثة تطبيقات منفصلة.

## 3. ما هو منفذ فعليًا الآن؟

| المجال | الحالة التي سيجدها Agent في الكود |
|---|---|
| Domain Core | نواة TypeScript مستقلة عن الواجهة وقاعدة البيانات وAuth؛ المسار الحالي هو `CraftOrder` محلي |
| التكلفة | مواد، وقت، تغليف، توصيل، هدر، تكلفة مخططة، تكلفة وحدة، وسعر حماية |
| المعرفة | حالات `known` و`estimated` و`variable` و`incomplete` و`stale`، مع حفظ المدخلات داخل Snapshot |
| الوقت المفقود | إذا كان `time === null` في Snapshot الحرفة، تكون الحالة `incomplete` ولا ينتج ربح نهائي معروف |
| النسخ التاريخية | `costSnapshots` يحتفظ بالنسخ، وتعديل التكلفة ينشئ Snapshot جديدًا بدل تغيير الماضي بصمت |
| invariant التعديل | `reviseOrderCost` يرفض Snapshot بكمية لا تطابق كمية الطلب |
| دورة الطلب | حالات الطلب والانتقالات الأساسية من المسودة حتى التسليم والتسوية أو الإلغاء |
| الكاش والتحصيل | العربون والتحصيل المتبقي والدين منفصلة؛ التسليم لا يسجل قبضًا تلقائيًا |
| التسوية | إلغاء الطلب لا يحذف التاريخ؛ رد العربون أو الاحتفاظ به قرار مستقل وموثق |
| منع التكرار | الأحداث الحساسة تحمل `idempotencyKey` وتُرفض إعادة آثارها داخل الكائن المحلي |
| الاختبارات | اختبارات Domain Core تغطي القواعد المالية والانتقالات والنسخ والحالات الجديدة؛ العدد الحالي بعد إصلاحات القراءة الأولى 22 اختبارًا |

هذه قائمة تنفيذية لا تعني أن النظام أصبح تطبيقًا قابلًا للاستخدام اليومي. هي تثبت أن النواة الحالية تحمل قواعد الشريحة الأولى ويمكن اختبارها دون UI أو قاعدة بيانات.

## 4. ما هو غير منفذ، ويجب ألا يدعي Agent أنه منفذ؟

| القدرة | الوضع الحالي | المرحلة المسموح بها |
|---|---|---|
| واجهة هاتف RTL | غير موجودة في هذه الحزمة | Prototype المرحلة 2 |
| Adapter وLocalStore | غير موجودين في Domain Core الحالي | Prototype المرحلة 2 |
| `local export/import` | هدف موثق، غير منفذ حاليًا | Prototype المرحلة 2 عند الحاجة |
| Ledger مالي عام | غير موجود؛ Domain Core يمثل طلبًا واحدًا | مرحلة مالية لاحقة |
| مصاريف مشروع فعلية وactual cost | غير منفذة | بعد عقد Ledger والتكلفة الفعلية |
| مخزون عام وتقييمه | غير منفذ؛ لا يُستنتج من شراء مادة | مرحلة لاحقة أو Spike محدد |
| نقطة التعادل | سياسة وصيغة موثقتان فقط | مرحلة مالية لاحقة بعد الفترات والتكاليف |
| Auth وworkspace وRLS | غير موجودة | MVP التجاري اللاحق |
| Backup/restore مركزي ومزامنة | غير منفذين؛ الفرق بينهما وبين التصدير المحلي موثق | MVP التجاري اللاحق |
| Billing والاشتراك | غير منفذين، وخارج Financial Domain | بعد إثبات القيمة |
| تقارير المشروع منذ البداية | غير ممكنة من `CraftOrder` وحده | بعد Ledger وفترات ومصادر مكتملة |
| AI أو تنبؤ أو قرار آلي | غير مطلوب لإثبات القيمة الأولى | لا يُضاف قبل دليل حاجة مستقل |

أكبر نقطة يجب أن يراها Agent هي أن **الوثائق تصف النظام المستهدف، ومصفوفة التغطية تصف ما ينفذ الآن**. لا يجوز تحويل القدرة المستقبلية إلى حقل أو شاشة لمجرد أنها موجودة في الـBlueprint.

## 5. القواعد المالية التي يجب أن تبقى ثابتة

يجب أن يخرج Agent من القراءة الأولى بالقواعد التالية دون أي غموض:

1. القبض ليس الربح، والعربون كاش محصل وليس ربحًا نهائيًا تلقائيًا.
2. الدين مستحق وليس كاشًا محصلًا، والتسليم لا يسجل قبضًا تلقائيًا.
3. شراء المخزون ليس تكلفة بيع كاملة لحظة الشراء.
4. السحب الشخصي وحقن رأس المال والقرض ليست مبيعات أو مصاريف تشغيل.
5. التكلفة الناقصة لا تساوي صفرًا، وغياب وقت الحرفة يصنف النتيجة `incomplete`.
6. `safetyBufferMinor` حماية **لكل وحدة** تضاف إلى `unitCostMinor`، وليست تكلفة محاسبية كلية.
7. تعديل Snapshot بكمية مختلفة عن الطلب يفشل، وتغير السعر اللاحق لا يغير Snapshot التاريخي.
8. المصروف العام أو المشترك لا يحمل على طلب بصمت، ونقطة التعادل ليست نتيجة طلب.
9. لا تعرض النواة الحالية ربح المشروع الكامل منذ البداية؛ ذلك يحتاج Ledger عامًا وفترات وتكاليف ومصادر متعددة.
10. إعادة المحاولة لا تضاعف الأثر المالي الحساس، والتعارض لا يحل بآخر كتابة صامتة.

## 6. ما قد يلتبس في أول قراءة، وكيف عولج؟

| موضع الالتباس المحتمل | سبب الالتباس | المعالجة الموجودة أو المطلوبة |
|---|---|---|
| عنوان Blueprint يذكر SaaS بينما Prototype محلي | خلط هدف المنتج بمرحلة التنفيذ | حالة Blueprint، `AGENTS.md`، وبوابة Pre-build تفصل المراحل |
| العقود تحتوي `workspace_id` وحقولًا تجارية | العقد الكامل أوسع من Domain Core | ملاحظة صريحة في عقد Snapshot ومصفوفة التغطية |
| الاعتراف عند التسليم يبدو كربح مشروع | `CraftOrder` يحمل حقول نتيجة على مستوى الطلب | عقد P0 وعقد النتيجة يصفانها كـ«نتيجة طلب» لا Ledger عامًا |
| تقارير البحث القديمة تستعمل Training أو توصي ببنية سابقة | المصدر التاريخي أطول أو أكثر تفصيلًا | وسم `HISTORICAL / SUPERSEDED` والمرجع الحالي في المكتبة canonical |
| وثائق التكلفة تذكر مصاريف عامة ونقطة تعادل | وصف الهدف قد يبدو كتنفيذ | عقد P0 يضعها مؤجلة ويمنع عرضها من Prototype |
| النسخ والـBackup | local export/import يختلط مع backup مركزي | بوابة Pre-build وAGENTS تفرّقان بينهما |
| `partial` موجود في أنواع أو عقود | حالة مستقبلية قد تبدو جاهزة | مصفوفة التغطية تقول إنها ليست مسارًا مستخدمًا في الحالة الحالية |
| «التوجيه» و«التعلم» | قد ينحرف المنتج إلى LMS | الوثائق الحالية تسميه توجيهًا سياقيًا؛ الملفات التاريخية موسومة ولا تحكم التنفيذ |

## 7. الحكم المهني للمراجعة المحاكية

### ما أصبح واضحًا بدرجة جيدة

الهوية والمستخدم والمشكلة والقيمة والـVertical Slice وحدود Prototype وMVP التجاري وقواعد المال الأساسية أصبحت مترابطة. وجود `AGENTS.md` مع فهرس وغطاء Pre-build وعقد P0 يقلل احتمال أن يبدأ Agent من ملف قديم أو يقفز مباشرة إلى SaaS أو UI.

كما أن الفجوة بين الهدف والكود لم تعد مخفية: الوثائق تقول بوضوح إن Domain Core والعقود مغلقة، بينما الواجهة والتخزين وLedger وSaaS لاحقة. هذا يجعل الانتقال التالي قابلًا للمراجعة بدل أن يكون وعدًا عامًا.

### ما يحتاج انتباهًا مستمرًا

لا يزال على Prototype أن يثبت أن صاحب مشروع حقيقي يستطيع إدخال هذه البيانات وفهم النتيجة والعودة إليها دون أن تصبح العملية أثقل من الدفتر أو الرسائل. المحاكاة المكتبية والاختبارات تثبت الاتساق الداخلي، لكنها لا تثبت سهولة الاستخدام أو العودة أو الاستعداد للدفع.

ولا تزال سياسات التسليم الجزئي والإرجاع والخصم والـactual cost وتوزيع المصاريف العامة وLedger الفترات ونقطة التعادل العامة غير منفذة، وهذا صحيح في هذه المرحلة وليس نقصًا يجب تغطيته بشاشات تخمينية.

## 8. ترتيب المرحلة التالية المقترح

1. تحويل عقد الشريحة إلى View Model وتجربة هاتف RTL محلية دون إدخال Auth أو SaaS.
2. بناء Adapter وLocalStore قابلين للاستبدال مع حفظ المسودات والتصدير المحلي عند تثبيت عقدهما.
3. تنفيذ تدفق واحد كامل: بدء طلب، إدخال التكلفة، رؤية حالة المعرفة وسعر الحماية، تثبيت الاتفاق والموعد، عربون، تنفيذ، تسليم، تحصيل أو دين، ثم نتيجة الطلب والفعل التالي.
4. تشغيل اختبارات Domain الحالية مع اختبارات Adapter وLocalStore، ثم اختبار مهام قابل للملاحظة مع أصحاب مشاريع حقيقيين.
5. تسجيل ما يفشل في الفهم أو الإدخال أو العودة قبل تقرير إضافة أي طبقة تجارية.

## 9. ما لا يجب بناؤه الآن

لا يجب أن يبدأ Agent ببناء Accounting جديد أو ERP أو POS أو CRM أو LMS، ولا أن يضيف شاشة نقطة تعادل أو ربح مشروع كامل دون Ledger، ولا أن يضيف مصاريف عامة موزعة بصمت، ولا أن يضيف Full Sync أو Auth أو Billing أو AI لأن الوثائق تذكرها كأهداف مستقبلية. ولا ينبغي توسيع الطعام والخدمات قبل إثبات مسار الحرفة أو بناء abstractions مبررة باختلاف حقيقي.

## 10. بروتوكول القراءة الفعلية المقترح لـCloud Code

عند طلب القراءة الفعلية، يجب توجيه Cloud Code بالنص التالي:

> اقرأ المستودع من `AGENTS.md` ثم `README.md` و`docs/00-document-index.md`، وبعدها اتبع ترتيب القراءة المذكور دون القفز إلى التنفيذ. راجع الوثائق canonical والعقود ومصفوفة تغطية Domain Core، ثم قارن كل ادعاء تنفيذي بملفات `src/` و`tests/`. لا تعتبر وصف MVP التجاري أو أي هدف مستقبلي كودًا منفذًا، ولا تستخدم الملفات الموسومة `HISTORICAL / SUPERSEDED` كمرجع حالي. سلّم تقريرًا يجيب بدقة: ما هو Micro؟ لمن؟ ما المشكلة والقيمة؟ ما أول Vertical Slice؟ ما المنفذ فعليًا؟ ما غير المنفذ؟ ما القواعد المالية غير القابلة للكسر؟ ما المرحلة التالية؟ وما الذي لا يجب بناؤه؟ اذكر كل تعارض أو نقص مع مساره، ولا تعدّل الملفات قبل عرض خطة التعديل ومعايير القبول.

يجب أن يرفق Cloud Code مع رأيه قائمة الملفات التي قرأها ونتائج `typecheck` و`test`، وأن يميز بين ملاحظات الوثائق وملاحظات الكود ومقترحات التنفيذ. هذه الخطوة لم تُنفذ بعد؛ التقرير الحالي يحضّرها ولا يستبدلها.

## 11. معيار نجاح القراءة الأولى

تُعد القراءة الأولى ناجحة إذا استطاع Agent الإجابة عن الأسئلة التسعة التالية دون خلط:

| السؤال | الإجابة التي يجب أن يصل إليها |
|---|---|
| ما Micro؟ | نظام إدارة مالية وتشغيلية كامل في الهدف، بتجربة بسيطة ونواة مستقلة |
| لمن؟ | صاحب مشروع منزلي أو متناهٍ في الصغر يدير العمل بنفسه |
| لماذا؟ | لتحويل الأحداث المتفرقة إلى تكلفة ونتيجة وكاش والتزام وفعل تالٍ |
| ما أول Slice؟ | حرفة يدوية مخصصة |
| ما الموجود؟ | Domain Core محلي وCraftOrder وعقود واختبارات |
| ما غير الموجود؟ | UI وAdapter وLocalStore وLedger وAuth وRLS وWorkspace وSaaS |
| ما القواعد المالية؟ | الربح منفصل عن الكاش، والنقص لا يساوي صفرًا، وSnapshot تاريخي |
| ما التالي؟ | Prototype هاتف RTL محلي ثم اختبار حقيقي |
| ما الممنوع؟ | القفز إلى ERP أو SaaS أو LMS أو تقارير عامة قبل الدليل والعقد |

## 12. الخلاصة

من منظور Agent يفتح المستودع للمرة الأولى، أصبح Micro مفهومًا وقابلًا للعمل بشرط أن يبدأ من `AGENTS.md` والفهرس ومصفوفة التغطية، لا من أي تقرير تاريخي أو من هدف MVP التجاري. نقطة القوة الحالية هي الصراحة بين **الرؤية الكاملة** و**النواة المنفذة**. نقطة الخطر المتبقية هي أن يبدأ منفذ متحمس ببناء طبقات مستقبلية قبل اختبار Prototype المحلي مع مستخدمين حقيقيين.

الحكم النهائي لهذه المحاكاة: **الوثائق جاهزة بدرجة جيدة للقراءة الأولى، والكود جاهز لبدء Prototype فقط بعد اجتياز فحص CI ومراجعة مالك المنتج؛ أما Cloud Code الحقيقي فما زال يحتاج أن يقرأ ويعطي حكمه المستقل.**
