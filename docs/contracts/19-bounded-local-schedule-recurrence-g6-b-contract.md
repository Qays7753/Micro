# عقد G6-B — تكرار محلي محدود للمواعيد التشغيلية

**الحالة:** DRAFT / G6-B — حزمة متسلسلة مع G7-A، تحتاج مراجعة PR قبل الدمج.

**النطاق:** إنشاء عدد محدود وصريح من الظهورات المستقبلية لموعد تسليم قائم، بتكرار أسبوعي أو شهري محلي، مع سجل قالب مستقل وإلغاء مستقبلي مسبب.

## 1. سؤال القرار

> **لدي موعد تشغيلي يتكرر بنمط واضح؛ ما المواعيد المقبلة التي قررت أن أنشئها من هذا النمط، وما الذي يحتاج تعديلًا أو تأجيلًا؟**

التكرار هنا أداة تقليل إعادة الإدخال. لا يعني أن الوقت متاح، أو أن العميل حجز، أو أن الموارد تكفي، أو أن Micro سيرسل تذكيرًا.

## 2. مصدر الحقيقة ومسار الحفظ

يمر الفعل عبر:

```text
React UI → ScheduleRecurrenceService → PrototypeLocalStore → IndexedDB
```

يبدأ القالب من `ScheduleEntry` موجود مرتبط بـ`StoredCraftOrder` موجود ونشط. القالب سجل محلي مستقل، وكل ظهور ناجح هو `ScheduleEntry` مستقل مرتبط بمعرف القالب ورقم ظهور. لا ينشئ القالب `CraftOrder` أو `Agreement` أو حدثًا ماليًا، ولا يعدّل الموعد الأصلي.

## 3. شكل القالب

| الحقل | القاعدة |
|---|---|
| المصدر | `sourceScheduleId` لموعد تسليم قائم، و`orderId` للطلب نفسه |
| التكرار | `weekly` أو `monthly` فقط؛ لا يومي ولا RRULE عام |
| العدد | `occurrenceCount` من 1 إلى 12، وهو عدد الظهورات المستقبلية الصريح |
| البداية | التاريخ اللاحق للمصدر: أسبوعًا واحدًا أو شهرًا واحدًا بحسب النمط |
| الحالة | `active` أو `cancelled` |
| الهوية | `idempotencyKey` يميز المصدر والنمط والعدد؛ إعادة التنفيذ لا تكرر القالب أو ظهوره |
| الإلغاء | وقت محلي/UTC للحفظ وسبب غير فارغ؛ يوقف المستقبل فقط |

في التكرار الشهري يحافظ النظام على يوم الشهر، ويقصه إلى آخر يوم في الشهر الهدف عند عدم وجود اليوم نفسه. يظل التفسير محليًا وفق `Asia/Amman` والتاريخ `YYYY-MM`/`YYYY-MM-DD`.

## 4. الظهور الفعلي

كل ظهور يحمل `recurrenceId` و`recurrenceIndex` ويحتفظ بوقت ومدة المصدر كما هما. إذا كان وقت/مدة المصدر غير معروفين، يبقى الظهور «وقت غير محدد» ولا يتحول إلى صفر دقيقة أو قدرة متاحة. الظهور مستقل بعد إنشائه؛ تعديل الموعد الأصلي لا يعيد كتابة الظهورات السابقة أو المستقبلية بصمت.

## 5. التخطي والتحذير

لا يكتب التطبيق بصمت عند تاريخ مصدر ماضٍ، أو مصدر غير موجود، أو طلب غير نشط، أو ظهور موجود. تعيد Application نتيجة صريحة تتضمن المصدر والسبب والظهورات المتجاوزة. التاريخ الموجود يُتخطى بدل إنشاء نسخة ثانية؛ التعارض وتجاوز السعة تحذير مشتق من ScheduleService ولا يمنع الحفظ.

إذا كان المصدر ماضيًا أو الطلب مغلقًا، تفشل العملية بـ`validation_error` ولا ينشأ قالب. إذا تعارض ظهور جديد مع سجل موجود، يبقى السجل الموجود كما هو وتظهر نتيجة `skipped`.

## 6. الإلغاء وإعادة التنفيذ

إلغاء القالب يحتاج سببًا غير فارغ، ويغير حالة القالب إلى `cancelled` فقط. لا يحذف أي ظهور أنشئ سابقًا، ولا يغير `ScheduleEntry` أو الطلب أو المال. لا ينشئ القالب ظهورات جديدة بعد الإلغاء. إعادة تنفيذ نفس القالب idempotent وتعيد نفس السجل دون كتابة نسخة ثانية.

## 7. ما لا يغطيه العقد

لا يغطي العقد التكرار اليومي، النوافذ الزمنية، الاستثناءات أو الاستئنافات المتقدمة، الموارد أو الموظفين، قدرة المواد، الحجز الذاتي، الإشعارات أو Push أو cron أو Background Worker، Service Worker جديدًا، Google Calendar أو iCal، أو أي تكامل خارجي.

لا يغير العقد السعر أو `CostSnapshot` أو الكاش أو الذمم أو G5 أو حالة الطلب المالية. لا يدعي التوافر أو القبول الآلي.

## 8. التخزين والاستيراد

يرفع التنفيذ `schemaVersion` و`localExportVersion` مع migration صريحة. تستعيد عملية export/import القوالب والظهورات وسبب الإلغاء، وتضيف الحقول الاختيارية للموعد القديم بقيم `null` دون تغيير معناه. يرفض الاستيراد السجل غير المترابط أو الظهور ذي القالب غير الموجود قبل لمس الحالة الحالية.

## 9. معايير القبول

يجب أن تثبت الاختبارات أن التكرار الأسبوعي بثلاثة ظهورات ينشئ ثلاثة مواعيد مستقلة فقط، وأن إعادة التنفيذ لا تكررها، وأن التكرار الشهري بوقت مجهول يحافظ على المجهول، وأن التعارض/السعة تحذير لا يمنع الحفظ، وأن الإلغاء المسبب يوقف المستقبل ولا يحذف السابق، وأن export/import يحافظ على القالب والظهورات والإلغاء، وأن الواجهة تعمل RTL وLight/Dark على 360 و390 و430 دون حجب BottomNav أفعال الحفظ أو الإلغاء.
