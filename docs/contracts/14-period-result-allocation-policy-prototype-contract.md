# Micro — عقد سياسة نتيجة الفترة الأوسع والمصاريف المشتركة G3

**الحالة:** `CURRENT / G3 IMPLEMENTED CONTRACT — EXTENDED SHARE INPUTS`
**المالك:** Manus Agent 1
**تاريخ القرار:** 23 أغسطس 2026

## 1. بطاقة القرار وسؤال النطاق

| العنصر | قرار G3 |
|---|---|
| المستخدم | صاحب مشروع صغير يراجع نتيجة فترة بعد التسليم وتسجيل المصروفات. |
| الموقف | يريد معرفة ما نتج فعليًا من أعمال مكتملة، وما دخل من تكلفة مباشرة أو مصروف مشروع أو حصة مشتركة. |
| الضرر | خلط العربون أو القبض أو شراء المخزون أو إجمالي فاتورة البيت بالربح، أو تحويل المجهول إلى صفر. |
| سؤال القرار | **«ما صافي ربحي التشغيلي المسجل لهذه الفترة، وما الذي دخل فيه من COGS أو مصروف مشترك، وما الذي ما زال تقديريًا أو ناقصًا أو غير محمل؟»** |
| أقل إدخال | تاريخ الواقعة، مبلغ أو إجمالي مصدر المصروف، العلاقة بالمشروع، وأساس الحصة عند وجود مصروف مشترك؛ وتكون النسبة اختيارية لا إلزامية. |
| المعنى المالي | القراءة المشتقة هي إيراد الأعمال المكتملة ناقص التكلفة المباشرة المستخدمة وفق سياسة المصدر، وناقص مصروف المشروع والحصص المشتركة المحملة صراحةً للفترة. وعند وجود استهلاك مثبت لعمل مكتمل يستبدل ذلك الاستهلاك جزء المواد من Snapshot مرة واحدة، وتبقى عناصر Snapshot الأخرى مرة واحدة. |
| حالة المعرفة | `recorded_only` عندما تكون الفترة صالحة ولا توجد أسباب مراجعة في بنود النتيجة، و`incomplete` عندما توجد بيانات مستبعدة أو تقديرية أو غير محملة أو سياق قديم؛ في الحالتين يبقى الرقم التشغيلي المسجل ظاهرًا. `invalid` وحدها تجعل الرقم `null`. |
| السيناريوهات المتأثرة | العربون قبل التسليم، التسليم قبل التحصيل، شراء/استهلاك/هدر المادة، المصروف المباشر والمشترك، السداد، العكس، وتصدير/استيراد السجل. |
| ما لا يتغير | لا يصبح القبض إيرادًا، ولا الشراء COGS، ولا توزع الحصة على طلب أو منتج، ولا يعاد كتابة Snapshot أو تاريخ مالي، ولا يبدأ O1 أو Profile قطاعي. |

يعالج هذا العقد سؤال صاحب المشروع: **«ما النتيجة التي سجّلتها لهذه الفترة بعد أن أدخلت المصروفات التي تخص المشروع، وما الذي يمنع اعتبارها مكتملة؟»**

لا يحوّل Micro إلى دفتر أستاذ قانوني، ولا يعرض «صافي ربح نهائي»، ولا يعيد تسعير طلبات قديمة، ولا يوزع مبلغًا مشتركًا على طلب أو منتج لمجرد وجوده. يوسّع فقط قراءة نتيجة الفترة الحالية لتكشف بوضوح كيف دخل المصروف التشغيلي إلى الفترة، وما إذا كانت حصة مشروع مشتركة مسجلة، وما الذي ما زال غير معروف.

> **قرار حاكم:** في هذه المجموعة، «تحميل المصروف المشترك» يعني إدخال **حصة المشروع المسجلة** إلى نتيجة الفترة مرة واحدة. لا يعني توزيعها على طلب أو منتج أو وحدة أو ساعة.

## 2. ما يدخل وما لا يدخل

| البند | يدخل في نتيجة الفترة الأوسع | لا يحدث في هذه المجموعة |
|---|---|---|
| طلب مسلّم بنتيجة `final` | إيراده وتكلفته المباشرة المستخدمة: استهلاك مثبت مرتبط به لمكوّن المواد، مع عناصر Snapshot غير المادية مرة واحدة؛ أو Snapshot كامل عند غياب الاستهلاك | لا تتحول حركة مادة غير صالحة أو عامة أو غير مرتبطة إلى COGS، ولا تتكرر Snapshot وCOGS لنفس مكوّن المواد |
| مصروف `relationship: project` | يدخل مرة واحدة حسب `occurredOn` | لا يُحمّل على اسم عمل أو طلب من دون عقد لاحق |
| مصروف `relationship: shared` | يدخل فقط بالمبلغ المسجل باعتباره حصة المشروع | لا يدخل إجمالي فاتورة البيت، ولا تنشأ نسبة مخفية |
| مصروف مستحق ثم تسديده | يدخل عند الاستحقاق مرة واحدة | لا يضيف التسديد مصروفًا ثانيًا |
| حدث قديم بلا سياق | لا يحذف ولا يفسر تلقائيًا؛ يبقى مبلغًا مسجلًا وحدًا معرفيًا | لا يعامل كصفر أو «للمشروع» افتراضيًا |
| رأس المال والسحب والتحويل والافتتاح | لا تدخل النتيجة | لا يعاد تصنيفها مصروفًا أو مبيعات |

## 3. سياسة الحصة المشتركة

### 3.1 نقطة الإدخال

يبقى `FinancialEvent.amountMinor` في المصروف المشترك **المحمل** هو حصة المشروع فقط. إذا كانت فاتورة البيت 50.00 د.أ وحصة المشروع التي عرفها المستخدم 15.00 د.أ، تسجل الواقعة التشغيلية هنا بـ15.00 د.أ فقط. وعند إدخال نسبة، يحفظ النظام إجمالي المصدر والنسبة الصريحة والحصة المحسوبة؛ لا تنشأ نسبة مخفية. إذا لم يعرف المستخدم الحصة، يمكن حفظ إجمالي المصدر بوصفه غير محمل، ولا يضاف إلى نتيجة الفترة ولا يتحول إلى صفر.

هذه قاعدة متعمدة لمنع خلط مصروف البيت بمصروف المشروع. المصروف المدفوع غير المحمل يمكن أن يظهر كخروج كاش موثق، لكنه لا يصبح مصروف مشروع في نتيجة الفترة قبل تحديد الحصة.

### 3.2 مصدر الحصة ودرجة المعرفة

يعتمد تنفيذ G3 على امتداد اختياري متوافق مع السجل القديم داخل `OperatingExpenseContext` للمصروف المشترك فقط. يقبل الامتداد مبلغ حصة ثابتًا، أو إجماليًا ونسبة، أو إجمالي مصدر مؤجلًا:

```ts
type SharedProjectShareBasis =
  | "agreed_fixed_share"
  | "agreed_percentage"
  | "owner_estimate"
  | "needs_review";

type SharedProjectShare = {
  basis: SharedProjectShareBasis;
  note: string | null;
  allocation: "allocated" | "unallocated";
  totalAmountMinor: number | null;
  percentageBps: number | null;
  calculatedShareMinor: number | null;
};
```

لا يدخل هذا الامتداد في أحداث `relationship: project`. وجوده يوضح **كيف عرف المستخدم أن هذا المبلغ هو حصة المشروع**، ويحفظ مدخلات النسبة ونتيجتها، لكنه لا يوزع المبلغ على طلب أو منتج.

| المسار | المعرفة المسموحة | معنى النتيجة |
|---|---|---|
| مبلغ حصة ثابت معلن | `known` | تدخل الحصة المسجلة مرة واحدة. |
| إجمالي + نسبة معلنة | `known` | تحسب الحصة في JOD minor units بسياسة ثابتة، وتحفظ المدخلات والنتيجة. |
| إجمالي + نسبة مقدرة من المالك | `estimated` | تدخل الحصة مرة واحدة، لكن سطح النتيجة `incomplete` ويذكر أنها تقديرية. |
| إجمالي بلا حصة محددة | `needs_review` | يحفظ الإجمالي بوصفه غير محمل، ولا يدخل النتيجة ولا يصبح صفرًا. |

تقبل الأحداث القديمة والمصروفات المشتركة التي لا تحمل هذا الامتداد، لكن القراءة تعرضها **«حصة مشتركة بلا مصدر موثق»** وتصبح النتيجة `incomplete`. لا تهاجر البيانات القديمة إلى قيمة مفترضة.

### 3.3 حد التوزيع

`purpose: order` أو `product` يصف ما قصده المستخدم عند تسجيل المصروف فقط. لا يجوز له في هذه المجموعة أن يغيّر `recognizedCostMinor`، أو `CostSnapshot`، أو هامش اسم العمل، أو فرق مادة الطلب، أو مؤشر التغطية. التوزيع على منتج/خدمة، إن ثبتت الحاجة إليه، يأتي بعد الكتالوج في المجموعة الرابعة بعقد مستقل ومصدر أساس قابل للمراجعة.

### 3.4 سياسة التقريب للنسبة

النسبة تحفظ بوحدة basis points صحيحة (`percentageBps` من 1 إلى 10,000، حيث 10,000 = 100%). تحسب الحصة في JOD minor units بالتقريب النصف إلى الأعلى:

```text
calculatedShareMinor = floor((totalAmountMinor × percentageBps + 5,000) / 10,000)
```

يحفظ النظام الإجمالي والنسبة والحصة المحسوبة كما دخلت في الحدث. إذا خرجت الحصة صفرًا من نسبة موجبة صغيرة، يرفض الإدخال ويطلب تصحيحًا أو اختيار «غير محمل» بدل إنشاء أثر مالي صفري.

## 4. سياسة COGS الاختيارية من الاستهلاك المثبت

لا تفرض G3 تسجيل الاستهلاك على كل مشروع، لكنها تستفيد منه عندما يكون موجودًا ومكتمل الدليل. مصدر COGS المقبول هو حركة `consumption` ذات `orderId` غير فارغ، وقيمة تكلفة سالبة صحيحة محفوظة في `valueDeltaMinor`، وكمية سالبة صحيحة، وغير مرتبطة بعكس فعال. لا يكفي وجود الكمية وحدها، ولا سعر المادة الحالي، ولا متوسط مخترع.

بالنسبة إلى كل طلب مسلّم بنتيجة `final` داخل الفترة، تطبق القراءة سياسة مصدر واحدة: إذا وجدت حركات استهلاك مؤهلة مرتبطة بالطلب، تستبدل قيمتها المطلقة مجموع `materialCostMinor` في Snapshot لذلك الطلب، وتبقي `timeCostMinor` و`packagingMinor` و`deliveryMinor` و`wasteMinor` من Snapshot مرة واحدة. إذا لم توجد حركة استهلاك مؤهلة، تستخدم القراءة تكلفة Snapshot المباشرة كاملة لذلك الطلب، وتعرض COGS بأنها غير متاحة لذلك الطلب؛ لا تملأها بصفر ولا تمنع الرقم التشغيلي المسجل لأن COGS اختيارية.

تستبعد من COGS حركات الافتتاح، واستلام الشراء، والهدر، والضبط، والاستهلاك بلا طلب صالح، والاستهلاك المرتبط بطلب غير مكتمل أو خارج مجموعة الأعمال المكتملة. يبقى الهدر والاستهلاك العام ظاهرين كحركات مخزون عامة/غير محملة حسب الدليل، ولا ينسبان إلى طلب أو منتج تلقائيًا. عند عكس استهلاك، يستبعد المصدر المعكوس والعكس نفسه لا يكرر قيمة COGS؛ يبقى الأصل والعكس وسببهما محفوظين.

| الحقل | المعنى |
|---|---|
| `recordedCogsMinor` | مجموع تكلفة الاستهلاك المؤهل من الحركات غير المعكوسة المرتبطة بأعمال `final` المكتملة |
| `snapshotDirectCostMinor` | مجموع التكلفة المباشرة المعترف بها من Snapshot قبل استبدال مكوّن المواد حيث يوجد COGS مؤهل |
| `effectiveDirectCostMinor` | التكلفة المباشرة التي تدخل معادلة النتيجة بعد تطبيق سياسة المصدر مرة واحدة لكل طلب |
| `cogsStatus` | `recorded` إذا توفر COGS لكل الأعمال النهائية، `partial` إذا توفر لبعضها، و`not_available` إذا لم يتوفر لأي عمل نهائي |
| `cogsMissingOrderCount` | عدد الأعمال النهائية التي رجعت إلى Snapshot لغياب استهلاك مؤهل |
| `unallocatedInventoryCostMinor` | قيمة حركات الاستهلاك العامة/غير المرتبطة، إن وجدت؛ لا تدخل النتيجة ولا توزع تلقائيًا |
| `generalInventoryWasteMinor` | قيمة الهدر العام، إن وجد؛ لا يسمى COGS ولا يحمّل على عمل تلقائيًا |
| `cogsReasons` و`cogsNextAction` | سبب النقص أو الاستبعاد وفعل المراجعة التالي، من دون تحويل الغياب إلى صفر |

## 5. نموذج قراءة نتيجة الفترة الأوسع

تظل النتيجة مشتقة لحظة القراءة من الطلبات والأحداث المحفوظة، ولا تحفظ كحدث مالي جديد:

```text
إيراد طلبات مسلّمة final
- التكلفة المباشرة المستخدمة وفق Snapshot/COGS الاختيارية
- مصروف مشروع مباشر مسجل
- مصروف عام/فترة مسجل
- حصة مشروع من مصروف مشترك مسجلة
= نتيجة الفترة الأوسع المسجلة
```

يعرض سطح G3-B التفصيل التالي بجانب الناتج، بدل رقم مجمل مضلل:

| الحقل | التعريف |
|---|---|
| `projectExpenseMinor` | مصروفات `relationship: project` في الفترة |
| `sharedProjectExpenseMinor` | حصص المشروع المشتركة المسجلة في الفترة |
| `legacyUnclassifiedExpenseMinor` | مصروفات قديمة بلا سياق؛ تعرض منفصلة ولا يختفي أثرها |
| `sharedEstimatedCount` | عدد الحصص المشتركة التقديرية أو التي تحتاج مراجعة |
| `sharedUnallocatedExpenseMinor` | إجمالي مصادر مشتركة محفوظة ولم تحدد حصتها؛ لا تدخل النتيجة |
| `sharedUnallocatedExpenseCount` | عدد المصادر المشتركة غير المحملة |
| `legacyUnclassifiedExpenseCount` | عدد مصاريف الفترة بلا سياق |
| `recordedCogsMinor` و`effectiveDirectCostMinor` | COGS المؤهلة والتكلفة المباشرة المستخدمة في المعادلة، مع Snapshot كمصدر منفصل |
| `cogsStatus` و`cogsReasons` | حالة توفر COGS الاختيارية وسبب النقص أو الاستبعاد وفعل المراجعة |
| `unallocatedInventoryCostMinor` و`generalInventoryWasteMinor` | استهلاك/هدر عام ظاهر لا يوزع تلقائيًا ولا يدخل النتيجة |
| `status` | `recorded_only` أو `incomplete` أو `invalid`؛ الرقم التشغيلي يبقى ظاهرًا في كل فترة صالحة، ولا توجد حالة «نهائية» |
| `reasons` | أسباب معرفة قابلة للقراءة وفعل تالٍ محدد، منفصلة عن أسباب COGS الاختيارية |

لأن المصروف القديم حقيقي ومسجل لكن سياقه مجهول، يبقى ضمن مجموع المصروف التشغيلي المسجل حفاظًا على استمرارية السجل؛ إلا أن التفصيل و`status: incomplete` يمنعان اعتباره مكافئًا لمصروف مصنف ومعروف. وبالمثل، لا يخفي نقص COGS الاختيارية الرقم التشغيلي إذا كانت تكلفة Snapshot المسجلة هي المصدر البديل المعلن؛ يظهر الرقم ونطاقه وحالة COGS وفعل المراجعة.

## 5. الاختيارية وعدم كسر النظام

المشروع الذي لا يملك مصروفًا مشتركًا لا يرى إعدادًا إلزاميًا جديدًا؛ يستمر بمصاريف `project` كما هي. المشروع الذي لا يعرف الحصة لا يُمنع من استخدام الكاش أو الطلب أو المورد أو المخزون، لكن Surface النتيجة يذكر بدقة أن الصورة ناقصة بالنسبة إلى السؤال المالي المتأثر. وضع أساس الحصة خيار يظهر فقط مع `relationship: shared` ولا يحوّل كل مستخدم إلى استبيان محاسبي.

## 6. التخزين والتاريخ

يحتاج G3-B إلى schema/export migration صريحة لأن سياق المصروف المخزن سيمتد بحقل اختياري جديد. يجب أن تبقى migration آمنة للأحداث القديمة: لا حذف، ولا تعديل مبلغ، ولا إنشاء أساس افتراضي. وتبقى واجهة React بعيدة عن IndexedDB؛ يمر الإدخال والقراءة عبر `ProjectFinancialService` و`PrototypeLocalStore`.

## 7. سيناريوهات القبول

| الحالة | النتيجة المطلوبة |
|---|---|
| مصروف مشروع معروف 20.00 د.أ | يظهر ضمن `projectExpenseMinor` مرة واحدة، وتبقى النتيجة مسجلة إذا لم يوجد نقص آخر |
| حصة كهرباء متفق عليها 15.00 د.أ | تدخل مرة واحدة ضمن `sharedProjectExpenseMinor`، ويظهر أساسها الثابت، ولا تدخل هامش أي طلب |
| حصة إنترنت تقديرية 8.00 د.أ | تدخل مرة واحدة، لكن `status: incomplete` ويظهر أنها تقديرية |
| مصروف مستحق 12.00 د.أ ثم تسديده | يظهر المصروف 12.00 مرة واحدة في الفترة الصحيحة؛ التسديد يغير الكاش والذمة فقط |
| مصروف قديم بلا سياق 10.00 د.أ | لا يحذف ولا يصنف تلقائيًا؛ يظهر منفصلًا ويجعل النتيجة ناقصة |
| حصة مشتركة غير محددة وإجماليها 50.00 د.أ | تظهر كغير محملة بقيمة 50.00 د.أ، ولا تخصم من النتيجة أو تصبح صفرًا |
| حصة مشتركة بلا مصدر توثيق | تبقى ضمن الإجمالي، مع سبب «مصدر الحصة غير موثق»؛ لا تفترض `known` |
| تغيير سياق مصروف عبر تعديل تاريخي | غير مسموح؛ التصحيح يحتاج عكسًا/حدثًا موثقًا خارج هذه الشريحة |
| شراء أو استلام مادة | لا يصبح COGS؛ يبقى أثر مخزون/شراء منفصلًا |
| استهلاك مثبت الكلفة لطلب `final` | يدخل COGS مرة واحدة لمكوّن المواد، وتبقى عناصر Snapshot الأخرى مرة واحدة |
| استهلاك بلا قيمة أو بلا ارتباط، أو هدر عام | لا يدخل COGS ولا يتحول إلى صفر؛ يظهر سبب الاستبعاد وفعل المراجعة |
| عكس استهلاك | يستبعد الحركة الأصلية المعكوسة مرة واحدة ولا يكرر COGS؛ يبقى الأصل والعكس وسبب التصحيح |
| حصة تقديرية أو سياق قديم مع فترة صالحة | يظهر الرقم التشغيلي المسجل من البنود الداخلة، مع `status: incomplete` وسبب التقدير/القدم |
| مصدر مشترك غير محمل | يظهر الرقم من البنود المحملة، ويظهر مبلغ المصدر المستبعد بأنه لم يخصم بعد |
| فترة غير صالحة | `resultMinor: null` و`status: invalid` فقط |

## 8. خارج الشريحة

لا تشمل G3 ضرائب، إهلاك، قروض، أصول، مرتجعات، COGS كاملة خارج الاستهلاك المثبت المرتبط بعمل مكتمل، تحميلًا حسب وحدات أو ساعات أو إيراد، توزيعًا على منتج/طلب، تغيير Snapshot، أو صافي ربح قانوني. تبقى COGS اختيارية؛ غياب دليل تكلفة لا يُملأ بصفر، وتستخدم القراءة Snapshot كبديل معلن عند غياب استهلاك مؤهل مع إظهار `cogsStatus` وسبب المراجعة. لا يدعي الرقم التشغيلي المسجل أنه نهائي أو ضريبي. يبقى مؤشر التغطية الحالي محافظًا، ويعاد تقييمه في المجموعة الخامسة مع سياسة هامش مساهمة مستقلة.
