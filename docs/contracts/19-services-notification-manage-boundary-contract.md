# Micro — عقد Attention والإشعار وحدود Manage N-03/N-04

**الحالة:** `CURRENT / EXPANSION E-00 / CONTRACT ONLY`
**المالك:** Manus Agent 1
**تاريخ القرار:** 28 أغسطس 2026

## Major Discussion Points

## 1. سؤال القرار والنطاق

يعالج هذا العقد سؤالين مرتبطين: **«كيف يرى Owner Attention داخل مصدرها في Market أو Delivery؟» و«كيف يعرف بوجود تغير خارجي من دون أن يصبح هذا التغير قيدًا ماليًا أو مخزنيًا داخل Manage؟»**

لا توجد وجهة مركزية اسمها `الخدمات`. Attention داخل Market أو Delivery تشير إلى سجل مصدر محفوظ وفعل تالٍ واحد، وليست Marketplace أو قائمة منتجات أو Review ثانية أو Dashboard مالية. لا يحول Badge أو Notification أي تغيير خارجي إلى حقيقة مشروع.

## 2. عناصر صندوق الخدمات

| الكيان | غرضه | أقل معلومات | لا يحتوي أو يعني |
|---|---|---|---|
| `network_attention` | عنصر قرار مرئي داخل صفحة المصدر: Market أو Delivery. | المصدر، المرجع، الحالة، آخر تحديث، الفعل التالي، ومستوى إلحاح مبرر. | مبلغ مالي أو تقييم عام أو سجل كامل أو حقيقة شراء/توصيل. |
| `network_notification` | سجل دائم داخل التطبيق لتغير موجّه. | المستلم، النوع، المرجع، الوقت، حالة القراءة. | Push مضمون أو دليل أن المستخدم قرأ أو قبل الواقعة. |
| `external_reference` | رابط اختياري بين سجل شبكة وسياق Manage اختاره Owner. | نوع مصدر ومحرف مرجعي وOwner intent. | صلاحية للطرف الخارجي أو نسخ تفاصيل Manage أو مزامنة تلقائية. |
| `recording_suggestion` | تذكير بأن واقعة خارجية قد تحتاج تسجيلًا محليًا. | نوع اقتراح ومحرف خارجي وشرح الحد. | إنشاء Event أو تعبئة مبلغ/تاريخ/حساب أو تغيير Snapshot تلقائيًا. |

## 3. قواعد العرض والترتيب

تظهر Attention Market في `احتياجاتي`، وتظهر Attention Delivery في `تحتاج إجراء` أو تفاصيل الحركة. كل مصدر يرتب عناصره: **قرار Owner الصريح أولًا، ثم موعد أو انتهاء صلاحية قريب، ثم الأحدث**. عناصر `information` لا تزاحم قرارًا أو موعدًا، ولا يظهر Badge بعدد عناصر معلوماتية فقط أو في قسم غير مصدرها.

| الحالة | النص والفعل المقبولان | ما لا يظهر |
|---|---|---|
| لا توجد Attention في Market | `استكشف` يعرض البحث أو بدء Need، و`احتياجاتي` تشرح أنها لا تضم ردودًا تحتاج قرارًا. | أرقام نشاط مصطنعة أو ادعاء شبكة حية أو انتقال إلى Delivery. |
| وصل رد مورد | مصدر الرد، العنصر، آخر تحديث، وفعل «راجع الرد». | عبارة «تم الشراء» أو تكلفة أو أثر مخزون. |
| عرض Courier ينتظر Owner | الموعد/النطاق المعلن وفعل «راجع العرض». | «تم الحجز» قبل تأكيد Owner أو مصروف نقل. |
| Courier سجل استثناء | سبب مختصر وفعل «راجع المهمة». | «تم التسليم» أو لوم طرف بلا دليل. |
| Supplier Listing يحتاج تعديلًا | سبب Moderation وفعل «عدّل العرض». | كشف اسم المبلغ أو قرار Admin غير متعلق بالعرض. |

## 4. الإشعار طريق وصول لا مصدر حقيقة

كل إشعار يقود إلى صفحة تفصيل لها حالة محفوظة داخل مصدرها. إذا فشل Push أو كان التطبيق غير مفتوح، تبقى Attention في Market أو Delivery بحسب المصدر. لا ينفذ فتح الإشعار أي انتقال حالة أو قراءة إجبارية أو تسجيل مالية. تكون حالة القراءة شخصية للمستلم ولا تغير أهمية الواقعة أو تاريخها.

في تجربة البيت، الإشعار محلي ومحاكى ومرتبط ببيانات الاختبار فقط. لا يدعي النظام أنه وصل إلى جهاز آخر أو أنه يعمل في الخلفية.

## 5. جسر الحقيقة إلى Manage

> **قرار حاكم:** Market وDelivery يصفان تفاعلًا أو نية أو ردًا أو حالة قالها طرف خارجي. Micro Manage وحده يسجل حقيقة المشروع المالية أو المخزنية، وفقط بعد مراجعة Owner وفعل حفظ صريح.

| واقعة شبكة | ما يظهر في مصدرها | ما يستطيع Owner فعله | ما لا يحدث تلقائيًا |
|---|---|---|---|
| وافق Owner على رد مورد | متابعة Market مكتملة أو تحتاج خطوة واقعية. | تسجيل ملاحظة، إغلاق التفاعل، أو «سجل ما حدث في مشروعي». | Purchase، تكلفة، دين، COGS أو مخزون. |
| قدم Courier عرضًا وقبله Owner | مهمة محجوزة بقرار Owner. | مراجعة الحالة أو إلغاء حسب العقد. | مصروف نقل أو حجز محاسبي أو تسليم طلب. |
| سجل Courier `arrived` أو `completed` | «تحديث من شركة التوصيل» بوقت وفاعل. | فتح المهمة ثم فتح مسار تسجيل واقع منفصل إن انطبق. | استلام مادة أو تسليم عميل أو قبض أو ربح. |
| رفض Admin Listing | تنبيه للمورد فقط. | تعديل وإعادة تقديم. | حذف صامت أو نشر بديل أو أثر على تعاملات سابقة. |

عند فتح `recording_suggestion` من Manage، لا يمرر الجسر إلا مرجعًا ومصدرًا اختاره Owner. يظل نوع الحدث والمبلغ والتاريخ ومحفظة الكاش ومواد المخزون حقولًا يراجعها Owner وفق عقود Manage الحالية. إن كان السياق الناقص قد يضلل، لا يفتح اقتراحًا ماليًا ويعرض رابطًا للمهمة فقط.

## 6. التكرار والتاريخ والفشل

ينشأ Attention أو Notification من حدث شبكة ذو محرف مستقر و`idempotency_key` عند وجود إعادة محاولة. تكرار التحديث لا ينشئ بطاقة مزدوجة أو Badge مضاعفًا. تغيير الحالة أو إغلاقها يحتفظ بتاريخ الفاعل والوقت والسبب عند الاستثناء؛ لا يعيد كتابة حدث Delivery أو قرار Market سابقًا.

عند عدم توفر الشبكة في المستقبل، تعرض Market أو Delivery حالة صادقة: محلي فقط، بانتظار إرسال، محدث، أو يحتاج مراجعة. لا يتحول الفشل إلى empty state ولا تخفي الواجهة العمل غير المتزامن.

## 7. ما لا يشمله العقد

لا ينشئ هذا العقد صفحة Home أو BottomNav أو API أو Push أو مزودًا خارجيًا. لا يقرر إذا كانت Market أو Delivery أول Beta، ولا يسمح بترقية الإشعار إلى رسائل دردشة أو تذكيرات أو SMS. Attention داخل المصدر ليست CRM ولا محرك Recommendation.

## 8. سيناريوهات القبول

| الحالة | النتيجة المطلوبة |
|---|---|
| Market أو Delivery بلا Attention | تفهم Owner الحالة الصادقة وتصل فقط إلى الفعل الذي يخص المصدر دون قراءة تعليمات طويلة. |
| رد Supplier مكرر بسبب إعادة محاولة | Attention واحد بحالة ووقت صحيحين، لا ردين ولا Badge مضاعف. |
| عرض Delivery ينتظر قرار Owner | يظهر «راجع العرض»؛ لا يظهر حجز أو مصروف. |
| تحديث `completed` | يظهر مصدر ووقت وحالة فقط؛ لا يتغير أمر محلي أو كاش أو مخزون. |
| Push لم يصل | تبقى Attention داخل مصدرها قابلة للوصول. |
| Owner يفتح تسجيل واقع | يرى مرجعًا اختياريًا ثم يتحكم في كل البيانات المالية قبل الحفظ. |
