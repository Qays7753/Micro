# Micro — عقد احتياج Market ورد المورد والعرض والمراجعة M-01/M-02

**الحالة:** `CURRENT / EXPANSION E-00 / CONTRACT ONLY`
**المالك:** Manus Agent 1
**تاريخ القرار:** 28 أغسطس 2026

## Major Discussion Points

## 1. سؤال القرار والنطاق

يعالج هذا العقد موقفين مختلفين لا يجوز دمجهما: **Owner يبحث عن مورد لمادة/خدمة، وSupplier يريد عرض Listing موثوقًا ومراجعًا**. النتيجة الأدنى هي تفاعل واضح يستطيع Owner مراجعته، لا عملية بيع أو فاتورة أو دفع داخل Micro.

تبدأ Beta بفئة واحدة ومنطقة واحدة وموردين معروفين أو مدعوين. لا يحول عقد Market المنصة إلى سوق عام لكل الأردن ولا يثبت سيولة العرض أو صلاحية السعر أو جودة المورد.

> **قرار حاكم:** `market_need` و`market_response` و`supplier_listing` سجلات متابعة شبكية. قبولها أو رفضها أو انتهاءها لا ينشئ Purchase أو التزامًا أو كاشًا أو COGS أو حركة مخزون أو نتيجة ربح.

## 1.1 صفحة السوق والاستكشاف

`السوق` وجهة Owner في BottomNav، وليست قائمة منتجات مستقلة. تتضمن `استكشف` و`احتياجاتي`. يسمح `استكشف` ببحث نصي وفلاتر فئة ومحافظة/نطاق تغطية مدعوم، وبنطاق سعر معلن عند وجوده. تعيد النتائج Listings معتمدة فقط؛ يفرق العرض بين `empty` و`no_results` و`error` و`loading`، ولا يدعي عرضًا خارج Wedge.

الفلاتر مدخلات اكتشاف لا سجل شبكة مستقل أو Profile أو دليل تغطية وطنية. لا يوجد Recommendation أو Ranking أو paid placement أو «الأفضل»، ولا يحتفظ Micro بسجل محادثة. يختار Owner عند التفاصيل إنشاء Need منظم أو فتح وسيلة اتصال خارجية معلنة؛ لا يفتح Chat داخل Micro.

## 2. أقل بيانات Market

| الكيان | منشئه | أقل إدخال لازم | حالات معرفة وحدود |
|---|---|---|---|
| `market_need` | Owner | وصف الحاجة، فئة/نوع، منطقة أو نطاق، وحدة/كمية اختيارية، نافذة زمنية اختيارية. | المسودة غير مرئية، والنشر لا يكشف مال Manage أو عميلًا أو Snapshot. |
| `market_response` | Supplier member مخول | مرجع الحاجة، ما يستطيع تقديمه، سعر/وحدة أو نطاق معلن إن اختار، زمن تجهيز، ملاحظة. | ليس عرضًا ملزمًا أو سعرًا نهائيًا أو إثبات توفر لحظي. |
| `supplier_listing` | Supplier member | اسم وصنف ووصف ووحدة/نطاق سعر اختياري ومنطقة/تغطية معلنة وطريقة تواصل يختارها ووسائط اختيارية. | ليس مخزونًا حيًا أو SKU أو عقد بيع أو تقييم سمعة أو ضمان تغطية. |
| `listing_media` | Supplier member ثم Admin | مرجع Listing والملف وحالة الفحص. | لا تصبح عامة قبل قرار Moderation، ولا تحتوي بيانات حساسة غير لازمة. |
| `market_decision` | Owner أو Admin حسب نوع القرار | المرجع والقرار والفاعل والوقت والسبب عند الرفض/السحب. | لا يمحو التاريخ ولا يغير واقعًا محليًا. |

## 3. حالات وTransitions

### 3.1 احتياج Owner

```text
draft
→ published
→ responses_received
→ owner_decision_recorded
→ closed

published → cancelled
responses_received → cancelled
published → window_ended          (النظام: انقضاء نافذة النشر)
responses_received → window_ended (النظام: انقضاء نافذة النشر)
window_ended → owner_decision_recorded | closed | published (إعادة نشر بنافذة جديدة)
```

يمكن أن يظل الاحتياج `published` مع ردود متعددة. لا يلغيه رد واحد، ولا ينتقل إلى «تم الشراء» أو «مكتمل» لمجرد أن Owner قبل ردًا. كل إغلاق يوضح هل السبب قرار خارجي أو لم يعد الاحتياج قائمًا أو انتهت نافذة النشر.

**انتهاء نافذة النشر (E-16) — لا احتياج منشور خالد:**

- **الانتقال `window_ended` («انتهت نافذة النشر»):** الفاعل النظام؛ يقيَّم زمنيًا عند فتح المصدر أو المزامنة (لا مؤقت خلفي في L، ومهمة مجدولة عند A) عند انقضاء النافذة المعلنة بتوقيت عمان. الاحتياج المنشور بلا نافذة معلنة يعامل بنافذة افتراضية 14 يومًا (قيمة افتراضية قابلة لتعديل المالك، لا قرار تجاريًا) كي لا يبقى منشورًا إلى ما لا نهاية.
- **أثر الانتقال:** لا تُقبل ردود جديدة بعد `window_ended` (يرد النظام برسالة صادقة «انتهت نافذة النشر لهذا الاحتياج»)؛ وتبقى الردود القائمة بيد Owner حتى يقرر.
- **مخارج `window_ended` — لكل حالة مخرجًا:** `owner_decision_recorded` (يقرر Owner على رد واصل قبل الانتهاء)، أو `closed` (بسبب مسجل، ومنه «انتهت نافذة النشر»)، أو `published` (إعادة نشر بنافذة جديدة؛ الردود السابقة تبقى تاريخية ولا تُنسخ).
- **الحالة الصادقة لانعدام الردود:** الاحتياج المنشور (أو المنتهي نافذته) الذي لم يصله أي رد يعرض دائمًا: **«لا ردود بعد — بيان، لا حكم»**. تحظر الواجهة تحويل هذا البيان إلى حكم: لا «لا يوجد موردون»، ولا «احتياجك غير جذاب»، ولا إخفاء الاحتياج وكأنه لم يكن. هذه هي إشارة «لا رد» التي تريد بطاقة السيولة E-00.13 قياسها، وتُعد حالة بلا تحويلها تقييم أشخاص.

### 3.2 رد المورد

```text
draft
→ submitted
→ owner_reviewed
→ accepted_for_external_follow_up | rejected | withdrawn | expired
```

`accepted_for_external_follow_up` تسمية مقصودة: تعني أن Owner يختار متابعة خارج Micro، لا أن المورد باع أو أن المال دُفع. المورد لا يغير قرار Owner، وOwner لا يغير محتوى رد مورد سابقًا؛ أي تعديل مهم ينشئ revision أو ردًا جديدًا مع تاريخ واضح.

**محفّز `expired` (E-16):** ينتقل الرد إلى `expired` بفعل النظام عندما يصل الاحتياج الأب إلى `closed` أو `cancelled` بينما الرد لا يزال `submitted` أو `owner_reviewed` ولم يُتخذ فيه قرار. القرارات المقررة سابقًا (قبول/رفض/سحب) لا تُغيّر بأثر رجعي. يُعرض الرد المنتهي بنص صادق: «انتهى الرد بانتهاء التفاعل — لا يعني رفضًا لمحتواه».

### 3.3 Listing والوسائط

```text
draft
→ submitted_for_review
→ approved_for_publish | changes_requested | rejected
approved_for_publish → paused | archived | update_required | expired
changes_requested → submitted_for_review
rejected → submitted_for_review          (إعادة تقديم بمراجعة جديدة؛ سبب الرفض السابق يبقى)
update_required → submitted_for_review   (بعد تعديل المورد)
paused → approved_for_publish            (بشرط ألا يكون المحتوى تغير منذ الاعتماد)
paused → submitted_for_review            (إذا تغير المحتوى، أو إذا كان الإيقاف قرار Admin فلا يرفعه إلا Admin بسبب)
expired → submitted_for_review           (تجديد/تحديث يعيد المراجعة)
```

لا ينشر Listing ولا صورة حتى `approved_for_publish`. قرار Admin يحمل سببًا قابلًا للقراءة للمورد. انتهاء صلاحية أو طلب تحديث يخفي العرض أو يوسمه بوضوح، ولا يثبت أن العرض ما زال متوفرًا.

**مخارج كل حالة (E-17) — لا حالة بلا مخرج:** `rejected` يعاد تقديمه كمراجعة جديدة (لا يبقى بابًا مغلقًا للأبد)؛ `paused` يُستأنف إلى `approved_for_publish` مباشرة فقط إذا لم يتغير المحتوى منذ الاعتماد، وإلا فإلى `submitted_for_review`؛ `update_required` يعود إلى `submitted_for_review` بعد تعديل المورد؛ و`expired` حالتها من يحددها النظام عند انقضاء نافذة تحديث معلنة (افتراضي 90 يومًا بلا تأكيد أو تحديث — قيمة قابلة للضبط) أو قرار Admin أو طلب المورد، وتخفي العرض من البحث بوسم صادق «انتهت صلاحية العرض — غير مؤكد توفره» لا بحذفه. أما `archived` فهي نهاية مقصودة بتاريخ وسبب (سجل محفوظ للعرض بلا ظهور عام)، لا حالة انتظار.

**آلة حالات `listing_media` (E-17):**

```text
uploaded_private
→ under_review
→ approved_public | changes_requested | rejected
approved_public → removed_from_public   (قرار Admin بسبب، وفق العقد 22 §2)
changes_requested → under_review        (إصلاح أو إعادة رفع للمرفق نفسه)
rejected → uploaded_private             (ملف بديل جديد؛ الملف القديم يبقى في التاريخ)
removed_from_public → under_review      (طلب إعادة مراجعة بعد معالجة السبب)
```

لا تُعرض وسيطة `approved_public` إلا وسيلة Listing الأم في `approved_for_publish`؛ إيقاف أو انتهاء الـListing يخفي وسائطه معه. لا ملف عام قبل قرار المراجعة، ولا حذف صامت (العقد 22 §2).

### 3.4 سياسة طابور المراجعة — متطلب مرحلة Pilot B (E-17)

الأداة مؤجلة (العقد 22 §1) لكن **السياسة لا تؤجل**: لا يجوز دخول Pilot B وطابور المراجعة بلا هدف زمني ولا تصعيد.

- **هدف زمن المراجعة:** كل تقديم Listing أو وسيطة يُراجع خلال 48 ساعة عمل (افتراضي بانتظار حسم المالك — EX-O15).
- **عتبة التصعيد:** أي تقديم أقدم من 7 أيام عمل، أو طابور يتجاوز 20 عنصرًا، يُرفع إلى المالك بمسؤول محدد وسبب الانتظار (افتراضي بانتظار EX-O15).
- **صدق العرض للمورد:** انتظار التقديم يعرض مدة الانتظار الفعلية وترتيبه التقريبي، لا «قيد المراجعة» أبدية.
- **التتبع:** يوثق Tracker B-07 الالتزام بهذه السياسة في Pilot؛ والقياس نفسه بلا بيانات حساسة إضافية.

## 4. رؤية المعلومات والخصوصية

| المرحلة | Owner يرى | Supplier يرى | Admin يرى |
|---|---|---|---|
| مسودة الحاجة | كل ما أدخله في جهازه/سياقه. | لا شيء. | لا شيء. |
| احتياج منشور | بيانات النشر التي وافق عليها. | ما تسمح سياسة الفئة/المنطقة بالرد عليه، لا مال Owner أو عميل أو بيانات خاصة. | ما يلزم للبلاغ/المراجعة فقط. |
| رد مورد | الرد وتاريخه والفعل التالي. | رده وسياق الحاجة المصرح به. | عند بلاغ أو سياسة فقط. |
| Listing قيد المراجعة | لا يعرض عامًّا. | عرضه وسبب المراجعة. | المحتوى والوسيط وسجل القرار. |
| Listing منشور | التفاصيل العامة المعتمدة فقط. | عرضه وإحصاءاته المسموح بها لاحقًا. | سجل المراجعة. |

التواصل الخارجي ليس Chat داخل Micro في Beta. يفصح Owner عن وسيلة تواصل أو يفتح رابطًا خارجيًا فقط عند قراره، ولا يسجل النظام محتوى اتصال أو يدعي إثبات اتفاق. يظهر رد المورد المنظم في `احتياجاتي` لا في inbox أو Dashboard خدمات عام.

## 5. Moderation والثقة والأخلاقيات

Admin لا يختار موردًا لOwner ولا يضمن السعر أو الجودة ولا يزيل عرضًا بلا أثر. تشمل أسباب المراجعة المسموح بها: محتوى ناقص، صورة غير مرتبطة أو مقلقة، وصف مضلل ظاهر، انتهاك خصوصية، أو مخالفة سياسة فئة. لا تُستخدم المراجعة لتفضيل مورد أو لإخفاء منافس لأسباب تجارية غير معلنة.

لا تقييمات نجوم أو شهادات أو توصيات عامة في E-00 أو Beta الأولى. أمان البداية يأتي من حالة عرض واضحة، تاريخ تحديث، سبب Moderation، ورد قابل للتتبع؛ لا من سمعة مصطنعة أو محتوى مستخدم مختلق.

## 6. التكرار، الإلغاء، والفشل

نشر الحاجة، إرسال الرد، رفع الوسيط، وقرار المراجعة عمليات حساسة تستخدم idempotency عند التنفيذ. فشل الرفع أو المراجعة يبقي Listing/Media في حالة صريحة قابلة للاستئناف؛ لا ينشر ملفًا جزئيًا ولا يحذف مسودة بلا سبب. لا يستطيع Admin أو Supplier تعديل Market Decision لOwner؛ التصحيح Revision أو Event جديد.

## 7. ما لا يشمله العقد

لا Cart أو Checkout أو Payment أو عمولة أو فاتورة أو حل نزاع مالي أو Chat أو AI Matching أو Ranking أو Ratings أو توصية سعر أو مخزون حي أو Auction. لا Driver ولا Delivery Task ضمن مسار Market؛ يجوز لOwner أن ينشئ نية Delivery مستقلة لاحقًا وفق عقد Delivery، لكنها لا تنشأ تلقائيًا من رد Market.

## 8. سيناريوهات القبول

| الحالة | النتيجة المطلوبة |
|---|---|
| Owner يفتح السوق للبحث عن مادة | يرى `استكشف` مع فلاتر ضمن التغطية المقررة، أو `no_results` صادقة؛ لا يرى موردين أو محافظات أو ترتيبًا مزعومًا. |
| Owner ينشر احتياج مادة | يراجع ما سينشر قبل النشر، ولا يخرج سعر بيع أو Snapshot أو عميل. |
| Supplier يرسل ردًا | يصل Owner رد له تاريخ وحالة وفعل مراجعة؛ لا تنشأ عملية شراء. |
| Owner يقبل ردًا | يسجل قرار متابعة خارجية فقط ويظهر اقتراح تسجيل واقع اختياري. |
| Listing بصور غير مراجع | لا يظهر عامًّا ولا في نتائج Owner. |
| Admin يطلب تعديلًا | Supplier يرى سببًا واضحًا، ويحتفظ النظام بالقرار والتاريخ. |
| رد مكرر أو إعادة نشر | لا ينشأ ردان/احتياجان بسبب إعادة المحاولة نفسها. |
| Owner يلغي الاحتياج | لا يمحو الردود التاريخية ولا ينشئ أثرًا ماليًا. |
| تنقضي نافذة نشر احتياج بلا ردود | الحالة `window_ended` مع النص «لا ردود بعد — بيان، لا حكم»؛ لا تفسير للسكوت ولا إخفاء للاحتياج. |
| يغلق Owner احتياجًا وفيه رد لم يقرر فيه | ينتقل الرد إلى `expired` بفعل النظام، ولا يُعدّل قرار سابق بأثر رجعي. |
| Listing مرفوض يعاد تقديمه | يدخل `submitted_for_review` من جديد وسبب الرفض السابق يبقى في السجل. |
| Listing منشور لم يُحدّث 90 يومًا | يدخل `expired` ويخفى من البحث بوسم صادق، لا بحذف؛ وتجديده يعيد المراجعة. |
| طابور المراجعة يتجاوز العتبة | يتصعد إلى المالك بمسؤول محدد؛ ويرى المورد مدة انتظاره الفعلية لا حالة أبدية. |
