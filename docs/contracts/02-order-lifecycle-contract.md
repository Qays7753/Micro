# عقد دورة الطلب

**الحالة:** CURRENT / يقرأ مع [`05-financial-p0-policies.md`](05-financial-p0-policies.md) قبل أي Use Case للطلب.
**الغرض:** جعل الطلب سجل اتفاق وتنفيذ مستقلًا عن الفاتورة والقبض.

## الحقول المطلوبة في الشريحة الأولى

على مستوى العقد الكامل، تشمل الحقول `order_id`، `workspace_id`، الزبون، مصدر الاتفاق، المطلوب، المواصفات، الكمية، السعر المتفق، `cost_snapshot_id`، موعد التسليم، الأولوية، العربون، المتبقي، الحالة، الفعل التالي، الملاحظة، `idempotency_key`، وسجل الأحداث. في Domain Core المحلي الحالي، `workspace_id` وموعد التسليم والأولوية ومصدر الاتفاق ليست مخزنة بعد؛ تبقى حدودًا مؤجلة لطبقة التخزين/الواجهة، ولا يجوز وصفها بأنها مطبقة.

المطبق في النواة الحالية هو هوية الطلب والزبون والمطلوب والمواصفات والكمية والسعر ونسخة التكلفة والعربون والمتبقي والحالة والفعل التالي وسجل الأحداث ومفاتيح منع التكرار. يمثل `CraftOrder` نتيجة الطلب على مستوى الشريحة، وليس Ledger عامًا أو سجل SaaS متعدد المساحات.

## الحالات

```text
مسودة → اتفاق مبدئي → مؤكد → قيد التنفيذ → جاهز → تم التسليم → تمت التسوية
```

المسارات الجانبية هي: `مؤجل`، `ملغى`، `معلق بسبب مادة أو قدرة`، و`يحتاج مراجعة`. حالة `معلق بسبب مادة أو قدرة` جزء من العقد الكامل لكنها مؤجلة في Domain Core المحلي؛ لا تُخلط مع `needs_review`. لا نستخدم «مكتمل» لتغطية التسليم والتحصيل معًا.

## الانتقالات المسموحة

| من | إلى | الشرط |
|---|---|---|
| مسودة | اتفاق مبدئي | وجود المطلوب والزبون أو ملاحظة اتفاق |
| اتفاق مبدئي | مؤكد | في العقد الكامل: وجود موعد أو قبول تأجيله وسعر متفق أو حالة سعر غير مكتملة معلنة؛ في Domain Core المحلي يتطلب إنشاء الطلب سعرًا متفقًا موجبًا، ولا يوجد مسار سعر غير مكتمل بعد |
| مؤكد | قيد التنفيذ | قرار بدء التنفيذ |
| قيد التنفيذ | جاهز | تسجيل أن العمل جاهز أو سبب التوقف |
| جاهز | تم التسليم | تسجيل التسليم أو سبب التسليم الجزئي |
| تم التسليم | تمت التسوية | المتبقي صفر أو تحويله إلى دين موثق |
| أي حالة قبل التسليم | مؤجل | سبب وموعد متابعة اختياري |
| أي حالة قبل التسليم | ملغى | عبر `cancelOrder` فقط، مع سبب ومعالجة العربون والمواد إن وجدت |
| أي حالة | يحتاج مراجعة | تعارض، تكرار، فشل مزامنة، أو نقص قرار مالي |

## قواعد لا يجوز كسرها

- تأكيد الطلب لا يقبض المال.
- تسجيل العربون لا يجعل الطلب مسوى.
- التسليم لا يسجل قبضًا تلقائيًا.
- تغيير المواصفات بعد الاتفاق ينشئ `revision` أو `order_event` ونسخة تكلفة جديدة إذا تغير الأثر.
- الإلغاء لا يحذف الطلب أو أحداثه؛ ينشئ تسوية أو عكسًا مع سبب عبر `cancelOrder`، ولا يوفّر `transitionOrder` إلغاءً عامًا يمكنه تجاوز هذه السياسة. إذا وُجد عربون، يحمل الطلب `depositSettlement: needs_review` إلى أن ينفذ المستخدم ردًا أو احتفاظًا صريحًا.
- لا يُسمح بالقبض العادي بعد الإلغاء؛ عمليات رد العربون أو الاحتفاظ به هي عمليات تسوية مستقلة ومحددة النوع والمبلغ والسبب والوقت ومفتاح منع التكرار.
- تغيير الموعد يسجل حدثًا ويعيد حساب تحذير القدرة.
- كل انتقال حساس قابل لإعادة المحاولة يحمل `idempotency_key` غير فارغ، ويُفحص ضمن نوع العملية حتى لا يمنع مفتاح عملية مختلفة بصمت.
- لا يمكن نقل الطلب من «تم التسليم» إلى «قيد التنفيذ» بصمت؛ في Domain Core الحالي يؤدي إدخال الطلب المسلّم إلى `needs_review` إلى تصفير مؤشر الربح وحجب النتيجة، ثم يمنع **كل عملية عامة تغيّر الحالة أو Snapshot أو أثرًا ماليًا** الخروج من المراجعة حتى يضاف Use Case تصحيح موثق. لا يوجد `correctDelivery` منفذ بعد.
- كل تغيير حالة مباشر في Domain Core، بما في ذلك الانتقال إلى `settled` عند قبض المتبقي أو تسجيل الدين، أو الانتقال إلى `needs_review` عند Revision، أو الإلغاء، يضيف حدث `status_changed` بوضوح `fromStatus` و`toStatus`. وإذا تم دفع السعر كاملًا قبل التسليم، يؤدي تسجيل التسليم إلى `settled` مع حدثين واضحين: التسليم ثم التسوية.
- `agreedPriceMinor` موجب إلزامي عند إنشاء `CraftOrder` المحلي. لا يجوز للواجهة تمثيل طلب بلا سعر على أنه طلب قابل للتأكيد قبل إضافة عقد صريح لحالة السعر الناقص.

## الفعل التالي

عند تسجيل التسليم، إذا كان `receivableMinor` يساوي صفرًا و`settlementStatus` يساوي `paid`، تنتقل الحالة إلى `settled` ولا يعرض النظام فعل تحصيل أو تسجيل دين؛ يكون الفعل التالي مراجعة النتيجة. أما إذا بقي متبقٍ موجب، فيبقى الفعل التالي تحصيل المتبقي أو تسجيل الدين.

لكل طلب غير مسوى فعل تالٍ واحد على الأقل، مثل: `سجل اتفاقًا`، `راجع التكلفة`، `اشترِ خامة`، `ابدأ التنفيذ`، `جهز للتسليم`، `حصّل المتبقي`، أو `سجل سبب التأجيل`. إذا لم يوجد فعل تالٍ، يعرض النظام سببًا واضحًا بدل ترك الطلب بلا متابعة.

## معايير قبول العقد

يُقبل العقد إذا أمكن إنشاء طلب، تسجيل عربون، بدء تنفيذ، تسليم، قبض أو دين، إلغاء، وتعديل مواصفات، مع بقاء سجل الأحداث والنتيجة المالية منفصلين. ويجب أن تفشل المحاولة التي تسجل قبضًا تلقائيًا عند التسليم أو تعيد فتح طلب مسلّم بلا تصحيح أو تحذف طلبًا ماليًا بلا أثر، وأن يحمل كل انتقال مباشر إلى التسوية حدث حالة مرافقًا.
