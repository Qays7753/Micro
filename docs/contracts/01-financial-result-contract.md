## المبادئ

القبض ليس الربح. الدين مستحق وليس كاشًا محصلًا. العربون يزيد الكاش لكنه ليس ربحًا نهائيًا تلقائيًا. إنشاء الطلب لا يغير الكاش ولا ينشئ ربحًا نهائيًا. التسليم حدث تشغيلي، ويحدد الاعتراف بالنتيجة وفق السياسة الموثقة، لكنه لا يسجل قبضًا تلقائيًا.

## الأحداث الأساسية

| الحدث | الكاش | الربح النهائي | الدين/العربون | قابل للعكس؟ |
|---|---:|---:|---|---|
| إنشاء طلب | لا تغيير | لا تغيير | لا تغيير | تعديل تشغيلي |
| اعتماد السعر | لا تغيير | لا تغيير | يثبت نسخة التكلفة | إنشاء snapshot جديد عند التعديل |
| قبض عربون | يزيد | لا يظهر كربح نهائي تلقائيًا | ينقص العربون المتبقي | تسوية أو رد موثق |
| تسليم كامل | لا تغيير تلقائيًا | قد ينشئ الاعتراف وفق سياسة الشريحة | إذا كان المتبقي موجبًا يصبح مستحقًا؛ وإذا كان السعر مدفوعًا كاملًا يصبح الطلب `settled` دون قبض جديد | إلغاء أو عكس موثق |
| قبض متبقي | يزيد | لا ينشئ الربح من جديد | ينقص المتبقي أو الدين | رد/عكس موثق |
| بيع بالدين | لا يزيد | قد ينشئ الاعتراف عند التسليم وفق السياسة | ينشئ مستحقًا | تسوية أو إلغاء موثق |

## سياسة الشريحة الأولى

في الشريحة الأولى نميز بين **نتيجة الطلب** و**الربح النهائي**. حالة التكلفة (`knowledgeState`) تصف جودة مدخلات التكلفة، أما `resultStatus` فتصف ما يجوز أن يفهمه المستخدم من نتيجة الطلب:

| `resultStatus` | المعنى |
|---|---|
| `final` | يمكن عرض النتيجة كنهائية لأن التكلفة المؤثرة `known` وفق سياسة الشريحة. |
| `estimated` | يمكن عرض مؤشر مشروط أو تقديري، ولا يسمى ربحًا نهائيًا. |
| `incomplete` | المعلومات غير كافية لإعطاء نتيجة ذات معنى؛ يجب إظهار النقص والفعل التالي. |
| `review_required` | يوجد قرار أو تعارض تجاري يحتاج مراجعة صريحة، مثل تسوية عربون الإلغاء أو تغيير المواصفات. |

حالات التكلفة الحالية هي:

- `known`: التكلفة المؤثرة معروفة ومحدثة.
- `estimated`: يوجد وقت أو هدر أو مصروف تقديري.
- `partial`: بعض التكلفة المؤثرة غير مدخلة؛ لا تسمى النتيجة ربحًا نهائيًا.
- `incomplete`: بند مؤثر مفقود، أو لا توجد مكونات مؤثرة في حرفة مخصصة؛ يظهر سبب النقص.
- `stale`: سعر مادة قديم وفق سياسة حداثة مطبقة في Domain Core الحالي؛ قدم الوقت يحتاج metadata مؤجلة.
- `variable`: التخصيص أو مصدر القيمة يجعل التكلفة متغيرة وتحتاج مراجعة.

في Domain Core الحالي، `resultStatus` إلزامي على مستوى الطلب. إذا كانت `knowledgeState === 'known'` عند التسليم أو التسوية، يكون `resultStatus: 'final'`. أما الحالات غير المعروفة فلا تجعل `profitIndicatorMinor` ربحًا نهائيًا؛ تكون النتيجة `estimated` أو `incomplete` بحسب كفاية البيانات، أو `review_required` عند وجود قرار لم يُحسم. لا يُعرض «ربح نهائي» إذا كانت حالة التكلفة `partial` أو `incomplete` أو `stale` أو `variable`. وفي مسار الحرفة، غياب `time` المؤثر أو إعلانه `known` بدقائق أو سعر ساعة صفري يصنف Snapshot كـ`incomplete` حتى لو كانت المواد معروفة، ولا يُعامل كوقت عمل مكتمل.

## قواعد الحساب

```text
material_cost = Σ(quantity × normalized_unit_price)
planned_cost = material_cost + estimated_time_cost + packaging + delivery + waste
unit_cost = planned_cost ÷ quantity
price_floor = unit_cost + required_buffer
profit_indicator = recognized_revenue - recognized_cost - applicable_expenses
```

تستخدم الأموال أصغر وحدة نقدية ثابتة أو `Decimal`، مع سياسة تقريب واحدة. لا تستخدم `float` للحسابات المالية. ويجب قراءة سياسة `safetyBufferMinor` بوصفها حماية لكل وحدة، لا تكلفة محاسبية كلية.

## معايير قبول العقد

يمر العقد إذا أثبتت الاختبارات أن العربون لا يظهر ربحًا نهائيًا تلقائيًا، وأن الدين لا يزيد الكاش، وأن التسليم لا يسجل قبضًا تلقائيًا، وأن التسليم بعد الدفع الكامل ينقل الطلب إلى `settled` دون فعل تحصيل مضلل، وأن تغير سعر مادة لا يغير نسخة طلب قديم بصمت، وأن Snapshot المعدل يطابق كمية الطلب ويُحفظ بالقيمة، وأن غياب وقت الحرفة أو الوقت المعروف الصفري يصنف النتيجة `incomplete`، وأن الطلب المسلّم لا يعاد فتحه أو إلغاؤه أو تعديل تكلفته بلا تصحيح موثق، وأن كل تغيير حالة حساسة يسجل أثره، وأن إعادة إرسال الحدث لا تضاعف أثره أو تمنعه عملية مختلفة بمفتاح مشترك.
