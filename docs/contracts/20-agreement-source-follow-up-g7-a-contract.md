# عقد G7-A — مصدر الاتفاق وملخص المتابعة

**الحالة:** DRAFT / G7-A — حزمة متسلسلة مع G6-B، تحتاج مراجعة PR قبل الدمج.

**النطاق:** حفظ وعرض سياق اختياري لطلب/اتفاق محلي قائم: مصدر اتفاق محدود، ملخص متابعة قصير يكتبه المالك، وتاريخ متابعة محلي اختياري مع هدف واضح.

## 1. سؤال القرار

> **من أين جاء هذا الاتفاق، وما آخر ما اتفقنا عليه، ومتى يجب أن أعود للمتابعة؟**

تنظم الشريحة ذاكرة سياق الطلب داخل Micro. لا تنشئ CRM أو Inbox أو قناة اتصال أو وعد متابعة تلقائية.

## 2. الحقول الاختيارية

| الحقل | القاعدة |
|---|---|
| `agreementSource` | `instagram` أو `whatsapp` أو `referral` أو `walk_in` أو `other` أو `null` لغير محدد |
| `followUpSummary` | ملخص قصير يكتبه المالك، أو `null`؛ لا تُحفظ محادثة منسوخة أو مرفق أو بيانات اتصال جديدة |
| `followUpDate` | تاريخ محلي `YYYY-MM-DD` أو `null`؛ لا تاريخ افتراضي |
| `followUpReason` | هدف/سبب قصير عند وجود موعد متابعة، أو `null` إذا لم يوجد موعد |
| `followUpEvents` | تاريخ تغييرات محلية للمتابعة، مع السابق والجديد والسبب و`idempotencyKey` |

لا يُعد `agreementSource` القديم (`conversation`/`call`/`in_person`) مصدرًا صالحًا جديدًا عند تحريره؛ يُحافظ عليه في السجلات القديمة بوصفه قيمة تاريخية غير معدلة، ويمكن للمستخدم اختيار `other` عند تحديث السياق. لا تُحوّل قيمة قديمة إلى معنى جديد بصمت.

## 3. مصدر الحقيقة ومسار الحفظ

يمر الحفظ عبر:

```text
React UI → AgreementContextService → PrototypeLocalStore → IndexedDB
```

السجل الحاكم هو `StoredCraftOrder` المرتبط بالاتفاق. يحفظ Application الحقول الاختيارية مع الطلب، ويعيد `validation_error` أو `storage_error` صريحًا. تعديل هذه الحقول لا يغير السعر أو العربون أو الدين أو الكاش أو `CostSnapshot` أو موعد التسليم أو `ScheduleEntry`.

## 4. التحقق

مصدر الاتفاق يجب أن يكون من مجموعة القيم المحددة أو `null`. يُقبل الملخص غير الفارغ ضمن طول عملي محدود، ولا يتجاوز وصفًا قصيرًا يكتبه المالك. إذا وجد `followUpDate` فيجب أن يطابق `YYYY-MM-DD` ويكون تاريخًا تقويميًا صحيحًا؛ إذا غاب يبقى `followUpReason` فارغًا. لا يثبت النظام أن المتابعة تمت بمجرد وجود التاريخ.

تغيير تاريخ متابعة موجود إلى تاريخ آخر أو إزالته يحتاج `reason` غير فارغ، ويحفظ حدث تعديل يذكر السابق والجديد والسبب. إنشاء موعد من `null` لا يحتاج سبب تأجيل، لكنه يحتاج هدفًا/سبب متابعة غير فارغ حتى يكون القرار مفهومًا. إعادة حفظ نفس القيمة idempotent ولا تضيف تاريخًا مكررًا.

## 5. القراءة التشغيلية

يعيد `AgreementContextService.dueFollowUps(today)` قراءة الطلبات القائمة ذات `followUpDate` المساوي لليوم أو السابق، والطلبات القادمة بترتيب التاريخ، مع مصدر وملخص وسبب المتابعة. هذه قراءة متابعة محلية فقط؛ لا تنشئ `ScheduleEntry`، ولا تدخل شبكة الشهر، ولا ترسل تنبيهًا أو Push أو رسالة.

لا تُعرض المتابعة بوصفها موعد تسليم، ولا يغير تعديلها `deliveryDate` أو سجل الموعد. لا يظهر الطلب المغلق كمتابعة نشطة إلا إذا كان العقد الحالي يسمح بقراءة سياقه؛ في هذه الشريحة تُحافظ القراءة على السياق المحفوظ ولا تنفذ تحصيلًا أو حالة مالية.

## 6. ما لا يغطيه العقد

لا يغطي العقد WhatsApp أو Instagram أو Email أو SMS أو OAuth أو APIs أو Contacts، ولا CRM pipeline أو Inbox أو حملات أو تحليلات تسويق أو عميلًا ككيان مستقل. لا يغطي إشعارًا أو cron أو Background Worker أو مزامنة أو Auth، ولا يضيف تكرارًا أو ظهورًا شهريًا أو موارد أو قدرة.

لا يغير العقد الاتفاق المالي أو العربون أو الدين أو الكاش أو السعر أو `CostSnapshot` أو G5. لا ينسخ رسائل أو مرفقات أو أرقام اتصال.

## 7. التخزين والاستيراد

يرفع التنفيذ `schemaVersion` و`localExportVersion` مع migration صريحة. تستعيد export/import الحقول الجديدة وتاريخ المتابعة مع الحفاظ على السجلات القديمة. الحقول الجديدة للبيانات القديمة تكون `null`، ولا يُخترع مصدر أو موعد أو ملخص. يرفض الاستيراد تاريخًا أو مصدرًا غير صالح قبل لمس الحالة الحالية.

## 8. معايير القبول

يجب أن تثبت الاختبارات أن المصدر غير المحدد يبقى واضحًا، وأن كل مصدر مسموح يحفظ ويستعاد، وأن الملخص الاختياري يحفظ دون نسخة محادثة، وأن الموعد الفارغ يظل غائبًا، وأن الموعد الصحيح المحلي يُحفظ، وأن تغيير تاريخ قائم يرفض بلا سبب ويحفظ السبب عند التعديل الصحيح، وأن القراءة لا تغير موعد التسليم أو `ScheduleEntry` أو المال، وأن export/import يحافظ على السياق، وأن الواجهة تعمل RTL وLight/Dark و360/390/430 ولا تخفي فعل الحفظ خلف BottomNav أو لوحة المفاتيح.
