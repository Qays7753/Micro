# Micro — عقد طلب Delivery والعرض والحالة والخصوصية D-01/D-02

**الحالة:** `CURRENT / EXPANSION E-00 / CONTRACT ONLY`
**المالك:** Manus Agent 1
**تاريخ القرار:** 28 أغسطس 2026

## Major Discussion Points

## 1. سؤال القرار والنطاق

يعالج هذا العقد سؤالًا محددًا: **«كيف يطلب Owner أو Supplier حركة جلب/إرسال، وكيف تقدم شركة توصيل عرضًا وتعلن ما فعلته، من دون ادعاء تتبع حي أو دفع أو تسليم مالي؟»**

Delivery في Micro تنظم طلبًا وعرضًا وحالة أعلنتها جهة التوصيل. هي ليست شركة توصيل ولا Dispatch ولا تطبيق سائق ولا خريطة. لا يثبت `completed` أن العميل قبض أو أن Owner استلم مخزونًا أو أن مصروف النقل دُفع.

`التوصيل` قسم Owner مستقل يفتح من رمز السيارة في AppBar. يعرض طلبات تحتاج قرارًا وعروضًا وحالات واستثناءات؛ الضغط على الرمز لا يفتح نموذجًا ولا ينشئ طلبًا. تبدأ الحركة فقط من فعل `اطلب توصيلًا` داخل القسم أو من مدخل سياقي له نية واضحة في Manage أو Order أو Market.

## 2. الكيانات الأدنى

| الكيان | المنشئ | أقل إدخال | لا يعني |
|---|---|---|---|
| `delivery_request` | Owner أو Supplier المصرح | نوع جلب/إرسال، نطاق مصدر/وجهة، نافذة موعد، وصف طرد اختياري، `vehicle_requirement` اختياري إن أقره Wedge، وطلب إفصاح. | حجز سيارة أو تكلفة أو قبول شركة أو اختيار سائق/سيارة محددة. |
| `delivery_quote` | Courier member لجهته | عرض سعر/نطاق إن اختار، نافذة متاحة، ملاحظة، ومدة سريان. | مصروفًا أو التزامًا أو حجزًا قبل قرار طالب الحركة. |
| `delivery_assignment` | النظام بعد قرار requester | مرجع Quote مقبول، جهة Courier، حالة العمل، وScope الإفصاح. | حساب Driver أو تتبع حي أو أثر Manage. |
| `delivery_status_event` | Courier member مخول | حالة سابقة/جديدة وفاعل ووقت ومصدر وسبب للاستثناء. | دليل قبض/دفع أو دخول مخزون أو تسليم Order داخل Manage. |
| `delivery_exception` | Owner أو Courier ضمن دوره | تصنيف سبب ومسؤول عن الفعل التالي وحالة. | حذف تاريخ المهمة أو وضع «مكتمل» لإخفاء المشكلة. |

اسم منفذ الحركة ورقم تواصل محدودان، إن لزما، حقول محكومة في Assignment أو Quote. لا ينشئان `driver_identity` أو حسابًا أو Portal مستقلًا.

`vehicle_requirement` يصف قدرة النقل المطلوبة فقط، مثل سيارة عادية أو بيك أب أو تبريد أو «غير متأكد». لا يثبت وجود هذه القدرة ولا يحجزها ولا يكشف شركة أو سائقًا قبل Scope وQuote وقرار Owner؛ لا يضاف كحقل واجهة أو Schema قبل قرار Wedge ومصفوفة الحقول في العقد 24.

## 3. حالات الحركة

```text
draft
→ submitted_for_quote
→ courier_reviewing
→ quote_submitted
→ requester_accepted_quote
→ booked
→ source_ready
→ picked_up
→ in_transit
→ arrived_or_completed
```

والحالات الاستثنائية هي `needs_clarification` و`courier_declined` و`requester_declined_quote` و`cancelled` و`reschedule_requested` و`source_not_ready` و`no_vehicle_available` و`pickup_failed` و`delivery_failed` و`recipient_unavailable` و`package_issue`.

لا ينتقل أي سجل إلى `booked` قبل قبول صريح من طالب الحركة. لا ينتقل إلى `picked_up` قبل حالة جاهزية مصدر معلنة. لا تستخدم تسمية `arrived_or_completed` لإخفاء غموض الواقع؛ تعرض الواجهة النص الدقيق الذي سجله Courier، مع الوقت والفاعل وأي سبب أو دليل متاح.

## 4. الإفصاح الأدنى حسب المرحلة

| المرحلة | Courier يرى | لا يرى |
|---|---|---|
| قبل تقديم عرض | منطقة/نطاق عام ونافذة وخصائص طرد لازمة فقط. | اسم عميل أو رقم أو عنوان تفصيلي أو سعر Market أو مال Owner. |
| بعد عرض قبل القبول | تفاصيل إضافية يبررها التسعير فقط إذا وافق Owner. | بيانات لا تتطلبها الشركة لتقديم العرض. |
| بعد الحجز | مصدر/وجهة وتواصل ضروري ونطاق المهمة كما وافق طالب الحركة. | تاريخ Manage أو Snapshot أو تحصيل أو ربح أو بيانات مهمة أخرى. |
| بعد الإغلاق | ملخص المهمة وسجل الحدث بحسب سياسة الاحتفاظ. | الوصول الدائم إلى عنوان/هاتف أو تقارير Owner. |

لا يمرر Owner عنوان عميل أو هاتفه من طلب Manage تلقائيًا. يظهر له معاينة «ما ستراه جهة التوصيل» ويقرها قبل الإرسال. إن لم يوافق أو كانت البيانات ناقصة، تبقى المهمة مسودة أو تحتاج توضيحًا.

## 5. الحدود المالية والتشغيلية

| ما تقوله Delivery | ما لا تستطيع قوله أو فعله |
|---|---|
| «قدمنا عرضًا بسعر/موعد معلنين». | لا تسجل مصروف نقل أو تسوية كاش. |
| «طالب الحركة أكد الحجز». | لا تثبت دفعًا أو التزامًا محاسبيًا. |
| «سجلت الشركة الاستلام/الطريق/الوصول/فشلًا». | لا تثبت تسليم Order أو استلام مخزون أو تحصيلًا. |
| «هناك استثناء يحتاج قرارك». | لا تخفيه أو تلوم طرفًا أو تغلقه بلا حدث. |

إذا أراد Owner تسجيل مصروف نقل أو شراء أو استلام مادة أو تسليم طلب، يفتح وظيفة Manage المناسبة من اقتراح منفصل، ويراجع جميع الحقول وعلاقتها بالعقد المالي قبل الحفظ. لا ينقل هذا العقد مبالغ Quote أو وقت Courier إلى مال Owner تلقائيًا.

## 6. التكرار والتاريخ والإلغاء

كل إرسال طلب وعرض وقبول وانتقال حالة يحمل عملية قابلة لإعادة المحاولة ومعرفًا/مفتاح تكرار عند التنفيذ. Event الحالة غير قابل للمحو الصامت؛ التصحيح Event لاحق يذكر السبب أو Revision موثق. الإلغاء يحدد من ألغى ومتى ولماذا وما تبقى للمتابعة، ولا يعيد كتابة Quote أو حالة وصول سابقة.

## 7. ما لا يشمله العقد

لا Live tracking أو GPS أو Map مستمر أو توزيع تلقائي لسائقين أو ETA مضمون أو تسعير تلقائي أو Payment أو Cash on delivery أو إثبات هوية متقدم أو Driver App أو Webhook/API لشركة خارجية. لا يفترض العقد وجود شركة واحدة أو أكثر؛ اختيار شركاء Beta قرار Pilot منفصل.

## 8. سيناريوهات القبول

| الحالة | النتيجة المطلوبة |
|---|---|
| Owner يبدأ طلبًا من Manage | تظهر مسودة ويعاين الإفصاح؛ لا ينسخ عنوانًا/هاتفًا/مالًا تلقائيًا. |
| Owner يفتح رمز التوصيل | يرى مركز Delivery وحالاته أو empty state صادقة؛ لا ينشأ طلب سيارة. |
| Owner يذكر حاجة بيك أب | تظهر كمتطلب وسيلة نقل في المسودة بعد قرار Wedge؛ لا تختار سيارة/سائقًا أو تحجز توفرًا. |
| Courier يقدم Quote | يظهر لطالب الحركة للمراجعة، ولا يصبح حجزًا أو مصروفًا. |
| Owner يرفض Quote | يبقى السجل تاريخيًا ويغلق/يعاد طلبه وفق الحالة؛ لا يتغير كاش. |
| Courier يسجل `picked_up` مرتين | لا ينشأ Eventان من العملية ذاتها. |
| العنوان يحتاج توضيحًا | لا تنتقل الحالة إلى الطريق أو الاكتمال؛ تظهر خطوة واضحة للطرف المسؤول. |
| Courier يسجل وصولًا | Owner يرى وقتًا وفاعلًا وحالة؛ لا يتغير Order أو Inventory أو Collection. |
| Courier X يطلب مهمة Courier Y | رفض بلا كشف عنوان أو تفاصيل. |
