# عقد المزامنة المحدودة في الشريحة الأولى

**الغرض:** تقديم راحة محلية مسؤولة دون الادعاء بأن مزامنة SaaS متعددة الأجهزة مكتملة.

## نطاق الشريحة

الشريحة الأولى تعمل محليًا أولًا لإثبات قيمة المجال، لكنها لا تعد بحماية بيانات تجارية مركزية ولا بمزامنة متعددة الأجهزة. تُسجل العمليات المحلية مع حالة واضحة، ويكون التصدير المحلي هو وسيلة الاستعادة الأولية إلى أن تُبنى طبقة Auth وWorkspace ونسخ مركزية مختبرة.

## الحالات

```text
local_only → pending_sync → synced
                         ↘ failed → pending_sync
                         ↘ conflict → needs_review → synced
```

- `local_only`: موجود على الجهاز ولم يُرسل.
- `pending_sync`: ينتظر محاولة إرسال.
- `synced`: تأكدت نسخة مركزية مطابقة، عندما تكون الخدمة المركزية مفعلة.
- `failed`: فشلت المحاولة مع سبب قابل للفهم.
- `conflict`: توجد نسختان لا يمكن دمجهما تلقائيًا.
- `needs_review`: يحتاج قرار المستخدم قبل اعتماد النسخة.

## ما يسمح به محليًا

في هذه المرحلة يمكن إنشاء مسودة قطعة وطلب غير مالي مكتمل، تعديل وصف أو موعد قبل التأكيد، وإعداد تكلفة أولية. أما القبض أو تثبيت حدث مالي حساس فلا يُعرض كمكتمل مركزيًا قبل تأكيد المزامنة عند إضافة الخلفية المركزية.

## التكرار والتعارض

كل عملية قابلة لإعادة المحاولة تحمل `idempotency_key` ثابتًا. لا تُنشأ نتيجة ثانية إذا وصلت العملية مرتين. لا يُحل تعارض السعر أو العربون أو حالة التسليم بآخر كتابة صامتة؛ يتحول إلى `needs_review` مع عرض الفرق.

## واجهة المستخدم

كل سجل غير متزامن يعرض حالته وآخر محاولة وفعلًا مناسبًا: أعد المحاولة، صدّر نسخة، راجع التعارض، أو انتظر الاتصال. لا نستخدم كلمة «محفوظ» إذا كان المقصود «محفوظ على الجهاز فقط».

## ما يؤجل

تؤجل المزامنة التجارية متعددة الأجهزة، وسياسة اختيار الفائز بالتعارض، وRLS، والنسخ المركزية، واستعادة Workspace، والإشعارات الخلفية، إلى ما بعد إثبات Domain Core وواجهة الشريحة. لا يبرر وجود Dexie أو RxDB أو أي مكتبة تسميتها local-first مكتملة.

## معايير القبول

يمر العقد إذا لم يكرر انقطاع الاتصال أو إعادة المحاولة أثرًا ماليًا، وإذا بقيت حالة العملية مرئية، وإذا أمكن تصدير البيانات المحلية، وإذا تحول التعارض الحساس إلى مراجعة بشرية بدل استبدال صامت.
