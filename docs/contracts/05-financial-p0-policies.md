# سياسات مالية P0 — Micro

**الحالة:** CURRENT / عقد مالي إلزامي قبل بناء واجهة مالية أو تقرير أو Adapter يحفظ بيانات حقيقية.
**السلطة:** يشرح هذا الملف السياسات التنفيذية للشريحة الأولى، ولا يلغي `financial-operating-model-v1.md` أو عقد النتيجة المالية أو عقد التكلفة؛ بل يحسم النقاط التي لا يجوز تركها ضمنية.
**النطاق:** Prototype المرحلة 2 ومسار الحرفة المخصصة، مع تمييز ما يؤجل إلى MVP التجاري اللاحق.
**العملة الأولى:** JOD، بوحدة نقدية صغرى صحيحة؛ في الشريحة الأولى يمثل الدينار 100 وحدة صغرى (قرشًا).
**المنطقة الزمنية:** `Asia/Amman` للعرض والفترات المحلية، مع حفظ الأوقات ذات التوقيت بصيغة ISO-8601؛ التاريخ المحلي للموعد لا يتحول إلى يوم مختلف بسبب UTC.

## 1. لماذا هذا العقد ضروري؟

Micro لا يكتفي بجمع الأرقام. عليه أن يوضح ما الذي حدث، وما الذي تغيّر، وما الذي يعرفه، وما الذي لا يعرفه، وما القرار التالي. لذلك لا يجوز أن تختار الواجهة أو مكتبة التخزين معنى الربح أو الكاش أو التكلفة بدل هذا العقد.

> **القاعدة المركزية:** لا نعرض نتيجة أدق من البيانات والسياسة التي بنتها، ولا نسمّي مؤشر الطلب ربح المشروع الكامل.

## 2. حدود المراحل

| التكلفة | مواد، وقت، تغليف، توصيل، هدر، وسعر حماية | مصاريف عامة، رسوم، تكلفة فعلية، وقواعد تحميل قابلة للمراجعة |

## 3. تعريفات المال

### 3.1 الكاش

الكاش هو ما تم قبضه أو دفعه فعليًا في قناة أو حساب محدد. إنشاء طلب أو اعتماد سعر أو تسليم لا يزيد الكاش تلقائيًا. العربون يزيد الكاش عند قبضه، والتحصيل المتبقي يزيد الكاش عند قبضه، والدين لا يزيد الكاش. شراء مادة قد يخفض الكاش أو ينشئ التزامًا، حتى إذا بقيت المادة في المخزون.

### 3.2 النتيجة والربح

في Prototype نستخدم عبارة **نتيجة الطلب**. لا نعرض «ربح المشروع منذ البداية» لأن `CraftOrder` الحالي يمثل طلبًا واحدًا ولا يملك Ledger عامًا أو مصاريف مشروع أو مخزونًا دائمًا أو فترة مالية.

وفق سياسة الشريحة الأولى:

| الحدث | الكاش | الإيراد المعترف به في الطلب | التكلفة المعترف بها | النتيجة |
|---|---:|---:|---:|---|
| إنشاء مسودة أو اتفاق | لا تغيير | 0 | 0 | لا نتيجة نهائية |
| اعتماد السعر | لا تغيير | 0 | 0 | تثبيت Snapshot فقط |
| قبض عربون | يزيد | 0 | 0 | كاش محصل، وليس ربحًا نهائيًا |
| التسليم الكامل | لا تغيير تلقائيًا | السعر المتفق | Snapshot المخطط | نتيجة طلب؛ نهائية فقط إذا كانت المعرفة `known`. إذا كان المتبقي صفرًا وكان السعر مدفوعًا كاملًا، تصبح الحالة `settled` ويكون الفعل التالي مراجعة النتيجة |
| قبض المتبقي | يزيد | لا يُعترف بالإيراد مرة ثانية | لا تُحمّل التكلفة مرة ثانية | تنخفض الذمة أو تغلق |
| تسجيل الدين بعد التسليم | لا تغيير | لا يُعترف بالإيراد مرة ثانية | لا تُحمّل التكلفة مرة ثانية | ذمة مستحقة مع طلب مسوى |
| إلغاء قبل التسليم | لا تغيير تلقائيًا | 0 | لا نتيجة طلب نهائية | العربون `needs_review` إن وجد |
| رد العربون | ينخفض | 0 | لا نتيجة تلقائية | تسوية موثقة |
| الاحتفاظ بالعربون | لا تغيير في الكاش | لا يحول الطلب تلقائيًا إلى بيع مكتمل | لا نتيجة تلقائية | تسوية موثقة تحتاج سياسة لاحقة للمصاريف |

هذه السياسة تجعل `recognizedRevenueMinor` و`recognizedCostMinor` في Domain Core الحالي تمثيلًا أوليًا لنتيجة الطلب عند التسليم، وليس دفترًا عامًا. التسليم الجزئي، الإرجاع، الخصم بعد الاتفاق، والاسترداد الجزئي خارج Prototype؛ يجب أن تنتقل الحالة إلى مراجعة صريحة بدل اختراع معالجة تلقائية.

### 3.2.1 نتيجة الفترة المسجلة

Slice E يضيف سطح مراجعة شهريًا باسم **نتيجة الفترة المسجلة**، ولا يطلق عليه «صافي ربح نهائي» أو «قيمة المشروع». يحسب هذا السطح، ضمن تاريخ بداية ونهاية محليين شاملين، ما يلي فقط:

```text
إيراد طلبات مسلّمة بنتيجة final
- التكلفة المباشرة المعترف بها للطلبات نفسها
- دلتا المصروف التشغيلي للأحداث العامة في الفترة
= نتيجة الفترة المسجلة
```

تاريخ إدخال الطلب في الفترة هو تاريخ حدث `status_changed → delivered` بعد تحويل وقت الحدث إلى `Asia/Amman`، لا تاريخ القبض ولا تاريخ إنشاء الطلب ولا اقتطاع أول عشرة محارف من UTC. يدخل المصروف التشغيلي المدفوع والمستحق مرة واحدة عند `occurredOn`؛ وتسديد الالتزام لا يضيف مصروفًا مرة ثانية. لا تدخل الاستثمارات أو السحوبات الشخصية أو الكاش أو الذمم أو تسويات الالتزامات في معادلة النتيجة.

إذا وجد طلب مسلّم داخل الفترة لكن `resultStatus` ليس `final`، يستبعد من الأرقام ويظهر عدده، وتكون حالة السطح `incomplete`. وإذا لم يوجد طلب مستبعد، تبقى الحالة `recorded_only`: فهي تؤكد فقط ما سجلته هذه السياسة، ولا تؤكد اكتمال المخزون أو المصاريف المشتركة أو التوزيع أو الضرائب أو الإرجاعات أو تسويات ما بعد التسليم. لا يجوز أن تغير الواجهة هذه الأسماء أو تخفي الاستبعاد.

### 3.3 مال المالك والتمويل

الاستثمار أو حقن رأس المال يزيد الكاش أو الأصل لكنه ليس مبيعات. السحب الشخصي ينقص الكاش ومال المالك لكنه ليس مصروف تشغيل. القرض يزيد الكاش وينشئ التزامًا، ولا يعد إيرادًا. هذه الأحداث تحتاج Ledger عام لاحقًا، ولا تدخل في `CraftOrder` كربح.

## 4. سياسة التكلفة في Prototype

### 4.1 العناصر الداخلة

التكلفة المباشرة في مسار الحرفة الأولى تتكون من:

```text
material_cost
+ time_cost
+ packaging
+ delivery
+ waste
= planned_cost
```

`required_buffer` أو `safetyBufferMinor` ليس تكلفة محاسبية؛ هو هامش حماية يضاف إلى **سعر الحماية لكل وحدة**. في الكود الحالي، `priceFloorMinor` قيمة لكل وحدة، و`unitCostMinor` يحسب من التكلفة المخططة والكمية.

### 4.2 الوقت المفقود

وقت العمل مؤثر في الحرفة. إذا كان `time` مفقودًا، أو كان الوقت المعلن `known` بدقائق أو سعر ساعة يساوي صفرًا، تصنف الشريحة Snapshot كـ`incomplete` ولا تعرض ربحًا نهائيًا، حتى لو كانت المواد معروفة. إذا أدخل المستخدم وقتًا بسعر ساعة تقديري غير صفري، تكون الحالة `estimated`. لا نضع صفرًا صامتًا، ولا نحجب سبب نقص الوقت بسبب كون مادة أخرى `stale` أو `variable`.

### 4.3 العناصر المؤجلة

`allocated_overhead` و`fees` وتوزيع التسويق والمصاريف المشتركة و`actual cost` ليست جزءًا منفذًا من حساب Prototype الحالي. إذا كانت مؤثرة ولم تدخل، يجب عرض النتيجة تقديرية أو ناقصة، ولا يجوز تسمية التكلفة «كاملة» أو النتيجة «ربحًا نهائيًا».

### 4.4 Snapshot والتاريخ

عند اعتماد السعر أو تأكيد الطلب أو تعديل المواصفات، تحفظ نسخة من الكمية والوحدة والسعر والتاريخ والمصدر وحالة المعرفة. تغيير سعر مادة لاحقًا يؤثر في Snapshot الجديد فقط. تعديل Snapshot مرتبط بطلب يجب أن يطابق كمية الطلب، وإلا يفشل. في Domain Core تُنسخ النسخة ومدخلاتها وتُجمّد عند حدود المجال، ولا يجوز تغييرها عبر مرجع خارجي.

## 5. سياسة السعر والحماية

### 5.1 سعر الحماية

في Prototype:

```text
unit_cost = ceil(planned_cost / quantity)
price_floor_per_unit = unit_cost + safety_buffer_per_unit
```

السعر الناتج يحمي من البيع تحت التكلفة المعروفة مع هامش حماية اختاره المستخدم. لا يمثل سعر السوق، ولا يضمن الطلب، ولا يفرض قرار القبول.

### 5.2 Markup مقابل Margin

```text
price_from_markup = unit_cost × (1 + markup_rate)
price_from_margin = unit_cost ÷ (1 - target_margin)
```

`markup_rate` نسبة تضاف إلى التكلفة، بينما `target_margin` نسبة من سعر البيع. لا نخلطهما في حقل واحد. `target_margin` يجب أن يكون أقل من 100% وغير سالب؛ أي قيمة خارج النطاق تفشل التحقق. `price_from_margin` قدرة لاحقة حتى يملك النظام عقد الرسوم والضرائب والتقريب، ولا تدخل شاشة Prototype كحقيقة جاهزة.

### 5.3 التقريب

الأموال تدخل وتخرج في وحدات صحيحة. في Domain Core الحالي تُقرّب تكلفة كل بند مادي ووقت إلى أقرب وحدة صغرى، ثم تُجمع البنود، وتُقرّب تكلفة الوحدة إلى الأعلى لحماية المستخدم من التقليل. هذه سياسة محافظة مؤقتة يجب أن تبقى مختبرة. لا تستخدم الواجهة أرقامًا أكثر دقة من الوحدة الصغرى، ولا تحول كمية مادية كسرية إلى مبلغ باستخدام `float` غير مضبوط.

## 6. المصاريف العامة والمشتركة

### 6.1 Prototype

يمكن للنظام أن يشرح أن الكهرباء أو الإنترنت أو التسويق مصروف عام أو مشترك، لكن لا يحمّله على طلب محدد تلقائيًا. إذا كان المصروف مؤثرًا في السؤال الذي يطلبه المستخدم، يظهر أنه غير موزع أو تقديري وتخفض درجة المعرفة. لا يُستبعد ولا يُحمّل كاملًا بصمت.

### 6.2 السياسة اللاحقة المطلوبة

قبل إضافة ربح كامل أو نقطة تعادل يجب أن يحدد المستخدم أو النظام لكل مصروف:

| البند | المطلوب |
|---|---|
| العلاقة | مشروع، شخصي، مشترك، أو غير محدد |
| الطبيعة | تشغيلي، أصل، تمويل، سحب، تحويل، أو تسوية |
| السلوك | ثابت، متغير، مختلط، أو غير معروف |
| الفترة | يوم، أسبوع، شهر، أو نطاق مخصص |
| التوزيع | طلب، منتج، حملة، ساعات عمل، وحدات، إيراد، أو غير موزع |
| أساس التوزيع | نسبة أو مبلغ أو ساعات أو وحدات، مع مصدر الافتراض |
| الثقة | معروف، مقدر، ناقص، أو يحتاج مراجعة |

التسويق المرتبط بحملة يمكن ربطه بالحملة والفترة. التسويق العام لا يوزع على طلب واحد إلا إذا اختار المستخدم قاعدة واضحة. المصروف المنزلي المشترك يحتاج نسبة أو تقديرًا؛ عدم معرفة النسبة لا يعني صفرًا.

## 7. نقطة التعادل

نقطة التعادل ليست جزءًا من نتيجة الطلب في Prototype. في المرحلة المالية اللاحقة تستخدم صيغة مفاهيمية:

```text
contribution_margin_per_unit = selling_price_per_unit - variable_cost_per_unit
break_even_units = fixed_costs_for_period ÷ contribution_margin_per_unit
```

لا تعرض النتيجة إذا كان هامش المساهمة صفرًا أو سالبًا، أو إذا كانت التكاليف الثابتة أو مزيج المنتجات ناقصة. يجب عرض الفترة، التكاليف الثابتة، الهامش، المزيج، الافتراضات، ودرجة المعرفة. يجب التفريق بين نقطة التعادل المحاسبية/التشغيلية والسيولة: قد يصل المشروع إلى التعادل بينما لا يملك كاشًا لدفع التزام قريب.

## 8. حالات المعرفة والنتيجة

| حالة التكلفة | ما يسمح به النظام |
|---|---|
| `known` | يمكن أن تكون نتيجة الطلب نهائية وفق سياسة التسليم |
| `estimated` | مؤشر تقديري مع شرح الافتراض |
| `partial` | نتيجة أولية؛ لا ربح نهائي |
| `incomplete` | يظهر البند الناقص والفعل التالي |
| `stale` | مراجعة السعر أو المدة قبل الاعتماد |
| `variable` | مراجعة أثر التخصيص أو مصدر التقدير |

إذا كان هناك قرار إلغاء أو تعارض أو تسليم جزئي غير مدعوم، تكون النتيجة `review_required` حتى لو كانت أرقام التكلفة معروفة.

## 9. قائمة الاختبارات المالية الإلزامية

قبل قبول أي واجهة أو Use Case مالي، يجب أن تطابق النتائج المتوقعة في `pre-build-experiment-simulation-v1.md` وأن تغطي على الأقل:

1. مواد مع وقت معروف، ومواد مع وقت مفقود.
2. تغيير سعر مادة بعد اعتماد الطلب، مع بقاء Snapshot القديم.
3. عربون ثم تسليم ثم قبض متبقٍ.
4. تسليم ثم تسجيل دين دون زيادة الكاش.
5. إلغاء بعربون ثم رد أو احتفاظ صريح.
6. Snapshot تعديل بكمية مختلفة، ويجب أن يفشل.
7. سعر حماية بوحدة وكمية صحيحتين مع سياسة التقريب.
8. مصروف عام أو مشترك لا يُحمّل على طلب بلا قاعدة.
9. نقطة تعادل بهامش موجب، وصفر، وسالب في المرحلة التي تدعمها.
10. عدم تكرار حدث حساس عند إعادة المحاولة، مع رفض مفتاح فارغ وتمييز نوع العملية.
11. دفع السعر كاملًا مقدمًا ثم التسليم ينقل الطلب إلى `settled` ولا يعرض فعل تحصيل متبقٍ.
12. دخول طلب مسلّم إلى `needs_review` يحجب النتيجة ويمنع كل عملية عامة للحالة أو Snapshot أو المال من الخروج بلا Use Case تصحيح موثق، وكل تغيير حالة مباشر يسجل حدث `status_changed` مرافقًا.
13. نتيجة فترة تشمل طلبًا مسلّمًا نهائيًا ومصروفًا مدفوعًا أو مستحقًا مرة واحدة، وتستبعد الاستثمار والسحب وتسديد الالتزام؛ وتضع تسليم `2026-07-31T22:30:00.000Z` ضمن آب في `Asia/Amman`.

## 10. قرارات لا يجوز للـAgent اختراعها

لا يخترع Agent سياسة تسليم جزئي أو إرجاع أو ضريبة أو عمولة أو توزيع مصروف مشترك أو تقييم مخزون أو اعتراف ربح عام أو تصحيحًا بعد التسليم. إذا لم تغط وثيقة أو عقد القرار، يسجل السؤال كفجوة ويوقف التنفيذ عند الحد الذي قد يغير معنى المال.
