# Micro — بوابة Pre-build Alignment v1

**الحالة:** CURRENT / بوابة إلزامية قبل كتابة Adapter أو واجهة Prototype.

## الغرض

تثبت هذه الوثيقة الحد الفاصل بين تعريف Micro الكامل، وPrototype المرحلة 2، وMVP التجاري اللاحق. كما تحدد ما يجب محاكاته أو اختباره قبل بدء البناء، حتى لا يقرأ Agent الوثائق الكاملة بوصفها قائمة تنفيذ فورية، ولا يختزل Micro في أول مسار فقط. تُقرأ مع [`prototype-build-charter-v1.md`](prototype-build-charter-v1.md) عند الانتقال من البوابة إلى التنفيذ؛ فالـCharter يثبت Web-first وAndroid-like وPWA-ready وCloudflare وخطة الشرائح دون توسيع النطاق.

## التعريفات الملزمة

| المصطلح | التعريف التنفيذي |
|---|---|
| Micro كمنتج | نظام إدارة مالية وتشغيلية كامل للمشروع وصاحب المشروع، عميق في المعالجة الداخلية، بسيط في تجربة المستخدم، ويجيب عن التكلفة والنتيجة والكاش والمخزون والذمم والقرار التالي. |
| Prototype المرحلة 2 | Web App بملء الشاشة، RTL، محلي، ومصمم بسلوك Android-like، يثبت أول قيمة عبر مسار حرفة مخصصة: تكلفة، سعر، اتفاق، موعد، عربون، تنفيذ، تسليم، تحصيل أو دين، نتيجة طلب، وفعل تالٍ. يمكن نشره على Cloudflare ويكون PWA-ready، وفق Build Charter، دون ادعاء Native أو SaaS. |
| MVP التجاري اللاحق | النسخة التي تأتي بعد إثبات Prototype والقيمة السلوكية، وتضيف عند الحاجة الهوية وworkspace والعزل والنسخ والتصدير والتخزين المركزي والمزامنة المحدودة. |
| التوجيه داخل العمل | سؤال قصير أو اقتراح أو تفسير مرتبط بحدث المستخدم، لا منهج دروس ولا LMS ولا شرط إكمال محتوى. |
| المحاكاة | فحص مكتبي حتمي للحالات والقواعد والنصوص والتغطية؛ لا يثبت أن مستخدمًا حقيقيًا فهم أو عاد أو دفع. |
| Pilot | استخدام أصحاب مشاريع حقيقيين بمهام وقياسات زمنية وسلوكية وتجارية بعد وجود Prototype صالح. |

## حدود Prototype المرحلة 2

يدخل في Prototype المحلي فقط ما يلزم لإثبات أول قيمة لمسار الحرفة المخصصة:

```text
إنشاء قطعة
→ إدخال خامات ووقت تقديري
→ حساب التكلفة وحالة المعرفة
→ اقتراح سعر حماية
→ تسجيل اتفاق وموعد
→ عربون اختياري
→ تنفيذ وتسليم
→ تحصيل أو تسجيل دين
→ نتيجة الطلب وفعل تالٍ
```

يستطيع Prototype استخدام بيانات محلية ومسودات محلية وحالة مزامنة توضيحية، ويعمل كتطبيق Web بملء الشاشة، لكنه لا يدعي SaaS مركزيًا أو نسخًا احتياطية أو عزل workspace أو تعدد أجهزة. لا يدخل فيه Auth أو Supabase أو RLS أو Billing أو مزامنة كاملة أو مخزون متقدم أو تقارير مالية عامة منذ البداية.

## ما يجب حسمه قبل الكود

| القرار | الصياغة المعتمدة في هذه البوابة |
|---|---|
| اسم الناتج | «نتيجة الطلب» في Prototype؛ لا تُسمى «ربح المشروع منذ البداية» قبل وجود سجل مالي عام وفترات وسياسة اعتراف واضحة. |
| العربون | كاش محصل مرتبط بطلب، وليس ربحًا نهائيًا تلقائيًا. |
| الدين | مبلغ مستحق، وليس كاشًا محصلًا. |
| المخزون | الشراء قد يزيد المخزون ويخفض الكاش أو ينشئ دائنًا؛ لا يتحول كله إلى تكلفة بيع لحظة الشراء. |
| الوقت | يمكن تقديره؛ وإذا لم يُدخل يظهر أثر النقص بدل افتراض أنه صفر. |
| المصروف المشترك | يُسجل بنسبة أو تقدير أو «غير متأكد» مع خفض درجة المعرفة، ولا يحمل أو يستبعد بصمت. |
| التكلفة الناقصة | لا تساوي صفرًا، ولا تسمح بعرض ربح نهائي. |
| التغيير | تعديل المواصفات أو التكلفة ينشئ revision أو snapshot جديدًا ولا يغير الماضي بصمت. |
| التوجيه | يبدأ من واقعة المستخدم وينتهي بأثر وفعل تالٍ؛ لا يعطل التسجيل بسبب نقص غير جوهري. |

## التجارب الإلزامية قبل البناء الكامل

| التجربة | نوعها | معيار الخروج |
|---|---|---|
| اختبار الحقيقة المالية | محاكاة حتمية على حالات مرجعية | لا خلط بين الربح والكاش والعربون والدين والمخزون، وكل نتيجة تذكر درجة المعرفة. |
| اختبار Prototype الورقي أو القابل للنقر | محاكاة مسار هاتف RTL | يمكن تتبع الحد الأدنى للإدخال والنتيجة والفعل التالي، وتظهر نقاط التعثر قبل الكود. |
| جلسات مهام مع أصحاب مشاريع | اختبار واقعي لا تعوضه المحاكاة | ينجز المستخدم مهامًا فعلية ويشرح ماذا حدث وما أثره وما الذي سيفعله. |
| اختبار يوم بلا طلب | محاكاة ثم تحقق واقعي | يرى المستخدم وضع المشروع والالتزامات والمخاطر القريبة، لا رسالة «لا يوجد طلب» فقط. |
| Pilot لمدة محدودة | لاحق بعد Prototype | يقاس الزمن، العودة، الفعل، الثقة، الأخطاء، والاستمرار؛ لا يبدأ قبل عبور التجارب السابقة. |

## حالة المحاكاة الحالية

تقرير `docs/quality/pre-build-experiment-simulation-v1.md` يوثق أن 12 من 12 حالة مالية حتمية اجتازت الفحص المكتبي، وأن تسلسل Prototype واختبار يوم بلا طلب اجتازا فحص الاتساق. بروتوكول جلسات المستخدمين جاهز لكنه لم يُنفذ مع مستخدمين، وPilot لمدة 30 يومًا مصمم لكنه لم يبدأ. لذلك تسمح النتيجة بالانتقال إلى Prototype محدود، ولا تسمح بادعاء فهم المستخدم أو العودة أو الدفع.

## بوابة الإيقاف

يتوقف الانتقال إلى الكود إذا لم توجد نتيجة متوقعة لحالة مالية، أو إذا كان النص يخلط بين Prototype وMVP التجاري، أو إذا ظهر «التدريب» كمسار مستقل، أو إذا كان التقرير يدعي ربحًا كاملًا مع تكلفة ناقصة، أو إذا لم نستطع تعريف ما الذي سيفعله المستخدم بعد النتيجة.

تُعامل السيناريوهات والمحاكاة كأدوات ضبط داخلية. لا يجوز استخدامها لإثبات حجم السوق أو العودة الأسبوعية أو الاستعداد للدفع. هذه الادعاءات تحتاج مستخدمين حقيقيين وPilot مناسبًا.

## ترتيب ما بعد البوابة

بعد اجتياز البوابة، يبنى Adapter محلي وUse Cases وواجهة هاتف لمسار الحرفة فقط. ثم تُشغّل الحالات المالية المرجعية واختبارات RTL والاستعادة المحلية. بعد إثبات الفهم والإنجاز، يختار الفريق — بناءً على G15/G16 — Profile واحدًا أو SaaS Boundary؛ لا يُفترض طعام أو خدمة تلقائيًا، ولا يركب مشروع مختلط قبل عقد سياق الواقعة والمورد المشترك. لا تُبنى طبقات SaaS أو تقارير عامة لمجرد أنها جزء من صورة Micro النهائية.
