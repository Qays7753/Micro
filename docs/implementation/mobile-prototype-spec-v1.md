# Micro — مواصفة Prototype الهاتف المحلي v1

**الحالة:** `CURRENT / CANONICAL / PROTOTYPE SPECIFICATION`

**الإصدار:** 1.1 — Prototype المرحلة 2 مع عقد ألوان وقياسات Light/Dark

**المستخدم:** صاحب مشروع واحد، على جهاز واحد، بواجهة عربية RTL محلية.

**الهدف:** إثبات أن Micro يستطيع تحويل مسار حرفة يدوية مخصصة من فكرة/طلب إلى تكلفة وسعر واتفاق وعربون وتنفيذ وتسليم وتحصيل أو دين ونتيجة وفعل تالٍ، مع درجة معرفة صادقة وتصدير/استيراد محلي قبل أي بيانات حقيقية.

**ليس الهدف:** بناء MVP تجاري، أو نظام محاسبي كامل بواجهة عامة، أو POS، أو Inventory عام، أو Ledger عام، أو SaaS/Auth/Sync/Billing، أو تطبيق تعليمي.

> هذه وثيقة تصميم وسلوك واختبار. لا تعني أن الواجهات أو Adapter أو LocalStore منفذة الآن. الكود الحالي في Micro هو Domain Core قابل للاختبار؛ أما هذا الملف فيحدد ما يجب أن يُبنى ويُختبر بعد اجتياز بوابة Pre-build.

# Major Discussion Points

## 1. شكل Prototype الإجمالي

يتكون Prototype من **10 أسطح شاشة رئيسية** مترابطة، مع Bottom Sheets ومسودات وحالات تأكيد داخلية. لا يعني العدد وجود عشر وحدات مستقلة أو عشر نقاط BottomNav؛ الغرض هو تقسيم قرارات المستخدم بحيث لا تتكدس في نموذج واحد.

```text
تأسيس محلي مختصر
  → مشروعي الآن
  → الطلبات والموعد
  → بدء طلب/تقدير واتفاق
  → بناء Snapshot التكلفة
  → مراجعة سعر الحماية والعربون
  → تفاصيل التنفيذ والتكلفة
  → التسليم والتحصيل أو الدين
  → نتيجة الطلب والفعل التالي
  → الإعدادات والنسخ المحلي
```

يستطيع المستخدم بدء المسار من طلب جديد، أو من منتج مخطط لم يُبع بعد. يبدأ Prototype بمسار الحرفة المخصصة، لكن لا يصمم Domain بحيث يمنع إضافة طعام أو خدمة لاحقًا؛ الاختلاف المستقبلي يكون في مدخلات النشاط لا في معنى الكاش والنتيجة والذمة ودرجة المعرفة.

## 2. قواعد عامة لكل شاشة

كل شاشة يجب أن تملك تعريفًا ثابتًا للهدف، وHero واحدًا، وتسلسلًا واضحًا للمعلومات، وقرارًا أو فعلًا رئيسيًا، وحالات فراغ وتحميل وخطأ ومراجعة. لا يجوز أن تكون الشاشة قائمة أرقام بلا سؤال. كل انتقال يحفظ مسودة أو يطلب تأكيد فقدها. كل أثر مالي حساس يستخدم Submit Guard وidempotency من Adapter/Domain.

### 2.1 عقد الشكل والتنفيذ المرئي

يطبق Prototype [`mobile-ui-ux-reference-v1.md`](../product/mobile-ui-ux-reference-v1.md) حرفيًا في القياسات وSemantic Tokens، لا في كود Accounting. عرض التصميم الأساسي `390px`، والاختبار الإلزامي `360/390/430px`. شبكة المسافات `4px` وقيمها المسموحة `4/8/12/16/20/24/32px`. الهدف الأدنى `44×44px`، الحقل/الزر `48px`، FAB `56×56px` بهامش `16px`، chip `36px`، BottomNav `56–64px`، وBottom Sheet radius علوي `20px`.

الوضعان مدعومان في العقد: `system` افتراضيًا عند البناء، و`light` و`dark` باختيار محلي إن أُضيفت شاشة الاختيار. Light يستخدم `#FAF9F5` للخلفية و`#FFFFFF` للسطح و`#CC785C` كهوية و`#964E33` للفعل الأساسي ذي النص الأبيض. Dark يستخدم `#1C1917` للخلفية و`#27231F` للسطح و`#D59172` للفعل الأساسي مع نص `#1F1E1D`. الدلالات الرسمية هي النجاح Light `#2E7D57/#E4F2EA` وDark `#7FC49E/#332D27`، والخطر Light `#B42318/#FBE7E6` وDark `#E47975/#332D27`، والتحذير Light `#8A6927/#F6ECCF` وDark `#E2C268/#332D27`، والسحب Light `#3E5C76/#E8EEF3` وDark `#8AA5B8/#332D27`.

كل شاشة تختبر النص العربي الطويل والأرقام وحالات Loading/Error/Needs-review في الوضعين. لا تستخدم المكونات Hex خامًا داخل JSX؛ يجب أن تمر عبر Semantic Tokens. لا يستخدم اللون وحده؛ كل حالة مالية تحمل نصًا، وإشارة `+` أو `−` عند الحركة، وأيقونة أو شكلًا عند الحاجة. هذه القيم Design Contract وليست دليلًا على أن CSS أو Dark Mode منفذان الآن.

### 2.2 قالب قراءة الشاشة

| العنصر | السؤال الذي يجب أن تجيب عنه المواصفة |
|---|---|
| الغرض | لماذا يفتح المستخدم هذه الشاشة الآن؟ |
| Hero | ما الرسالة أو الرقم أو الحالة التي يراها أولًا؟ |
| المحتوى | ما الحد الأدنى من الحقول/المعلومات؟ |
| عمق المعلومات | منخفض، متوسط، أو مرتفع، ولماذا؟ |
| قرار المستخدم | ما الذي يستطيع أن يقرره بعد القراءة؟ |
| الفعل التالي | ما الزر أو المسار الأساسي؟ |
| الحالات | ماذا يرى في الفراغ، التحميل، الخطأ، النقص، أو المراجعة؟ |
| الربط | ما الذي يذهب إلى Domain/LocalStore، وما الذي يبقى مؤجلًا؟ |

## 3. الشاشة 1 — تأسيس Micro محليًا

### الغرض

تبدأ الجلسة بأقل قدر من التأسيس الذي يسمح بعرض قيمة، لا باستبيان محاسبي. المستخدم يعرّف مشروعه ويختار أن يبدأ بمسار «حرفة مخصصة».

### Hero

> «لنرتب أول قرار يهمك: طلب مخصص تريد تسعيره أو متابعته.»

### المحتوى ودرجة المعلومات

العمق **منخفض**. تظهر ثلاثة مدخلات مطلوبة فقط: اسم النشاط أو الاسم الشخصي، العملة الافتراضية (الدينار الأردني في Prototype الأول مع إمكانية تثبيتها)، ونوع المسار «حرفة يدوية مخصصة». يمكن إظهار شرح سطر واحد عن التخزين المحلي والتصدير.

لا تظهر Auth، بريد، كلمة مرور، خطة، دفع، Google Drive، Workspace، Roles، أو إعداد مخزون. لا يُطلب رصيد افتتاحي أو قائمة مواد كاملة قبل إنشاء أول طلب؛ يمكن إدخالها داخل مسار التكلفة عند الحاجة.

### القرار والفعل التالي

الفعل الأساسي «ابدأ أول طلب». الفعل الثانوي «استكشف بدون بيانات» إذا احتجنا اختبارًا داخليًا، لكنه لا يصنع نتائج مالية وهمية. بعد الحفظ ينتقل المستخدم إلى الشاشة 2 أو 4 حسب اختياره.

### الحالات الحدية

إذا ترك الاسم فارغًا، يظهر خطأ field-level لا رسالة عامة. إذا أغلق الشاشة، تحفظ مسودة تأسيس محلية أو يظهر تأكيد. إذا فشل LocalStore، تعرض الشاشة سببًا عمليًا ولا تدعي أن المشروع محفوظ. إذا كانت الجلسة قائمة، تتجاوز الشاشة إلى «مشروعي الآن».

### الربط

تنشئ `local workspace profile` في Adapter/LocalStore، لا `workspace_id` تجاريًا ولا Auth. لا تتغير Domain Core المالية بهذه الشاشة.

## 4. الشاشة 2 — مشروعي الآن

### الغرض

تعطي نقطة بداية يومية وتجيب: «ما أهم شيء أحتاج أن أفعله الآن؟» سواء كان هناك طلب أم لا.

### Hero

يكون Hero عبارة عن أولوية واحدة، مثل: «طلب سارة يحتاج مراجعة السعر قبل بدء التنفيذ» أو «لا توجد طلبات اليوم؛ لديك تكلفة ناقصة في طلب مفتوح». إذا لم توجد بيانات، يكون: «ابدأ بطلب مخصص أو سجّل ما حدث في المشروع».

### المحتوى ودرجة المعلومات

العمق **متوسط**. تحت Hero يظهر ملخص محدود من ثلاث بطاقات أو صفوف: الطلبات القريبة، المبالغ المرتبطة بطلبات مفتوحة، وأهم نقص في المعرفة. لا تعرض الشاشة Ledger أو «ربح المشروع منذ البداية» أو مؤشرات POS أو المخزون العام.

يمكن عرض نتيجة الطلب المفتوح بدرجة معرفة، والعربون المحصل، والمتبقي، وموعد التنفيذ. الأرقام تُسمى صراحة: «عربون»، «متبقٍ»، «تكلفة معروفة»، «نتيجة تقديرية». لا تستخدم جرتي Accounting أو لغة «بالدرج/حق التاجر».

### القرار والفعل التالي

الفعل الأساسي يتغير حسب الأولوية: «راجع السعر»، «أكمل التكلفة»، «افتح الطلب»، «سجل التحصيل»، أو «أنشئ طلبًا». لا تعرض أكثر من أولويتين متنافستين. FAB يفتح أحداثًا محدودة: طلب/تقدير، شراء أو مصروف، قبض/عربون/تحصيل، أو سحب مؤجل إن لم يكن عقده جاهزًا.

### الحالات

| الحالة | Hero | الفعل |
|---|---|---|
| فارغة | «لنبدأ بأول طلب أو تقدير» | إنشاء طلب |
| طلبات مفتوحة | «لديك طلب يحتاج انتباهًا» | فتح الطلب |
| يوم بلا طلب | «لا يوجد طلب اليوم، لكن هذه صورة الالتزامات والتكاليف المعروفة» | مراجعة/تسجيل حدث |
| بيانات ناقصة | «النتيجة جزئية لأن الوقت/الهدر غير مسجل» | إكمال أو المتابعة كتقدير |
| خطأ قراءة محلية | «تعذر تحميل صورة المشروع» | إعادة المحاولة أو التصدير |

### الربط

تقرأ الشاشة من LocalStore وUse Cases، لكنها لا تنشئ Ledger عام. النتيجة الحالية في Prototype تكون على مستوى الطلب أو ملخص الأحداث المنفذة، ولا توصف كتقرير مشروع شامل.

## 5. الشاشة 3 — الطلبات والموعد

### الغرض

تحفظ الاتفاقات وتمنع نسيان ما يجب تنفيذه ومتى، وتتيح الوصول إلى الطلبات المفتوحة والمسودة والمسلّمة.

### Hero

«ما يجب أن تتابعه» مع تبويب أو segment بسيط: اليوم/القادم/كل الطلبات. يمكن عرض تقويم خفيف لاحقًا داخل نفس السطح، لكنه ليس شرطًا لبداية المسار.

### المحتوى ودرجة المعلومات

العمق **متوسط**. بطاقة الطلب تعرض اسم العميل أو معرفًا، وصف القطعة، الكمية، الموعد، الحالة، العربون، المتبقي، ووسم النتيجة/التكلفة عند وجوده. لا تعرض رقم الهاتف أو أفعال الاتصال في المقدمة إلا إذا اختار المستخدم فتح التفاصيل؛ الأفعال الخارجية ثانوية.

الفرز الأساسي: يحتاج انتباهًا، قيد التنفيذ، جاهز، تم التسليم، مكتمل ماليًا، أو يحتاج مراجعة. لا نعيد استخدام `needs_review` بمعنى «متوقف» أو `on_hold`؛ إذا لم يوجد عقد on_hold، تظهر «تحتاج مراجعة» بوصفها حالة معرفة/تصحيح لا حالة تشغيل عامة.

### القرار والفعل التالي

من كل بطاقة فعل واحد بحسب الحالة: «راجع السعر»، «ابدأ التنفيذ»، «سجل التسليم»، «سجل التحصيل»، أو «راجع النتيجة». البحث يفتح في الهيدر عند كثرة السجلات، والفلتر لا يمسح اختيار المستخدم عند الرجوع.

### الحالات الحدية

الحالة الفارغة تميز بين «لا توجد طلبات» و«لا توجد نتائج لهذا البحث». Skeleton يحافظ على شكل البطاقات. عند فشل البحث المحلي، يعرض السبب وخيار إعادة المحاولة. عند موعد مفقود، لا يخترع تاريخًا؛ يضع «موعد غير محدد» ويقود إلى إكمال الاتفاق.

### الربط

تستخدم القائمة LocalStore لحقول الطلب والموعد ومصدر الاتفاق المستهدفة. موعد التسليم ومصدر الاتفاق ليسا منفذين في Domain Core الحالي؛ لذلك يجب أن يملك Adapter عقدهما قبل ادعاء التخزين.

## 6. الشاشة 4 — بدء طلب أو تقدير واتفاق

### الغرض

تنشئ نقطة البداية لقطعة حرفة مخصصة: إما طلب حقيقي وصل من عميل، أو منتج/تصميم مخطط لم يُبع بعد.

### Hero

«ماذا تريد أن تعرف الآن؟» مع خيارين واضحين: «لدي طلب من عميل» و«أخطط لتصميم/منتج». هذا التفريق يمنع خلط التقدير بنتيجة بيع فعلي.

### المحتوى ودرجة المعلومات

العمق **متوسط**. الحد الأدنى: وصف القطعة، الكمية، مواصفات أو ملاحظات التخصيص، السعر المتفق عليه إن وجد، موعد التسليم المقصود إن كان طلبًا، ومصدر الاتفاق اختياريًا (مثل رسالة أو محادثة) إذا كان مفيدًا. اسم العميل اختياري في المسودة لكنه مطلوب قبل اتفاق قابل للمتابعة إذا كان ذلك جزءًا من عقد التخزين.

لا تظهر مواد أو ساعات أو مصاريف هنا إلا كملخص؛ التفاصيل تدخل الشاشة 5. لا يظهر زر «قبول الطلب» كقرار آلي. Micro يعرض ما يعرفه ويسمح للمستخدم بتعديل السعر/الموعد قبل تثبيت الاتفاق.

### القرار والفعل التالي

«حفظ كمسودة»، «احسب التكلفة»، أو «أكمل الاتفاق». إذا كان السعر معروفًا لكن التكلفة ناقصة، لا يمنع الانتقال إلى التكلفة. إذا اختار المستخدم منتجًا مخططًا، تتغير اللغة من «المبلغ المتفق عليه» إلى «السعر المستهدف/المفترض».

### الحالات

المسودة غير المكتملة تبقى قابلة للاستكمال. إذا كان السعر صفرًا، يظهر أنه غير محدد لا أنه مجاني. إذا كان الموعد في الماضي، يظهر تحذير قابل للتصحيح. عند عودة المستخدم بعد الإغلاق، يعرض استئناف المسودة بدل إنشاء نسخة ثانية.

### الربط

تنشئ أو تحدّث `CraftOrder` ومواصفاته، وتجهز `CostSnapshot` لاحقًا. لا تنشئ قبضًا أو عربونًا أو نتيجة بمجرد حفظ الاتفاق.

## 7. الشاشة 5 — بناء Snapshot التكلفة

### الغرض

تساعد المستخدم على تكوين صورة تكلفة الطلب أو المنتج تدريجيًا، وتظهر ما هو معروف وما هو مقدر وما ينقص قبل التسعير.

### Hero

«هذه التكلفة المعروفة حتى الآن» مع إجمالي فرعي واضح ووسم معرفة: «مقدرة» أو «ناقصة». تحت الرقم سطر: «لا نعطي ربحًا نهائيًا ما دام الوقت/الهدر/المصاريف المؤثرة غير معروف» عند الحاجة.

### المحتوى ودرجة المعلومات

العمق **مرتفع لكن متدرج**. يبدأ ببنود الحرفة: المواد، الكمية، تكلفة الوحدة أو كون المادة موجودة، وقت العمل بالدقائق أو سعر الساعة، التغليف، التوصيل، المصروف المباشر، ومصاريف عامة مقدرة إذا كانت سياسة Prototype تدعمها. لا تُفرض كل البنود؛ يُسأل المستخدم عن البنود التي تؤثر في الحالة.

كل بند يملك مصدرًا: «أدخله المستخدم»، «من تقدير سابق»، «غير معروف»، أو «غير منطبق». المواد «الموجودة» لا تُعامل كأنها مجانية؛ إذا لم يوجد عقد مخزون في Prototype، يسجل المستخدم تكلفة المادة المعروفة أو يختار «غير متأكد» وتظل النتيجة ناقصة. لا ينشئ هذا السطح Inventory عامًا.

### القرار والفعل التالي

«احفظ نسخة التكلفة»، ثم «راجع السعر». يمكن إضافة بند أو تخطيه مع تفسير. بعد الحفظ، لا تعدل النسخة التاريخية في مكانها؛ أي تعديل ينشئ Revision جديدة وفق Domain.

### الحالات

| الحالة | السلوك |
|---|---|
| لا توجد بنود | يشرح أن النتيجة غير قابلة للحكم بعد، ويقود لإضافة مادة أو وقت |
| وقت مفقود | يوسم Snapshot `incomplete` ولا يحسب ربحًا نهائيًا |
| رقم غير صالح | خطأ بالقرب من الحقل دون مسح بقية المسودة |
| تكلفة مقدرة | يظهر الافتراض والسماح بتعديله |
| Revision | يعرض «نسخة جديدة» ويحتفظ بملخص النسخة السابقة |
| فشل الحفظ | يبقى الإدخال المحلي كمسودة إن أمكن، ولا ينشئ أثرًا ماليًا نصف مكتمل |

### الربط

يربط السطح بـ`CostSnapshot` و`costKnowledgeState` و`reviseOrderCost`. لا يدعي BOM عامًا، أو تكلفة مخزون تلقائية، أو calculation version غير موجودة.

## 8. الشاشة 6 — مراجعة سعر الحماية والاتفاق

### الغرض

تحول التكلفة المعروفة والافتراضات إلى قرار تجاري مفهوم: هل السعر الحالي يحمي التكلفة والوقت بدرجة معرفة مناسبة؟

### Hero

«قبل أن تثبت السعر: ماذا يغطي؟» ويعرض السعر الحالي أو المستهدف، تكلفة معروفة، عناصر ناقصة، وسعر حماية/نطاق مقترح إذا كان العقد يسمح بذلك.

### المحتوى ودرجة المعلومات

العمق **متوسط إلى مرتفع**. الترتيب: السعر، التكلفة المعروفة، التكلفة المقدرة، ما ينقص، هامش/نتيجة متوقعة، والعربون المقترح لتغطية ما سيدفعه المستخدم قبل التنفيذ. كل رقم يحمل وسمه، ولا تظهر عبارة «مربح» إذا كانت المعرفة ناقصة؛ تستخدم «قد يترك نتيجة إيجابية تقديرية» أو «السعر الحالي أقل من التكلفة المعروفة».

يعرض النظام سبب الفرق: وقت غير محسوب، تغليف ناقص، توصيل، هدر، أو مصروف عام. لا يعطي سعرًا وحيدًا إلزاميًا، ولا يقرر قبول الطلب أو رفضه. إذا لم يتحمل السوق السعر، يعرض خيارات: تغيير المواصفات، تقليل العمل، رفع السعر، أو المتابعة مع علم النقص.

### القرار والفعل التالي

الأفعال بالترتيب: «تعديل التكلفة»، «تعديل السعر»، «تثبيت الاتفاق»، أو «حفظ كتقدير». عند تثبيت الاتفاق، يحفظ السعر والموعد والمواصفات وSnapshot المرجعي، ولا ينشئ قبضًا إلا إذا اختار المستخدم «تسجيل عربون» كخطوة مستقلة.

### الحالات

السعر غير موجود: «أدخل سعرًا أو احفظ كتقدير». السعر تحت التكلفة المعروفة: warning واضح بلا لوم. التكلفة الناقصة: نتيجة محجوبة أو موسومة «ناقصة». تغير السعر بعد الاتفاق: Revision/تعديل اتفاق موثق، لا تعديل صامت.

### الربط

يربط `CraftOrder` و`CostSnapshot` ونتيجة السعر الوقائي المستهدفة. السعر الوقائي ليس حقلًا منفذًا في Domain Core إلا بقدر ما تسمح به العقود الحالية؛ واجهة Prototype تضعه كUse Case يجب اختباره، لا كحساب تجاري مكتمل قبل بناء عقده.

## 9. الشاشة 7 — تفاصيل التنفيذ والتكلفة

### الغرض

تتابع ما يحدث بعد الاتفاق: الحالة، الموعد، المواصفات، التكلفة المسجلة، وما يحتاج إلى تحديث قبل التسليم.

### Hero

«ما الخطوة التالية في هذا الطلب؟» مع status واحد وفعل واحد، مثل «ابدأ التنفيذ»، «حدّث التكلفة»، أو «جهز للتسليم».

### المحتوى ودرجة المعلومات

العمق **متوسط**. تظهر Timeline مختصرة: إنشاء الاتفاق، العربون إن وجد، بدء التنفيذ، تحديث التكلفة، الجاهزية، التسليم. تحتها المواصفات والموعد والمبلغ والعربون والمتبقي ودرجة النتيجة. يمكن إضافة وقت أو مادة مستخدمة للطلب إذا كان ذلك داخل Use Case Prototype، لكن لا يظهر مخزون عام أو قائمة مشتريات مستقلة.

إذا ارتفعت التكلفة أثناء التنفيذ، يعرض الفرق بين Snapshot السابق والنسخة الجديدة وما سببه، ويطلب قرارًا تجاريًا إذا أثر السعر. لا يعيد فتح طلب مسلّم أو يغير نتيجة قديمة دون تصحيح موثق.

### القرار والفعل التالي

«سجل تحديثًا»، «غيّر الحالة»، «راجع العميل/الموعد» أو «انتقل إلى التسليم». التغيير في الحالة ليس قبضًا، ولا يساوي «مكتمل ماليًا». إذا كان الطلب `needs_review`، يكون الفعل «افتح المراجعة» ولا تظهر أفعال مالية عامة قد تتجاوز الحارس.

### الحالات

مسودة، طلب جديد، متفق عليه، قيد التنفيذ، جاهز، تم التسليم، مكتمل ماليًا، ملغى مع تسوية/مراجعة، و`needs_review` وفق العقود. لا نضيف `on_hold` من عندنا. الموعد المفقود يظهر كفجوة لا كتاريخ افتراضي.

### الربط

يستخدم انتقالات `CraftOrder`، أحداث الحالة، Snapshots، وحارس ما بعد التسليم. `agreement source` وموعد التسليم يحتاجان عقد Storage/Adapter مستهدفًا.

## 10. الشاشة 8 — التسليم والتحصيل أو الدين

### الغرض

تفصل لحظة التسليم عن القبض وعن الدين، وتمنع أن ينشئ زر واحد أثرًا ماليًا غامضًا.

### Hero

«هل سلّمت الطلب؟ وماذا حدث للمبلغ المتبقي؟»

### المحتوى ودرجة المعلومات

العمق **متوسط**. قبل التسليم: عرض السعر، العربون المحصل، المتبقي، والنتيجة الحالية. بعد اختيار «تم التسليم»، تظهر ثلاثة مسارات منفصلة: «تحصيل المتبقي الآن»، «تسجيله كمبلغ مستحق»، أو «تسليم مع مراجعة». لا تظهر «كاش» باعتباره ربحًا.

العربون قبل التسليم يمر عبر `collectDeposit`. التحصيل بعد التسليم يمر عبر `collectRemaining`. الدين يمر عبر `registerDebt`. إذا كان الدفع الكامل مقدمًا، لا ينشئ النظام تحصيلًا مضللًا عند التسليم؛ ينتقل إلى نتيجة/مراجعة بحسب العقد.

### القرار والفعل التالي

الفعل الأساسي يتغير وفق اختيار المستخدم. بعد التحصيل: «راجع نتيجة الطلب». بعد الدين: «حدد موعد/ملاحظة متابعة» إذا كان هذا ضمن Adapter، ثم «راجع النتيجة». عند عربون يحتاج ردًا/احتفاظًا بسبب إلغاء، لا يخترع Prototype السياسة؛ يظهر `needs_review` أو Use Case تسوية مستقل.

### الحالات

لا يمكن التسليم إذا كانت الحالة لا تسمح. لا يمكن التحصيل مرتين بالمفتاح نفسه؛ يظهر نجاح idempotent أو رسالة أن العملية موجودة. إذا كان المتبقي صفرًا، لا تعرض زر تحصيل. إذا كان السعر أو Snapshot ناقصًا، يُسمح بالتسليم عند العقد لكن النتيجة تبقى ناقصة/تحتاج مراجعة.

### الربط

يربط `collectDeposit`, `collectRemaining`, `registerDebt`, status events، وidempotency. لا يكتب Ledger عام، ولا يساوي الدين بالكاش.

## 11. الشاشة 9 — نتيجة الطلب والفعل التالي

### الغرض

تفسر ما يعرفه النظام عن الطلب بعد التسليم أو التسوية، وتوضح للمستخدم ما الذي يفعله أو ما الذي ما زال ناقصًا.

### Hero

واحد من ثلاثة: «النتيجة معروفة وفق البيانات المدخلة»، «النتيجة تقديرية»، أو «لا يمكن إكمال النتيجة بعد؛ هذه البيانات الناقصة». لا تستخدم «ربح المشروع» أو نتيجة تراكمية في Prototype الأول.

### المحتوى ودرجة المعلومات

العمق **متوسط**. تعرض: السعر/الإيراد وفق سياسة الطلب، التكلفة المعروفة، ما هو مقدر، العربون والتحصيل والدين، `resultStatus`، وملخص سبب النتيجة. يمكن فتح التفاصيل لرؤية بنود Snapshot والتغييرات، لكن لا يغرق المستخدم في قيود أو جداول.

إذا كانت النتيجة سلبية بسبب مادة أو توصيل أو وقت معروف، يُذكر السبب. إذا كانت البيانات ناقصة، يقال ما الذي ينقص وما الذي سيتغير عند إدخاله. لا يقال «خسرت» من دون فترة وسياسة ودرجة معرفة.

### القرار والفعل التالي

فعل واحد: «أكمل البيانات»، «راجع السعر للطلبات القادمة»، «تابع التحصيل»، أو «أنشئ نسخة منتج مخطط». لا توجد قائمة تنبيهات طويلة. يمكن للمستخدم الرجوع إلى الطلب، تصدير بياناته، أو بدء طلب جديد.

### الحالات

`known`, `estimated`, `incomplete`, `needs_review` تظهر كنصوص مفهومة. بعد تعديل غير مسموح بسبب التسليم، يُعرض سبب الحجب ومسار التصحيح المؤجل. إذا لم يوجد Snapshot، لا توجد نتيجة مالية مصطنعة.

### الربط

يستخدم `CraftOrder.resultStatus` والحقول الأولية على مستوى الطلب. لا يمثل هذا الشاشة Ledger أو P&L أو تقريرًا تراكميًا.

## 12. الشاشة 10 — الإعدادات والنسخ المحلي

### الغرض

تحمي بيانات Prototype وتوفر التصدير والاستيراد وإعادة الضبط المنضبطة، دون إدخال SaaS أو Cloud إلى تجربة محلية.

### Hero

«بياناتك محلية في هذا Prototype — صدّر نسخة قبل تغيير الجهاز أو إعادة الضبط.»

### المحتوى ودرجة المعلومات

العمق **منخفض إلى متوسط**. تعرض فقط: اسم النشاط/العملة، تصدير، استيراد، حالة آخر تصدير، تحقق من نسخة الملف، إعادة ضبط محمية، وبيان الخصوصية. يمكن إظهار hide amounts كعنصر مستهدف P1 إذا اكتمل عقد PIN، لا كميزة شكلية غير مختبرة.

قبل الاستيراد، يقرأ Adapter الملف ويتحقق من schema/version والبيانات المطلوبة، ثم يعرض ملخصًا: عدد الطلبات، Snapshots، الأحداث، وتاريخ التصدير. لا يمسح البيانات الحالية قبل نجاح التحقق والتأكيد. يُفضّل إنشاء نسخة احتياطية تلقائية من الوضع الحالي قبل restore إن أمكن.

### القرار والفعل التالي

«تصدير الآن»، «اختيار ملف للاستيراد»، أو «إلغاء». إعادة الضبط تحتاج كتابة عبارة تأكيد أو تأكيدًا مزدوجًا، وتذكر أن العملية تحذف البيانات المحلية. لا توجد Google Drive أو مزامنة أو تسجيل دخول.

### الحالات

ملف ناقص أو قديم، JSON غير صالح، schema غير معروف، استيراد ناجح، استيراد فاشل دون فقد، تنزيل محجوب، أو مساحة تخزين غير متاحة. كل حالة تذكر هل بقيت البيانات الحالية كما هي.

### الربط

هذه الشاشة عقد Adapter/LocalStore/export/import، وليست Domain Core. يجب أن يمر الاستيراد باختبار round-trip واختبارات رفض الملف الجزئي قبل اعتبار Prototype صالحًا لبيانات المستخدمين.

## 13. مسار قرار نموذجي من البداية إلى النهاية

### حالة: قطعة خشبية مخصصة

1. تفتح ليان «مشروعي الآن» وتختار «طلب جديد».
2. تدخل وصف القطعة والكمية والموعد والسعر المقترح، وتحفظ اتفاقًا أوليًا.
3. تضيف الخشب والطلاء والتغليف ووقت العمل والتوصيل. إذا لم تعرف الوقت، تختار «غير متأكدة» بدل صفر.
4. ترى أن التكلفة المعروفة أقل من السعر، لكن النتيجة تقديرية بسبب الوقت والهدر. تعدل السعر أو تثبت الاتفاق مع وسم واضح.
5. تسجل عربونًا، فتزيد حركة الكاش المرتبط بالطلب ولا يظهر ربحًا نهائيًا.
6. تبدأ التنفيذ وتحدث Snapshot إذا تغيرت مادة أو وقت، مع بقاء النسخة السابقة.
7. تسجل التسليم، ثم تختار تحصيل المتبقي أو تسجيله كدين.
8. ترى نتيجة الطلب بدرجة معرفة وتفسيرًا: ما هو معروف، ما هو مقدر، وما الفعل التالي.
9. تصدر نسخة محلية بعد إنهاء الجولة أو قبل تجربة تغيير جديد.

### حالة: يوم بلا طلب

تفتح ليان «مشروعي الآن». لا تعرض الشاشة «لا يوجد طلب» فقط؛ تعرض أن الصورة الحالية فيها مصروف أو التزام أو Snapshot ناقص، وتقودها إلى تسجيل الحدث أو مراجعة طلب قديم. لا تنشئ شاشة Dashboard محاسبية عامة في Prototype لتعويض غياب البيع.

### حالة: مصروف شراء خامات

تبدأ من FAB وتختار «شراء/مصروف». يسأل النظام هل الخامات مرتبطة بطلب أم ستبقى للمخزون. إذا لم يوجد Inventory عام في Prototype، يحفظ العلاقة كبيان تكلفة/ملاحظة أو يضعها «تحتاج مراجعة»، ولا يدعي كمية مخزون عامة أو ربحًا متغيرًا على كل الطلبات.

## 15. ما هو غائب عمدًا

هذه العناصر ليست نسيانًا، بل حدود Prototype: Auth، Roles، Permissions، Workspace تجاري، Supabase، RLS، Billing، Cloud Sync، Google Drive، full offline sync، Ledger عام، P&L تراكمي، Break-even عام، Inventory عام، BOM عام، POS، CRM، Food Profiles، Service Profiles، AI، إشعارات خلفية مضمونة، recurring events، owner draw كعقد كامل، وshared expenses كسياسة كاملة. تُحفظ الرؤية في وثائق Micro، لكنها لا تظهر في Prototype حتى يثبت المسار الأول قيمته وتُبنى عقودها.

كذلك لا تعرض الواجهة «التكلفة الفعلية المطلقة» أو «الربح منذ فتح المشروع» أو «الأكثر ربحًا» قبل وجود سجل مالي ومخزون ووقت وسياسات كافية. المصطلح الدقيق في هذه المرحلة هو: تكلفة معروفة/مقدرة/ناقصة، ونتيجة طلب بدرجة معرفة.

## 16. بنية البناء المطلوبة خلف Prototype

يُبنى Prototype بطبقات منفصلة:

```text
RTL UI
  ↓
Use-case/application adapters
  ↓
Micro Domain Core
  ↓
LocalStore Port
  ↓
IndexedDB أو تخزين محلي معزول
  ↘ local export/import adapter
```

الواجهة لا تستورد Dexie مباشرة، ولا تضع قواعد المال في React component. كل فعل حساس يستدعي Use Case يحقق preconditions، ويعيد نتيجة قابلة للعرض، ويضع `idempotencyKey`. LocalStore يحتفظ بالمسودات والأحداث وSnapshots دون تغيير الماضي. Export/import يملك schema version وvalidation وround-trip tests.

## 17. معيار قبول Prototype

### 17.1 معيار المنتج

ينجح Prototype إذا استطاع مستخدم واحد إكمال المسار من طلب مخصص إلى نتيجة طلب، واستطاع أن يشرح بلسانه: ماذا حدث، ما أثره، وما الذي يفعله الآن. ينجح أيضًا إذا عاد في يوم بلا طلب ليجد صورة مفيدة، لا رسالة فراغ فقط.

### 17.2 معيار المال

لا يظهر العربون أو التحصيل أو الدين أو التسليم بمعنى واحد. لا تستخدم التكلفة الناقصة في ربح نهائي، ولا تغير Revision سجلًا سابقًا بصمت، ولا يتكرر الأثر عند إعادة الضغط، ولا يسمح الحارس بعملية ممنوعة بعد `needs_review`.

### 17.3 معيار الهاتف

كل شاشة أساسية تعمل على 360px و390px و430px، والزر الأساسي لا يختفي فوق keyboard، وBottom Sheet يغلق بالرجوع دون فقد المسودة، والـtargets مناسبة للإبهام، وRTL لا يقطع أسماء الحقول أو الأفعال. يُختبر على جهاز/viewport حقيقي، لا عبر zoom أو DOM manipulation.

### 17.4 معيار التخزين

ينجح export ثم import في إعادة الحالة نفسها، ويُرفض الملف الناقص أو القديم قبل مسح البيانات الحالية، ويظهر الخطأ للمستخدم، وتوجد اختبارات فشل التخزين وإعادة المحاولة. لا يدخل مستخدم حقيقي قبل ذلك.

3. تُنفذ الشاشة 10 مع LocalStore قبل إدخال بيانات مستخدمين حقيقية، حتى لو كان الاستخدام single-user.
4. تُبنى أفعال «تسجيل مصروف/شراء» كمدخل مساعد محدود فقط لا كوحدة Accounting مستقلة؛ وتُختبر على مصروف مرتبط بطلب وشراء خامات لمخزون غير منفذ.
5. تُراجع كل واجهة مقابل [`mobile-ui-ux-reference-v1.md`](../product/mobile-ui-ux-reference-v1.md) ومقابل [`02-domain-contract-coverage.md`](02-domain-contract-coverage.md) قبل الدمج.
6. بعد أول تنفيذ، يجب تشغيل سيناريوهات P01 كاملة ثم عينة من P02–P10؛ لا يكفي نجاح مسار ليان أو طلب واحد.
7. أي إضافة مثل Inventory أو Break-even أو SaaS تحتاج عقدًا مستقلًا، قرارًا في سجل القرارات، واختبارات قبل دخول Prototype.
