# البرنامج والسلطة والقرارات

## 1. النطاق الثابت

إصلاح كل المشكلات المعروفة التقنية وغير التقنية: النصوص والمصطلحات وكثافة المحتوى، تركيب الصفحات والتناسب والتفاعل، المداخل والرجوع، جاهزية الرئيسية، أداء مثبت، اكتمال السجل، الاستيراد/الاستعادة والتخزين والإتاحة والتوثيق. لا تعني هذه العبارة وعدًا باكتشاف كل عيب مجهول أو تنفيذ تحسين غير مثبت.

الهاتف أولًا؛ العربية RTL، أرقام 0–9، العملة د.أ. نطاق التصميم الحالي Light. تبقى قدرات المخزون والجهات اختيارية، ولا يفرض عميل أو مورد في بيع/شراء لا يحتاجهما العقد. لا Auth أو Cloud أو Sync أو AI أو قروض أو مشاركة أو PIN جديد. التوصيل والسوق يبقيان وفق القرار الحالي دون توسع هنا.

## 2. سلطة هذه الحزمة والاختلافات المحسومة

هذه تعليمات تحسين عرض وسلوك مقترحة للتنفيذ بعد مراجعة مانوس ونشر الأمر. لا تعيد تعريف الحساب المالي أو قواعد البيانات. `AGENTS.md` هو جدول القراءة وسلّم السلطة الوحيد؛ لا تصنع الحزمة سلّمًا بديلًا. يحتفظ كل UNIT بمعرفه ومالكيه. يربط سجل التنفيذ كل تعديل بعقده و UNIT الأصلي، ويثبت ما يحل محله من تعليمات العرض فقط.

| القرار | التوجيه الصريح | ما يمنع الخطأ |
|---|---|---|
| UXR-D01 | تحسين تركيب المنتج قبل استبدال الألوان أو primitives | وجود مكتبة مستقلة لا يثبت دمجها؛ لا استيراد Showcase أو fixtures |
| UXR-D02 | مصدر القيم البصرية الحية هو الجسر المعتمد في `styles/vf-tokens.css` والعقود القائمة إلى أن يعتمد تكامل جديد | الألوان والخط في المعاينة توضيحية؛ لا يُنسخ teal أو IBM أو قياس خام إلى المنتج بمجرد ظهوره هنا |
| UXR-D03 | لا إعادة تصميم Dark ضمن هذا العمل؛ إن كان موجودًا كما تصف ADR-009، يحفظ ويفحص كعدم تراجع | لا حذف له ولا تغيير إعداد المستخدم بناءً على وصف قديم بأنه غير موجود |
| UXR-D04 | «نتيجة الفترة المسجلة» لا تقتصر على الطلبات | تصحيح ادعاء المصدر أن سعر/تكلفة الطلبات وحدهما مكونا نتيجة المشروع |
| UXR-D05 | `activatedOn` = «متابعة المخزون منذ …» | يرفض N13/DEC-INV-01 «آخر جرد مؤكد»؛ لا اختراع تاريخ جرد |
| UXR-D06 | النقد المسجل ≠ النقد الفعلي، والتحصيل ≠ الربح | لا تعويض نقص معرفة بصفر أو يقين |
| UXR-D07 | العربية المبسطة المهنية هي نبرة هذه الجولة | لا «دفتر الناس»، ولا ترجمة حرفية للمعمارية، ولا قلب «لك/عليك»؛ لا فرض عامية |
| UXR-D08 | نحفظ معنى الإفصاح وشرط ظهوره لا طول عبارته حرفيًا | يلغى اشتراط إبقاء كل فقرة حماية كما هي؛ يحفظ الأثر المالي والإجراء اللازم |
| UXR-D09 | المصروف مدخل واحد واضح يحدد حالة الدفع قبل الحفظ | يعاد استخدام محرري المدفوع/المستحق ودفعاتهما؛ لا تحويل تلقائي لمدفوع، ولا كاتب ثالث |
| UXR-D10 | لا حذف مدخل متكرر بناءً على تطابق URL فقط | اختلاف النطاق أو النية أو دور الجهة قد يبرر الاختصار السياقي |
| UXR-D11 | فهرس المالية يفتح الوظيفة المختارة؛ لا قائمة دائمة من 5 أكورديونات في الجذر | يحدّث DEC-FIN القديمة في العرض فقط، دون حذف قدرات |
| UXR-D12 | فشل أتمتة حقل التاريخ فرضية لا حكم بفساد المنتقي | يعاد إنتاج العيب على جهاز/متصفح مناسب أولًا |
| UXR-D13 | تعويض القاع موجود؛ يُفحص مالك التمرير والتركيز | لا إضافة فراغ عام آخر، ولا قبول قياس «70px محجوب من زر 48px» دون حساب تقاطع |
| UXR-D14 | انتظار الرئيسية قد ينتهي؛ السببية تحتاج تتبعًا | لا تعميم تعليق دائم، ولا eager لكل الخدمات أو تأخير ثابت أو كتابة مالية لتجهيز الصفحة |
| UXR-D15 | إبقاء تنقل المالية/الطلبات/الرئيسية/التوصيل/السوق | لا فتح قرار السوق والتوصيل مجددًا ضمن تحسين المحتوى |
| UXR-D16 | لا حدود اعتباطية لعدد الكلمات أو ارتفاع الصفحة أو مهلة تحميل مصطنعة | يقارن قبل/بعد بالمهام والبيانات والبيئة نفسها |
| UXR-D17 | بلوغ حد القراءة لا يثبت وحده وجود المزيد | لا شارة «بقيت عمليات» بلا hasMore أو دليل استعلام |
| UXR-D18 | كل نمط أداء مسجل يقاس ويصلح أو يغلق بدليل | لا إهمال P3 ولا فهرس/schema أو debounce بمجرد توصية التقرير |

**الخطوط:** فحص الخط الفعلي والأوزان والتكلفة في UXR-02. الاختيار الموافق للهوية لا يزال منفصلًا عن قرار حذف خط fallback. إن تطلب العلاج تكامل نظام UI المستقل أو تغيير tokens، يُسلّم تعارض تكامل محدد، ويستمر إصلاح التركيب الذي لا يعتمد عليه. لا يعيد المنفذ تصميم الهوية بنفسه.

## 3. المراحل والتبعيات

9 دفعات مرقمة UXR-00..UXR-08؛ أولها توثيقية، و 8 بعدها للتنفيذ والتحقق. ليست إعادة ترقيم S01–S18 ولا R0–R10 القديمين.

| الدفعة | النتيجة | بيت العمل | التبعية ونوعها |
|---|---|---|---|
| UXR-00 | نشر الحزمة، مصالحة main/Control، Claim وخريطة السلطة، مراجعة أمر 01 | تنسيق مانوس؛ لا كود منتج | مصدر توثيقي وبوابة تسليم |
| UXR-01 | إقلاع الرئيسية والتجهيز والفشل وإعادة المحاولة | السياق وتجهيز الخدمات و Home | تسلسل البرنامج بعد UXR-00؛ ليس عقد API |
| UXR-02 | قشرة متسقة، تركيز وقاع آمن، أنماط إدخال/قائمة/إفصاح، قرار خط قائم قابل للتبرير | shell/primitives/navigation/styles؛ لا إعادة هوية | تسلسل البرنامج بعد UXR-01؛ يسبق أي كود حسم مرجع التصميم/الثيم |
| UXR-03 | المالية والطلبات والرئيسية بصورتها المختصرة ومداخلها السليمة | الصفحات الثلاث ولوحة المالية والتقويم؛ إصلاح المصروف من جميع مداخله | تسلسل البرنامج بعد UXR-02؛ قد يعتمد فنيًا على مكونات مثبتة عند بدء الأمر |
| UXR-04 | النماذج والعمليات وتفاصيل الطلب والنقد والجهات والمشتريات والتكرار | عائلات العمليات، تسليمات داخلية منفصلة | تسلسل البرنامج بعد UXR-03؛ التبعية الفنية تثبت عند كل أمر |
| UXR-05 | القراءات والكشوف والسجل والمخزون والأصول والأدوات | مصدر السجل مع واجهته؛ باقي القارئات والعائلات | تسلسل البرنامج بعد UXR-04؛ التبعية الفنية تثبت عند كل أمر |
| UXR-06 | الإعدادات والبداية والاستكمال والنسخ والاستعادة والحجم والحصة | Settings/Foundation/Setup/Profile وخدمات النقل | تسلسل البرنامج بعد UXR-05؛ الضوابط المالية محفوظة |
| UXR-07 | علاج عنق أداء مثبت دون قِدم أرقام أو ضياع مسودة | القراءات/الكتابات/المسودات/التسليم حسب القياس | تسلسل البرنامج بعد UXR-06؛ قياس الأساس يبدأ في كل دفعة |
| UXR-08 | قبول تكاملي، مراجعة ختامية، مصالحة توثيق وأدلة انتقال/دمج | كل الرحلات والهواتف والـ Control | تسلسل البرنامج بعد UXR-07؛ لا يغلق عائق جهاز غير مختبر |

يمتلك كل finding دفعة أساسية واحدة؛ إعادة الاختبار لاحقًا لا تعني إصلاحه مرتين. تعديل Home في 01 للتجهيز ثم 03 للعرض مبرر باختلاف المسؤولية، لا يكرر إصلاح السبب. تجمع الملفات المشتركة داخل الدفعة، ولا يكتب وكيلان في العقد أو المساحة نفسها.

دفعات UXR-04 الداخلية: (1) الطلبات وتفاصيلها، (2) النقد ومال المالك، (3) الشراء/الجهات/المتكرر. لكل تسليم commit وأدلته وفحوصه وحد رجوعه؛ كاتب واحد متتابع، ولا تبدأ الدفعة التالية قبل تحقق الجزء الحالي. هذه حدود إدارة داخل UXR-04 وليست مراحل أو Claims جديدة. تبعيات الجدول ترتيب برنامج غالبًا لا اعتماد API؛ يثبت الأمر الفعلي عند البدء.

## 3-أ. بوابة الهيكلة والثيم

قبل أي عمل هيكلي، استخدم تقرير مسح S11 الشامل وخط أساسه، وافحص الفروق المرتبطة فقط؛ S-1..S-5 تبقى غير منفذة. لا نقل ملفات أو تقسيمها أو تنظيم واسع. إذا كشف التنفيذ حاجة هيكلية غير محسومة في التقرير، أوقف ذلك التغيير وقدّم مسحًا تكميليًا محددًا ومخاطر وحدود رجوع، ثم انتظر قرار المالك الصريح. يبقى ADR-009 وسلوك الثيم الحالي كما هما؛ تحسم سلطة مرجع الهوية قبل UXR-02، ولا تعطل UXR-01.

## 4. فرع البرنامج والأدوار

- فرع تكامل جديد واحد من `origin/main` الحي عند بدء هذا البرنامج؛ اسم مقترح `uxr/integration-20261105`، يثبته مانوس بعد فحص الفروع والـ Claims. لا يُعاد فتح الفرع القديم أو حذفه أو الكتابة فيه بالافتراض.
- commits متميزة لكل دفعة وتصحيحاته؛ لا force-push أو rebase للتاريخ المسلم؛ لا دمج إلى main بين الدفعات. PR Draft واحدة للبرنامج إن أجاز المسار الحي ذلك.
- المالك: قرارات الأعمال والانتقال والدمج؛ Manus: التنسيق وكتابة الأوامر والمراجعة المستقلة الخفيفة؛ ZAI: كاتب كود المنتج الوحيد والاختبارات والأدلة. ChatGPT غير مطلوب كشرط أو بوابة.
- أمر كل دفعة مستقل، يحمل الروابط/المسارات والرؤوس وشروط القبول ولا يتطلب المحادثة السابقة أو Drive. **الأمر الوحيد المكتوب الآن هو مسودة UXR-01**؛ الأوامر اللاحقة تكتب عند وصولها لكي تستخدم الرأس الفعلي والأدلة السابقة.
- نراجع نحن ومانوس نفس candidate SHA. نجاح CI لا يعني قبولًا بصريًا، ولا قبول فرع يعني VERIFIED على main.
- Operations Control يحتفظ بالحالة الرسمية. Tracker الحزمة مرآة مع إحالات؛ لا يعدل generated يدويًا، ولا ينشئ ZAI tracker منافسًا.

## 5. بوابة القرار

التوجيهات أعلاه توصية محددة تحت نطاق الإصلاح المفوض. لا نعيد سؤال المالك عن العبارات والأحجام الروتينية. يظهر قرار مالك جديد فقط إن تغير معنى مالي/سياسة/نطاق أو تعذر حل تعارض سلطة. مراجعة مانوس للحزمة ليست تحليل نظام جديدًا؛ هي فحص أن خطة التنفيذ مطابقة وأن حواجز المستودع والمراجع متسقة.


## 6. دليل كل دفعة

كل دفعة تسلّم مقارنة بصرية قبل/بعد للسطح المتغير وقياسًا أداءً للرحلة المتأثرة متى انطبق، أو سبب عدم الانطباق. لا تؤجل هذه الأدلة إلى UXR-07/08. تلتزم جميع الدفعات ببوابة الهيكلة في §3-أ؛ لا نقل أو تقسيم أو تنظيم ملفات دون تقرير وقرار مالك محدد.
