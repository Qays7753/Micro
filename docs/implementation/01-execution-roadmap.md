# خارطة التنفيذ المرحلية

## الهدف

تحويل Micro من مرجع قرار إلى إثبات قابل للتشغيل دون بناء SaaS كامل أو إدخال بيانات حقيقية قبل اجتياز بوابات المجال والأمان والاستعادة.

## المرحلة 0 — تثبيت القرار

**المدخل:** `docs/decisions/01-first-vertical-slice.md` والعقود الأربعة في `docs/contracts/`.

**مخرج القبول:** مواصفة الحرفة المخصصة، حالات الطلب، قواعد التكلفة والنتيجة، ونطاق المزامنة مكتوبة ومراجعة.

## المرحلة 0.5 — تثبيت تعريف النظام والسيناريوهات

قبل تصميم الواجهة التالية، يجب تثبيت الوثائق canonical في `docs/product/` و`docs/scenarios/` و`docs/quality/`، وربطها بالمرجع الأساسي والفهرس وسجل القرارات والمهارات. يجب أن تكون Problem Statement، System Definition، User Operating Model، Financial Operating Model، Guidance Policy، مجموعة الشخصيات العشر، الحالات المئة، الأسئلة المئة، ومصفوفة التغطية متوافقة.

**بوابة القبول:** يستطيع شخص جديد فهم المشكلة، المستخدم، قيمة النظام، الاستخدام اليومي والأسبوعي والشهري، المعالجة المالية، حدود التوجيه، وأول Vertical Slice. تنجح الوثائق في وصف حالات يوم الطلب ويوم بلا طلب والشراء والمصروف والمخزون والربح والكاش والذمم ونقطة التعادل، دون ادعاء أن التطبيق التجاري جاهز.

## المرحلة 0.75 — بوابة ما قبل البناء والمحاكاة

هذه بوابة تنفيذية قصيرة تسبق كتابة Adapter أو واجهة. مخرجها هو تعريف Prototype المرحلة 2، وسياسات P0 المالية، وحالات مالية مرجعية بنتائج متوقعة، ونصوص التوجيه لمسار الحرفة، وبروتوكول اختبار مستخدم. لا تضيف هذه البوابة ميزات أو كودًا؛ هدفها إزالة الالتباس واكتشاف أخطاء النموذج قبل أن تصبح شاشة أو قاعدة بيانات.

**تعريف Prototype المرحلة 2:** نموذج هاتف RTL محلي محدود يثبت مسار الحرفة المخصصة من التكلفة إلى السعر والطلب والموعد والعربون والتنفيذ والتسليم والتحصيل أو الدين والنتيجة وفعل تالٍ. لا يثبت SaaS أو Auth أو Supabase أو RLS أو Ledger ماليًا عامًا أو Pilot تجاريًا.

**بوابة الخروج:** تنجح الحالات المالية المرجعية دون خلط الربح بالكاش أو العربون بالدخل النهائي أو شراء المخزون بالتكلفة المستهلكة، وتكون نصوص التوجيه قابلة للفهم، ويستطيع مستخدم حقيقي في اختبار محدود إنجاز المسار أو تظهر فجواته بوضوح قبل بدء الكود.

## المرحلة 1 — Domain Core

يبنى منطق مستقل عن React والتخزين والمزود، ويغطي:

- المال بوحدة نقدية ثابتة وسياسة تقريب.
- تكلفة الخامات والوقت والتغليف والتوصيل والهدر.
- حالات معرفة التكلفة ونسخة التكلفة، بما فيها `incomplete` و`stale` عند وجود سياسة حداثة صريحة.
- دورة الطلب وانتقالاته وسجل الأحداث.
- العربون والمتبقي والقبض والدين دون خلط الربح بالكاش.
- `resultStatus` الذي يمنع اعتبار مؤشر النتيجة ربحًا نهائيًا عندما لا تكون التكلفة `known`.
- إلغاء آمن يبدأ بـ`needs_review` عند وجود عربون، وتسوية رد أو احتفاظ مستقلة قابلة لإعادة المحاولة.
- التخصيص والتعديل بعد الاتفاق.
- `idempotency_key` للأحداث القابلة لإعادة المحاولة.

**بوابة القبول:** اختبارات Domain تمر على الحالات الطبيعية والناقصة والصعبة، بما فيها عدم اعتبار Snapshot بلا مكونات مؤثرة `known`، وعدم إظهار ربح نهائي مع تكلفة غير معروفة، وتسوية العربون بعد الإلغاء، دون واجهة أو قاعدة بيانات.

**حالة البوابة:** أُغلقت فجوات النواة والعقود في Foundation الحالي. هذا لا يعني أن التطبيق أو التخزين أو العزل أو Pilot بُني؛ يعني فقط أن Domain Core قابل للانتقال إلى Prototype الهاتف وفق الحدود أدناه.

## المرحلة 2 — Prototype محلي: Adapter وواجهة الهاتف

لا تبدأ هذه المرحلة إلا بعد إغلاق بوابة المرحلة 0.5 وبوابة 0.75. تضاف طبقة تخزين محلية بسيطة، ثم واجهة هاتف لمسار واحد:

```text
إنشاء قطعة → إدخال خامات ووقت → فهم التكلفة → اعتماد سعر
→ تسجيل اتفاق وموعد → عربون اختياري → تنفيذ → تسليم
→ قبض/دين → نتيجة وفعل تالٍ
```

لا يُضاف Auth أو Supabase أو مخزون متقدم في هذه المرحلة. الهدف هو قياس الفهم والإنجاز لا إثبات البنية التجارية.

**بوابة القبول:** مستخدم غير محاسبي ينجز المسار ويرى درجة معرفة النتيجة والفعل التالي على شاشة RTL ضيقة.

## المرحلة 3 — Profile ثانٍ

بعد نجاح الحرفة فقط، نختبر العقد العام على الطعام أو الخدمات. يضاف ما يخص القطاع فقط:

- الطعام: الوصفة، الدفعة، الحصص، وتحويل الوحدات.
- الخدمات: المدة، التوفر، التعارض، وقائمة الإتمام.

إذا كسر القطاع معنى التكلفة أو الطلب، نراجع العقد بدل إضافة استثناءات صامتة.

## المرحلة 4 — SaaS foundation

بعد إثبات القيمة السلوكية، تضاف الهوية وWorkspace وRLS ونسخ/تصدير/استعادة، ثم مزامنة محدودة وفق العقد. لا تدخل بيانات Pilot الحقيقية قبل اختبار العزل والاستعادة.

## المرحلة 5 — Pilot

يُجرى Pilot محدود بقياسات واضحة: زمن أول قيمة، إكمال أول تكلفة، زمن تسجيل الطلب، فهم الربح مقابل الكاش، إتمام الفعل التالي، العودة في اليوم 7 و14 و30، وعدد القرارات التي تغيرت بسبب المنتج.

## المرحلة 6 — قرار تجاري

بعد Pilot فقط نقرر مزود الإنتاج، المزامنة الأوسع، الانتقالات بين حالات entitlement، Billing، السعر، الدعم، والتوسع. لا يُعتبر دينار واحد شهريًا سعرًا معتمدًا قبل معرفة تكلفة التشغيل والاستعداد للدفع.

## ممنوعات التنفيذ

لا نضيف نظام محاسبة مؤسسي، POS، CRM، WhatsApp automation، تعدد فروع، صلاحيات كاملة، AI، أو تقارير متقدمة في أي مرحلة قبل دليل مستقل يبررها.
