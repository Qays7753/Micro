## 1. السلوك المؤكد قبل الإصلاح

تأكيد «من تحمّل الباقي» للفاتورة المشتركة كان قائمًا كقيمة منطقية بلا ربط بقيمة: النية في الواجهة لا تحمل الزوج (الحصة+المدفوع) لحظة التأكيد، وحد الكتابة `recordSharedBillExpense` لا يعرف مفهوم تأكيد أصلًا. أي تغيير في حصة المشروع أو المبلغ المدفوع (أو أي مدخل يغيّر قيمة الجزء الشخصي المشتقة) بعد التأكيد وقبل الحفظ يبقي التأكيد قائمًا، فيُكتب سحب مالك جديد بجمهور تأكيد قديم. الاستغلال الحي أُثبت بمسبار مركّز: تغيير الحصة بعد تأكيد 30/60 كان يمر إلى الكتابة بلا إعادة طلب.

## 2. الإصلاح الجذري (لا حل واجهة)

1. **الزوج الكنوني مصدر واحد:** `expandExpenseRecordIntent` (وحدة النية الكنسية `expenseRecordIntent.ts`) تصدّر زوج `(shareAmountMinor, paidAmountMinor)` مجمّدًا مع مطابقة حتمية — `sharedBillOwnerPartConfirmationOf` — لا حسابًا ثانيًا في React إطلاقًا؛ الواجهة والحد يستهلكان الاشتقاق نفسه.
2. **الإبطال قبل الكتابة:** صندوق التأكيد يتبع `matchesSharedBillOwnerPartConfirmation(ownerPartConfirmedFor, currentPair)` — أي تغيير في الحصة/المدفوع يغيّر الزوج الحي فيصبح التأكيد غير مطابق ويُعاد طلبه بالقيم الجديدة تلقائيًا.
3. **الرفض عند الحد حتى مع تجاوز الواجهة:** `recordSharedBillExpense` يشتق الزوج المطلوب من النية نفسها ويرفض القيمة المتغيرة غير المؤكدة قبل أي كتابة؛ المسار العام `record` يرفض نية «مدفوع فوق الحصة» بلا كاتب الفاتورة المشتركة؛ ومسار تأكيد دورة المصروف المتكرر يرفضها كذلك عند كاتبه.
4. **المسار بلا جزء شخصي غير مثقل:** حين لا يوجب المدخلات جزء مالك، لا يُطلب أي تأكيد جديد — كما كان.
5. **المحفوظ كما هو:** `paidAmountMinor` والكاتب الكنوني والإيدمبوتنسي والنتيجة الجزئية/المجهولة وأسبقية الرفض ودلالة المصروف/السحب — بلا تغيير مالي أو محاسبي.
