## 4. Scope

### 4.1 UNIT-042 — إلغاء القفل وPIN

- Remove the application lock cover, idle timers, lock configuration, PIN setup/change/disable flows, PIN gates, and lock-only session state from their actual consumers.
- Remove the dependency on `local-security` only where the inventory proves it is lock-specific. Migrate or retire obsolete lock-only records with a known outcome.
- Do not delete business data, identities, profiles, transactions, drafts, financial guards, or independent integrity/encryption behavior.
- Do not replace PIN with fingerprint, device code, account login, cloud auth, roles, or any other in-app security product.
- Keep explicit confirmation, file validation, integrity checks, rollback protection, concurrency protection, and ordinary error handling where they protect against data loss rather than against a user identity.
- A previously enabled lock must not block startup, restore, or return after the change. An old pending gated action must not execute automatically after refresh, migration, or navigation; it requires a new explicit intent and confirmation.

### 4.2 UNIT-044 — النسخ الاحتياطي والاستعادة

- Keep one clear settings entry for backup and restore; do not create a parallel screen or a cloud-sync/account flow.
- Backup must read a consistent snapshot, validate it, and distinguish preparing a file from a platform-confirmed save. A browser `link.click()` is not proof that the user retained the file.
- Restore must select one file, perform no write on selection, validate schema/export version and all applicable families/relationships/knowledge/coverage, show a review, and require one confirmation tied to the same file and current revision.
- Before destructive replacement, create and durably verify a rollback copy outside the replacement boundary. Do not start replacement if that protection is not proven.
- Replace the supported snapshot atomically as one bounded operation. Do not merge files, replay business events, create new sales/collections/opening balances, or perform partial writes.
- Advance the local generation and isolate or clear affected form drafts in the same contract where required. An old command must be rejected after the generation changes even if `projectId` is unchanged.
- Preserve the current state completely on invalid, unsupported, cancelled, quota-exhausted, late-failure, or unknown-outcome paths. Resolve unknown outcomes explicitly; do not report false success.
- Keep `localSchemaVersion=38` and `localExportVersion=30` unless a real contract change is proven. If a schema/export/import/migration change is genuinely required, update the paired Memory/IndexedDB adapters, migrations, import/export wire contract, compatibility fixtures, counters, and guards in the same wave, with an explicit before/after evidence table. Never raise a version or weaken a guard merely to make a test pass.
