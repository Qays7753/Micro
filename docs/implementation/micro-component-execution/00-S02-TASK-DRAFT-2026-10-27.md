- Remove the application lock cover, idle timers, lock configuration, PIN setup/change/disable flows, PIN gates, and lock-only session state from their actual consumers.

### 4.2 UNIT-044 — النسخ الاحتياطي والاستعادة

- Keep one clear settings entry for backup and restore; do not create a parallel screen or a cloud-sync/account flow.
- Backup must read a consistent snapshot, validate it, and distinguish preparing a file from a platform-confirmed save. A browser `link.click()` is not proof that the user retained the file.
- Restore must select one file, perform no write on selection, validate schema/export version and all applicable families/relationships/knowledge/coverage, show a review, and require one confirmation tied to the same file and current revision.
- Before destructive replacement, create and durably verify a consistent rollback copy outside the database being replaced, or use an equivalent recovery mechanism whose independence from the destructive boundary and survival of reload/crash are proven. Another object store that the same database replacement deletes is not sufficient, and neither an in-memory object nor download.click() proves recovery. Do not start replacement unless the chosen protection is proven.
- Replace the supported snapshot atomically as one bounded operation. Do not merge files, replay business events, create new sales/collections/opening balances, or perform partial writes.
- Replace all supported business snapshot families, clear/invalidate the active old-generation form drafts, and issue the new local generation within the same atomic replacement boundary. Before that boundary, preserve existing transient drafts with the protected old state and provide a compatible recovery path as required by UNIT-044 B6/C; do not silently lose them. Saved business order drafts remain snapshot business records, distinct from transient form drafts. After replacement, an old command must be rejected even if `projectId` is unchanged. The local generation is not imported from a file or restored as an old form authorization.
- Distinguish outcomes: rejection/cancellation before commitment performs no business write; a confirmed aborted transaction leaves the complete previous state; a confirmed committed transaction yields the complete new state, never a mixture. When the outcome is unknown after interruption, retain the same intent, inspect the durable replacement marker/generation/receipt, and block a new replacement intent until resolved. Do not claim that nothing changed, retry blindly, restore the old state automatically, or create a new commandId merely because a response timed out. A failed optional post-restore diagnostic is separate from the successful replacement.
- Treat `localSchemaVersion=38`, `localExportVersion=30`, and the existing protected import/export contract as guarded baselines. Approval of this task does not authorize their alteration. If a change to a protected number or wire contract is required, stop before implementing it and submit the concrete before/after representation, affected families, paired Memory/IndexedDB adapters, migrations, export/import compatibility, fixtures, counters, guards, and recovery plan for explicit owner authorization. After that specific authorization, implement its complete touchpoints in the same affected slice; do not defer data portability to S17 or weaken a guard to pass.
