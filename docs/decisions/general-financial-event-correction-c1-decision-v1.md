# قرار C1 — حدود تصحيح الأحداث المالية العامة

**القرار:** توثيق عقد تصحيح قابل للمراجعة، مع عدم تنفيذ أي زر عكس أو تعديل أو مسار مالي جديد في هذه المرحلة.

## سبب القرار

يملك Micro حاليًا أحداثًا عامة منفصلة عن الطلبات، مع قواعد واضحة للكاش والالتزام ومال المالك والمصروف، لكنه لا يملك في Prototype شاشة تعديل أو حذف لحدث حساس. بناء وظيفة تصحيح قبل حسم علاقة الأصل بالتصحيح، وأثر التصحيح على نتيجة الفترة، وسلوك التسوية وإعادة المحاولة، قد يحول الخطأ إلى حذف تاريخي أو مضاعفة كاش أو التباس بين المصروف والالتزام. لذلك تكون مخرجات C1 عقدًا واقتراحًا وقائمة اختبار فقط.

## ما نعدّه أصلًا

الأصل هو `FinancialEvent` العام المحفوظ محليًا، بهويته ونوعه ومبلغه وتاريخ واقعته ووقت تسجيله ومفتاح idempotency وسببه وروابطه وسياق مصروفه عند وجوده. لا يدخل `CraftOrder` أو عربون الطلب أو تحصيله أو دينه في هذا الأصل؛ لهذه الوقائع عقد مستقل.

| سؤال | قرار C1 |
|---|---|
| هل نحرر الحدث الأصلي؟ | لا. يبقى immutable ولا يُحذف أو يُستبدل بصمت. |
| كيف يظهر التصحيح؟ | كحدث جديد مرتبط بـ`sourceEventId` أو ما يعادله، مع نوع عملية وسبب ووقت. |
| هل نعيد كتابة الفترة؟ | لا افتراضيًا. يظهر الأثر بتاريخ التصحيح أو حالة مراجعة؛ restatement يحتاج قرارًا مستقلًا. |
| هل يسمح بعكس جزئي؟ | غير محسوم. لا تنفيذ قبل قرار صريح حول `reverse` الكامل و`adjust` الجزئي. |
| كيف نمنع التكرار؟ | مفتاح idempotency للتصحيح يعيد النتيجة نفسها ولا يضاعف الأثر. |
| كيف نتصرف مع التسديد؟ | لا تسديد بلا التزام مصدر، ولا يتجاوز مجموع التصحيحات/التسديدات رصيد الالتزام. |
| كيف نعالج السياق؟ | لا إعادة تصنيف أو توزيع صامت، خصوصًا للمصروف المشترك أو المصروف القديم بلا سياق. |

## أنواع الأحداث وأثرها

يجب أن يبقى أثر كل تصحيح مفككًا: الكاش، الالتزام، مال المالك، والمصروف التشغيلي. لا يُسمى المجموع «ربحًا» أو «تصحيحًا ماليًا» من دون مكونات. ويجب أن تبقى نتيجة الطلب مستقلة عن صورة الأحداث العامة، وألا تصبح نتيجة الفترة «صافي ربح نهائيًا» بسبب تصحيح واحد.

العكس المقترح للاستثمار يخفض الكاش ومال المالك، وعكس السحب يعيدهما، وعكس المصروف المدفوع يعيد الكاش ويخفض المصروف، وعكس المصروف المستحق يخفض الالتزام والمصروف بلا كاش، وعكس تسديد الالتزام يعيد الكاش والالتزام مع رابط المصدر. هذه ليست معالجة منفذة؛ هي قاعدة اختبار وقرار يجب اعتمادها قبل أي بناء.

## ما يحتاج قرار مالك المنتج

قبل فتح PR وظيفية لاحقة، يجب أن يجيب مالك المنتج عن أربعة أسئلة: هل نسمح بالعكس الكامل فقط أم بالتعديل الجزئي؟ هل يجوز تصحيح سياق مصروف قديم داخل نفس المسار؟ كيف يظهر أثر التصحيح في شهر سبق إغلاقه؟ وما مستوى حماية العملية إذا انتقل Micro لاحقًا من جهاز محلي إلى مستخدمين متعددين؟ ما لم تُجب هذه الأسئلة، يبقى الحد الصحيح هو التسجيل الحالي مع مراجعة بشرية، لا وظيفة صامتة.

## قائمة التحقق قبل التنفيذ المستقبلي

| المجال | شرط البوابة |
|---|---|
| المجال | الأصل حدث عام مدعوم، وليس عربونًا أو تحصيلًا أو دين طلب. |
| التحقق | هوية أصل موجودة، مبلغ صحيح موجب، تاريخ محلي صحيح، سبب غير فارغ، ومفتاح غير فارغ. |
| الربط | رابط واحد قابل للفحص بين الأصل والتصحيح، مع منع عكس الأصل مرتين. |
| الذرية | فشل التحقق أو الكتابة لا يترك تصحيحًا جزئيًا أو orphan. |
| التكرار | إعادة المحاولة بنفس المفتاح لا تضاعف أي دلتا. |
| القراءة | تعرض السلسلة ومكونات الأثر ودرجة المعرفة والفعل التالي. |
| التاريخ | لا تعديل صامت لفترة سابقة؛ restatement مسار قرار منفصل. |
| الاختبار | تمر حالات الاستثمار والسحب والمصروف والتسديد والمبالغ غير الصحيحة والاستيراد والتكرار والفشل الذري. |

## قرار التوقف

لا يتضمن هذا PR تعديلًا في `src/domain` أو LocalStore أو schema/export أو React routes أو Finance. لا يُبنى زر «عكس»، ولا شاشة تعديل، ولا migration، ولا adapter. بعد دمج هذا القرار، تكون الخطوة التالية المسموح بها — إن طلبها المالك — PR وظيفية منفصلة تبدأ باعتماد الأسئلة أعلاه والاختبارات المقترحة.
