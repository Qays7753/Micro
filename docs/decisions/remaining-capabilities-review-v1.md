# Micro — قائمة مراجعة موحدة لما تبقى من القدرات

**الحالة:** `CURRENT / REVIEW BASELINE UPDATED AFTER G3 IMPLEMENTATION`
**المالك:** Manus Agent 1
**تاريخ المراجعة:** 26 أغسطس 2026

## كيف تُقرأ هذه القائمة

هذه ليست قائمة ميزات يتوجب بناؤها دفعة واحدة، ولا وعدًا بأن كل مشروع يحتاج كل قدرة. هي خط المراجعة الذي يفصل بين ما أصبح حقيقة في `main`، وما أصبح مدمجًا على Bridge في برنامج متعدد المراحل، وما له عقد فقط، وما سنبنيه تاليًا، وما يحتاج Pilot قطاعيًا، وما يؤجل حتى تنضج البيانات أو السياسة.

## لوحة مراجعة سريعة

استخدم هذا الجدول للمراجعة السريعة. **«نعم، بالتسلسل»** تعني أن القدرة ضمن الطريق المعتمد، لكنها لن تبدأ قبل إنهاء ودمج ما قبلها. أما **«عند الحاجة»** فتعني أنها ليست حقًا تلقائيًا لكل مشروع؛ نثبت أولًا أن نشاطًا محددًا يحتاجها.

| القسم | البند | حالته اليوم | ماذا سنفعل به ببساطة | هل نبنيه تلقائيًا؟ |
|---|---|---|---|---|
| منفذ | افتتاح، محافظ كاش، تحويل، ضبط وعكس | منفذ | نحافظ عليه ونستخدمه كأساس صادق لكل الأرقام التالية | لا يحتاج بناء جديد |
| منفذ | تصنيف المصروف، المورد، الشراء، الدفعات، المادة، الاستهلاك، الهدر | منفذ | نحافظ على الفصل بين الشراء والمصروف وCOGS | لا يحتاج بناء جديد |
| منفذ محدود | نتيجة فترة مسجلة، مؤشرات، فرق مادة الطلب | منفذ بحدود | لا نسميه صافي ربح أو تكلفة فعلية كاملة | لا يحتاج بناء جديد وحده |

| **بعده** | نقطة التعادل والسيولة القصيرة | لم ينفذ | هامش مساهمة وتغطية فترة وتحصلات/التزامات قريبة معلنة | نعم، بعد اكتمال بياناتها |
| قطاعي | شهر وتكرار وتذكير داخل التطبيق | لم ينفذ | تخطيط شهر يفتح يوم العمل، وتكرار بسيط | عند وجود أعمال موزعة ومتكررة |
| قطاعي | توسعة القدرة: وقت/مواد/ضغط | منفذ جزئي | نضيف نوافذ وقدرة مواد وسبب تأجيل فقط عند الحاجة | للخدمات والطعام والحرف المضغوطة |
| قطاعي | مصدر الاتفاق والمتابعة | لم ينفذ | مصدر ومختصر وموعد متابعة فقط | عند وصول الطلبات من قنوات متعددة |
| قطاعي | POS ومرتجعات | لم ينفذ | بيع سريع محدود لمنتج جاهز مع عكس صحيح | **لا**؛ فقط بعد Pilot إعادة بيع/منتج جاهز |
| مؤجل | استيراد افتتاحي | لم ينفذ | معالج بسيط لأرصدة وبيانات بداية مع تقرير أخطاء | بعد اختبار الاستعادة والحاجة |
| مؤجل | PWA | لم ينفذ | تثبيت وفتح offline صادق وسياسة تحديث | بعد اختبار offline واستعادة فعليين |
| مؤجل | نسخ واستعادة محسنان | منفذ جزئي | تقوية export/import وتقرير أخطاء واستبدال ذري | بعد اختبار فقد/تغيير جهاز |
| مؤجل | مزامنة أجهزة متعددة | لم ينفذ | هوية جهاز وتضارب وسجل مزامنة | بعد Pilot جهازين واستعادة موثوقة |
| مؤجل | Auth وWorkspace وصلاحيات | لم ينفذ | حسابات ومشاريع وصلاحيات | بعد إثبات حاجة مستخدم ثانٍ |
| مؤجل بعقد متخصص | أصول، إهلاك، قروض، أجور، ضرائب، إرجاع جزئي، توقعات | لم ينفذ | كل قدرة لها عقد مالي/قانوني مستقل قبل البناء | لا؛ لا نخمن قواعدها |
| لا يبنى تلقائيًا | CRM كامل، WhatsApp automation، POS تجزئة عام، فروع، MRP، AI يقرر | خارج النطاق الحالي | لا نفتحها إلا إذا تغيرت الشريحة وأثبت Pilot الضرر والحل | لا |

| الحالة | المعنى |
|---|---|
| **منفذ** | كود واختبارات وPR/CI ودمج في `main` |
| **منفذ على Bridge** | كود واختبارات ووثائق مدمجة في فرع Bridge المعلن، لكنها ليست قدرة منشورة على `main` حتى يصدر تفويض وPR تجميعية ودمج لاحق |
| **منفذ في PR** | كود واختبارات وواجهة ووثائق في فرع مستقل وقيد PR؛ لا يعد قدرة منشورة على `main` حتى ينجح Bridge/CI ويُدمج التفويض اللاحق |
| **عقد جاهز** | سياسة معتمدة، لكن لا يوجد تنفيذ أو واجهة أو migration لها بعد |
| **البناء التالي** | شريحة مستقلة تبدأ فقط بعد إغلاق الشريحة السابقة |
| **قطاعي / Pilot** | لا يبنى لكل مستخدم؛ يحتاج نمط عمل ودليل استخدام محددين |
| **مؤجل بعقد** | مهم، لكن يلزم سياسة أو بيانات أو مصدر قانوني قبل الكود |
| **خارج النطاق الحالي** | لا يدخل تلقائيًا؛ قد يعاد النظر به إذا تغيرت الشريحة أو ثبت الضرر |

> المبدأ الذي يحكم كل الصفوف: غياب القدرة لا يكسر السجل أو يجعله صفرًا، لكنه يخفض السؤال الذي يستطيع Micro الإجابة عنه، ويجب أن يظهر الحد صراحة.

## أولًا: ما أصبح منفذًا فعلًا

| المجال | ما هو منفذ | الحد الذي لا يجوز تجاوزه في العرض |
|---|---|---|
| بداية السجل والكاش | محافظ، أرصدة افتتاحية، تحويلات، ضبط وعكس بسبب | الافتتاح والتحويل والضبط ليسوا دخلًا أو مصروفًا أو مال مالك |
| المصروف | سياق مشروع/مشترك، سلوك، غرض، ودرجة معرفة | لا سياسة توزيع على طلب أو منتج بعد |
| المورد والشراء | مورد وشراء مواد والتزام ودفعات جزئية وتسوية | شراء المادة لا يصبح COGS أو مصروفًا تلقائيًا |
| المادة والمخزون | رصيد/استلام، استهلاك لطلب، هدر، ضبط وعكس | لا وصفات أو LOT أو مستودعات أو COGS فعلي |
| الوضع والنتيجة | كاش وذمم والتزامات ومال مالك مسجل، ونتيجة فترة ومؤشرات محافظة | ليست قيمة المشروع أو صافي ربح نهائي أو توقع سيولة |
| تحليل الطلب | فرق مادة مخطط/منفذ للطلب مع عكس محفوظ | ليس تكلفة فعلية كاملة أو تعديلًا لـSnapshot |
| التشغيل الأساسي | موعد وسجل تعديل وقائمة اليوم/القادم/المتأخر ويوم/أسبوع وتحذير قدرة محدود | لا شهر أو تكرار أو حجز ذاتي أو Push مضمون |
| الحفظ المحلي | LocalStore وIndexedDB وexport/import متحققان | ليسا مزامنة أو backup مركزيًا أو PWA مكتملًا |

## ثانيًا: المجموعات التي سنبنيها بالترتيب

### المجموعة الثالثة — نتيجة الفترة الأوسع والمصاريف المشتركة

**الحالة الحالية: G3 مدمجة على Bridge عبر PR #98 وPR #99، وليست مدمجة في `main`.** يطابق التنفيذ العقد الحالي: حصة ثابتة أو نسبة معلنة أو تقدير مالك أو تأجيل غير محمل، ونتيجة تشغيلية مسجلة ضمن فترة صالحة، وCOGS اختيارية من استهلاك مثبت القيمة مرتبط بطلب `final` غير معكوس مع Snapshot بديل معلن. تبقى COGS الكاملة/القانونية والتوزيع على طلب/منتج وصافي الربح النهائي خارج الشريحة.

| الشريحة | ما سنبنيه تحديدًا | ما لا سنبنيه | شرط القبول |
|---|---|---|---|
| G3-B: سياق الحصة المشتركة | منفذ على Bridge عبر PR #98: مبلغ ثابت، إجمالي + نسبة صريحة، تقدير مالك، أو إجمالي مؤجل غير محمل؛ تحفظ المدخلات والحصة المحسوبة عند وجودها | لا نسبة خفية، ولا إجمالي فاتورة البيت داخل نتيجة المشروع، ولا توزيع على طلب/منتج | الحدث القديم يبقى كما هو؛ التقديري يبقى `estimated`، والمؤجل يظهر غير محمل ولا يتحول إلى صفر |
| G3-C: قراءة الفترة الأوسع | منفذ على Bridge عبر PR #98 و#99: تفصيل التكلفة المباشرة المسجلة، وCOGS الاختيارية عند دليل الاستهلاك، ومصروف المشروع، والحصة المحملة، والمصدر غير المحمل، والسجل القديم، مع أسباب `incomplete` وفعل تالٍ | لا اسم «صافي ربح نهائي»، ولا COGS كاملة/قانونية خارج الدليل المسجل، ولا ledger قانوني | المصروف المستحق ثم تسديده يدخل مرة واحدة فقط، والمصدر المؤجل لا يخصم من النتيجة، وSnapshot لا يتكرر مع COGS |
| G3-D: التخزين والتجربة | منفذ على Bridge عبر PR #98: schema 21/export 12، قبول السابق 20/11، round-trip، وواجهة Finance/Review RTL تمر عبر Application؛ PR #99 أضاف تصحيح COGS قراءةً فقط بلا migration جديدة | لا React مباشر إلى IndexedDB، ولا تعديل تاريخي صامت | round-trip يحفظ السياق، والسجل القديم لا يختفي، وmigration لا تخترع أساسًا |
| G3-E: QA والدمج | منفذ على Bridge: Domain/Application/Storage وworkspace check/build وQA Chromium اصطناعي؛ PR #98 وPR #99 وCI وCloudflare والدمج إلى Bridge مكتملة | لا الانتقال إلى الكتالوج بسبب نجاح sandbox وحده، ولا إعلان G3 على `main` أو قبول نهائي للجهاز/الإنتاج/Pilot | كل سيناريو عقد G3 الآلي يمر، والقبول الجهاز/الإنتاج/Pilot يبقى منفصلًا |

**سؤال المستخدم الناتج:** «هذه نتيجة ما سجلته للفترة بعد حصة المشروع من المصاريف المشتركة؛ ما الذي ما زال تقديريًا أو غير مصنف أو غير محمل؟»

### المجموعة الرابعة — منتجات/خدمات وربحية قابلة للتفسير

**الحالة الحالية: بناء لاحق بعد G3.** لا نسمّي تجميع `itemName` الحالي كتالوجًا أو ربحية منتج مكتملة.

| الشريحة | ما سنبنيه تحديدًا | ما لا سنبنيه | بوابة الانتقال |
|---|---|---|---|
| G4-A: كتالوج اختياري | تعريف منتج أو خدمة كمرجع عملي قابل للإيقاف، مع اسم ووحدة/نوع مناسب للنشاط | لا SKU إلزامي، ولا متجر، ولا inventory لكل خدمة | G3 مدموج، وحالة استخدام تثبت تكرار عمل أو منتج |
| G4-B: ربط عمل بسجل مرجعي | ربط اختياري للطلب بالمنتج/الخدمة مع بقاء اسم واتفاق وSnapshot الطلب تاريخيًا | لا تعديل الطلبات القديمة عند تغيير الكتالوج | الكتالوج يساعد التكرار ولا يلزم من لا يحتاجه |
| G4-C: عناصر التكلفة الفعلية الاختيارية | وقت فعلي للطلب عندما يكون الوقت مؤثرًا، وربط فرق المادة المنفذ الحالي بالتفسير | لا timesheet مؤسسي، ولا COGS فعلي، ولا تغيير لسعر سابق | عدم تسجيل الوقت يجعل التحليل ناقصًا لا صفرًا |
| G4-D: قراءة الربحية | مقارنة كمية البيع وهامش مباشر مسجل وعناصر فرق ظاهرة: مادة/وقت/هدر عند توفرها | لا «سبب الخسارة» أو توصية تسعير آلية أو سببية زائفة | يفرق التقرير بين الأكثر مبيعًا والأعلى هامشًا ويذكر الناقص |

**سؤال المستخدم الناتج:** «أي عمل أو منتج متكرر حقق هامشًا مباشرًا مسجلًا، وما عناصر التكلفة التي ما زالت مجهولة أو اختلفت؟»

### المجموعة الخامسة — نقطة التعادل والسيولة القصيرة

**الحالة الحالية: بناء لاحق بعد G4.** مؤشر التغطية والسيولة الحاليان محافظان ومحدودان؛ ليسا هذه المجموعة كاملة.

| الشريحة | ما سنبنيه تحديدًا | ما لا سنبنيه | بوابة الانتقال |
|---|---|---|---|
| G5-A: سياسة هامش المساهمة | فصل ثابت/متغير/مختلط على سياسة صريحة، واستبعاد ما لا يمكن ربطه بصدق | لا فرض توزيع للمختلط أو المتغير | مصاريف الفترة وسياقها معرفان أو ظاهر نقصهما |
| G5-B: نقطة تعادل مفككة | فترة، تكاليف ثابتة، هامش مساهمة، مزيج مسجل وافتراضات ودرجة معرفة | لا رقم تعادل عند هامش غير موجب أو بيانات ناقصة | يشرح الرقم المدخل والمستبعد ويتغير عند تغير الافتراض |
| G5-C: سيولة قصيرة | تواريخ استحقاق/تحصيل معلنة، كاش، ذمم، والتزامات قريبة | لا تنبؤ سحري أو وعد بتحصيل دين | يفصل الكاش عن الذمم ويصرح بنقص التواريخ |
| G5-D: تجربة القرار | فعل تالٍ تفسيري مثل مراجعة سعر أو تحصيل أو تسجيل التزام قريب | لا أمر تلقائي بشراء/سحب/اقتراض | لا يوصي النظام بفعل مالي نيابة عن المستخدم |

**سؤال المستخدم الناتج:** «كم يلزم من هامش مسجل لتغطية هذه الفترة؟ وهل الكاش المسجل مع التحصيلات والالتزامات القريبة يكفي للمرحلة القصيرة؟»

## ثالثًا: التشغيل والمبيعات — لا يبنى للجميع

هذه العناصر مهمة، لكن **بعد** مجموعات الحقيقة المالية أعلاه وبحسب طريقة العمل، لا بحسب كونها مألوفة في التطبيقات التجارية.

| القدرة | ما يبنى عند تحقق الحاجة | لمن تصلح | ما يمنع البدء | الحالة الآن |
|---|---|---|---|---|
| شهر وتكرار وتذكير داخل التطبيق | شهر يفتح يوم العمل، تكرار بسيط، مؤشرات تأخر | طلبات موزعة ومتكررة | لا توجد بيانات موعد/نمط تكرار كافية | قطاعي / Pilot |
| قدرة تشغيل أوسع | نافذة وقت، ضغط قدرة مواد، سبب قبول أو تأجيل | خدمة، طعام، حرفة تحت ضغط | لا وقت/مدة/مواد قابلة للقياس | قطاعي / Pilot |
| مصدر الاتفاق والمتابعة | مصدر، ملخص، موعد متابعة، ملاحظة خاصة | من يتلقى طلبات من قنوات متعددة | لا حاجة لقراءه رسائل أو CRM كامل | قطاعي / بناء صغير لاحق |
| استيراد افتتاحي | معالج بسيط لأرصدة وبيانات افتتاحية مع تقرير أخطاء | مشروع قائم لديه دفتر/Excel | لا استيراد شامل أو تفسير تلقائي لسجل تاريخي | مؤجل بعد اختبار الاستعادة |
| POS ومرتجعات | بيع سريع واحد لمنتج جاهز بسعر معتمد وكاش/دين وإرجاع قابل للعكس | إعادة بيع أو منتج جاهز متكرر | كتالوج وسعر ومخزون وقبض/دين وإرجاع وPilot | Pilot قطاعي فقط |

| أصل وإهلاك | سياسة منفعة وفترة وتصنيف أصل | لا يجوز أن تتحول ماكينة أو ثلاجة إلى مصروف طلب كامل |
| قرض وأقساط وتمويل | فصل أصل القرض وكلفة التمويل والكاش والالتزام | خلطها يفسد النتيجة والسيولة |
| أجر مالك أو عامل | سياسة تفرق بين السحب وأجر العمل وتكلفة الوقت | لا يخلط الوقت المقدر بأجر المالك |
| ضرائب ورسوم قانونية | مصدر أردني محدث ونوع مشروع وحالة قانونية محددة | لا نخمن التزامًا قانونيًا |
| إرجاع جزئي بعد التحصيل | عقد عكس للمبيعات والكاش والذمة والمخزون | لا يحذف تاريخ البيع أو يكرر الأثر |
| موازنات وتوقعات أوسع | سجل حقيقي كافٍ وافتراضات قابلة للمراجعة | لا توقع موثوق من بيانات قليلة |

## سادسًا: ما لا سنبنيه تلقائيًا

| القدرة | الحكم | السبب |
|---|---|---|
| CRM كامل أو Inbox موحد أو قراءة/إرسال WhatsApp | خارج النواة الحالية | يحول Micro إلى منصة تواصل ويتطلب خصوصية وتكاملات لا تحل المشكلة المالية أولًا |
| Retail POS عام، طاولات، فروع، ولاء، خصومات مركبة | خارج نطاق POS الأول | يوسع النظام إلى متجر تجزئة بدل حل بيع جاهز متكرر محدد |
| موظفون وصلاحيات وworkflow موافقات | مؤجل | لا يوجد إثبات حاجة لأكثر من مستخدم في Prototype |
| MRP، مستودعات متعددة، LOT وصلاحية | مؤجل قطاعيًا | أبعد من مادة/استهلاك/هدر التي تعالج القرار الحالي |
| AI يقرر السعر أو الشراء أو القبول | مرفوض حاليًا | لن يحوّل بيانات ناقصة إلى توصية تبدو يقينية |
| Ledger قانوني وإقفال محاسبي عام | مؤجل بعقد متخصص | Prototype ليس نظام محاسبة قانونيًا ولا يملك سياسة كاملة للفترات والضرائب والإرجاعات |

## قواعد التنفيذ التي لا تتغير

1. تعمل **شريحة وظيفية واحدة فقط** في كل مرة: عقد، اختبارات، تنفيذ، QA، PR/CI، دمج `main`، ثم التالية.
2. كل نتيجة مالية تسمي مصادرها وفترتها وما استبعدته، ولا تستبدل المجهول بصفر.
3. كل تصحيح يعكس أو يسوي حدثًا بسبب؛ لا يحذف الحقيقة التاريخية بصمت.
4. لا يتصل React مباشرة بـIndexedDB؛ يمر كل أثر عبر Application Service وDomain وLocalStore.
5. الميزات القطاعية لا تفتح لمجرد توفرها في خارطة الطريق؛ تحتاج سؤال قرار متكرر وPilot أو دليل استخدام مناسب.
