# قرار الـVertical Slice الأول: طلب حرفة يدوية مخصصة

**الحالة:** معتمد للتنفيذ الأولي

**القرار:** يبدأ Micro بمسار واحد كامل لطلب حرفة يدوية مخصصة، وليس بتطبيق عام للفئات الثلاث ولا بنظام SaaS كامل.

## Job-to-be-Done

> عندما أوافق على طلب حرفة مخصصة أو أراجع نتيجته، أريد أن أعرف تكلفة العمل وسعره وما قبضته وما بقي وما الخطوة التالية، حتى لا أقبل أو أسعّر أو أسحب المال على أساس رقم مضلل، دون أن أضطر لبناء نظام محاسبة كامل.

هذا الـJTBD يصف لحظة الاستخدام التي نختبرها في الشريحة، ولا يثبت وحده أن الحرفة هي أفضل سوق تجاري أو أن المسار ينطبق بلا تعديل على الطعام والخدمات.

## سبب القرار

هذا المسار يختبر أكبر عدد من المخاطر المشتركة في مشكلة المنتج ضمن تجربة واحدة قابلة للفهم. فهو يجمع الخامات، والوقت التقديري، والتخصيص، ونسخة التكلفة، والسعر، والاتفاق، والموعد، والعربون، والتنفيذ، والتسليم، والتحصيل أو الدين، ثم يعرض النتيجة والفعل التالي.

وفي الوقت نفسه، لا يجبرنا على بناء محرك وصفات وتحويل وحدات خاص بالطعام، ولا نظام توفر وجدولة كامل خاص بالخدمات، ولا مخزون مؤسسي أو CRM أو POS.

## مسار المستخدم الأول

```text
قطعة مخصصة
  → خامات ووقت تقديري
  → تكلفة بدرجة معرفة
  → سعر حماية
  → اتفاق مع الزبون
  → موعد تسليم
  → عربون اختياري
  → قيد التنفيذ
  → تم التسليم
  → قبض أو دين
  → نتيجة وفعل تالٍ
```

## ما يدخل في الشريحة

| المجال | الحد الأدنى |
|---|---|
| النشاط | ملف نشاط واحد للحرفة اليدوية المخصصة |
| الكتالوج | قطعة/خدمة قابلة للتخصيص باسم ووصف وسعر مقترح |
| التكلفة | خامات، كمية، وحدة، سعر وتاريخ؛ ووقت تقديري اختياري بسعر ساعة يحدده المستخدم |
| النتيجة | تكلفة مخططة أو فعلية، تكلفة ناقصة/مقدرة، وسعر حماية |
| الطلب | الزبون، مصدر الاتفاق، المواصفات، الكمية، السعر المتفق، الموعد، الأولوية، والملاحظة |
| المال | عربون اختياري، متبقي، قبض أو دين؛ مع فصل الكاش عن الربح |
| التنفيذ | الحالات الأساسية وفعل تالٍ واضح |
| التاريخ | cost snapshot عند اعتماد السعر أو تأكيد الطلب وسجل أحداث الطلب |
| الهاتف | إدخال لمس RTL بعرض ضيق، دون لوحة مالية مؤسسية |

## ما لا يدخل

لا يدخل في هذه الشريحة محرك وصفات الطعام، تحويل الوحدات الغذائية، عدّ مخزون متقدم، مشتريات، تعدد المستخدمين، فروع، أدوار، Billing، بوابة دفع، WhatsApp API، ذكاء اصطناعي، إشعارات خلفية مضمونة، مزامنة متعددة الأجهزة، أو تقارير محاسبية كاملة.

يجوز تسجيل العربون والقبض والدين كأحداث بسيطة داخل الطلب لإثبات المعنى، لكن لا نبني دفتر أستاذ عامًا أو دورة فواتير مؤسسية.

## قابلية التعميم

بعد نجاح الشريحة، نختبر العقد العام على الطعام والخدمات دون بناء واجهتين كاملتين فورًا:

- الطعام يضيف الوصفة والدفعة والحصص وتحويل الوحدات.
- الخدمات تضيف المدة والتوفر وتعارض الموعد وقائمة الإتمام.

إذا احتاج أحدهما تغيير معنى الطلب أو التكلفة الأساسية، نضيف Activity Profile جديدًا ولا نلوّي نواة الحرفة لتناسبه.

## معايير النجاح

تنجح الشريحة الأولية إذا استطاع مستخدم غير محاسبي أن:

1. يسجل قطعة مخصصة بمواصفات واضحة.
2. يضيف خامتين ووقتًا تقديريًا أو يصرح بأن التكلفة ناقصة.
3. يرى تكلفة وسعر حماية مع تفسير درجة المعرفة.
4. يسجل اتفاقًا وموعدًا وعربونًا اختياريًا.
5. يغير الحالة حتى التسليم دون أن يتحول التسليم تلقائيًا إلى قبض.
6. يرى المتبقي والنتيجة والفعل التالي.
7. يفهم الفرق بين الكاش والربح والدين والعربون دون شرح محاسبي مطول.

## معايير الفشل

تُراجع الشريحة أو تُصغر إذا احتاج المستخدم إلى إدخال حقول كثيرة قبل تسجيل الطلب، أو إذا لم يفهم لماذا النتيجة مقدرة أو ناقصة، أو إذا تكرر الخلط بين التسليم والقبض، أو إذا فشل النموذج في تمثيل تعديل المواصفات بعد الاتفاق.

## قرار لاحق مطلوب

لا ننتقل إلى Profile الطعام أو الخدمات ولا إلى Auth/Workspace/مزامنة تجارية قبل تسجيل نتائج الاختبار، بما فيها زمن أول قيمة، إكمال أول تكلفة، تسجيل أول طلب، فهم الربح مقابل الكاش، والعودة للاستخدام.
