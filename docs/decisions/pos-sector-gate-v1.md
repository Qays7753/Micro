# قرار POS: بوابة قطاعية، لا نواة افتراضية لـMicro

**الحالة:** معتمد للتخطيط؛ لا يجيز البناء الآن
**التاريخ:** 23 أغسطس 2026
**المالك:** Manus Agent 1

## المشكلة المرتبطة

Micro يعالج فجوة بين أحداث اليوم والصورة المالية المترابطة: ما الذي بيع، وما الذي دُفع أو بقي دينًا، وما تكلفة ما تم بيعه، وما الأثر على الكاش والمخزون والنتيجة. هذه ليست في الأصل مشكلة «كاشير» أو سرعة تمرير سلة.

تظهر مشكلة بيع سريع مستقلة فقط عندما يبيع المشروع **منتجات جاهزة متكررة** بكميات أو مرات كثيرة، ويصبح إنشاء طلب كامل لكل عملية عبئًا يدفع المستخدم إلى التسجيل المتأخر أو عدم التسجيل. عندئذ لا يحل POS محاسبة المشروع؛ بل يلتقط حدث البيع بسرعة ضمن القواعد التي حُسمت أصلًا.

## الأدلة وقوتها

| المصدر | ما يثبته | القوة والحد |
|---|---|---|
| تعريف Micro والمشكلة المركزية | القيمة الأساسية هي وضوح الكاش والذمم والتكلفة والنتيجة والقرار التالي، لا تجربة retail checkout | قوي لنطاق المنتج، لا يثبت حجم طلب POS في السوق |
| نمط النشاط | الحرفة المخصصة والخدمة يحتاجان طلبًا واتفاقًا وموعدًا وتنفيذًا؛ البيع السريع ليس تدفقهما الافتراضي | قوي كمطابقة مجال |
| الطعام والمنتج الجاهز وإعادة البيع | قد يتكرر فيها بيع جاهز بمخزون وسعر ثابت؛ هنا يمكن أن يقل إدخال البيع المتأخر | فرضية قطاعية تحتاج Pilot |
| السيناريوهات والمحاكاة | سيناريو إعادة البيع يوضح احتمال الحاجة للبيع والإرجاع السريع | اختبار مفهومي، وليس دليلًا إحصائيًا أو تجاريًا |

## التوصية

**لا نبني POS الآن، ولا نعتبره جزءًا إلزاميًا من النظام.** إضافته الآن ستكون قرارًا خاطئًا للأسباب التالية:

1. سيصرف البناء عن السؤال الأهم الذي لم يكتمل: كيف نحسب نتيجة فترة أوسع بمصاريف مشتركة ودرجة معرفة صريحة.
2. لا يعمل POS بصدق قبل كتالوج اختياري وسعر معتمد وقواعد قبض/دين وإرجاع وربط مخزون. بدونه يصبح زر بيع سريع وسيلة أسرع لخلق أثر مالي ناقص أو مكرر.
3. غالبية التدفقات الأولى في Micro هي حرفة مخصصة أو خدمة أو طعام بالطلب؛ هذه تحتاج طلبًا وموعدًا وعربونًا وتنفيذًا أكثر مما تحتاج سلة.
4. تحويل Micro إلى POS عام سيقربه من ERP/retail software ويضعف وعده كشريك مالي تشغيلي لمشاريع صغيرة غير متجانسة.

هذا **ليس رفضًا دائمًا**. يصبح POS مبررًا بعد المجموعة الخامسة، ومن خلال Pilot قطاعي منفصل، لمشروع إعادة بيع أو منتجات جاهزة متكررة فقط.

## أقل نطاق مسموح إذا اجتاز Pilot

يتكون من منتج جاهز وسعر معتمد وكمية، وبيع نقدي أو آجل، وإرجاع أو إلغاء موثق، وأثر وحيد قابل للعكس على الكاش/الذمة والمخزون. لا تدخل طاولات أو فروع أو موظفون أو بوابات دفع أو خصومات مركبة أو CRM أو شاشة كاشير عامة.

## شروط البوابة ومعيار النجاح

لا يُكتب عقد POS قبل تحقق كل الآتي:

| الشرط | سبب الشرط |
|---|---|
| كتالوج اختياري وسعر معتمد | منع بيع عنصر بلا هوية أو مرجع سعري |
| مخزون منتج جاهز أو سياسة عدم تتبعه | منع خصم كمية لا نعرف مصدرها |
| قواعد قبض ودين وإرجاع وعكس | منع تكرار الكاش أو اعتبار الإرجاع حذفًا |
| Pilot قطاعي يثبت البيع المتكرر | يمنع بناء cashier عام لمشكلة لا تحدث |
| سؤال قرار متكرر | يجب أن يثبت أن سرعة التسجيل تحسن اكتمال السجل أو قرار إعادة الشراء/المخزون |

يُقبل Pilot فقط إذا سجّل المستخدم البيع المتكرر أسرع من مسار الطلب من دون تكرار الأثر المالي أو المخزني، وأظهر أن البيانات المسجلة تحسن قرارًا محددًا. إذا لم يحدث ذلك، يبقى مسار الطلب و«تسجيل بيع مختصر» بديلين كافيين ويؤجل POS.

## القرار التنفيذي

تبدأ الآن المجموعة الثالثة المالية، ثم الرابعة والخامسة، كل واحدة كـSlice مستقل بعقد واختبارات وPR/CI ودمج إلى `main`. لا يُفتح POS بالتوازي معها ولا عند نهايتها تلقائيًا؛ يمر أولًا ببوابة Pilot أعلاه.
