# قرار G9.4 — الإبقاء على حد G7-A في نطاق Pilot

**الحالة:** `CURRENT / G9.4 DECISION — NO G9.5 FUNCTIONAL EXTENSION`

## الفرضية المفحوصة

قد يمنع ملخص الاتفاق ومصدره وموعد المتابعة المحلي فقد اتفاق متكرر دون قراءة رسائل خاصة. راجعنا عقد G7-A، سطح `/schedule`، قراءة `dueFollowUps`، واختبارات السياق المحلي. في نطاق Micro الحالي، يستطيع G7-A حفظ مصدر الاتفاق، آخر ملخص يكتبه المالك، تاريخ المتابعة وسببها، وقراءة المستحق/القادم مع تاريخ تغيير أو إزالة.

## النتيجة

لم تظهر فجوة واحدة محددة ومدعومة تمنع قرارًا متكررًا في Pilot الحالي. إضافة حقل عام أو stages أو tags أو inbox ستخترع CRM صغيرًا دون دليل، وقد تدفع إلى تخزين اتصالات خاصة بلا سؤال قرار. لذلك لا نبني G9.5 وظيفة جديدة في هذه المرحلة؛ يتحقق الهدف بقرار عدم التوسعة مع إبقاء الحد قابلًا لإعادة المراجعة إذا قدم Pilot دليلًا جديدًا.

## ما يغطيه G7-A

| الحاجة | القدرة الحالية | الحد |
|---|---|---|
| مصدر الاتفاق | قيمة محلية اختيارية | لا API أو قراءة قناة |
| آخر اتفاق | ملخص يكتبه المالك | لا نسخ محادثات أو مرفقات |
| المتابعة | تاريخ وسبب وتاريخ تغييرات | لا Push أو تذكير تلقائي |
| القرار التشغيلي | مستحق/قادم محليًا | لا CRM أو pipeline |

## سيناريوهات القرار

في متابعة مستحقة أو قادمة، يراجع المالك الملخص والسبب ويقرر الفعل يدويًا. عند تغيير أو إزالة التاريخ، يكتب السبب ويحفظ النظام الحدث. عند غياب المتابعة، تبقى الحالة غير محددة ولا يخلق النظام موعدًا. لا يتغير الكاش أو الدين أو النتيجة أو الموعد التشغيلي.

## بوابة إعادة الفتح

لا تفتح G9.5 إلا إذا أظهر Pilot حقيقي فقدًا متكررًا لمعلومة محلية محددة لا يمكن تمثيلها بالحقول الحالية، مع أثر قرار قابل للقياس. لا تكفي الرغبة في CRM أو التكامل مع WhatsApp/Instagram.
