## §2 الفشول الوسيطة (كشفها الاختبار — قبل الوصول للنهائي)

1. طابع زمني كمعامل Date داخل قالب SQL أرسله postgres.js نصًّا:

```

 ❯ worker/application/manage/operationHandler.ts (INSERT INTO operation ...)
```

صُحح بمعلمة ISO-8601 (`${timestamptz(now)}`).

2. النموذج الأول كان يمرر سطر الرصيد مفردًا فلم يُدرَج صف balance_line — **والتأكيد المفرد INV-1/INV-2 أمسكه فور أول استخدام له** (ترحيل AR لسطر رصيد غائب = خرق مرجعي):

```

- INV-2: ترحيل AR يشير إلى سطر رصيد غير موجود «aaaaaaaa-0000-4000-8000-000000000002»
  (القيد «6ce87f03-…») — لا يُحسب مستحق سطر غائب.
```

صُحح النموذج إلى `balanceLines` مصفوفة §3.6 (وهي صيغة §3.6 الصحيحة أصلًا: العملية قد تفتح أكثر من سطر).

3. اختبار التزامن الأول عدّ 2 عمليات لأن الاختبارات كانت تشارك مشروعًا واحدًا → عزل بمشروع لكل اختبار (زرع مشروع بمعرّف فريد لكل حالة) فصارت تأكيدات العدّ دقيقة.

4. استعلام عمود `operation_id` غير الموجود على جدول الحجز في اختبار الجسم المختلف → صُحح الاستعلام.

5. أول صياغة لإثبات الشكل القديم وضعت تخزين الحجز داخل معاملة الكتابة الساذجة فاصطدمت بالقيد الفريد (duplicate key) بدل إثبات الازدواج — صُححت إلى الشكل الحرفي لما وجده التدقيق: قراءة المفتاح خطوة، التنفيذ بمعاملة مستقلة خطوة، والتخزين خطوة ثالثة يُبتلع فشلها (`ON CONFLICT DO NOTHING` + `.catch(() => undefined)`) — فأنتج السباق **عمليتين** كما يثبت القسم §3.

## §5 دليل SRV-03 (عناصر خطة أدلة الأمن §2 — على شجرة المهمة)

**(١) قيد القاعدة (من `0019_manage_v2_idempotency.sql`):**

```sql
CREATE TABLE IF NOT EXISTS manage_v2_idempotency (
  project_id UUID NOT NULL,
  request_id TEXT NOT NULL,
  ...
  CONSTRAINT manage_v2_idempotency_pkey PRIMARY KEY (project_id, request_id),
  CONSTRAINT manage_v2_idempotency_project_fkey FOREIGN KEY (project_id) REFERENCES project (id)
);
```

**(٢) الحجز داخل المعاملة (من `operationHandler.ts` — لا قراءة idempotency خارج `sql.begin` إطلاقًا):**

```ts
return sql.begin(async tx => {
  const inserted = await tx`
    INSERT INTO manage_v2_idempotency (...) VALUES (..., ${RESERVED_STATUS}, ...)
    ON CONFLICT (project_id, request_id) DO NOTHING
    RETURNING request_hash`;
  if (inserted.length === 0) { /* replay | conflict | in-progress | takeover */ }
  // ... operation row → balance lines → entries → postings ...
  await tx`UPDATE manage_v2_idempotency SET response_status = 200, response_body = ... WHERE ...`;
  return { outcome: "applied", result };
});
```

**(٣) اختبار التزامن:** الحالة 2 في §3 — طلبان متوازيان بالمفتاح نفسه → applied+replay وعملية واحدة. **والفشل قبل الإصلاح:** الحالة 8 — الشكل القديم (خطوات منفصلة) ينتج عمليتين بالسباق نفسه (تأكيد `expect(ops).toBe(2)` يمرّ على الشكل القديم ويفشل على المعالج الجديد حيث العملية واحدة).

**(٤) اختبار الفشل الجزئي:** الحالة 3 في §3 — خطأ محقون بعد أول كتابة → `count(*) = 0` على operation وledger_entry وmanage_v2_idempotency جميعًا.

**(٥) الجسم المختلف:** الحالة 4 في §3 — `E-IDEMPOTENCY-CONFLICT` صريحًا، لا تطبيق ولا تجاهل صامت.

**حالة السجل:** تبقى `OPEN` حتى مراجعة مانوس (قاعدة الخطة: لا إغلاق من وصف كود ولا من CI أخضر — الإغلاق FIXED-VERIFIED يُسجَّل بعد المراجعة على SHA محددة).
