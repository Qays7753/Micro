## ما تغيّر — ملفًا ملفًا

1. **`apps/prototype-web/worker/db/migrations-pg/0018_manage_v2_schema.sql` (جديد):** هجرة المخطط الكاملة، كل عباراتها `CREATE` فقط (لا ALTER ولا DROP ولا أي DML — لا جدول قديم مُمسّ):
   - الجداول الثلاثة عشر كاملة بالأعمدة والأنواع والمفاتيح والقيود الحرفية من §3: `project` (3.1)، `box` (3.2)، `product` و`product_component` (3.3)، `sale` (3.4)، `sale_line` (3.5)، `balance_line` (3.6)، `operation` (3.7)، `ledger_entry` و`ledger_posting` (3.8)، `absence_event` (3.9)، `reconciliation` و`reconciliation_box` (3.10).
   - المال `BIGINT` فلسًا حصرًا؛ الكميات `INT` ملّية (افتراضي 1000 حيث تنص §3.5 على قيمة ثابتة)؛ التواريخ `DATE`؛ الطوابع `TIMESTAMPTZ`؛ `payload`/`components_snapshot` بنوع `json` كما يذكرها §3.
   - `project_id` على كل جدول عدا الجدول الجذري `project` مع FK إليه (نطاق §3 التمهيدي)، والـFK السبعة التي يعيّنها §3 حرفيًا (product_component→product، sale_line→sale، balance_line→operation، ledger_entry→operation، ledger_posting→ledger_entry، reconciliation_box→reconciliation و→box). المراجع التي لا يعلّمها §3 بـFK تبقى مراجع مجردة (منها `ledger_posting.ref_id` متعدد الشكل حسب الحساب) — منضبطة في مسار الكتابة (M2.4+).
   - قيود الإحكام الحرفية: `UNIQUE(owner_account_id)`، `UNIQUE(project_id, kind)` (وهي نفسها R-9: صندوق نقد واحد وحساب واحد)، تعدادات kind/status/opening_status/direction/kind/entry_type (Q1–Q20)/account/context، تعيين direction↔kind، قاعدة counterparty_name، قاعدة Q20 (`reverses_entry_id` على Q20 فقط وبالعكس)، `delta_minor <> 0`، حصر `category` في حساب EXP بتعداد R-10 الثابت، حصر `rev_kind` في REV بتعداده الخمسة، وشكل `ref_id` حسب الحساب (BOX/AR/AP/PRE إلزامي، OPEN/OWN_IN/OWN_OUT/EXP/UNEXP ممنوع، REV حر). وعمود §14.5 الأمامي `created_by_account_id TEXT NOT NULL`.
   - **فرض append-only على مستوى القاعدة (§3.8):** اختير **الحارس (trigger)** دون revoked grants، والسبب موثق في رأس الهجرة: مالك الجدول في PostgreSQL يبقى له حق ضمني على جداوله فلا يحميه REVOKE، والمستخدم الإنتاجي مالك الجداول، وحراسة الاختبار نفسها تتصل كـsuperuser (خادم الاختبار المدمج initdb بمستخدم `micro` superuser) — أي أن مسار المنح لا يحمي أي مسار حقيقي يعيشه هذا المستودع. الشكل المنفَّذ: حارسا `BEFORE UPDATE OR DELETE` صفّيان على `ledger_entry` و`ledger_posting` بشرط `WHEN` يحوّل نصًّا غير رقميًا (قيمة الصف متصلة بالإشعار الكامل) إلى `int4` فيرفضه محرك القاعدة قبل أي تعديل برسالة تحمل الإشعار نصًّا، والدالة المذكورة (`pg_catalog.suppress_redundant_updates_trigger` — الدالة الكتالوجية العامة الوحيدة من نوع trigger) لا تعمل قط لأن الشرط لا يمرّ أصلًا. تعذّر الشكل التقليدي (دالة plpgsql بـRAISE) موثق بمسار المشغّل: مُشغّل الهجرات الرئيسي (`harness.ts applyMigrations`) يحذف أسطر `--` ويقسم الملف على كل `;`، فأي جسم دالة يحوي فاصلًا ينكسر («unterminated dollar-quoted string» — مُجرّب فعليًا)، ودوال LANGUAGE sql لا تقبل `RETURNS trigger` أصلًا («SQL functions cannot return type trigger») — كلاهما مُثبت بمحاولة حية على PostgreSQL 17 قبل كتابة الهجرة، والمحارب الكاملة في ملف الأدلة.
   - **معادلة التوازن لكل قيد (§3.8):** تجميع عبر صفوف القيد الواحد لا يعبَّر عنه بقيد إعلاني، ودالة تحقق متعددة العبارات يستحيل تمريرها عبر تقسيم المشغّل — فتُنفَّذ في M2.2 (INV-10) وفق بند الهروب المكتوب في نص المهمة نفسها («otherwise in M2.2»)، مع اختبار يثبت رفض القيد السيئ قبل بلوغه القاعدة. كل ما هو قابل للتعبير الإعلاني نُفِّذ هنا (البند السابق).
   - **إعادة التطبيق آمنة:** كل `CREATE TABLE ... IF NOT EXISTS` و`CREATE INDEX IF NOT EXISTS` و`CREATE OR REPLACE TRIGGER`؛ إعادة تطبيق الملف كاملًا عبر مسار التقسيم وكمكالمة واحدة (مسار rtl-review) لا تفشل — مُثبت بالاختبار.
   - **فهارس مسارات القراءة (14):** `ledger_entry(project_id, effective_on)` و`(operation_id)`، `ledger_posting(entry_id)` و`(project_id, account, ref_id)` (مجاميع أشكال §8)، `operation(project_id, effective_on)`، `sale(project_id, planned_delivery_on)` (حالة البيع مشتقة §6 فتُفهرس مدخلات اشتقاقها)، `sale_line(sale_id)`، `balance_line(project_id, counterparty_name)` و`(project_id, origin_on)` و`(sale_id)`، `product(project_id)`، `product_component(product_id)`، `reconciliation(project_id, performed_on)`، `reconciliation_box(box_id)`.
