## الخلاصة التنفيذية

الفرق بين النسختين ليس تغييرًا شاملًا في متطلبات واجهة UNIT-001. أقسام الشاشة، القواعد U001-R01..R15، الحقول، النصوص، حدود عدم إنشاء أي أثر مالي، والحماية من Schema/Export/Import لم تتغير جوهريًا.

النسخة V3 أضافت طبقة جديدة فوق V2 تتعلق بـ:

1. مصالحة قرارات المالك التنظيمية.
2. مسؤوليات الجيران UNIT-039 وUNIT-022 وUNIT-044 وUNIT-002.
3. شروط إزالة أي مدخل أو نموذج مع بديل وسياق رجوع وحماية للبيانات.
4. بوابات قبول جديدة باسم U001-ORG-AC01..03.
5. فتح بند الاستعادة Q01 واختبار الهاتف كشرط قبل ختم الجاهزية.
6. تغيير حالة القرار U001-D01 من «توصية غير معتمدة» إلى «اتجاه معتمد أعاد المالك تأكيده».

لذلك لا يوجد أساس لتعديل كود التطبيق تلقائيًا من المقارنة وحدها. يوجد أولًا عمل توثيقي/حوكمي، ثم مراجعة تأثير محددة لـQ01 وORG-AC03 قبل تقرير أي تعديل كود.

## الفروقات الجديدة بالتفصيل

### 1. هوية الملف وحالته

انتقلت النسخة من V2 إلى V3. Drive V3 تقول إن التنفيذ والتحقق التشغيلي لم يبدآ، بينما تنفيذ UNIT-001 موجود فعليًا في PR #377 ومُجمّع في PR #378. هذه ليست مشكلة كود، لكنها تعارض في حالة المصدر يجب تسويته قبل اعتبار V3 مصدرًا كنسيًا للتنفيذ.

**التصنيف:** إصلاح توثيقي الآن قبل أي تنفيذ لاحق.

### 2. مصالحة قرارات المالك `U001-ORG-20261018`

أضيفت أربعة قرارات تنظيمية:

- `ORG-001`: البداية باسم المشروع، واستكمال البيانات الأخرى عند الحاجة.
- `ORG-002`: بيانات البداية الاختيارية داخل الإعدادات وبواسطة مكونات مختصة.
- `ORG-009`: توحيد ملف المشروع داخل الإعدادات وإعادة استخدام هوية التأسيس نفسها.
- `ORG-024`: تنظيم الإعدادات وبيانات المشروع والتفضيلات والأمان والنسخ والاستعادة، مع إبقاء التفاصيل التقنية والحذف ضمن الخيارات المتقدمة.

هذه القرارات توسع خارطة البرنامج، لكنها لا تضيف بمفردها حقلًا أو عملية مالية أو تغيير Schema إلى شاشة UNIT-001.

**التصنيف:** تثبيت توثيقي الآن؛ تنفيذ كل قرار داخل المكوّن المالك له، وليس بإضافته صمتًا إلى UNIT-001.

### 3. مسؤوليات الجيران وترتيب العمل

V3 تحدد صراحةً ما يلي:

- `UNIT-039`: يجب استخدام مصدر هوية المشروع نفسه؛ التعديل يكون في 039 أو باختبار تكامل إذا لم يتغير العقد.
- `UNIT-022`: إعداد النقد ينتقل خارج UNIT-001 مع المحافظة على حالة الرصيد غير المعروف وعدم تحويله إلى صفر.
- `UNIT-044`: الاستعادة في البداية تفويض إلى 044، لكن فتح الاستعادة والرجوع والإلغاء والتعافي يجب حسمها قبل الإغلاق.
- `UNIT-002`: استكمال بيانات المشروع اختياري لاحقًا وليس خطوة إجبارية بعد الحفظ.

**التصنيف:** جزء من خريطة التكامل؛ لا يستدعي تعديل كود UNIT-001 تلقائيًا، لكنه يمنع إعلان الإغلاق النهائي قبل حسم بوابة 044/Q01.

### 4. قواعد جديدة قبل إزالة أي مدخل أو نموذج

V3 تضيف قاعدة إجرائية: قبل إزالة أي مدخل يجب تجهيز البديل، وحفظ معرف السجل والقصد والمدخلات وسياق العودة، وتحديد مصير الروابط والبيانات القديمة، ثم نجاح الفحص المشترك.

**التصنيف:** حارس عمل وتوثيق، وليس تغييرًا في السلوك الحالي. يجب إدخاله في Prompt المكوّنات اللاحقة وفي سجل Tracker، لا تنفيذه كتعديل عشوائي داخل UNIT-001.

### 5. التبسيط الداخلي وحدود السلامة

V3 تثبت مبادئ إضافية:

- التفاصيل المتقدمة عند الحاجة لا داخل البداية.
- لا توريث صامت لسعر أو موعد أو دفع من عملية قديمة.
- يجب تحديد مصدر كل قيمة ووحدتها وإلزامها وأثرها ومسار الخطأ والتكرار والتصحيح والتعافي.
- لا خلط بين النقد والإيراد والربح والدين والعربون ومال المالك.
- لا تحويل للفشل أو المعرفة الناقصة إلى صفر.

**التصنيف:** مبادئ حماية للنظام؛ معظمها محفوظ أصلًا في عقود Micro، ولا يثبت من المقارنة وحدها وجود عيب جديد في كود UNIT-001.

### 6. ما لم يُحسم: Q01 والاستعادة

V3 تقول صراحةً إن تفصيل الاستعادة `Q01` وشروط التعافي وسلامة الفصل بين إعداد المشروع وإنشاء المحفظة تحتاج فحصًا، وإن الاتفاق التنظيمي لا يثبت اختبار الهاتف.

هذا أهم فرق عملي في النسخة الجديدة. التنفيذ الحالي يحتوي مدخل استعادة مفوضًا، لكن V3 لا تعتبر ذلك وحده دليلًا على اكتمال:

- فتح الاستعادة قبل إنشاء هوية جديدة.
- الإلغاء والرجوع مع الحفاظ على السياق.
- نجاح الاستعادة دون إنشاء هوية ثانية.
- التعافي عند فشل القراءة أو الاستبدال.
- تحقق الهاتف الفعلي.

**التصنيف:** مراجعة قبول مستقلة قبل ختم UNIT-001. لا نقرر تعديل الكود قبل إتمام هذه المراجعة، لكن لا يجوز اعتبار UNIT-001 مغلقًا نهائيًا إذا بقيت هذه الشروط غير مثبتة.

| الفحص | المطلوب | الحالة الظاهرة في V3 |

**التصنيف:** توسيع عقد القبول والتوثيق الآن؛ تنفيذ أو تعديل كود فقط إذا كشفت مراجعة Q01 فجوة فعلية.

### 8. حالة `U001-D01`

تغيرت حالة القرار من:

> التوصية المقدمة للمالك؛ لا تسجل اعتمادًا جديدًا.

إلى:

> اتجاه معتمد أعاد المالك تأكيد حسمه؛ ORG-001.

هذا يؤكد أن «الاسم فقط» قرار مالك، وليس مجرد اقتراح تصميم.

**التصنيف:** تحديث Tracker والعقد التوثيقي؛ لا تغيير سلوكي جديد لأن التنفيذ الحالي يطبق الاتجاه نفسه.
