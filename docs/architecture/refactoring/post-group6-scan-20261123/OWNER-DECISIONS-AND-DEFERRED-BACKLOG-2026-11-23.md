## 4. موجات المعالجة الدنيا المعتمدة للتخطيط

هذه الموجات هي الحد الأدنى المقبول للتحضير والتنفيذ المرحلي، وليست تفويضًا لتجاوز بوابات Operations Control أو لتغيير فروع أخرى. قبل لمس الكود يجب إنشاء/تحديد مطالبة Workstream مناسبة وفق `AGENTS.md` §14، وفحص عدم التداخل، وتسجيل الفرع وBase SHA والمسارات والعقود والحدود. تبقى الموجات على الفرع الحالي وPR #386 فقط؛ لا Claim أو كتابة على `main`، ولا تعديل للمطالبة `WS-251` أو البند `DOC-041`.

### الموجة 0 — تسجيل القرار والمصدر

**الحالة:** اكتمل قرار المالك، وحُفظ التقرير الأصلي وسجل القرارات.<br>
**النطاق:** مستندات القرار والإحالات الحاكمة فقط؛ لا تغيير إنتاجي.<br>
**معيار القبول:** مطابقة بصمة التقرير، وجود كل نتيجة مع قرارها وتصنيفها ومحفز إعادة فتحها، وضوح فصل هذا السجل عن مراجعة `WS-251/DOC-041` وسجل الأمن.<br>
**حد الرجوع:** ملفات التوثيق الجديدة والإحالات فقط؛ لا بيانات أو مخطط أو أثر مالي أو تشغيلي.

### الموجة 1A — توثيق التطبيق والترحيلات ومسؤوليات Worker (R04, R08, R11, R18, R19)

**النطاق:** توثيق التطبيق كاملًا مع فصل المسار المحلي عن المتصل؛ إكمال جدول PostgreSQL من `0001` إلى `0017`؛ تحديث `ARCHITECTURE.md` إلى `42/34`؛ توثيق مسؤوليات `worker/api/delivery.ts` دون تقسيمه؛ وإضافة قسم Worker مستقل إلى `FILE-SIZE-AND-RESPONSIBILITY-REGISTER.md` نفسه، لا إنشاء سجل موازٍ. **القبول:** لا citations فارغة بلا تفسير؛ المصدر النصي والملف المولّد متصالحان؛ اختبار المولّد يكشف أي انجراف؛ لا ادعاء بأن الاختبارات المدرجة قد شُغلت ما لم توجد نتيجة تشغيل على SHA نفسه.<br>

### الموجة 4 — أخطاء المجال وحد HTTP (R03)

**الاعتماديات:** عقد أخطاء محايد موثق وتوصيف مرجعي للاستجابات الحالية؛ تنفذ منفصلة عن الموجتين 2 و3 وعن أي تغيير مالي أو أمني.<br>
**النطاق:** تعريف أخطاء/نتائج مجال محايدة وترجمتها عند API فقط.<br>
**القبول:** لا اعتماد مجال على `HttpError`؛ تبقى استجابات HTTP الحالية (الحالة والرمز والتفاصيل والحقول/الرسائل المتعاقد عليها) مطابقة؛ لا تغيير لقبول المجال أو التفويض أو المال. إذا لم يثبت التكافؤ، تتوقف الموجة. اختبارات توصيف وموجة CI على SHA نفسها مطلوبة.<br>
**حد الرجوع:** commit منفصل لمحولات المجال وAPI واختباراتها فقط.

**قاعدة كل موجة تنفيذية:** فحوص مركزة ثم CI على SHA الموجة نفسها؛ لا تغييرات مباشرة على `main`، ولا نقل جماعي، ولا دمج بين موجات يجعل التراجع ملتبسًا. لا تتضمن أي موجة ترحيلات قاعدة بيانات أو اتصالًا حيًا أو بيانات حقيقية. لا يُجرى أي تعديل مالي أو أمني أو سلوكي مخفي؛ إذا كشف التنفيذ ضرورة لذلك، تتوقف الموجة ويُطلب قرار مستقل.

## 5. الأعمال المؤجلة والمراجعات المستقبلية ومحفزات إعادة فتحها

| المؤجل/المراجعة المستقبلية | متى يعاد فتحه | ما يلزم قبل أي تنفيذ |
|---|---|---|
| دراسة تقسيم مدققات النقل (R06) | بعد التشغيل الأولي أو عند تغيير عقد يمسها مباشرة | قائمة المستهلكين ومصدر الحقيقة؛ اختبارات توصيف وتكافؤ للمحولات وعائلات البيانات. |
| مراجعة محرر شراء المورد (R07) | مراجعة لاحقة بعد بدء التشغيل | جرد بصري/مسؤوليات؛ حدود صريحة تمنع خلط استخراج الواجهة مع المبالغ والدفع والتراجع والاستلام. |
| تقسيم API التوصيل (R08، بعد توثيق المسؤوليات في 1A) | بعد اكتمال الجرد ووجود سبب مثبت؛ يقرر المالك إن كان يلزم بعد التشغيل | خريطة المعالجات والمستهلكين والاختبارات وحدود المسارات؛ ثم قرار مستقل قبل أي نقل. |

| توحيد حراس التحقق (R12) | بعد اكتمال المرحلة الحالية والتشغيل الأولي | تعريف عقد موحد ورسائل الرفض والمستهلكين واختبارات تكافؤ؛ لا توحيد افتراضي. |
| مراجعة أسماء العقود (R13) | عند المراجعة التالية للفهرس أو عقود الشبكة/المحلي | حفظ L/N وكل المعرّفات والإحالات كما هي؛ لا إعادة ترقيم، مع سجل تعارضات للأسماء. |
| مراجعة تمثيل المبلغ (R15) | بقرار مستقل خارج موجات التنظيم | فحص مالي/عقدي يحدد مصدر الحقيقة والتوافق والآثار قبل أي تغيير. |

تبقى محولات التخزين (R05) وترحيلات D1 التاريخية (R14) محفوظة؛ ليستا ديونًا مؤجلة لإصلاحها. CSS (R09) خارج النطاق البنيوي. قائمة المؤجلات لا تمنح إذنًا بتغيير سلوكي أو مالي أو أمني بعد التشغيل؛ كل إعادة فتح تحتاج نطاقًا ودليلًا وقرارًا مناسبًا.
