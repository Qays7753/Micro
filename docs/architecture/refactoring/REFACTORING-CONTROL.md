## 1. الهدف

إعادة تنظيم **التطبيق الحالي** تدريجيًا بحيث يصبح أسهل في التطوير والتوسع وتغيير المبادئ وإصلاح المشاكل، من دون إعادة بناء التطبيق من الصفر ومن دون تغيير معنى المال أو البيانات أو السلوك لمجرد تحسين شكل المجلدات.

الرأي المعماري المعتمد في الخطة المرجعية هو **Modular Monolith** بحدود وحدات حقيقية مبنية على مسؤوليات العمل، لا Microservices ولا إعادة كتابة شاملة.

## 4. المرحلة الأولى المسموحة: تثبيت الفهم وبناء خطة الانتقال

المخرَج المطلوب هو تقرير/خطة واحدة شاملة، مصنفة ومسنودة بالأدلة، تبدأ من الواقع الحي ولا تعتمد على تقرير بنيوي سابق كاختصار، ثم تبني خطة الانتقال. تغطي الخطة:

1. حدود الوحدات والميزات الحالية.
2. مسؤولية كل مجلد وملف كبير أو مركب.
3. الملفات المتضخمة والملفات التي تحمل أكثر من مسؤولية.
4. اتجاهات الاعتماديات وخرق الطبقات والدورات وDeep Imports.
5. التكرار ومصادر الحقيقة المتنافسة ومكان الحساب الحاكم.
6. قابلية اكتشاف المكونات والخدمات والعقود والاختبارات.
7. تركيب Presentation / Application / Domain / Storage / Adapters.
8. علاقة التخزين والاستيراد/التصدير والاختبارات بالحدود الحالية.
9. خريطة الاختبارات والوثائق والمراجع لكل وحدة.
10. خريطة هدف مبدئية: ما الذي يبقى، وما الذي يُعاد تسميته أو يعاد توجيهه، وما الذي يمكن نقله فقط بعد بوابة لاحقة.
11. قابلية المستقبل: Android/iOS أو Dart/Flutter أو Python/API تُدرس كـTriggers وعقود، لا كتنفيذ أو إعادة بناء الآن.
12. جرد كل ملف إنتاجي واختباري وScript وGenerated Artifact وFixture وSnapshot وConfiguration داخل النطاق، مع الحجم والمسؤوليات والنمو وقرار `PRESERVE` أو `WATCH` أو `SPLIT_CANDIDATE` أو `SPLIT_NOW` أو استثناء مبرر.
13. الآثار الجانبية والتهيئة، Public APIs والعقود، حدود الإعدادات والأسرار والأمان والصلاحيات، الاعتماديات والأداة، التزامن والفشل والاستعادة، دورة حياة الحالة والكاش والأحداث والإبطال، دورة حياة البيانات والنسخ الاحتياطي والاستعادة والاحتفاظ، الأداء والموارد، مصادر الملفات المولدة، حتمية الاختبارات، الترحيل والرجوع، التشخيص، قابلية إعادة البناء وتطابق بيئة الإصدار، وتتبع الفروع والـPRs والتقارير.

## 5. تصنيف كل نتيجة

كل Finding يجب أن يحمل تصنيفًا واحدًا على الأقل:

- `FIX_NOW`: إصلاح آمن ومحدود لا يغيّر المعنى، ويوافق عليه المالك قبل التنفيذ.
- `PRESERVE`: سليم أو حساس؛ لا يلمس لمجرد النظافة.
- `DEFER`: مهم لكن يحتاج مرحلة أو دليلًا أو قرارًا لاحقًا.
- `OUT_OF_SCOPE`: خارج برنامج الهيكلة الحالي، مثل UI/UX أو منصة جديدة.
- `OWNER_DECISION_REQUIRED`: تعارض أو اختيار قد يغيّر الملكية أو السلوك أو التاريخ ولا يجوز تخمينه.

يفصل التقرير دائمًا بين `VERIFIED` و`INFERRED` و`UNVERIFIED` و`NOT_EXECUTED` و`DEFERRED` و`BLOCKER`.

## 6. ما يجب ألا يدخل في هذه المرحلة

- لا تغيير في منطق المجال أو المعادلات أو السياسات أو المصطلحات.
- لا تغيير في Schema أو Export/Import أو Migration أو البيانات التاريخية.
- لا تغيير في React أو TSX أو CSS أو tokens أو DOM أو Navigation أو UI/UX.
- لا نقل ملفات جماعي ولا حذف ولا إعادة تسمية.
- لا استخراج Ports أو Facades أو Shared Kernel تنفيذية.
- لا إضافة Dart أو Flutter أو Kotlin أو Swift أو Python أو Backend أو API أو Sync أو Auth.
- لا إنشاء `features/` أو `common/` أو `utils/` عامة لمجرد التنظيم.
- لا دمج PRs قديمة أو فروع قديمة لمجرد أن التقرير وجدها.

## 7. بوابة الانتقال بعد التقرير

لا تبدأ أي Wave تنفيذية حتى:

1. يوجد تقرير كامل ومساراته صحيحة.
2. كل نتيجة مصنفة ومسنودة بدليل.
3. توجد خريطة ملكية ومستهلكين لكل مفهوم أو حد مرشح للتغيير.
4. يحدد التقرير الحد الأدنى للموجات وترتيب اعتمادياتها.
5. يراجع المالك التقرير ويقبل أو يرفض أو يؤجل كل مجموعة نتائج.
6. تُكتب بطاقات الموجات المقبولة مع نطاق وملفات وحدود اختبار وحد رجوع.
7. لا توجد نتيجة `OWNER_DECISION_REQUIRED` مخفية داخل `FIX_NOW`.
8. لا يوجد ملف داخل النطاق مفقود من `FILE-SIZE-AND-RESPONSIBILITY-REGISTER.md`، ولا يوجد `SPLIT_NOW` أو `REVIEW_REQUIRED` بلا مالك ومستهلكين وإجراء وحد رجوع.
9. كل سطح مهني إضافي له دليل أو تصنيف صريح `DEFER` أو `OUT_OF_SCOPE`، ولا يُفترض أنه سليم لأنه لم يكن من الملفات الثلاثة الأصلية.

## 8. معيار إعادة الهيكلة لاحقًا

كل موجة معتمدة لاحقًا يجب أن تحتوي على:

- Base SHA وBranch واضح؛
- سبب جذري ومشكلة مستقلة؛
- Consumer Inventory قبل النقل؛
- Parity Oracle أو Characterization/Contract Tests عند الحاجة؛
- قائمة الملفات المسموحة والممنوعة؛
- أثر صريح على Schema/Export/Import/Financial/UI: غالبًا «لا أثر»؛
- Acceptance Criteria قابلة للفحص؛
- Rollback Boundary للكود والبيانات؛
- سجل حجم ومسؤولية ونمو محدث، مع سبب واضح للإبقاء على أي ملف كبير أو قريب من الحد؛
- تقرير مختصر وPR مستقل أو شريحة مفهومة؛
- فحوص مركزة وCI بعد كل موجة فعلية.

لا يُحسب تحسين عدد المجلدات نجاحًا إذا زاد الاقتران أو ظهرت مصادر حقيقة ثانية أو تغير السلوك.
