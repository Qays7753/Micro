## الغرض

هذا المجلد يجمع الملفات التي يحتاجها برنامج إعادة هيكلة **التطبيق الحالي** فقط، بهدف تحسين:

- سهولة التطوير والتوسع؛
- سهولة تغيير قاعدة أو مبدأ دون تعديل النظام كله؛
- سهولة اكتشاف المشكلة وإصلاحها؛
- وضوح ملكية كل مفهوم ومصدر حقيقته؛
- حماية المنطق المالي والتاريخي من التغيير الصامت.

وجود هذا المجلد يعني أن برنامج إعادة الهيكلة **اكتمل بنيويًا ومُتحقق على `main`**؛ ولا يمنح ذلك أي Agent إذنًا بفتح موجة جديدة أو نقل الملفات أو إعادة تنظيم الكود. أي مسار مستقبلي يحتاج مسحًا قراءة-فقط وبوابة مالك جديدة وحدودًا مكتوبة.

## السلطة

1. `AGENTS.md` هو بوابة القراءة والتنفيذ الحاكمة.
2. `docs/operations/current-state.md` هو الحالة الحية لـ`main`.
3. `REFACTORING-PLAN-A-TO-Z.md` هو الخطة المعمارية المرجعية الوحيدة لهذا البرنامج.
4. `REFACTORING-CONTROL.md` يحدد حالة البرنامج وبواباته التشغيلية.
5. خطة الانتقال الموحدة `REFACTORING-ARCHITECTURE-AND-MIGRATION-PLAN.md` — **موجودة ومقبولة ومصالح عليها بعد الدمج** (v1.1 و§23) — مبنية على الأدلة، وليست تفويضًا لفتح موجة جديدة.

إذا تعارض أي ملف هنا مع عقد أو سياسة مالية أو قرار مالك، تتغلب الوثيقة الحاكمة ويسجل التعارض بدل التخمين.

## الممنوعات الدائمة (خط الأساس لأي مرحلة)

هذه الممنوعات سارية دائمًا كخط أساس، وقد كانت نص مرحلة المسح الأولية؛ الموجات التنفيذية المقبولة وحدها تمس مساراتها المسموحة المكتوبة في بطاقتها (جدول الموجات §23.9 من خطة الانتقال)، وكل ما عدا ذلك يظل ممنوعًا:

- تعديل `apps/` أو `src/` أو `tests/` أو `scripts/` خارج مسارات موجة مقبولة بنطاقها المكتوب؛
- نقل أو إعادة تسمية أو حذف أي ملف؛
- إنشاء مجلد `features/` أو `shared/` أو `utils/` جديد؛
- تغيير المعادلات أو المصطلحات أو السياسات المالية؛
- تغيير Schema أو Migration أو Export/Import أو Historical Interpretation؛
- تعديل UI/UX أو CSS أو TSX أو tokens أو DOM أو visual QA؛
- بناء Dart أو Flutter أو Python أو API أو Sync أو Auth؛
- دمج نتائج المسح أو تنفيذ أي موجة بنيوية قبل مراجعة المالك وقبولها المسجل.

يجوز إنشاء/تحديث تقارير المسح وملفات التحكم التوثيقية داخل هذا المجلد بـPR منفصل وواضح، وفق البوابات الموصوفة في `REFACTORING-CONTROL.md`.
