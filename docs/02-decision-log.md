# سجل قرارات مشروع SaaS

**قاعدة:** القرار الأحدث الموثق في الملف المرجعي الأساسي هو المعتمد. القرارات المسحوبة محفوظة للتاريخ فقط.

## قرارات معتمدة

| المعرّف | القرار | المرجع |
|---|---|---|
| D-001 | المنتج خدمة SaaS يملكها المطور، والمستخدم صاحب مشروع؛ لا Billing داخل تطبيق المستخدم في MVP | `docs/01-product-and-technical-blueprint.md` |
| D-002 | السوق الأول الأردن والدينار الأردني، والفئات الحرف والطعام والخدمات | المرجع الأساسي |
| D-003 | المشكلة المركزية هي فقدان السيطرة على التكلفة والربح والكاش والطلبات والفعل التالي | Problem Statement داخل المرجع الأساسي |
| D-004 | النواة مستقلة عن Accounting وzman-app؛ يستفاد منهما كمراجع فقط | قسم المعمارية في المرجع الأساسي |
| D-005 | التنفيذ يبدأ بVertical Slice وModular Monolith، لا Rewrite شامل ولا ERP | `docs/research/architecture-decision-reassessment.md` |
| D-006 | التخزين المستهدف هجين، لكن اختيار المزود النهائي يمر عبر prototype وقياس | المرجع الأساسي + قرار Stack |
| D-007 | الطلب رحلة من الاتفاق إلى التنفيذ والتسليم والتحصيل، وليس فاتورة فقط | المرجع الأساسي + Order Truth Map |
| D-008 | التدريب داخل المنتج كتدرج ومهام، لا LMS كامل | المرجع الأساسي + حارس المنتج |
| D-009 | كل ميزة تحتاج فرضية، دليلًا، أقل نطاق، معيار قبول وفشل | حزمة المهارات |
| D-010 | لا كود خارجي دون ترخيص ومصدر ونسخة وفحص ملاءمة | مكتبة المراجع + حارس التنفيذ |
| D-011 | أول Vertical Slice هو طلب حرفة يدوية مخصصة قبل الطعام والخدمات | `docs/decisions/01-first-vertical-slice.md` |
| D-012 | خبرة صاحب المنتج الممتدة قرابة 14 عامًا دليل مؤسس على الحاجة، وليست إثباتًا إحصائيًا أو دليل دفع؛ تفاصيل الحالات والتعميم تحتاج خريطة دليل وPilot | `docs/07-field-evidence-map.md` و`docs/04-product-truth-map.md` |
| D-013 | لا يكون مؤشر النتيجة ربحًا نهائيًا إلا عندما تكون `knowledgeState` مساوية لـ`known`؛ ويُحمل الطلب `resultStatus` يميز النهائي والتقديري والناقص والمراجعة المطلوبة | `docs/contracts/01-financial-result-contract.md` وDomain Core |
| D-014 | إلغاء طلب ذي عربون لا يُسوّى تلقائيًا؛ يبدأ بـ`needs_review` وتنفذ عملية رد أو احتفاظ مستقلة قابلة لإعادة المحاولة | `docs/contracts/02-order-lifecycle-contract.md` وDomain Core |
| D-015 | لا تُستخدم حالة `stale` بلا سياسة حداثة صريحة قابلة للاختبار، وSnapshot الحرفة المخصصة بلا مكونات مؤثرة يكون `incomplete` | `docs/contracts/03-cost-snapshot-contract.md` وDomain Core |
| D-016 | مجموعة السيناريوهات ذات 10 شخصيات و100 حالة و100 سؤال عائلة اختبار دائمة؛ تثبت أن الطلب أول Vertical Slice داخل نظام إدارة مالية مستمر، ولا تختزل المنتج في طلب أو مصروف | `docs/decisions/03-scenario-validation-and-system-scope.md` |
| D-017 | الوثائق canonical الجديدة تفصل Problem Statement وتعريف النظام ونموذج الاستخدام والنموذج المالي والتوجيه والأدلة والسيناريوهات؛ التدرج في التنفيذ لا يلغي اكتمال تعريف النظام | `docs/00-document-index.md` وحوكمة الوثائق |

## قرارات مسحوبة أو غير معتمدة

| القرار القديم | سبب السحب | الوضع الحالي |
|---|---|---|
| الاعتماد على Accounting كنواة المنتج الجديد | انحياز لإعادة الاستخدام وإرث مفاهيمي قد يفرض نموذجًا قديمًا | مسحوب؛ النواة مستقلة |
| نقل zman-app إلى المنتج | يحول حالة زوجية إلى افتراض سوقي وينقل flow غير مثبت | مسحوب؛ نأخذ patterns فقط |
| بناء نظام محاسبة شامل أولًا | يزيد المصطلحات والحقول ولا يبدأ من قرار المستخدم | مرفوض |
| بناء SaaS متعدد المستخدمين وفروع مبكرًا | لا دليل على القيمة الأولى أو العودة أو الدفع | مؤجل؛ حد معماري فقط |
| إضافة Billing أو بوابة دفع داخل تطبيق المستخدم | خلط SaaS الخاص بالمالك مع تجربة صاحب المشروع | خارج MVP |
| اعتبار offline-only بديلًا عن SaaS | لا يحمي من فقد الجهاز ولا يوفر نسخة مركزية | مسحوب؛ النموذج الهجين قيد الاختبار |
| اعتبار دينار واحد شهريًا سعرًا نهائيًا | لا توجد اقتصاديات تشغيل أو استعداد دفع مثبتة | فرضية تجارية فقط |
| نقل كود GitHub لأنه مفتوح أو مشهور | الترخيص والنضج والملاءمة تختلف | ممنوع دون بوابة الكود الخارجي |

## بوابة تغيير القرار

لا يغير الذكاء الاصطناعي قرارًا معتمدًا بعبارة عابرة. يجب أن يذكر القرار القديم، الدليل الجديد، التعارض، أثر التغيير، الملفات المتأثرة، وتجربة الاعتماد. بعد الموافقة، يحدث المرجع الأساسي وسجل الفرضيات وTruth Map.
