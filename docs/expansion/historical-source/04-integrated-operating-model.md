# النموذج التشغيلي المتكامل
## البوابات الثلاث، الحالات، وتبادل المعلومات داخل Micro

## 1. القاعدة الأساسية

تعمل Micro Market وMicro Delivery كقدرتين متجاورتين داخل منصة Micro. تظهر التجربة مترابطة لصاحب المشروع، لكن يبقى معنى كل قدرة منفصلًا:

> **Market يجيب عن: ما المنتج؟ من المورد؟ وما التفاصيل التي أحتاجها قبل التواصل؟**
>
> **Delivery يجيب عن: ماذا سينقل؟ من أين؟ إلى أين؟ متى؟ وما عرض شركة التوصيل؟**

الاتفاق التجاري بين صاحب المشروع والمورد يحدث خارج Micro. يمكن تسجيل تفاعل أو اتفاق خارجي بشكل اختياري، لكن Micro لا يصبح طرفًا في البيع ولا يضمن الدفع أو السعر النهائي أو المطابقة.

## 2. الجهات والحدود

| الجهة | ما تراه وما تفعله |
|---|---|
| صاحب المشروع | يرى النظام المالي وMarket وDelivery وكل ما يرتبط بمشروعه. يبحث ويتواصل ويسجل متابعة اختيارية وينشئ طلب جلب أو إرسال ويتابع السعر والحجز والتسليم. |
| المورد | يرى منتجاته وListings الخاصة به، والتفاعلات أو الطلبات المرتبطة بها، ويضيف ويحدث ويؤكد الجاهزية وينشئ أو يتابع Delivery تخصه. |
| شركة التوصيل | ترى طلبات الجلب والإرسال التي وصلت إليها فقط، وتراجعها وتحدد سعرها وموعدها وتسجل حالات الرحلة من بوابتها. |
| إدارة المنصة الداخلية | تراجع Listings قبل النشر وتتعامل مع المحتوى أو البلاغات وفق السياسة. لا تدير Orders اليومية ولا تبحث عن سيارة لكل طلب. |

لا توجد جهة سائق داخل Micro. شركة التوصيل تدخل اسم ورقم منفذ الرحلة عند الحاجة، وتحدث جميع حالات التنفيذ من بوابتها. ولا توجد واجهة أو حساب أو صلاحية مستقلة للسائق.

## 3. البوابات

### 3.1 بوابة صاحب المشروع

هي تطبيق Micro الأساسي، وتضم النظام المالي وMarket وDelivery ضمن سياق المشروع. يستطيع صاحب المشروع:

- البحث عن منتج أو مادة.
- مشاهدة الصور والوصف والسعر والوحدة والكمية والتوفر ووقت التجهيز وبيانات المورد.
- التواصل مع المورد.
- تسجيل أن التواصل أو الاتفاق الخارجي حصل، مع تفاصيل اختيارية.
- طلب جلب من المورد أو إرسالًا من مشروعه.
- رؤية عرض شركة التوصيل، بما فيه السعر والموعد واسم ورقم منفذ الرحلة.
- تأكيد الحجز أو رفض العرض.
- متابعة الجاهزية والاستلام والطريق والتسليم أو الفشل.
- تقييم تجربة المورد بعد وجود تفاعل مناسب.
- تسجيل أثر مالي أو مخزني يدويًا في Micro عند الحاجة، دون إنشاءه تلقائيًا من Delivery.

### 3.2 بوابة المورد

بوابة مستقلة في الواجهة والوصول، مخصصة لعمل المورد، وتحتوي على:

| القسم | المحتوى |
|---|---|
| منتجاتي | إنشاء وتعديل الصور والاسم والفئة والوصف والوحدة والسعر والكمية والتوفر ووقت التجهيز والموقع. |
| حالات النشر | مسودة، قيد المراجعة، منشور، بحاجة إلى تحديث، موقوف، أو غير متاح. |
| التفاعلات والطلبات | ما يرتبط بمنتجات المورد فقط. إدخال الطلب اختياري من صاحب المشروع، لذلك قد يرى المورد تفاعلًا مختصرًا أو سجل متابعة. |
| التأكيد | رأيت التفاعل، أستطيع التجهيز، غير متوفر، أحتاج تواصلًا، أو لا أتعرف على الطلب. |
| التوصيل | إنشاء جلب أو إرسال مرتبط، أو متابعة مهمة تحتاج المورد أو نقطة الاستلام لديه. |
| التاريخ | سجل منتجاته وتفاعلاته وطلباته وتوصيلاته وتقييماته. |

لا يرى المورد النظام المالي لصاحب المشروع، ولا طلبات الموردين الآخرين، ولا يعدل اتفاقًا خارجيًا لم ينشئه أو يؤكده.

### 3.3 بوابة شركة التوصيل

ترى الشركة فقط الطلبات التي وصلت إليها أو أصبحت مرتبطة بها. تحتوي على:

- طلبات الجلب والإرسال الجديدة.
- المصدر والوجهة والعناوين وأرقام الاتصال الضرورية.
- وصف الطرد وعدده وحجمه التقريبي.
- التاريخ والوقت المفضل.
- قبول مبدئي أو رفض مع سبب.
- إدخال سعر التوصيل والموعد المتاح.
- إدخال اسم ورقم منفذ الرحلة، دون إنشاء حساب له.
- تحديث جاهزية الاستلام والاستلام والطريق والتسليم والفشل.
- إعادة الجدولة عند الحاجة.
- سجل كامل للطلبات السابقة الخاصة بالشركة.

لا ترى الشركة النظام المالي لصاحب المشروع، ولا سعر المنتج أو العربون أو كامل تفاصيل الاتفاق التجاري بين المشتري والمورد. ترى فقط ما يلزم لتنفيذ الحركة.

## 4. وظيفة الإدارة الداخلية

توجد وظيفة إدارة داخلية لأن Listings تحتاج إلى مراجعة قبل النشر. هذه الوظيفة ليست «مشغلًا» بالمعنى الذي يتولى الطلبات اليومية، ولا طرفًا في التفاوض أو التوصيل.

صلاحياتها المفاهيمية محدودة إلى:

- مراجعة Listing الجديدة.
- الموافقة على النشر أو طلب تعديل أو الرفض أو الإيقاف.
- التحقق من اكتمال الصورة والوصف والفئة والسعر وبيانات التواصل.
- متابعة انتهاء مدة الـ60 يومًا وطلب تحديث Listing.
- معالجة المحتوى المخالف أو البلاغات المتعلقة بالمنصة.

لا تقوم الإدارة بقبول الطلب بدل المورد، ولا تحدد سعر التوصيل بدل الشركة، ولا تبحث عن سيارة لكل مهمة، ولا تفصل في نزاع الدفع أو الجودة.

## 5. الصلاحيات المفاهيمية

في مرحلة الدخول الحقيقي تطبق الصلاحيات على مستوى الجهة والكيان والعلاقة، وليس بمجرد إخفاء زر في الواجهة. وفي المفهوم الحالي نثبت حدود الرؤية نفسها حتى أثناء المحاكاة المحلية.

| الفعل | صاحب المشروع | المورد | شركة التوصيل | الإدارة الداخلية |
|---|---:|---:|---:|---:|
| تصفح Listings المنشورة | نعم | نعم | عند الحاجة | نعم |
| إنشاء Listing | لا | نعم | لا | لا |
| تعديل Listing يخصه | لا | نعم | لا | مراجعة/إيقاف |
| تسجيل تواصل أو اتفاق خارجي | نعم | يمكنه تأكيد التفاعل | لا | لا |
| إنشاء Delivery | نعم | نعم عند ارتباطها به | يمكن حسب السياسة لاحقًا | لا |
| تقديم عرض سعر توصيل | لا | لا | نعم | لا |
| تأكيد حجز عرض التوصيل | نعم، إذا كان طالب السيارة | نعم، إذا كان هو الطالب | لا | لا |
| إعلان جاهزية الطرد | لا | نعم عند المصدر | لا | لا |
| تسجيل الاستلام والتسليم | يرى النتيجة المرتبطة به | يرى المهمة المرتبطة به | نعم من بوابتها | لا إلا تصحيح موثق |
| إدخال اسم ورقم منفذ الرحلة | لا | لا | نعم | لا |
| رؤية النظام المالي للمشروع | نعم | لا | لا | لا |
| مراجعة نشر Listing | لا | لا | لا | نعم |

## 6. تبادل المعلومات داخل Micro

المقصود بالتبادل هنا أن الأطراف تستخدم بوابات Micro نفسها، لا أن Micro يرسل البيانات إلى أنظمة خارجية عبر API.

| المصدر | المستقبل داخل Micro | البيانات الضرورية |
|---|---|---|
| المورد | Market وإدارة المنصة | Listing، الصور، الوصف، الفئة، الوحدة، السعر، الكمية، التوفر، التجهيز، الموقع والتواصل. |
| Market | صاحب المشروع | العرض، حالة النشر، تاريخ التحديث، البيانات التشغيلية، بيانات المورد. |
| صاحب المشروع | Micro | سجل تواصل أو اتفاق خارجي اختياري، الكمية أو الوصف عند الرغبة، وطلب Delivery عند الحاجة. |
| Micro | المورد | تفاعل أو طلب مرتبط بمنتجه، والكمية والموعد والتفاصيل التي أدخلها صاحب المشروع. |
| صاحب المشروع أو المورد | شركة التوصيل | المصدر والوجهة والطرد والموعد وبيانات الاتصال اللازمة. |
| شركة التوصيل | طالب السيارة والمهمات المرتبطة | قبول/رفض، سعر، موعد، اسم ورقم منفذ الرحلة، جاهزية، استلام، طريق، تسليم أو فشل. |
| Micro | النواة المالية | اقتراح أو رابط لفعل صريح يسجله صاحب المشروع، لا كتابة تلقائية من Market أو Delivery. |

لا ترسل الشركة إلى Micro أو ترى أكثر من حاجتها. لا يرسل المورد كاش المشروع أو ديونه. ولا يحتاج صاحب المشروع إلى رؤية لوحة تشغيل الشركة الداخلية.

## 7. دورة Market وDelivery المتكاملة

```text
صاحب المشروع يجد Listing
→ يتواصل مع المورد خارجيًا
→ يسجل تفاعلًا أو اتفاقًا خارجيًا اختياريًا
→ المورد يرى التفاعل ويؤكد الاستلام/القدرة/عدم التوفر
→ عند الحاجة ينشئ صاحب المشروع أو المورد طلب Delivery
→ شركة التوصيل تراجع المهمة
→ الشركة تحدد السعر والموعد واسم ورقم منفذ الرحلة
→ طالب السيارة يؤكد الحجز أو يرفض العرض
→ المصدر يعلن الجاهزية
→ الشركة تسجل الاستلام والطريق والتسليم أو الفشل
→ صاحب المشروع يقيّم التجربة أو يسجل أثرًا ماليًا يدويًا
```

كل سهم يصف حدثًا مختلفًا. لا يثبت التسجيل أن الاتفاق تم، ولا يثبت قبول الشركة أن الطرد جاهز، ولا يثبت التسليم أن المال دُفع.

## 8. الحالات ومصدر الحقيقة

### Market

```text
draft → pending_review → published → update_required → published
                              ├→ paused
                              └→ unavailable
```

### سجل التفاعل

```text
started → agreed_externally (اختياري)
       → details_saved (اختياري)
       → delivery_requested (اختياري)
       → closed / not_confirmed
```

### Delivery

```text
created
→ sent_to_courier
→ under_review
→ courier_offer
→ booked_after_requester_confirmation
→ waiting_for_ready
→ ready_for_pickup
→ picked_up
→ in_transit
→ delivered
```

وتوجد حالات فشل أو توقف مثل: رفض الشركة، رفض الطالب، إلغاء، تأجيل، المورد غير جاهز، لا توجد سيارة، عنوان ناقص، فشل الاستلام، المستلم غير موجود، فشل التسليم، أو طرد ناقص/متضرر.

مصدر الحقيقة هو الحالة المسجلة وسجل الحدث داخل Micro، وليس إشعارًا مؤقتًا أو اتصالًا خارجيًا. في المرحلة الحالية لا توجد API أو Webhooks خارجية؛ وإذا حصل تواصل هاتفي، تسجل الجهة النتيجة يدويًا داخل بوابتها أو في السجل المناسب.

## 9. الثقة والتقييم

تحمي المنصة المورد وصاحب المشروع وشركة التوصيل بالوضوح، لا بالادعاء. يظهر للمستخدم الفرق بين:

| العبارة | معناها |
|---|---|
| تم تسجيل التواصل | صاحب المشروع سجل أنه تواصل، ولا يثبت أن المورد رد. |
| المورد رأى التفاعل | المورد فتح السجل أو أكد الاطلاع. |
| المورد يستطيع التجهيز | المورد أعلن قدرة تشغيلية، لا ضمانًا لجودة أو دفع. |
| عرض توصيل مقدم | الشركة حددت سعرًا وموعدًا مقترحين. |
| الحجز مؤكد | طالب السيارة وافق على العرض. |
| تم الاستلام | الشركة سجلت انتقال الغرض إليها. |
| تم التسليم | الشركة سجلت وصول الغرض أو محاولة التسليم وفق ما أدخلته. |

يبنى تقييم المورد من تفاعل أو تجربة مسجلة، ويمكن أن يغطي الاستجابة ودقة الإعلان والتوفر والجاهزية والوضوح وتجربة التعامل. لا يحول التقييم Micro إلى ضامن للصفقة أو محكم للنزاع.

## 10. البيانات المالية

Market وDelivery ينتجان مراجع وأحداثًا تشغيلية. لا ينشئان تلقائيًا:

- قبضًا.
- ربحًا.
- شراءً.
- تكلفة بيع.
- دخول مخزون.
- مصروف توصيل.
- دينًا أو عربونًا مثبتًا.

يستطيع صاحب المشروع، من Micro المالي، تسجيل الأثر المناسب يدويًا. يمكن للواجهة أن تعرض اقتراحًا أو رابطًا مثل «تسجيل شراء»، لكن لا يحدث الحفظ دون فعل وتأكيد المستخدم، وبما يلتزم بعقود Micro المالية.[1] [2]

## 11. ما لا نفعله

لا نبني API أو Webhook في هذا المفهوم. لا نبني تطبيق سائق أو بوابة سائق. لا نضيف مشغلًا يدير الطلبات اليومية. لا نجعل الإدارة الداخلية تتفاوض أو تعيد توزيع كل سيارة. لا نضيف سلة متعددة الموردين أو مسارات متعددة التوقفات أو دفعًا داخل المنصة أو ضمانًا ماليًا قبل قرار مستقل.

## 12. القرار

النظام المستهدف هو منصة Micro مستقلة ذات ثلاث بوابات تجارية: Owner App، Supplier Portal، وCourier Company Portal. يتشارك الأطراف الحالات الضرورية داخل Micro، لكن كل طرف يرى واجهته وبياناته وأفعاله فقط. الاتفاق التجاري خارج التطبيق، والتأكيد داخل التطبيق تشغيلي واختياري ومفيد للمتابعة والتقييم. Delivery تبدأ بطلب إلى شركة افتراضية واحدة، تحدد الشركة السعر والموعد، ويؤكد طالب السيارة الحجز، ثم تسجل الشركة كل حالات التنفيذ. لا يوجد سائق كمستخدم، ولا API خارجي، ولا مشغل تشغيلي.
