# Micro Market وMicro Delivery
## المسار التقني والتنفيذي بعد اعتماد المفهوم

## 1. وضع الوثيقة

هذه الوثيقة تصف المسار الذي سيأتي بعد اعتماد مفهوم Market وDelivery. لا تعني أن البناء بدأ، ولا أن هذه القدرات موجودة في `main`. لا تغيّر هذه الوثيقة حدود Prototype الحالي لـMicro، ولا تضيف Auth أو Cloud أو API إلى الكود القائم.

القرار الأساسي هو أن Micro Market وMicro Delivery **نظام مستقل قائم بذاته داخل منصة Micro**. المورد وشركة التوصيل يستخدمان بوابات Micro الخاصة بهما. لا يوجد في المرحلة الأساسية ربط تلقائي مع نظام خارجي لمورد أو شركة توصيل.

## 2. تعريف النسخة المطلوبة

النسخة الأولى التي نريد إثباتها هي دورة مترابطة، لا Marketplace مؤسسي ولا شبكة توصيل وطنية:

```text
صاحب المشروع يجد Listing
→ يتواصل مع المورد خارج Micro
→ يسجل تفاعلًا أو اتفاقًا خارجيًا اختياريًا
→ المورد يؤكد الاطلاع أو القدرة على التجهيز
→ ينشئ صاحب المشروع أو المورد طلب جلب/إرسال عند الحاجة
→ شركة التوصيل تراجع الطلب
→ الشركة تقدم السعر والموعد واسم ورقم منفذ الرحلة
→ طالب السيارة يؤكد الحجز أو يرفض العرض
→ الشركة تسجل الجاهزية والاستلام والطريق والتسليم أو الفشل
→ صاحب المشروع يراجع التجربة، ويقرر يدويًا أي أثر مالي أو مخزني
```

الاتفاق التجاري والدفع بين صاحب المشروع والمورد خارج Micro. سجل Market لا يصبح فاتورة أو قبضًا. وDelivery لا تصبح شراءً أو مصروفًا أو ربحًا تلقائيًا.

## 3. المراحل

### المرحلة الأولى: تثبيت المفهوم والعقود

نثبت المصطلحات، الجهات الثلاث، حدود الرؤية، Listing، Market Interaction Record، DeliveryTask، حالات التوصيل، معنى موافقة المورد، ومعنى عرض شركة التوصيل وتأكيد الحجز. نثبت أيضًا أن إدارة المنصة تراجع Listings فقط ولا تدير الطلبات اليومية.

### المرحلة الثانية: Prototype محلي مترابط

يبنى Prototype على جهاز واحد وقاعدة Local، ويتيح للمالك محاكاة الأدوار التالية دون Login أو Authorization حقيقي:

```text
Owner View
Supplier View
Courier Company View
```

لا توجد Driver View. إذا احتاجت التجربة إلى اسم أو رقم منفذ الرحلة، تدخل شركة التوصيل البيانات يدويًا من بوابتها المحاكاة. لا توجد API أو Webhook أو Cloud Sync أو إشعارات خارجية حقيقية.

يجب أن تتشارك Views الثلاث Local Database واحدة حتى تظهر دورة العمل كاملة: Listing المورد تظهر لصاحب المشروع، ومهمة صاحب المشروع تظهر لشركة التوصيل، وتحديث الشركة يظهر لصاحب المشروع أو المورد ذي العلاقة.

### المرحلة الثالثة: Pilot متصل ببوابات Micro

بعد اختبار Prototype لمدة شهر، وإذا ثبتت قيمة الدورة، نضيف Backend مركزيًا وLogin وصلاحيات وبيانات مشتركة. تصبح لكل جهة بوابة دخول مستقلة في الواجهة والوصول:

- Owner App لصاحب المشروع.
- Supplier Portal للمورد.
- Courier Company Portal لشركة التوصيل.

لا نضيف في هذه المرحلة API مع أنظمة خارجية. المستخدمون يدخلون إلى Micro ويحدثون البيانات يدويًا من بواباتهم.

### المرحلة الرابعة: MVP مستقل

نضيف ما يلزم لتشغيل المنصة المستقلة: عزل المؤسسات، الهوية، الصلاحيات، مراجعة Listings، الإشعارات المناسبة، سجل الأحداث، الإثباتات، الرصد، النسخ، وسياسات الاستثناء. تبقى Company Portal هي قناة شركة التوصيل الأساسية.

أي API خارجي محتمل لشركة تملك نظامًا خاصًا يفتح لاحقًا كقرار مستقل، بعد دليل حاجة واتفاق محدد، ولا يدخل في العقد الأساسي أو في Prototype أو Pilot الأول.

## 4. الترتيب التقني

### 4.1 عقد Market

يحتاج النظام إلى `MarketListing` يملكه مورد، و`MarketInteractionRecord` ينشئه صاحب المشروع عند الرغبة. يسجل Listing الصور والوصف والفئة والوحدة والسعر والكمية والتوفر ووقت التجهيز والموقع والتواصل، مع تاريخ تحديث وصلاحية 60 يومًا.

يظهر Listing للمراجعة الداخلية قبل النشر. بعد مرور 60 يومًا تنتقل إلى `update_required` حتى يحدثها المورد وتراجعها الإدارة قبل إعادة النشر.

### 4.2 عقد Delivery

يحتاج النظام إلى `DeliveryTask` بنوع جلب أو إرسال، ونقطتي استلام وتسليم، وموعد مفضل، ووصف طرد، ومرجع اختياري لـMarket أو طلب صاحب المشروع، وطرف يتحمل النقل بحسب الاتفاق الخارجي.

تكون الشركة الافتراضية واحدة في البداية. تقدم الشركة السعر والموعد واسم ورقم منفذ الرحلة، ويؤكد طالب السيارة العرض قبل انتقال المهمة إلى حالة الحجز المؤكد.

### 4.3 عقد الأحداث

كل تغيير حساس ينتج حدثًا واضحًا يحفظ الفاعل والوقت والحالة السابقة والجديدة وسبب الفشل عند وجوده. في Prototype يكون المصدر Persona محلية. في Pilot يكون المصدر صاحب المشروع أو المورد أو شركة التوصيل من بوابته.

لا نستخدم إشعارًا مؤقتًا كمصدر حقيقة. الإشعار يوجه الطرف إلى حالة محفوظة داخل Micro.

## 5. النموذج المحلي للـPrototype

يناسب Prototype بنية Micro الحالية:

```text
RTL Phone-first UI
  → Application Services
  → Domain Contracts
  → LocalStore
  → IndexedDB
  → Export/Import
```

يستخدم Prototype Local Database واحدة، مع Views منفصلة للأدوار الثلاثة. يجب أن يحتوي على Role/Persona Switcher لأغراض الاختبار فقط، لا على Login حقيقي. يجب أن يوضح أن الإشعارات والبوابات محاكاة محلية.

تحتاج LocalStore إلى كيانات Market وDelivery، ونسخة Schema وترحيل، وExport/Import ذري، وبيانات اختبار يمكن إعادة ضبطها. لا تحفظ في بيانات الاختبار أسرارًا أو بيانات أشخاص حقيقية.

## 6. بوابة المورد في النسخ اللاحقة

تكون Supplier Portal سطحًا مستقلًا وموبايل أولًا. تبدأ العملية بإضافة المنتج ثم مراجعته داخليًا قبل النشر. بعدها يرى المورد:

- منتجاته وListings الخاصة به.
- حالات النشر والصلاحية والتحديث.
- التفاعلات أو الطلبات المرتبطة بمنتجاته.
- تأكيد الاطلاع أو القدرة على التجهيز أو عدم التوفر.
- مهام الجلب والإرسال التي أنشأها أو ترتبط بنقطة الاستلام لديه.
- سجل المنتجات والطلبات والتوصيلات والتقييمات.

لا يطلب النظام من المورد تسجيل عقد أو دفع أو نزاع تجاري داخل Micro عندما يكون الاتفاق خارج التطبيق.

## 7. بوابة شركة التوصيل في النسخ اللاحقة

تكون Courier Company Portal سطحًا مستقلًا ومخصصًا للشركة. ترى الشركة الطلبات التي وصلت إليها فقط، وتراجع تفاصيل المصدر والوجهة والطرد والموعد، ثم:

1. تقبل المراجعة أو ترفض الطلب مع السبب.
2. تحدد السعر والموعد المتاح.
3. تدخل اسم ورقم منفذ الرحلة عند الحاجة.
4. تنتظر تأكيد طالب السيارة للحجز.
5. تسجل الجاهزية والاستلام والطريق والتسليم أو الفشل.
6. تعيد الجدولة عند الحاجة.

لا يحتاج منفذ الرحلة إلى حساب أو بوابة في Micro. الشركة تسجل الحالات نيابة عن عملية التنفيذ.

## 8. صاحب المشروع في النسخ اللاحقة

يظل Owner App هو السطح الأوسع، ويضم Micro المالي وMarket وDelivery. يرى صاحب المشروع:

- Listings والمنتجات والأسعار والصور وبيانات المورد.
- سجل التفاعل أو الاتفاق الخارجي الذي اختار تسجيله.
- مهام الجلب والإرسال الخاصة به.
- سعر التوصيل والموعد بعد تقديم الشركة للعرض.
- اسم ورقم منفذ الرحلة الذي أدخلته الشركة.
- كل الحالات المرتبطة بمهمته.
- التقييمات والاقتراحات اليدوية لتسجيل أثر مالي أو مخزني.

لا يرى شاشات تشغيل المورد أو الشركة الداخلية، ولا يمنح صلاحية تعديل بيانات لا تخصه.

## 9. الحوكمة الداخلية

تحتاج المنصة إلى سطح داخلي لمراجعة Listings قبل النشر. هذه الوظيفة لا تعني وجود مشغل لإدارة الطلبات اليومية.

| الفعل الداخلي | يدخل في الحوكمة؟ |
|---|---:|
| مراجعة صورة ووصف وفئة وسعر وبيانات Listing | نعم |
| الموافقة أو طلب تعديل أو رفض أو إيقاف Listing | نعم |
| متابعة صلاحية الـ60 يومًا | نعم |
| إدارة طلبات الشراء اليومية بدل المورد | لا |
| البحث عن سيارة لكل طلب | لا |
| تحديد سعر التوصيل بدل الشركة | لا |
| الفصل في نزاع دفع أو جودة | لا |

## 10. الاختبارات قبل Pilot

يجب اختبار المسارات التالية بالبيانات الاصطناعية:

- إنشاء Listing ومراجعتها ونشرها.
- انتهاء الـ60 يومًا وطلب التحديث وإعادة النشر.
- بحث صاحب المشروع عن Listing والتواصل مع المورد.
- تسجيل تفاعل أو اتفاق خارجي اختياري دون أثر مالي تلقائي.
- تأكيد المورد للاطلاع أو القدرة أو عدم التوفر.
- إنشاء جلب مرتبط بـMarket.
- إنشاء إرسال مستقل أو مرتبط بالمشروع.
- تقديم الشركة عرض السعر والموعد واسم ورقم منفذ الرحلة.
- قبول الطالب أو رفضه للعرض.
- تسجيل الجاهزية والاستلام والطريق والتسليم.
- رفض الشركة أو عدم جاهزية المورد أو فشل العنوان أو غياب المستلم.
- إعادة الجدولة والإلغاء دون حذف السجل.
- منع التسليم من إنشاء قبض أو ربح أو دخول مخزون تلقائي.
- منع أي جهة من رؤية بيانات الجهة الأخرى خارج نطاقها المفاهيمي.

## 11. ما لا يبدأ به التنفيذ

لا يبدأ هذا المسار بالدفع الإلكتروني أو Escrow أو ضمان الصفقة أو إدارة ائتمان أو سلة متعددة الموردين أو تحسين مسارات أو GPS حي أو تطبيق سائق أو بوابة سائق أو API أو Webhook أو ربط نظام خارجي أو شبكة وطنية. هذه قرارات مستقبلية مستقلة، وليست جزءًا من النموذج المعتمد.

## 12. بوابة الانتقال

لا ننتقل إلى Pilot متصل إلا إذا أثبت Prototype أن:

- صاحب المشروع يفهم Market وDelivery دون شرح طويل.
- المورد يفهم ما الذي يؤكده وما الذي لا يلتزم به داخل Micro.
- شركة التوصيل تفهم المهمة وتستطيع تقديم السعر والموعد وتسجيل الحالات.
- حالات عرض السعر والحجز والاستلام والتسليم واضحة وغير متداخلة.
- الفشل وإعادة الجدولة والإلغاء مفهومة.
- التقييمات مرتبطة بتفاعل حقيقي ولا تدعي ضمانًا.
- الأثر المالي يبقى فعلًا منفصلًا لصاحب المشروع.
- لا تتحول العملية إلى إدارة يدوية يومية مركزية.

## 13. القرار التنفيذي

المسار المعتمد هو: **مفهوم مستقل أولًا، ثم Prototype محلي مترابط بلا Login أو Authorization أو API، ثم Pilot متصل بثلاث بوابات داخل Micro، ثم MVP مستقل كامل.** لا يدخل أي تكامل مع نظام خارجي إلا بقرار لاحق منفصل بعد إثبات حاجة حقيقية. ولا يوجد سائق كمستخدم في أي مرحلة ضمن هذا المفهوم.
