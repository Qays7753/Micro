# Micro Delivery
## خدمة الجلب والإرسال داخل Micro

## 1. وضع الوثيقة

Micro Delivery خدمة مستقلة داخل منصة Micro لتنظيم حركة غرض من نقطة إلى نقطة. قد ترتبط بسجل تفاعل في Micro Market، أو بطلب صاحب المشروع، أو تكون مهمة جلب أو إرسال مستقلة. هذه الوثيقة تصف المفهوم التشغيلي المنقح، ولا تعني أن الخدمة منفذة في `main`.

> **Micro Delivery ينظم طلب السيارة وحركة الغرض؛ لا ينفذ الاتفاق التجاري، ولا يضمن الدفع، ولا يثبت مطابقة المنتج لمجرد اكتمال التوصيل.**

## 2. الجهات في دورة Delivery

الجهات التجارية ثلاث:

| الجهة | ما تفعله في Delivery |
|---|---|
| صاحب المشروع | ينشئ طلب جلب أو إرسال، يحدد التفاصيل، يرى عرض الشركة، ويؤكد الحجز أو يرفضه ويتابع الحالة. |
| المورد | يستطيع إنشاء مهمة مرتبطة بمنتجه أو طلبه، أو يؤكد جاهزية طرد موجود عنده، ويتابع النقل الذي يخصه. |
| شركة التوصيل | تستقبل الطلب في بوابتها، تراجعه، تحدد السعر والوقت، تدخل اسم ورقم منفذ الرحلة، وتحدث جميع حالات التنفيذ. |

لا يوجد سائق كمستخدم في Micro، ولا يوجد تطبيق أو حساب أو بوابة للسائق. إذا احتاج صاحب المشروع إلى التواصل مع منفذ الرحلة، تدخل شركة التوصيل الاسم والرقم داخل بوابتها، ويظهران لطالب السيارة.

## 3. أنواع المهام

| النوع | الوصف |
|---|---|
| جلب مرتبط بـMarket | استلام غرض من مورد أو نقطة أخرى وتسليمه إلى مشروع صاحب المشروع. |
| إرسال مرتبط بمشروع | استلام غرض من المشروع وتسليمه إلى عميل أو نقطة أخرى. |
| جلب مستقل | جلب غرض لا يرتبط بـMarket أو Listing. |
| إرسال مستقل | إرسال غرض أو عينة أو مستند أو منتج خارج Market. |
| مهمة ينشئها المورد | المورد يطلب جلبًا أو إرسالًا من بوابته عندما يكون النقل متعلقًا به. |
| توصيل خارجي | اتفق الطرفان على أن المورد أو ناقلًا خارجيًا يتولى النقل، ولا توجد مهمة Delivery داخل Micro. |
| استلام ذاتي | لا تنشأ رحلة؛ يستلم صاحب المشروع بنفسه. |

لا نبدأ بسلة متعددة الموردين أو رحلة متعددة التوقفات. إذا احتاج صاحب المشروع إلى منتجات من ثلاثة موردين، فلكل مورد وسجل ومهمة واضحة عند الحاجة. هذا يجعل السعر والمسؤولية والحالة مفهومة.

## 4. إنشاء طلب السيارة

ينشئ صاحب المشروع أو المورد مهمة جلب أو إرسال. إدخال تفاصيل الطلب ليس فاتورة شراء ولا عقد توصيل؛ هو بيانات لازمة لتقييم المهمة وتنفيذها.

| الحقل | القاعدة |
|---|---|
| نوع المهمة | جلب أو إرسال. |
| نقطة الاستلام | العنوان والوصف واسم ورقم جهة الاتصال. |
| نقطة التسليم | العنوان والوصف واسم ورقم جهة الاتصال. |
| التاريخ والوقت المفضل | يحدده الطالب؛ لا يصبح موعدًا نهائيًا قبل قبول الشركة وتأكيد الحجز. |
| وصف الطرد | النوع والعدد والحجم التقريبي وأي تعليمات مؤثرة. |
| المرجع المرتبط | Market Interaction أو طلب المشروع عند وجوده. |
| من يتحمل النقل | صاحب المشروع أو المورد أو بحسب الاتفاق الخارجي. |
| ملاحظات الوصول | بوابة أو طابق أو علامة مميزة أو تعليمات خاصة. |
| السعر | لا يكتبه الطالب كسعر نهائي؛ تحدده شركة التوصيل عند تقديم العرض. |

## 5. شركة التوصيل في المرحلة الأولى

توجد شركة توصيل افتراضية واحدة في البداية. لا يختار صاحب المشروع بين عدة شركات، ولا نحتاج في هذه المرحلة إلى خوارزمية توزيع أو تغطية بين شركات متعددة. تصل المهمة إلى الشركة الافتراضية داخل Micro، وتعمل الشركة من بوابتها يدويًا.

هذا ليس API ولا مزامنة مع نظام الشركة. الشركة نفسها تدخل إلى Micro لاحقًا بحسابها، وتراجع المهام وتدخل السعر والموعد والحالة. إذا وافقت الشركة مبدئيًا، لا يصبح الحجز نهائيًا قبل أن يرى طالب السيارة العرض ويؤكده.

## 6. دورة المهمة المعتمدة

أوصي بالدورة التالية لأنها تفصل بين قبول الشركة وبين تأكيد الطالب للحجز:

```text
1. صاحب المشروع أو المورد ينشئ طلب جلب أو إرسال.
2. تنتقل المهمة إلى بوابة شركة التوصيل الافتراضية.
3. تراجع الشركة المصدر والوجهة والطرد والموعد المفضل.
4. ترفض الشركة الطلب، أو تقدّم عرض توصيل مبدئيًا.
5. إذا قدمت عرضًا، تدخل سعر التوصيل والوقت المتاح واسم ورقم منفذ الرحلة.
6. يصل إشعار إلى الشخص الذي طلب السيارة.
7. يرى الطالب العرض كاملًا: السعر، الموعد، المصدر، الوجهة، واسم ورقم منفذ الرحلة.
8. يضغط الطالب «تأكيد الحجز» أو «رفض العرض».
9. عند التأكيد تصبح المهمة «محجوزة/مؤكدة».
10. يؤكد المورد أو نقطة المصدر أن الطرد جاهز.
11. تسجل شركة التوصيل من بوابتها الجاهزية والاستلام والطريق والتسليم أو الفشل.
12. يرى صاحب المشروع أو المورد الحالات المرتبطة بمهمته حتى النهاية.
```

إذا أرادت الشركة قبول المهمة دون تحديد السعر أو الوقت، يمكن أن تبقى الحالة «قيد المراجعة» ولا تظهر «محجوزة». وإذا رفض الطالب العرض، يمكن إعادة المهمة إلى «تحتاج عرضًا جديدًا» أو إلغاؤها.

## 7. آلة الحالات

```text
مسودة
→ أُرسلت إلى الشركة
→ قيد مراجعة الشركة
→ عرض توصيل مقدم
→ محجوزة بعد تأكيد الطالب
→ بانتظار جاهزية الطرد
→ جاهزة للاستلام
→ تم الاستلام/الجلب
→ في الطريق
→ تم التسليم
```

الحالات النهائية أو الاستثنائية هي:

```text
رفض الشركة
رفض الطالب العرض
ملغاة
مؤجلة أو أعيدت جدولتها
المورد غير جاهز
لا توجد سيارة متاحة
العنوان غير واضح
فشل الاستلام
المستلم غير موجود
فشل التسليم
الطرد ناقص أو متضرر
```

### معنى كل حالة مهمة

| الحالة | ما تثبته |
|---|---|
| أُرسلت | وصلت المهمة إلى قناة شركة التوصيل داخل Micro. |
| قيد المراجعة | الشركة لم تقدم قبولًا أو عرضًا نهائيًا بعد. |
| عرض توصيل مقدم | الشركة أدخلت سعرًا ووقتًا وبيانات تنفيذ مبدئية. |
| محجوزة | طالب السيارة أكد العرض. |
| جاهزة للاستلام | نقطة المصدر أعلنت أن الطرد جاهز. |
| تم الاستلام/الجلب | الشركة سجلت أنها أخذت الطرد. |
| في الطريق | الشركة سجلت بدء الحركة. |
| تم التسليم | الشركة سجلت وصول الطرد وأكدت النتيجة المطلوبة في المهمة. |

## 8. من يسجل الحالات؟

بما أنه لا توجد واجهة للسائق، تسجل شركة التوصيل من بوابتها كل حالات الرحلة:

```text
قبول مبدئي/عرض
→ إدخال السعر والوقت
→ إدخال اسم ورقم منفذ الرحلة
→ جاهز للاستلام
→ تم الاستلام
→ في الطريق
→ تم الجلب أو الإرسال
→ تم التسليم أو فشل
```

اسم ورقم منفذ الرحلة معلومة تشغيلية تدخلها الشركة. لا تعني أن الشخص يملك حسابًا أو صلاحية مستقلة داخل Micro.

## 9. إثبات التسليم

في المفهوم الحالي يكفي أن تسجل الشركة تأكيد التسليم من بوابتها، مع وقت التنفيذ واسم المستلم أو ملاحظة مختصرة عند الحاجة. يمكن أن يدعم النظام لاحقًا رقم تأكيد أو صورة أو توقيع بحسب حاجة Pilot، لكن لا نضيف آلية إثبات ثقيلة قبل ظهور حاجة واقعية.

لغة الحالة يجب أن تبقى دقيقة:

```text
تم التسليم ≠ تم الدفع
تم التسليم ≠ المنتج مطابق
تم التسليم ≠ تم تسجيل الشراء في Micro
```

إذا قال صاحب المشروع إن المنتج ناقص أو مختلف، تُفتح ملاحظة أو مشكلة محتوى مرتبطة بالتجربة. لا يحكم Micro على النزاع التجاري بمجرد وجود تأكيد توصيل.

## 10. مسؤولية النقل

عند إنشاء مهمة، يحدد الطالب أو الطرفان كيف يتعاملان مع النقل:

| الخيار | المعنى |
|---|---|
| طلب Micro Delivery | تصل المهمة إلى شركة التوصيل داخل Micro. |
| المورد يتولى النقل | المورد يرتب النقل خارجيًا؛ لا تظهر مهمة مؤكدة في Micro إلا إذا أنشأها أو ربطها. |
| ناقل خارجي خاص | يتفق الطرفان خارجيًا؛ يسجل Micro ملاحظة اختيارية فقط. |
| استلام ذاتي | لا توجد رحلة. |

أجرة التوصيل تحددها شركة التوصيل في عرضها. يرى الطالب السعر قبل تأكيد الحجز. لا تسجل الأجرة تلقائيًا كـمصروف في النظام المالي، ولا يدفع Micro المبلغ أو يحتفظ به في هذا المفهوم.

## 11. حالات الفشل وإعادة الجدولة

| الحالة | الإجراء المقترح |
|---|---|
| الشركة رفضت | تظهر للمستخدم مع سبب؛ يمكن طلب عرض جديد أو استخدام نقل خارجي. |
| لا توجد سيارة | تبقى غير مؤكدة، أو تعاد جدولتها، أو تلغى. |
| المورد غير جاهز | لا تبدأ الرحلة؛ يحدد المورد وقتًا جديدًا أو تلغى المهمة. |
| العنوان ناقص | تطلب الشركة معلومات إضافية؛ لا تخمن الموقع. |
| الطرد غير موجود | تسجل الشركة فشل الاستلام مع السبب. |
| المستلم غير موجود | تسجل محاولة فاشلة؛ يعرض موعد جديد أو إرجاع حسب الاتفاق. |
| الطرد ناقص أو متضرر | يسجل التسليم إن حصل وتفتح ملاحظة محتوى منفصلة. |
| الطالب رفض السعر | لا يصبح الحجز مؤكدًا؛ يمكن إعادة طلب عرض. |
| انقطاع أو تكرار الإرسال | يحتفظ النظام بمحاولة واحدة وحالة معلقة واضحة، ولا ينشئ مهمة ثانية. |

## 12. العلاقة مع Micro Market

يمكن فتح Delivery من صفحة المنتج أو من سجل التفاعل بعد اتفاق خارجي. تنتقل البيانات الضرورية فقط:

| تنتقل إلى المهمة | لا تنتقل تلقائيًا |
|---|---|
| اسم المنتج أو وصفه | كامل النظام المالي لصاحب المشروع |
| الكمية وعدد الطرود | العربون كقبض مؤكد |
| المورد ونقطة الاستلام | ضمان المطابقة |
| المصدر والوجهة والموعد | سعر المنتج كإيراد |
| جهة الاتصال اللازمة | قرار النزاع أو التعويض |
| مرجع سجل التفاعل | أي بيانات لا يحتاجها الناقل |

يمكن إنشاء Delivery مستقلة بلا Market. هذا يحافظ على وظيفة الجلب والإرسال لأغراض المشروع العامة.

## 13. الحدود المالية

- إنشاء طلب السيارة ليس شراءً.
- قبول الشركة ليس دفعًا.
- عرض السعر ليس مصروفًا مسجلًا.
- تأكيد الحجز ليس قبضًا أو التزامًا ماليًا على Micro.
- الاستلام ليس دخولًا تلقائيًا للمخزون.
- التسليم ليس قبضًا أو ربحًا أو COGS.
- أجرة التوصيل لا تدخل Finance تلقائيًا.
- يستطيع صاحب المشروع لاحقًا تسجيل شراء أو مصروف يدويًا في Micro، ويمكن عرض اقتراح «تسجيل أثر» دون تنفيذ تلقائي.

## 14. القرار

Micro Delivery تكون خدمة مستقلة للجلب والإرسال، يستدعيها صاحب المشروع أو المورد عند الحاجة. تبدأ بشركة توصيل افتراضية واحدة تستخدم بوابة Micro يدويًا. الشركة تراجع المهمة، تقدم السعر والموعد واسم ورقم منفذ الرحلة، ويؤكد الطالب الحجز. بعد ذلك تسجل الشركة كل حالات التنفيذ من بوابتها. لا توجد شاشة أو بوابة أو حساب للسائق، ولا API أو Webhook أو تكامل مع نظام خارجي في المفهوم الحالي.
