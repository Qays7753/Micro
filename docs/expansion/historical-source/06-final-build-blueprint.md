# مخطط البناء الشامل لـMicro Market وMicro Delivery

**الإصدار:** v1.0 — مخطط قرار وبناء قبل التنفيذ
**السوق الأول:** الأردن
**الهدف:** تحويل المفهوم المعتمد إلى صورة نظام كاملة قابلة للبناء والاختبار ثم التشغيل

## 1. ماذا نريد أن نبني بالضبط؟

نريد بناء **منصة Micro مستقلة** تضيف إلى Micro الحالي قدرتين مترابطتين:

- **Micro Market:** مساحة لاكتشاف المنتجات والمواد، قريبة في بساطتها من السوق المفتوح الأردني: فئات، بحث، صور، وصف، سعر، موقع، وبيانات تواصل.
- **Micro Delivery:** خدمة مستقلة للجلب والإرسال، يمكن أن تبدأ من Market أو من داخل Delivery مباشرة.

الاتفاق التجاري بين صاحب المشروع والمورد يحدث خارج Micro. لا تنفذ المنصة الدفع ولا تستلم العربون ولا تضمن السعر النهائي أو جودة المنتج. لكنها تسجل، عند رغبة المستخدم، **تفاعلًا أو اتفاقًا خارجيًا أو حالة متابعة**، وتتيح للمورد تأكيد الاطلاع أو القدرة على التجهيز. هذه المعلومات تخدم المتابعة والتقييم، ولا تجعل Micro طرفًا في البيع.

أما التوصيل، فيتم داخل Micro من خلال بوابة شركة التوصيل. تبدأ المرحلة الأولى بشركة توصيل افتراضية واحدة. تقدم الشركة سعر التوصيل والموعد المتاح واسم ورقم منفذ الرحلة، ثم يؤكد صاحب المشروع أو المورد الذي طلب السيارة الحجز. بعد ذلك تسجل الشركة الجاهزية والاستلام والطريق والتسليم أو الفشل من بوابتها.

> **الصورة النهائية ليست شاشة واحدة للجميع. هي ثلاث تجارب منفصلة فوق منصة بيانات ومنطق مشترك: Owner App، Supplier Portal، وCourier Company Portal. لا يوجد سائق كمستخدم، ولا Driver App، ولا Driver Portal، ولا API مع أنظمة شركات خارجية.**

## 2. ما الذي تعنيه «البوابات»؟

البوابة ليست بالضرورة نظامًا تقنيًا منفصلًا أو قاعدة بيانات منفصلة. المقصود أن لكل جهة **نقطة دخول وتجربة وصلاحيات ومعلومات مختلفة**.

| الجهة | البوابة | طبيعة التجربة |
|---|---|---|
| صاحب المشروع | Micro Owner App | التطبيق الأساسي الحالي، يضم المال وMarket وDelivery وكل ما يخص المشروع. |
| المورد | Supplier Portal | واجهة مستقلة لإضافة المنتجات ورؤية التفاعلات والطلبات والتوصيلات المتعلقة به. |
| شركة التوصيل | Courier Company Portal | واجهة مستقلة لرؤية طلبات السيارات والجلب والإرسال التي وصلت إليها وتسعيرها وتحديثها. |
| الإدارة الداخلية | Moderation Console | وظيفة داخلية لمراجعة Listings قبل نشرها ومتابعة البلاغات؛ ليست جهة تجارية ولا مشغلًا للطلبات. |

لا نكرر قواعد العمل في ثلاثة أنظمة. نستخدم Domain وApplication مشتركين، وتختلف البوابات في الـViews والصلاحيات. وفي المرحلة الأولى يمكن أن تكون البوابات الثلاث داخل مشروع Web واحد بمسارات منفصلة، ثم تفصل إلى تطبيقات أو نطاقات مستقلة لاحقًا إذا أثبت الاستخدام الحاجة.

## 3. قرار التقنية العام

أوصي بـ **Modular Monolith + Shared Domain + Separate Portal Surfaces**. أي منصة واحدة منطقية وبياناتها موحدة، مقسمة إلى وحدات واضحة، فوقها ثلاث واجهات مستقلة، بدل بناء Microservices أو ثلاثة أنظمة منفصلة منذ البداية.

```text
Owner App       Supplier Portal       Courier Company Portal
       \              |               /
        └────── Shared Micro Platform ──────┘
                 ├── Market Module
                 ├── Delivery Module
                 ├── Notification Module
                 ├── Review/Moderation Module
                 └── Micro Financial Core
```

هذا القرار يحقق ثلاثة أمور: تجربة مختلفة لكل جهة، وحالة واحدة مشتركة للمنتج والتفاعل والتوصيل، وتكلفة تشغيل أقل من تكرار الخدمات والبيانات. كما أنه يحافظ على استقلال Micro عن أنظمة الموردين وشركات التوصيل.

## 4. الجهات وتجاربها بالتفصيل

### 4.1 صاحب المشروع — Owner App

صاحب المشروع هو المستخدم الأوسع وصولًا لأنه يدير مشروعه. يرى النظام المالي الحالي، وMarket، وDelivery، والطلبات والمواعيد والمخزون أو المواد وفق ما هو موجود في Micro. لا يرى لوحات المورد الداخلية أو كل طلبات شركة التوصيل؛ يرى ما يخص مشروعه.

رحلته الأساسية:

```text
يدخل إلى Micro
→ يفتح Market
→ يبحث عن منتج
→ يراجع Listing والمورد
→ يتواصل خارجيًا
→ يسجل تفاعلًا/اتفاقًا اختياريًا
→ يطلب جلبًا أو إرسالًا عند الحاجة
→ يرى عرض شركة التوصيل
→ يؤكد أو يرفض الحجز
→ يتابع الاستلام والتسليم
→ يقيّم المورد أو يسجل مشكلة
→ يسجل الأثر المالي/المخزني يدويًا إن أراد
```

### 4.2 المورد — Supplier Portal

المورد لا يدخل إلى النظام المالي لصاحب المشروع. يدخل إلى بوابة تركز على المنتج والعرض والتعامل التشغيلي:

```text
يدخل إلى بوابته
→ يضيف Listing
→ تنتظر المراجعة الداخلية
→ تنشر Listing
→ يرى تفاعلًا أو طلبًا مرتبطًا بمنتجه
→ يؤكد الاطلاع أو القدرة أو عدم التوفر
→ يعلن الجاهزية عند وجود طلب فعلي
→ ينشئ أو يتابع Delivery عند الحاجة
→ يرى التاريخ والتقييمات المرتبطة بتجاربه
```

بما أن الاتفاق التجاري خارج Micro، لا يحتاج المورد إلى إدخال عقد أو فاتورة أو دفعة أو نزاع مالي داخل البوابة.

### 4.3 شركة التوصيل — Courier Company Portal

شركة التوصيل لا ترى Market بوصفه متجرًا كاملًا، ولا ترى النظام المالي أو سعر المنتج أو تفاصيل الاتفاق التجاري. ترى فقط المهام التي وصلت إليها:

```text
تصل مهمة سيارة
→ تراجع المصدر والوجهة والطرد والموعد
→ ترفض أو تقدم عرضًا
→ تدخل سعر التوصيل والموعد واسم ورقم منفذ الرحلة
→ ينتظر النظام تأكيد طالب السيارة
→ تصبح المهمة محجوزة
→ تسجل الشركة الجاهزية والاستلام والطريق والتسليم أو الفشل
```

لا يوجد حساب لمنفذ الرحلة. الشركة تسجل اسمه ورقمه يدويًا من بوابتها عند الحاجة.

### 4.4 الإدارة الداخلية — Moderation فقط

هذه ليست جهة تجارية رابعة. هي سطح داخلي محدود حتى لا تظهر Listing مباشرة في السوق دون مراجعة. صلاحياتها:

- مراجعة Listing الجديدة.
- الموافقة أو طلب تعديل أو الرفض أو الإيقاف.
- متابعة صلاحية Listing بعد 60 يومًا.
- مراجعة بلاغات المحتوى أو التقييمات عند الحاجة.

لا تقبل Orders بدل المورد، ولا تسعر Delivery بدل الشركة، ولا تبحث عن سيارة لكل طلب، ولا تتدخل في الاتفاق التجاري أو الدفع.

## 5. ما الذي نبنيه داخل Owner App؟

يحتفظ Owner App بكل ما هو موجود في Micro، وتضاف إليه شاشات Market وDelivery. لا نخلطها مع النظام المالي في شاشة واحدة، بل نربطها عبر مراجع وأفعال واضحة.

### 5.1 الشاشات المالية والتشغيلية الحالية

هذه موجودة في Micro الحالي وتبقى جزءًا من Owner App:

| المجموعة | الشاشات/المسارات |
|---|---|
| البداية | مشروعي الآن، التهيئة، الأولويات، التنبيهات الداخلية. |
| الطلبات | قائمة الطلبات، إنشاء مسودة، تفاصيل الطلب، الاتفاق، التكلفة، التنفيذ والتسليم. |
| المواعيد | جدول المواعيد والتأجيل والتكرار المحلي عند انطباقه. |
| المال | الوضع المالي، الأحداث، الكاش، الشراء، المصاريف، العربونات، والتحصيل/الدين وفق العقود الحالية. |
| المواد | المواد والمخزون والحركات عندما يستخدمها المشروع. |
| الإعدادات | التفضيلات، البيانات المحلية، التصدير والاستيراد، وإعادة الضبط الاختبارية. |

التكامل الجديد لا يغير معنى هذه الشاشات. Delivery لا تنشئ قبضًا، وMarket لا ينشئ شراءً أو ربحًا، ولا يتغير الطلب التاريخي بصمت.

### 5.2 شاشات Micro Market لصاحب المشروع

| الشاشة | الهدف | المحتوى الأساسي | الإجراء الرئيسي |
|---|---|---|---|
| Market Home | بدء الاكتشاف | فئات، بحث، منتجات محدثة، اختصارات للمنتجات المحفوظة والتفاعلات | البحث أو فتح فئة |
| Category Results | مقارنة Listings | صورة، اسم، سعر، وحدة، منطقة، وقت تجهيز، حالة التوفر، آخر تحديث | فتح Listing |
| Search Results | العثور على منتج | نتائج حسب الاسم والفئة والمنطقة والتوفر وطريقة النقل | فتح Listing أو تغيير التصفية |
| Listing Detail | فهم العرض قبل التواصل | الصور، الوصف، المواصفات، السعر، الكمية، الشرائح، التوفر، التجهيز، الموقع، اسم المورد، الهاتف، النقل، التقييمات | التواصل، حفظ، تسجيل تفاعل، طلب جلب |
| Contact/Interaction Sheet | تسجيل تفاعل بأقل إدخال | نوع التواصل، ملاحظة اختيارية، هل تم الاتفاق خارجيًا، هل يحتاج Delivery | حفظ السجل أو العودة |
| My Market Activity | متابعة ما بدأه المستخدم | تفاعلات، اتفاقات خارجية مسجلة، حالات المورد، Delivery المرتبطة | فتح التفاصيل أو طلب توصيل |
| Market Interaction Detail | رؤية الحقيقة التشغيلية | Listing، المورد، ما أدخله المستخدم، تأكيد المورد، الملاحظات، التقييم المتاح | ربط Delivery، تقييم، تسجيل ملاحظة |
| Supplier Public Profile | فهم المورد | الاسم، الهاتف، المنطقة، المنتجات، وقت العمل أو التجهيز، التقييمات والإشارات المحددة | فتح منتج أو تواصل |
| Rating Sheet | تقييم تجربة محددة | الاستجابة، دقة العرض، التوفر/الجاهزية، وضوح التعامل، ملاحظة | حفظ التقييم |

لا نطلب من المستخدم ملء Order طويل قبل التواصل. إدخال تفاصيل Market اختياري. إذا أدخلها، يوضح النظام أنها **بيانات متابعة لاتفاق خارجي**.

### 5.3 شاشات Micro Delivery لصاحب المشروع

| الشاشة | الهدف | المحتوى الأساسي | الإجراء الرئيسي |
|---|---|---|---|
| Delivery Home | رؤية الحركة | مهام قادمة، قيد التنفيذ، مكتملة، فاشلة، واختصارات جلب/إرسال | إنشاء مهمة |
| Create Delivery | طلب سيارة | النوع، المصدر، الوجهة، جهات الاتصال، الموعد المفضل، وصف الطرد، عدد الطرود، من يتحمل النقل، المرجع الاختياري | إرسال للشركة |
| Delivery List | متابعة المهام | رقم المهمة، النوع، الحالة، الموعد، السعر إن توفر، المصدر/الوجهة المختصرة | فتح المهمة |
| Delivery Detail | معرفة أين وصلت المهمة | Timeline، نقاط الاستلام والتسليم، الطرد، الموعد، عرض الشركة، بيانات منفذ الرحلة، الملاحظات | تأكيد العرض، إلغاء، إعادة جدولة، الإبلاغ |
| Courier Offer | اتخاذ قرار الحجز | سعر التوصيل، الموعد المتاح، اسم ورقم منفذ الرحلة، الشروط/الملاحظة | تأكيد الحجز أو رفض العرض |
| Delivery Proof | رؤية إثبات النهاية | وقت التسليم، اسم المستلم أو الملاحظة، مصدر التأكيد | تأكيد الاطلاع أو فتح مشكلة |
| Delivery Issue | تسجيل الفشل | نوع المشكلة، الوصف، الصور/المرفقات عند الحاجة لاحقًا، الفعل المطلوب | حفظ المشكلة أو طلب إعادة الجدولة |
| Financial Link | تسجيل الأثر يدويًا | اقتراح تسجيل شراء/مصروف/مادة، مع تحذير أن التسجيل منفصل | فتح المسار المالي دون حفظ تلقائي |

### 5.4 Owner Navigation المقترحة

لا نضع كل الأقسام في Bottom Navigation. أوصي بأن تكون الوجهات العليا في Owner App خمسًا كحد أقصى، مع بقاء الإعدادات في مسار ثانوي:

```text
مشروعي الآن | الطلبات | Market | Delivery | المالي
```

تظل المواعيد والمواد والمراجعة والإعدادات متاحة من السياق أو من القائمة الثانوية. يجب تنفيذ هذا القرار بعد مطابقة `navigation.ts` الحالي وعقد التنقل الموجود، لا بإضافة تبويبات عشوائية. معيار الاختيار هو أن Market وDelivery يحتاجان وصولًا متكررًا، لا أن كل شاشة يجب أن تصبح تبويبًا.

## 6. ما الذي نبنيه داخل Supplier Portal؟

Supplier Portal ليست نسخة من Owner App. هي واجهة إدخال وعمل للمورد.

### 6.1 الشاشات الأساسية

| الشاشة | ما يراه المورد | الأفعال |
|---|---|---|
| Supplier Home | Listings التي تحتاج فعلًا، التفاعلات الجديدة، مهام التوصيل الحالية، طلبات التحديث | فتح أولوية |
| My Listings | منتجاته فقط وحالة كل Listing وصلاحيتها | فتح أو إيقاف أو تعديل |
| Create Listing | الصورة، الاسم، الفئة، الوصف، الوحدة، السعر، الكمية، التوفر، التجهيز، الموقع، النقل | حفظ مسودة وإرسال للمراجعة |
| Edit Listing | البيانات الحالية وسجل آخر تحديث وسبب طلب التعديل | تعديل وإعادة إرسال |
| Listing Review Status | قيد المراجعة، منشور، يحتاج تعديل، مرفوض، بحاجة لتحديث بعد 60 يومًا | قراءة السبب والتعديل |
| Interaction Inbox | التفاعلات أو Market Order Records التي تخص منتجاته | فتح السجل |
| Interaction Detail | المنتج، الكمية/التفاصيل التي أدخلها المستخدم، هل يحتاج Delivery، وبيانات الاتصال المسموحة | رأيت، أستطيع التجهيز، غير متوفر، أحتاج تواصلًا |
| Delivery Requests | مهام الجلب أو الإرسال التي أنشأها أو ترتبط بنقطة الاستلام لديه | إنشاء أو فتح المهمة |
| Delivery Detail | المصدر والوجهة والموعد والعرض والحالة | تأكيد الجاهزية ومتابعة الحالة |
| History | Listings والطلبات والتفاعلات والتوصيلات والتقييمات السابقة | البحث والمراجعة |
| Supplier Profile | الاسم، الهاتف، المنطقة، أوقات العمل، بيانات التواصل | تحديث الملف |

### 6.2 ماذا يعني Order لدى المورد؟

حتى لا يتحول الاتفاق الخارجي إلى طلب شراء قانوني داخل Micro، أوصي باستخدام تسمية واضحة:

> **Market Order Record — سجل طلب Market**

هو سجل متابعة أنشأه صاحب المشروع بعد تواصل أو اتفاق خارجي، وقد يحتوي تفاصيل اختيارية. يراه المورد لأنه مرتبط بمنتجه، ويستطيع تأكيد الاطلاع أو القدرة على التجهيز، لكنه لا يُطلب منه تسجيل عقد أو دفع أو نزاع.

في الواجهة يمكن عرض الاسم المبسط «طلب Market مسجل»، وتحت الاسم شرح قصير: «هذا سجل متابعة لاتفاق خارجي، وليس فاتورة أو عملية دفع داخل Micro».

## 7. ما الذي نبنيه داخل Courier Company Portal؟

### 7.1 الشاشات الأساسية

| الشاشة | ما تراه الشركة | الأفعال |
|---|---|---|
| Courier Home | الطلبات الجديدة، عروض تنتظر تأكيد الطالب، المهام الحالية، الاستثناءات | فتح الأولوية |
| New Requests | طلبات وصلت للشركة ولم تراجعها | فتح المهمة، رفض أو تقديم عرض |
| Request Detail | المصدر، الوجهة، جهات الاتصال، الطرد، الموعد المفضل، المرجع الضروري | مراجعة البيانات |
| Courier Offer Form | السعر، الموعد المتاح، اسم ورقم منفذ الرحلة، ملاحظة | تقديم العرض |
| Awaiting Confirmation | العروض التي تنتظر تأكيد طالب السيارة | تعديل العرض أو سحبه وفق السياسة |
| Active Deliveries | المهام المحجوزة والقادمة | فتح المهمة وتحديث الحالة |
| Delivery Detail | نقاط الرحلة، الطرد، الموعد، بيانات الاتصال، الحالة الحالية | جاهز/استلمت/في الطريق/تم التسليم/فشل |
| Exception Form | عدم الجاهزية، عنوان ناقص، غياب المستلم، تلف، عدم توفر سيارة | تسجيل السبب، اقتراح إعادة الجدولة |
| History | سجل كامل لطلبات الشركة السابقة | البحث والتصفية |
| Company Profile | اسم الشركة، الهاتف، المناطق، الأوقات، القدرة التشغيلية | تحديث البيانات |

### 7.2 لا توجد شاشة سائق

الشركة تدخل اسم ورقم منفذ الرحلة عند تقديم العرض أو قبل تنفيذ المهمة. لا يُنشأ له حساب، ولا يسجل الدخول، ولا يرى أي شاشة. شركة التوصيل هي مالكة سجل التنفيذ داخل Micro في المرحلة الحالية.

## 8. نموذج البيانات الذي يجب أن نبنيه

نحتاج كائنات تشغيلية منفصلة، لا كائنًا واحدًا ضخمًا يخلط Market والمال والتوصيل.

| الكيان | المالك | الغرض | أهم الحقول |
|---|---|---|---|
| `SupplierProfile` | المورد | تعريف المورد وبيانات التواصل | الاسم، الهاتف، المنطقة، الوصف، الحالة، آخر تحديث |
| `CourierCompany` | الشركة | تعريف شركة التوصيل الافتراضية | الاسم، الهاتف، نطاق الخدمة، الحالة |
| `MarketListing` | المورد | العرض المنشور | الاسم، الصور، الفئة، الوصف، الوحدة، السعر، قاعدة الكمية، التوفر، التجهيز، الموقع، النقل، الحالة، تواريخ المراجعة والصلاحية |
| `ListingReview` | الإدارة الداخلية | سجل قرار النشر | Listing، القرار، السبب، المراجع، الوقت، revision |
| `MarketInteractionRecord` | صاحب المشروع | تفاعل أو اتفاق خارجي مسجل | المشروع، المورد، Listing، المصدر، الملاحظات، هل تم الاتفاق خارجيًا، البيانات الاختيارية، الحالة |
| `SupplierResponse` | المورد | تأكيد تشغيلي على التفاعل | رأيت، أستطيع التجهيز، غير متوفر، أحتاج تواصلًا، لا أتعرف، الوقت والملاحظة |
| `SupplierRating` | صاحب المشروع | تقييم تجربة مرتبطة بتفاعل | الأبعاد، الدرجة، التعليق، المرجع، الحالة، سبب التعديل إن وجد |
| `DeliveryTask` | طالب المهمة | مهمة جلب أو إرسال | النوع، المنشئ، المرجع، المصدر، الوجهة، الطرد، الموعد المفضل، من يتحمل النقل، الحالة |
| `DeliveryOffer` | شركة التوصيل | عرض الشركة قبل الحجز | الأجرة، الموعد المتاح، اسم/رقم منفذ الرحلة، الملاحظة، تاريخ العرض، الحالة |
| `DeliveryEvent` | النظام/الشركة | تاريخ انتقال الحالة | المهمة، الحالة السابقة، الجديدة، المصدر، الفاعل، الوقت، السبب، مفتاح التكرار |
| `DeliveryProof` | الشركة | تأكيد النهاية أو المحاولة | وقت الحدث، اسم المستلم/الملاحظة، نوع الإثبات، المصدر |
| `DeliveryIssue` | الطرف المرتبط | فشل أو استثناء | التصنيف، الوصف، المسؤول عن الخطوة التالية، الحالة، الإجراء |
| `NotificationRecord` | النظام | سجل إشعار داخل Micro | المستلم، النوع، المرجع، الحالة، الوقت، القراءة |
| `AuditEvent` | النظام | أثر تدقيق للعمليات الحساسة | الفاعل، الجهة، العملية، الكيان، قبل/بعد، السبب، الوقت |

### 8.1 ما لا نضعه في النموذج

لا نضع `DriverUser` أو `DriverPortal` أو `CourierExternalIntegration` أو `ExternalWebhook` في النموذج الحالي. اسم ورقم منفذ الرحلة حقول داخل `DeliveryOffer` أو `DeliveryTask`، وليسا كيان مستخدم.

ولا نضع `PaymentTransaction` أو `Escrow` أو `SupplierSettlement`؛ لأن الدفع والاتفاق خارج Micro في هذا المفهوم.

## 9. الحالات وقواعد الانتقال

### 9.1 Listing

```text
draft
→ pending_review
→ published
→ update_required
→ pending_review
→ published
```

وتوجد حالات `changes_requested` و`rejected` و`paused` و`unavailable`. مدة صلاحية Listing النشطة 60 يومًا. انتهاء المدة لا يعني صحة البيانات؛ ينتقل العرض إلى التحديث والمراجعة قبل عودته للعرض النشط.

### 9.2 Market Interaction Record

```text
started
→ agreed_externally (اختياري)
→ details_saved (اختياري)
→ supplier_seen
→ supplier_can_prepare / supplier_needs_contact / supplier_unavailable
→ delivery_requested (اختياري)
→ closed / not_confirmed
```

لا تكون هذه الحالات عقدًا أو حالات دفع. يستطيع المورد أن يتواصل خارجيًا ولا يحتاج إلى تسجيل تفاصيل الاتفاق داخل Micro.

### 9.3 DeliveryTask

```text
created
→ sent_to_courier
→ under_courier_review
→ courier_offer_submitted
→ booked_after_requester_confirmation
→ waiting_for_source_ready
→ ready_for_pickup
→ picked_up
→ in_transit
→ delivered
```

حالات الإخفاق:

```text
courier_rejected
requester_rejected_offer
cancelled
rescheduled
source_not_ready
no_vehicle_available
address_needs_information
pickup_failed
delivery_failed
recipient_unavailable
package_issue
```

### 9.4 قواعد لا يجوز كسرها

| القاعدة | التطبيق |
|---|---|
| لا حجز نهائي بلا تأكيد الطالب | عرض الشركة يبقى `offer_submitted` حتى يوافق طالب السيارة. |
| لا استلام قبل جاهزية المصدر | لا تنتقل الشركة إلى الاستلام إذا لم يعلن المورد/المصدر الجاهزية. |
| لا تسليم بمجرد إرسال إشعار | الحالة لا تتغير إلا بفعل من بوابة الشركة. |
| لا سائق كمستخدم | الشركة تسجل اسم ورقم منفذ الرحلة، لا حسابًا مستقلًا. |
| لا أثر مالي تلقائي | Market وDelivery لا ينشئان قبضًا أو شراءً أو مصروفًا أو ربحًا. |
| لا تعديل تاريخي صامت | التصحيح يكون بحدث جديد أو Revision موثق. |
| لا رؤية خارج النطاق | كل بوابة ترى فقط ما يتعلق بجهتها. |

## 10. تدفقات العمل النهائية

### 10.1 شراء/اتفاق خارجي ثم جلب

```text
1. صاحب المشروع يبحث عن المنتج.
2. يفتح Listing ويرى الصور والتفاصيل والسعر وبيانات المورد.
3. يتواصل مع المورد خارج Micro.
4. يعود إلى Micro ويسجل تفاعلًا أو اتفاقًا خارجيًا اختياريًا.
5. يصل السجل إلى المورد في Supplier Portal.
6. المورد يؤكد أنه رأى التفاعل أو يستطيع التجهيز أو يحتاج إلى تواصل.
7. إذا أراد صاحب المشروع جلب المنتج، ينشئ DeliveryTask مرتبطة بالسجل.
8. تصل المهمة إلى شركة التوصيل الافتراضية.
9. تقدم الشركة سعر التوصيل والموعد واسم ورقم منفذ الرحلة.
10. يرى صاحب المشروع العرض ويؤكد الحجز أو يرفضه.
11. يعلن المورد الجاهزية.
12. تسجل الشركة الاستلام والطريق والتسليم أو الفشل.
13. يقيّم صاحب المشروع المورد أو يسجل مشكلة.
14. إذا أراد أثرًا ماليًا أو مخزنيًا، يسجله من Micro المالي بفعل مستقل.
```

### 10.2 طلب Delivery مستقل

```text
1. صاحب المشروع أو المورد يفتح Delivery.
2. يختار جلبًا أو إرسالًا.
3. يدخل المصدر والوجهة والجهات والطرد والموعد المفضل.
4. تصل المهمة إلى الشركة الافتراضية.
5. تقدم الشركة عرض السعر والموعد ومنفذ الرحلة.
6. يؤكد الطالب الحجز.
7. تنفذ الشركة وتسجل الحالات.
```

### 10.3 المورد هو طالب السيارة

إذا كان المورد هو الذي يحتاج إلى إرسال أو جلب، ينشئ المهمة من Supplier Portal. يصبح المورد هو **طالب السيارة**، وتصل إليه نتيجة العرض ليؤكد أو يرفض الحجز. يرى صاحب المشروع فقط المهمة إذا كان طرفًا فيها أو نقطة تسليم/استلام تخصه.

### 10.4 المورد يتولى النقل

إذا اتفق المورد وصاحب المشروع على أن المورد يتولى النقل خارجيًا، لا تنشأ DeliveryTask مؤكدة داخل Micro. يمكن تسجيل «توصيل خارجي» أو ترك العملية خارج Delivery. لا تعرض المنصة «تم التسليم» داخل Micro بلا مهمة وحالة تعيدها شركة التوصيل عبر بوابتها.

## 11. نموذج الإشعارات

في المرحلة النهائية تكون الإشعارات داخل منصة Micro ومبنية على السجل، لا على رسالة عابرة:

| الحدث | المستلم | محتوى الإشعار |
|---|---|---|
| Listing تحتاج مراجعة | الإدارة الداخلية | إعلان جديد يحتاج قرار نشر. |
| Listing تحتاج تعديل | المورد | سبب التعديل وما يلزم تصحيحه. |
| تفاعل جديد | المورد | يوجد تفاعل أو سجل Market مرتبط بمنتجك. |
| المورد أكد/لم يؤكد | صاحب المشروع | حالة تفاعل المورد والخطوة التالية. |
| Delivery جديدة | شركة التوصيل | طلب جلب/إرسال يحتاج مراجعة. |
| عرض شركة التوصيل | طالب السيارة | السعر والموعد واسم ورقم منفذ الرحلة. |
| تأكيد الحجز | شركة التوصيل والمصدر | الطالب أكد العرض. |
| جاهزية المصدر | الشركة والطالب | الطرد جاهز للاستلام. |
| استلام/طريق/تسليم | الأطراف المرتبطة | تحديث حالة المهمة. |
| فشل أو تأجيل | الطرف المسؤول | سبب الفشل والإجراء التالي. |

في Prototype تكون هذه إشعارات محلية محاكاة. في Pilot المتصل تكون إشعارات داخل منصة Micro. لا نحتاج ربط نظام شركة خارجية حتى تصل الحالة؛ الشركة تدخل إلى Micro وتحدّثها يدويًا.

## 12. التقنية المطلوبة

### 12.1 Prototype المحلي

يجب البناء فوق بنية Micro الحالية، لا بدء تطبيق منفصل:

| الطبقة | التقنية/القرار |
|---|---|
| UI | React + TypeScript + Vite الموجود في Prototype. |
| التنقل | Wouter والمسارات الحالية، مع مسارات مستقلة لـMarket وDelivery وViews الأدوار. |
| UI system | التوكنات والمكونات الحالية وTailwind/shadcn، مع RTL وphone-first وLight/Dark. |
| Application | خدمات Use Cases وView Models؛ لا تتصل صفحات React مباشرة بـIndexedDB. |
| Domain | عقود وحالات Market وDelivery مستقلة عن الواجهة والتخزين. |
| Local persistence | `PrototypeLocalStore` فوق IndexedDB، مع schema migration وExport/Import. |
| Composition | إضافة الخدمات إلى `PrototypeServicesContext` مثل بقية الخدمات الحالية. |
| Notifications | Notification Records محلية مع Persona/Role Switcher. |
| QA | اختبارات Domain/Application، ثم تدفقات واجهة على 360/390/430px وRTL وLight/Dark. |

في Prototype لا توجد قاعدة مركزية أو Auth أو Login أو Workspace أو API أو Cloud Sync أو إشعارات خارجية. يجب أن تكون البوابات الثلاث محاكاة كاملة بصريًا ومنطقيًا، لا شاشة واحدة تجمع كل الأدوار.

### 12.2 Pilot المتصل داخل Micro

بعد نجاح Prototype، نضيف Backend مركزيًا لنفس منصة Micro:

| الطبقة | الاختيار الموصى به |
|---|---|
| الواجهات | React + TypeScript + Vite مع App Shell مستقل لكل بوابة. |
| Domain/Application | حزمة TypeScript مشتركة قدر الإمكان، مع منع الواجهة من كتابة البيانات مباشرة. |
| Backend | Modular Monolith TypeScript بطبقة API داخلية بين البوابات والمنصة. هذا API داخلي لـMicro وليس تكاملًا مع نظام شركة خارجية. |
| Database | PostgreSQL مركزي، مع ملكية واضحة للمنظمة والمشروع والكيان. |
| Auth | خدمة هوية وOTP/Password بحسب قرار المنتج، مع حسابات منفصلة للمالك والمورد والشركة. |
| Authorization | Role + Organization + Entity Scope، وليس إخفاء الأزرار فقط. |
| Files | Object Storage للصور والإثباتات، مع روابط محمية وسياسة احتفاظ. |
| Jobs | Outbox/worker للإشعارات الداخلية وإعادة المحاولة والمهام غير المتزامنة. |
| Observability | أخطاء، زمن الاستجابة، فشل الإشعارات، تغييرات الحالة، وسجل تدقيق. |
| Hosting | استضافة Web وBackend وقاعدة البيانات وفق بيئة Micro المعتمدة وقت تفويض Pilot. |

لا نبدأ Microservices. ولا نبني Adapter أو Webhook لشركة توصيل خارجية. إذا ظهر احتياج مستقبلي لشركة لديها نظام خاص، يكون ذلك قرارًا جديدًا منفصلًا ولا يغير Portal-first.

### 12.3 تطبيق Native أم Web/PWA؟

أوصي بأن تكون البوابات الثلاث **Web Apps/PWAs مستقلة في التجربة** أولًا، لا تطبيقات Native منفصلة من اليوم الأول. السبب أن المطلوب الحالي هو إثبات سير العمل، وليس استخدام GPS أو خصائص جهاز خاصة. يمكن لاحقًا تغليف Owner App أو Supplier Portal أو Courier Portal كتطبيق Native إذا أثبت Pilot الحاجة إلى متجر أو صلاحيات جهاز أو استخدام يومي كثيف.

هذا لا يقلل من قيمة «التطبيق الخاص» بكل جهة؛ فلكل جهة واجهة ومسار دخول وتجربة مستقلة، حتى لو بدأت تقنيًا كـPWA على نفس المنصة.

## 13. الصلاحيات في المنتج المتصل

في Prototype نحاكي الحدود بالـViews، لكن عند إضافة الدخول الحقيقي يجب أن تكون الصلاحيات في Backend:

| الجهة | ترى | تعدل | لا تستطيع |
|---|---|---|---|
| صاحب المشروع | بيانات مشروعه، Market العام، تفاعلاته، Delivery الخاصة به | تفاعلاته، مهامه، تأكيد عروضه، تقييماته، وآثاره المالية عبر Micro | تعديل Listing مورد أو تحديث حالة شركة بدلًا عنها. |
| المورد | Listings الخاصة به، تفاعلات وطلبات منتجاته، Delivery المرتبطة به | Listingsه، ردوده، الجاهزية، مهامه الخاصة | رؤية Finance أو طلبات موردين آخرين أو تعديل اتفاقات خارجية. |
| شركة التوصيل | المهام التي وصلت إليها وسجلها | العرض، السعر، الوقت، منفذ الرحلة، حالات التنفيذ، الاستثناءات | رؤية سعر المنتج أو مال المشروع أو بيانات خارج المهمة. |
| الإدارة الداخلية | Queue المراجعة والبلاغات وحالة المحتوى | قرار نشر Listing أو إيقافها وملاحظات المراجعة | قبول البيع أو تسعير النقل أو تحريك الطلبات الطبيعية. |

يجب اختبار كل Endpoint أو Use Case بسياق الجهة، وليس الاعتماد على أن الواجهة أخفت الزر.

## 14. دور الـCTO في المشروع

الـCTO هنا ليس الشخص الذي يختار مكتبة أو يكتب أكبر كمية كود. هو المسؤول عن أن ما نبنيه قابل للتشغيل، مفهوم، قابل للتوسع، ولا يخرّب معنى Micro.

### مسؤوليات الـCTO

| المجال | مسؤولية الـCTO |
|---|---|
| Product/Tech Boundary | منع إدخال API خارجي أو سائق أو دفع أو نظام عام دون قرار مالك واضح. |
| Architecture | تثبيت Modular Monolith وShared Domain وفصل بوابات الواجهات عن المنطق. |
| Domain Contracts | اعتماد الكيانات والحالات والانتقالات وعدم خلط Market وDelivery والمال. |
| Data | تصميم الملكية والعلاقات وschema/migrations وExport/Import والتدقيق. |
| Security | وضع Authorization وعزل بيانات المورد والشركة والمشروع عند Pilot. |
| UX/Engineering Alignment | التأكد أن الشاشات تعكس حالات حقيقية ولا تعرض نجاحًا وهميًا. |
| Quality | فرض اختبارات للحالات السعيدة والفاشلة والتكرار والتأخير والتحديثات. |
| Delivery | تقسيم العمل إلى Vertical Slices قابلة للقبول، لا إصدار ضخم غير قابل للمراجعة. |
| Operations | تحديد الرصد والنسخ والاستعادة واستجابة الفشل قبل تشغيل أطراف حقيقيين. |
| Cost/Risk | اختيار أبسط تقنية تحقق الهدف، ومراقبة تكلفة الاستضافة والتخزين والدعم. |
| Vendor Independence | عدم جعل Micro تابعًا لشركة توصيل أو مزود API واحد. |
| Release Gate | منع الانتقال من Prototype إلى Pilot قبل تحقق معايير القبول. |

### ما لا يفعله الـCTO

لا يقرر وحده أن الدفع يجب أن يدخل، ولا يضيف Driver App لأن السوق يملكه، ولا يفرض API لأن التكامل ممكن، ولا يبني لوحة Admin ضخمة، ولا يعتبر اكتمال الكود دليلًا على نجاح المشكلة.

## 15. مراحل البناء الفعلية

### المرحلة 0 — المواصفة والعقود

المخرجات:

- Product Decision Brief.
- Domain contracts للكيانات والحالات.
- State Matrix.
- Permission Matrix للمنتج المتصل.
- Screen Inventory وScreen Contracts.
- سيناريوهات قبول صاحب المشروع والمورد والشركة.

لا كود في هذه المرحلة.

### المرحلة 1 — Prototype Shell وPersona Views

المخرجات:

- Owner View داخل App Shell الحالي.
- Supplier View منفصلة بصريًا.
- Courier Company View منفصلة بصريًا.
- Persona Switcher للاختبار فقط.
- Local Notification Center.
- بيانات اختبار اصطناعية وإضافة الأطراف والمنتجات والشركات.

لا Login ولا Auth ولا API ولا Cloud.

### المرحلة 2 — Market Vertical Slice

نبني المسار من Listing المورد إلى مشاهدة صاحب المشروع ثم تسجيل التفاعل:

```text
إضافة Listing
→ مراجعة داخلية
→ نشر لمدة 60 يومًا
→ بحث وعرض
→ تواصل/تفاعل اختياري
→ ظهور التفاعل للمورد
→ تأكيد المورد
→ تقييم التجربة
```

### المرحلة 3 — Delivery Vertical Slice

نبني المسار المستقل للجلب والإرسال:

```text
إنشاء DeliveryTask
→ شركة افتراضية
→ مراجعة الشركة
→ عرض السعر والموعد ومنفذ الرحلة
→ تأكيد الطالب
→ جاهزية المصدر
→ استلام
→ طريق
→ تسليم/فشل
```

### المرحلة 4 — ربط Market وDelivery

من سجل Market Interaction يستطيع المستخدم إنشاء جلب أو إرسال. تنتقل البيانات اللازمة فقط، ويظل السجلان منفصلين. نختبر أيضًا Delivery المستقلة التي لا ترتبط بـMarket.

### المرحلة 5 — توسيع الاختبار المحلي

نضيف الحالات الحدية، وإعادة الجدولة، والإلغاء، وفشل العنوان، وعدم جاهزية المورد، ورفض الشركة، ورفض الطالب للعرض، والتكرار، وExport/Import وReset.

### المرحلة 6 — Pilot متصل

لا تبدأ إلا بعد قرار جديد وفحص قابلية الاستخدام. يضاف Backend وLogin وصلاحيات وبوابات حقيقية داخل Micro، لكن لا يضاف API خارجي.

### المرحلة 7 — MVP المستقل

بعد Pilot، نثبت ما يحتاج إلى دعم ورصد ونسخ وإثباتات وسياسات تشغيل. لا نضيف تعدد الشركات أو تكاملًا خارجيًا إلا بدليل حاجة.

## 16. معيار «شغال» لكل مرحلة

### Prototype شغال

نقول إن Prototype شغال عندما يستطيع المالك من جهاز واحد:

1. إضافة مورد ومنتج وشركة توصيل.
2. مراجعة Listing ونشرها وإظهار انتهاء صلاحيتها بعد 60 يومًا.
3. فتح Owner View والبحث عن المنتج ورؤية التفاصيل ورقم المورد.
4. تسجيل تفاعل أو اتفاق خارجي اختياري.
5. تبديل Supplier View ورؤية التفاعل وتأكيده أو رفضه أو طلب التواصل.
6. إنشاء جلب أو إرسال من Owner أو Supplier.
7. تبديل Courier Company View ورؤية المهمة.
8. تقديم سعر وموعد واسم ورقم منفذ الرحلة.
9. العودة إلى Owner أو Supplier وتأكيد الحجز أو رفضه.
10. تسجيل الجاهزية والاستلام والطريق والتسليم أو الفشل من بوابة الشركة.
11. رؤية Timeline موحد من الطرف المرتبط.
12. تقييم المورد بعد تجربة مناسبة.
13. رؤية اقتراح تسجيل أثر مالي دون حفظ تلقائي.
14. حفظ كل شيء محليًا وتصديره واستيراده وإعادة ضبطه.

### Pilot شغال

نقول إن Pilot شغال عندما يدخل كل طرف من جهازه أو متصفحه إلى بوابته داخل Micro، ويرى فقط بياناته، وتعمل الرحلة دون اتصال هاتفي مركزي لكل خطوة. لا يشترط Pilot API خارجيًا؛ يكفي أن تعمل البوابات اليدوية داخل Micro.

### MVP شغال

نقول إن MVP شغال عندما يكون النظام قابلًا لاستخدام أطراف حقيقيين مع هوية وصلاحيات وعزل بيانات وسجل تدقيق وإشعارات داخلية واستعادة ورصد، وتكون حالات الفشل قابلة للمعالجة ولا تتضارب الأرقام أو الحالات.

## 17. اختبار القبول بالسيناريوهات

| السيناريو | النتيجة المطلوبة |
|---|---|
| مورد يضيف Listing ناقصة | لا تنشر مباشرة؛ يظهر طلب استكمال أو مراجعة. |
| Listing عمرها 60 يومًا | تنتقل إلى تحديث ومراجعة، ولا تبدو حديثة بلا تأكيد. |
| صاحب مشروع يرى منتجًا | يرى الصورة والوصف والسعر والوحدة والموقع وبيانات المورد. |
| اتفاق خارجي بلا تفاصيل | يستطيع تسجيل التفاعل دون نموذج طويل. |
| المورد لا يعرف الطلب | لا تظهر لصاحب المشروع حالة بيع مؤكدة؛ يظهر أن التفاعل غير مؤكد. |
| المورد غير متوفر | يراه صاحب المشروع بوضوح ويمكنه البحث عن بديل. |
| شركة التوصيل ترفض | لا تظهر المهمة محجوزة؛ يظهر سبب وخيار تالٍ. |
| الشركة تقدم سعرًا | لا تصبح المهمة مؤكدة قبل موافقة طالب السيارة. |
| صاحب المشروع يرفض العرض | تبقى غير محجوزة ويمكن طلب عرض آخر أو الإلغاء. |
| المصدر غير جاهز | لا تسجل الشركة استلامًا ناجحًا. |
| الشركة تسجل التسليم | يرى الطالب الحالة، لكن لا ينشأ قبض أو شراء أو ربح. |
| صاحب المشروع يريد أثرًا ماليًا | يفتح فعلًا ماليًا صريحًا ويؤكده يدويًا. |
| تكرار ضغط زر | لا تنشأ Listing أو مهمة أو حدث مكرر. |
| تبديل الدور | كل View ترى نطاقها، ولا تظهر بيانات الجهة الأخرى بلا سبب. |
| استيراد ملف غير صالح | لا تُمسح البيانات الحالية ولا يدعي النظام نجاحًا. |

## 18. قائمة ما يجب أن يوافق عليه المالك قبل الكود

التصميم المقترح يحسم معظم الأمور، لكن هذه القرارات يجب أن تظهر في المواصفة الرسمية قبل التنفيذ:

| القرار | اقتراح البناء |
|---|---|
| اسم السجل بعد الاتفاق الخارجي | `Market Interaction Record`، ويظهر للمستخدم «سجل طلب Market». |
| ظهور تفاصيل الطلب للمورد | تظهر التفاصيل التي أدخلها صاحب المشروع اختياريًا، مع الاسم والرقم حسب ما اعتمدته، ولا تظهر بيانات مالية أو نزاع. |
| تأكيد المورد | تأكيد اطلاع/قدرة/عدم توفر، وليس قبول بيع أو عقدًا. |
| تقييم المورد | أبعاد الاستجابة ودقة العرض والتوفر/الجاهزية ووضوح التعامل، بعد تفاعل مناسب. |
| شركة التوصيل الأولى | شركة افتراضية واحدة، ولا توزيع حقيقي بين عدة شركات. |
| تسعير النقل | الشركة تدخل السعر والموعد، والطالب يؤكد الحجز. |
| منفذ الرحلة | اسم ورقم يسجلان في المهمة، بلا حساب أو بوابة مستقلة. |
| الإدارة الداخلية | مراجعة Listings والبلاغات فقط، بلا تشغيل يومي للطلبات. |
| التطبيق | Web/PWA مستقل التجربة لكل جهة أولًا، وNative لاحقًا عند إثبات الحاجة. |
| API | لا API خارجي؛ API داخلي بين بوابات Micro وBackend فقط عند مرحلة Login/Backend. |
| المالية | اقتراح تسجيل أثر، ولا حفظ تلقائي. أجرة التوصيل لا تدخل Finance تلقائيًا. |

## 19. النتيجة النهائية

إذا اعتمدنا هذا المخطط، فالمخرَج النهائي الذي نبنيه ليس «Marketplace مع صفحة توصيل» فقط، بل نظام Micro مستقل ومترابط:

```text
Micro Owner App
  ├── Micro Financial Core
  ├── Micro Market
  └── Micro Delivery

Supplier Portal
  ├── Listings
  ├── Market Interactions / Market Orders
  └── Delivery Requests

Courier Company Portal
  ├── New Delivery Requests
  ├── Offers and Booking
  ├── Active Deliveries
  └── Delivery History and Exceptions

Internal Moderation Console
  └── Listing Review and Platform Reports only
```

الـPrototype الأول يحاكي هذه التجارب على جهاز واحد بقاعدة محلية، بلا Login أو Auth أو API خارجي أو إشعارات حقيقية. وبعد شهر الاختبار، نقرر الانتقال إلى Backend وLogin وصلاحيات وبوابات حقيقية داخل Micro، مع بقاء المورد وشركة التوصيل مستخدمين لمنصة Micro نفسها، لا لعمليات تكامل مع أنظمتهما الخارجية.

هذا هو المسار الذي يحقق الصورة التي تريدها: **ثلاث بوابات واضحة، بيانات مترابطة، مسؤوليات منفصلة، توصيل مؤكد عبر بوابة الشركة، اتفاق تجاري خارجي، وMicro يحافظ على معناه المالي دون إضافة أدوار أو تقنيات غير مطلوبة.**
