# Expansion — قائمة التشغيل المشتركة للـ7 Agents

**الحالة:** `CURRENT / E-00 GOVERNANCE / DOCUMENTATION ONLY`
**الغرض:** توحيد طريقة عمل سبعة Agents على توسعة Micro من دون أن يتحول العمل المتوازي إلى تعارض في العقود أو إيهام بأن PR كثيرة تعني تنفيذًا صحيحًا.

## Major Discussion Points

## 1. مبدأ «متوازٍ في الفحص، متسلسل في الحقيقة»

يمكن للـAgents السبعة قراءة العقود، مراجعة الأدلة، إعداد مسودة سيناريو، أو تدقيق وثائق **بالتوازي** عندما تكون ملكية الملفات منفصلة. لكن أي تغيير للحالة الحية أو العقد أو Tracker أو Schema أو كود أو PR مدمجة يكون **متسلسلًا**: فرع من `origin/main` → PR مستقلة → قبول نظيف → CI وCloudflare → Squash merge → رأس `main` جديد.

> لا تعمل سبع فروع كود على Home أو App Shell أو Domain أو LocalStore في الوقت نفسه. السرعة الصحيحة تأتي من إزالة الغموض وتوزيع المراجعة، لا من خلق سبع نسخ متعارضة من الحقيقة.

## 2. قائمة التحقق الثابتة لكل Agent

لا يبدأ Agent مهمة ولا يؤشر انتهاءها قبل المرور بهذه القائمة وتسجيل الدليل في تقريره أو PR:

- [ ] 1. نفّذ `git fetch origin --prune` وسجل SHA قاعدة `origin/main` ورقم PRات الحية.
- [ ] 2. اقرأ `AGENTS.md` و`docs/operations/current-state.md` وميثاق التفكير والفهرس وREADME التوسعة وDECISIONS وTRACKER.
- [ ] 3. عرّف معرّف العمل، الشخص المتأثر، الموقف، الضرر، سؤال القرار، أقل إدخال، النتيجة، والفعل التالي.
- [ ] 4. اقرأ العقد والسيناريو ومصفوفة الوصول والـSOP المتصلين؛ لا تستبدلها بتقرير تاريخي أو ملف تحت `historical-source/`.
- [ ] 5. اكتب قبل التعديل: ما ستغيره، ما لن تغيره، وما الذي يبقى مجهولًا أو قرار Owner.
- [ ] 6. أضف بند عمل محلي غير مكتمل إلى `todo.md` قبل التعديل، ثم أبقه خارج staging وcommit.
- [ ] 7. أنشئ فرعًا/worktree نظيفًا من `origin/main`؛ لا تبدأ من فرع Agent آخر أو SHA قديم.
- [ ] 8. راجع النطاق أولًا: لا تحول مشكلة دليل إلى Feature، ولا تغير معنى المال أو تاريخًا أو Snapshot أو schema/export بلا عقد وبوابة مستقلة.
- [ ] 9. اكتب أو عدّل فقط الملفات المصرح بها لمهمتك. لا تلمس ملف ملكية Agent آخر أو `current-state.md`/TRACKER إلا إن كنت Agent التكامل أو كانت المهمة تطلب ذلك صراحة.
- [ ] 10. أضف الاختبار أو دليل المراجعة المتناسب: عقد/سيناريو/رابط/فحص روابط أو اختبار تقني حسب نوع العمل.
- [ ] 11. شغّل الفحوص المطلوبة: `pnpm install --frozen-lockfile` و`pnpm check` و`git diff --check`، واختبارات أو تدقيق روابط مخصص. لا تخفِ فشلًا بتحذير عام.
- [ ] 12. افحص الفرق وغياب `todo.md` و`version.json` وبيانات QA وملفات build، ثم افتح PR واحدة ضيقة وواضحة إلى `main`.
- [ ] 13. ضع في PR: معرّف المهمة، سؤال القرار، المغير/غير المغير، الدليل، حدود القبول، والقرار أو البوابة التالية.
- [ ] 14. راجع Agent مستقل الرأس في worktree قبول نظيف؛ يقرأ الفرق والعقود ويعيد الفحوص. لا يقبل صاحب التعديل عمله وحده.
- [ ] 15. يدمج Agent التكامل فقط بعد نجاح CI وCloudflare والقبول المستقل، ثم يتحقق من SHA `origin/main` ويحدّث Tracker/Sجل الحالة بالدليل. لا ينتقل Agent الكود التالي قبل ذلك.

## 3. توزيع المسؤوليات السبعة

| Agent | ملكية التحقيق/التوثيق | لا يملك | مخرج قابل للتسليم |
|---|---|---|---|
| 1 — حارس التكامل | current-state، Tracker، قائمة قبول E-00، وربط الأدلة وPR التوثيقية المتجانسة. | تغيير عقد مالي أو اختيار Wedge أو بدء كود L/A. | تقرير قبول/فشل E-00 ورابط الدليل لكل بند. |
| 2 — الهوية والوصول | العقود 18 و23، Matrix الأدوار، بوابات الجهات الأربع واستعادة الوصول. | مزود Auth أو DB أو Login أو API. | مراجعة N-01/N-02/N-05 ونطاق Admin والاستعادة. |
| 3 — Market | العقد 20 وسيناريوهات Need/Response/Listing/Media وحدود Moderation المتصلة. | شراء/دفع/تقييم/Chat أو تأثير Manage. | Coverage map لـMarket مع حالات رفض. |
| 4 — Delivery | العقد 21 وسيناريوهات Request/Quote/Status/Exception والإفصاح. | GPS/Dispatch/Driver/دفع أو اعتبار الحالة أثرًا ماليًا. | Coverage map لـDelivery مع فشل/تأخير/خصوصية. |
| 5 — البيانات والخصوصية | العقدين 22 و24، التصنيف، Audit، موافقات، lifecycle وMigration/Export gate. | سياسة قانونية نهائية أو نقل Manage أو schema/export. | جدول فجوات الحقل/الغرض/Scope/الاحتفاظ وقرار No-change. |
| 6 — تجربة البيت والقبول | سيناريوهات E-00، SOP تجربة البيت، سجل التجربة، خطة QA وقيود Simulator. | ادعاء حماية متعددة الأطراف أو دعوة حقيقية أو Pilot. | خطة تحقق L ودليل أن السيناريو لا يدعي أكثر مما يثبت. |
| 7 — المعمارية والتشغيل | قرار المعمارية، Activation/Pilot SOP، قابلية التشغيل، وتنسيق دمج مراجعات Agents 2–6. | اختيار مزود أو تكلفة أو استضافة أو تنفيذ خدمة متصلة. | Gate packet قبل L وبعدها قبل A، مع قرارات Owner المفتوحة. |

هذه ملكية مراجعة وتوثيق، لا إذن بفتح سبع PRات متنافسة على الملف نفسه. Agent 1 يحدد ملف الملكية لكل PR؛ وإن اختلف Agentان على عقد واحد، يجمعان الدليل في تقريرين ويرفعان القرار إلى Agent 1 بدل تعديل النص في فرعين.

## 6. حواجز التوقف الموحدة

يتوقف Agent عن الدمج والانتقال، ويكتب تقريرًا بدلًا من التخمين، عند الحاجة إلى: اختيار فئة/منطقة/Wedge/شريك/مزود هوية؛ تغيير `localSchemaVersion` أو `localExportVersion`؛ نقل Manage إلى الشبكة؛ تغيير معنى مال أو تاريخ أو Snapshot؛ دعوة شخص حقيقي؛ اختيار سياسة قانونية أو احتفاظ؛ أو فتح قدرة دفع/تقييم/Chat/GPS/Driver/Dispatch.

## Action Points

1. يبدأ الآن Agent 1 بمراجعة E-00 المستقلة، بينما تعمل Agents 2–7 على أدلة مراجعة منفصلة فقط إذا كانت ملفات ملكيتها لا تتداخل.
2. لا يبدأ أي Agent كود توسعة أو محاكي أدوار أو واجهة السوق/التوصيل قبل قبول E-00.14 وL-00 وقرار Wedge.
3. لا يؤشر Tracker أي بند E-00 لمجرد وجود هذا الدليل؛ يلزم PR قبول ومراجع مستقل ورابط دليل.
