# Expansion — بوابة Migration وExport بين Manage والشبكة

**الحالة:** `CURRENT / DECISION: NO MANAGE MIGRATION`
**الغرض:** منع تغير schema/export أو نقل بيانات مالية باسم ربط Market أو Delivery من دون عقد ومراجعة مستقلة.

## Major Discussion Points

## 1. القرار الحالي

لا تتغير `localSchemaVersion` أو `localExportVersion` بسبب E-00 أو L-01 أو E-01. لا تنقل Micro Manage مالًا أو طلبات أو عملاء أو Snapshotات أو مخزونًا إلى الشبكة. لا يشمل `local export/import` بيانات Market/Delivery المتصلة أو عضوياتها أو وسائطها كأنها جزء من Snapshot Manage.

> **رابط خارجي اختياري ليس Migration.** `external_reference` أو `recording_suggestion` يحملان مرجعًا ومصدرًا اختاره Owner، ولا ينسخان payload أو يعطيان قدرة قراءة متبادلة.

> **ملاحظة مؤرخة 2026-11-13 (EX-D22 — تفويض المالك المنقح `MASTER-PROMPT-EN.md` عند `0d4ae258`):** هذا القرار `NO MANAGE MIGRATION` **يبقى نافذًا كما هو**. المصرح به إضافيًا لهذه المهمة حصرًا هو **الجسر القشري/الهوياتي الأدنى**: مدخل/مسار من القشرة المشتركة يعرض تجربة Manage المحلية القائمة كما هي، وعقد ربط مستقبلي مستقر (principal + حدود هوية→Workspace) يُنفذ في طبقة الشبكة **خارج** لقطة التصدير والمخازن المحلية — بشرط ألا يغيّر سلوك Manage المالي/المحلي ولا `localSchemaVersion`/`localExportVersion` ولا أزواج الاستيراد المقبولة ولا التصدير/الاستعادة، وأن يثبت ذلك بفحوص Manage القائمة دون تغيير. نقل بيانات/مال Manage إلى هدف PostgreSQL يتم في مرحلة وفرع مستقلين ببطاقة قرار من قالب §3 — ولا يُنشأ ذلك الفرع الآن، ولا يُربط مال محلي بهوية سحابية بالبريد الإلكتروني وحده أبدًا.

## 2-ب. بروتوكول ربط حساب Manage المستقبلي (حد مستقر — EX-D22، 2026-11-14)

> المصرح به الآن هو الجسر القشري/الهوياتي الأدنى فقط (ملاحظة §1 أعلاه). الحدود
> المستقرة لأي ربط فعلي لاحق — التي لا يجوز تجاوزها دون بطاقة قرار من قالب §3:

1. **لا ربط بالبريد وحده أبدًا:** مطابقة بريد إلكتروني بين `network_identity` و
   `OwnerProfile.email` المحلي لا تثبت ملكية المال — flow المطالبة الساذج يتيح
   انتزاع بيانات مالية لشخص خاطئ.
2. **إثبات الملكية المزدوج الموقع (المسار المرشح):** سر عشوائي يُولّده المالك من
   داخل Manage ويُودع في ملف التصدير المحلي (خارج لقطة البيانات) + تأكيد ثانٍ
   داخل الجلسة السحابية؛ أو تأكيد مزدوج صريح يعتمده المالك.
3. **مكان جدول الربط:** طبقة الشبكة حصرًا (نمط `network_identity`)، خارج مظروف
   التصدير المحلي وعلى الهدف PostgreSQL نفسه المعَد لذلك (EX-D20) — لا يدخل
   `workspace_id` ولا أي معرف شبكة في ملف التصدير إلا كبيانات وصفية اختيارية
   تحفظ قابلية النقل (وعد المظروف: يعمل مستقلًا على جهاز نظيف).
4. **ما قبل الربط:** MFA/إعادة تحقق قرار مالك مستقل؛ وعرض حدود «فقد الجهاز =
   فقد المال ما لم يوجد Export» كما هي حتى اكتمال الترحيل.
5. **ما لا يتغير:** 41/34 والـ29 زوجًا والتصدير/الاستعادة و`runProtectedReplacement`
   كما هي؛ الترحيل نفسه (نقل السجلات إلى PostgreSQL) فرع وقرار مستقلان ببطاقة
   كاملة من قالب §3 — لا يُنشأ ذلك الفرع ضمن المهمة الحالية.


> **ملاحظة مؤرخة 2026-11-14 (EX-D23 — أمر المالك `MANAGE-ONLINE-IMPLEMENTATION-PROMPT-EN.md` عند `cf9ac194`):** قَبِل المالك مسح S13 وفتح **تنفيذ Manage Online المستودعي** بالموجات M1–M6 على الفرع المخصص `zai/micro-manage-online-20261114`. قرار `NO MANAGE MIGRATION` أعلاه **يبقى نافذًا كما هو للنقل الفعلي للبيانات الحقيقية**: لا يُطبق أي مخطط على مشروع/فرع Neon، ولا تُنقل أي بيانات مالك حقيقية، ولا يُفعَّل القطع لأي Workspace حقيقي — تلك كلها بوابات مشغّل لاحقة. المصرح به مستودعي حصرًا: عقود وسيناريوهات (M1)، أساس خادمي معطِّل افتراضيًا (M2)، مسارات قراءة بحالات صدق (M3)، كتابات معاملاتية حتمية (M4)، مسار ترحيل **ببيانات اصطناعية فقط** مع بقاء التصدير المحلي مصدر الاسترداد (M5)، ووضع متصل-فقط محروس غير مفعّل (M6). البطاقات أدناه (§3-أ) هي بطاقات قرار §3 المطلوبة قبل أي جدول/مسار مالي شبكي جديد، مسجلة من القرار الملزم لا مُخترعة.

## 2-ج. متى يحتاج الأمر عقد Migration مستقلًا

| التغيير المقترح | هل يحتاج عقد/PR مستقلة؟ | لماذا |
|---|---:|---|
| إضافة Domain/Storage محلي جديد لـL | نعم. | يغير Schema/Export/Restore أو يحتاج قرارًا صريحًا «لا تغيير» مثبتًا. |
| ربط Need باسم مادة مختارة | نعم، إذا خزّن رابطًا في Manage. | يجب تحديد تاريخية الرابط وExport/Import وغياب المادة. |
| عرض Attention/Notification متصل داخل Market أو Delivery | لا في Manage Schema إن كان منفصلًا تمامًا. | لا ينسخ سجل الشبكة ولا يعدل مالًا؛ يحتاج عقد Network فقط. |
| اقتراح تسجيل Expense/Purchase/Inventory | نعم، إن مرر أي حقل مالي أو غير مرجع محدود. | خطر مبلغ/تاريخ/نوع مفروض أو تكرار. |
| نسخ Order/Customer/address إلى Delivery | نعم، قبل أي حقل؛ وقرار خصوصية مستقل. | ليس سياقًا تقنيًا عاديًا بل إفصاح حساس وتاريخي. |
| دمج/مزامنة Manage بين أجهزة | نعم، مشروع منفصل. | تعارضات/تكرار/Recovery وتحويل نموذج local-first. |

## 3. قالب القرار الإلزامي

أي PR تقترح تغييرًا في الجدول أعلاه تكتب قبل الكود:

| الحقل | المطلوب |
|---|---|
| المشكلة والبديل الأخف | لماذا لا يكفي Reference أو إدخال Owner منفصل؟ |
| الكيانات والحقول | ما الجديد وما السابق وما الحساس؟ |
| نسخة Schema/Export | القيمة قبل/بعد، وخطة الملفات القديمة والجديدة. |
| التاريخ والمال | هل يغير طلبًا/Snapshot/نتيجة/كاش؟ وكيف يمنع الكتابة الصامتة؟ |
| الاستعادة والتراجع | Restore وImport وrollback وما يحدث للفشل/التكرار. |
| الخصوصية | ما الذي يخرج من Manage ولماذا ومن يراه؟ |
| الاختبارات | Domain/Application/Store/Export-Import/negative cases/QA. |
| القبول والحد | ما يثبت وما يبقى خارج النطاق. |


## 3-أ. بطاقات القرار المنفذة — تنفيذ Manage Online المستودعي (EX-D23، 2026-11-14)

> أربع بطاقات من قالب §3، مسجلة قبل أي كود M2+ بأمر المالك المؤرخ 2026-11-14 (الالتزام cf9ac194). كل بطاقة تحمل حد رجوعها.

**البطاقة أ — قدرة manage وقيد المالك الواحد (موجة M2):**
- المشكلة والبديل الأخف: لا يوجد اليوم أي مفهوم «مالك Manage» شبكيًا؛ البديل الأخير (عرض تجربة محلية بلا قدرة) نفذ في EX-D22 ولا يكفي للقراءة/الكتابة المتصلة المصرح بها الآن.
- الكيانات والحقول: عمود قدرة `manage_enabled` على `workspace` (افتراضي 0 — معطل حتى يطبق المشغل المخطط ويتحققه) + جدول ربط شبكي الجانب حصرًا. لا كيان مالي جديد في M2.
- نسخة Schema/Export: **لا تغيير** — 41/34 والـ29 زوجًا كما هي (يُثبت بفحوصها القائمة بلا تعديل).
- التاريخ والمال: M2 لا تحمل أي مال؛ كل مسارها بوابة/ربط/تعطيل بفشل مغلق.
- الاستعادة والتراجع: revert التزام M2 يعيد الجذر بلا أثر (لا بيانات منتقلة).
- الخصوصية: الربط لا يكشف بريدًا لأي طرف آخر؛ التدقيق بلا PII.
- الاختبارات: فحوص سالبة (ضيف/غير مربوط/بريد فقط/مورد/سائق/أدمن/عبور Workspace/مالك ثانٍ) فوق PostgreSQL حقيقي.
- القبول والحد: القيد خادمي مفروض بالجدول والبوابة معًا؛ خارج النطاق: أي تفعيل حقيقي للقدرة.

**البطاقة ب — ربط الهوية الموثق (موجة M2، بروتوكول §2-ب):**
- المشكلة والبديل الأخف: مطابقة البريد وحدها تتيح انتزاع بيانات مالية لشخص خاطئ — مرفوضة نصًا؛ البديل الأدنى (لا رابط إطلاقًا) يحجب القدرة المصرح بها.
- الكيانات والحقول: جدول `manage_owner_link` شبكي الجانب حصرًا: workspace، هوية، نيون (nonce) خادمي، بصمة سر الإثبات (تجزئة فقط — لا سر خام)، حالة (pending/linked)، طابعان زمنيان؛ خارج مظروف التصدير المحلي تمامًا.
- نسخة Schema/Export: **لا تغيير** — الحقلان المحجوزان المحليان (`provider`/`externalAccountId`) يبقيان فارغين؛ لا يدخل `workspace_id` ملف التصدير.
- التاريخ والمال: الربط لا ينشئ أي أثر مالي؛ يؤكد الملكية فقط.
- الاستعادة والتراجع: فك الربط ممكن بتدقيق؛ revert الالتزام يزيل الجدول كاملًا (لا بيانات إنتاج).
- الخصوصية: بصمة السر فقط تُخزن؛ لا يُعرض بريد المالك لأي دور آخر.
- الاختبارات: اختبار سلبي صريح أن مطابقة البريد بلا التوقيع المزدوج تُرفض؛ الربط لا يمس 41/34 (فحوص التخزين خضراء بلا تعديل).
- القبول والحد: بروتوكول §2-ب كما هو (سر يولَّد داخل Manage + تأكيد ثانٍ داخل الجلسة السحابية)؛ خارج النطاق: MFA/إعادة تحقق ما قبل الربط (قرار مالك مستقل قائم).

**البطاقة ج — جداول بيانات Manage المتصلة (موجات M3–M5، بيانات اصطناعية فقط):**
- المشكلة والبديل الأخف: القراءة/الكتابة المتصلة المصرح بها تحتاج مخزنًا خادميًا للسجلات المالية؛ البديل الأخف (نسخ يدوية) مرفوض (كتابة صامتة/تكرار).
- الكيانات والحقول: مخزن سجلات مفاتيحه (workspace، عائلة، معرف السجل) وقيمته سجل JSON محفوظ **بالقيم الدقيقة كما في مظروف التصدير** + عمود `updated_at` لفرض CAS، مع فصل التسمية (`manage_*`) وحقول workspace_id وفرض الوصول في طبقة API كما اليوم — لا اعتماد على RLS جلسي عبر Hyperdrive.
- نسخة Schema/Export: **لا تغيير** — مخزن الشبكة صورة للعائلات القائمة؛ التصدير المحلي يبقى مصدر الاسترداد وصمام الرجوع.
- التاريخ والمال: كل كتابة معاملة واحدة + حتمية (نمط 24 ساعة/409 القائم) + فحص حالة داخل المعاملة (CAS) — لا آخر-كاتب-يفوز؛ لا حساب في طبقة الشبكة أصلًا (العقد 25).
- الاستعادة والتراجع: مسار الترحيل (M5) idempotent بنفس بصمة التصدير، مع رجوع كامل مجرب (حذف بيانات الworkspace المهاجرة) قبل أي بوابة قطع.
- الخصوصية: لا بيانات شريك حقيقية — اصطناعية حصرًا حتى حل قرارات الاحتفاظ/الحذف/التصدير/الخصوصية/الاسترداد بقرار مالك موثق (لا تُخترع مدد قانونية).
- الاختبارات: عدادات/قيم دقيقة/بصمات متطابقة آليًا قبل/بعد؛ تزامن وإعادة محاولة وانقطاع؛ عزل عبور Workspace/دور.
- القبول والحد: المخطط ملفات مستودعية لا تُطبق على Neon إلا بيد المشغل؛ خارج النطاق: نقل بيانات حقيقية (بوابة مشغل لاحقة).

**البطاقة د — قاعدة الوصول: مالك موثق واحد (موجات M2–M6):**
- المشكلة والبديل الأخف: بدون بوابة خادمية صريحة يصبح إخفاء الواجهة «تصريحًا» — مرفوض (عقد 18 §4).
- الكيانات والحقول: حارس `requireManageOwner` (أو ما يعادله) يفحص في كل طلب: جلسة موثقة + قدرة manage مفعلة للمخطط المطبق + ربط موثق قائم + المالك هو المالك الوحيد المرتبط؛ يُرفض ضيف (401) وغير مربوط وأدمن منصة وأي دور آخر (403/404 مدقق).
- نسخة Schema/Export: لا يمس.
- التاريخ والمال: البوابة شرط كل مسار مالي متصل — لا مسار يمر دونها.
- الاستعادة والتراجع: revert يزيل المسارات معها.
- الخصوصية: الرفض لا يكشف وجود سجل لغير المالك (404 للأجنبي).
- الاختبارات: موجبة/سالبة لكل مسار قراءة/كتابة (MO-06/MO-07).
- القبول والحد: الأدمن لا يلمس مال Manage أبدًا (تمديد عقد 18)؛ خارج النطاق: أي دور مالي إضافي للموظف/المحاسب (مرفوض بقرار المالك §3).

## 4. اختبار الحارس

قبل دمج أي Feature Network، يفحص المراجع أن فرقها لا يغير ملفات Schema/Export/LocalStore أو عقود المال، ما لم تشير إلى قرار Migration مستقل ومعتمد. اختبار واحد على الأقل يثبت أن قبول Response أو Quote أو Status لا يغير Snapshot أو كاش أو دين أو مخزون أو Order التاريخي.

## Action Points

- [ ] يبقى هذا القرار `NO MANAGE MIGRATION` حتى يظهر سبب مستخدم مثبت وموافقة مالك على بطاقة قرار كاملة.
- [ ] يضاف رابط هذه البوابة إلى كل PR L/E تمس سياق Manage أو تخزينًا أو Export/Import.
- [ ] لا تُخفى migration ضمن dependency update أو refactor أو «تحسين تجربة»؛ توقف الـPR وتفصلها.
