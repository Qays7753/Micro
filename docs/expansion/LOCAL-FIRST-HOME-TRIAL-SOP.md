# Expansion — إجراء تجربة البيت Local-first لمدة 1–3 أشهر

**الحالة:** `CURRENT / PREPARATION ONLY / RUNS AFTER L-00 TO L-04`
**الحد:** هذا إجراء تجربة صاحب المنتج على جهازه؛ لا يثبت Pilot أو أمانًا متعدد الأطراف أو سوقًا حيًا.

## Major Discussion Points

## 1. هدف التجربة

هدف تجربة البيت ليس «إثبات أن الشاشات تعمل» بل اختبار أسئلة محددة: هل تصل Owner إلى متابعة خارجية دون أن تفسد أولويتها المالية؟ هل تميز بين رد/عرض وحقيقة شراء أو تسليم؟ هل تستطيع استئناف مسودة بعد refresh أو انقطاع؟ وهل حل Market أو Delivery ضررًا تكرر فعلًا أم أضاف واجهة؟

تستخدم التجربة بيانات اصطناعية أو بيانات المالك التي يملك حق استعمالها. لا يدخل مورد أو Courier أو عميل حقيقي إلى Role Simulator، ولا تحفظ أرقام هواتف أو عناوين أو صور أشخاص حقيقيين داخل بيانات اختبار مشتركة.

## 2. إعداد قبل اليوم الأول

| البند | ما يجب فعله | دليل التأشير |
|---|---|---|
| بيئة منفصلة | Browser profile أو جهاز اختبار منفصل عن بيانات Manage الشخصية متى أمكن. | اسم البيئة وتاريخ البدء. |
| نسخة استعادة | Export محلي قبل التجربة، ثم اختبار Restore في بيئة منفصلة. | تاريخ Export ونتيجة Restore. |
| بيان الحدود | تأكيد ظهور وسم محاكي الدور وعدم وجود Login/Cloud/إشعارات حقيقية. | لقطة/ملاحظة QA. |
| سيناريوهات | اختيار 12–20 سيناريوًا من `E00-SCENARIOS-AND-ACCEPTANCE.md`. | قائمة المعرفات المختارة. |
| مقياس الضرر | تسجيل الوقت/الخطوات/التردد والفهم لا «إعجاب عام». | سجل أسبوعي فارغ جاهز. |

## 3. روتين الاستخدام

| التكرار | ما يختبر | ما يسجل |
|---|---|---|
| عند حدث حقيقي أو محاكى | فتح السوق أو رمز التوصيل، إنشاء Need أو Delivery draft، ثم Role Simulator للرد/Quote/Status. | هل عرف الفعل التالي؟ هل دخل من المكان المتوقع؟ كم خطوة أخذ؟ |
| أسبوعيًا | مراجعة Attention داخل مصدرها والعودة من الإشعار وحالات Market/Delivery. | عناصر مهملة/مربكة أو حالة لا تفسر نفسها. |
| كل أسبوعين | Export ثم Restore في بيئة اختبار والتحقق من المسودات والتاريخ. | نجاح/فشل وسبب، بلا استبدال بيانات العمل الوحيدة. |
| شهريًا | مراجعة فرضيات القيمة وحدود الخصوصية وعدم الأثر المالي. | تكرار المشكلة، قرار بناء/تعديل/تأجيل. |

## 4. تصنيف كل ملاحظة

| التصنيف | مثال | التصرف |
|---|---|---|
| UX | Owner لا تعرف الفرق بين Quote وBooking. | بطاقة UX مع لقطة وسيناريو وفعل تالي. |
| Domain/Contract | حالة Delivery تسمح انتقالًا غير واضح. | أوقف الشريحة وحدّث العقد قبل الكود. |
| Storage/Recovery | مسودة تختفي بعد refresh. | بطاقة LocalStore واختبار Restore؛ لا patch واجهة فقط. |
| حقيقة مالية | يفهم المستخدم أن الوصول يعني قبضًا. | عيب حرج؛ أوقف الانتقال حتى يعالج العقد والعرض. |
| فرضية سوق | لا يستخدم Owner البحث أو لا يرد شخص محاكى بطريقة واقعية. | لا تسمى مشكلة كود؛ تجمع دليلًا أو تؤجل. |
| صلاحية مستقبلية | Role simulator يسرب View عند URL مباشر. | توثق كفجوة A؛ لا تدعي أمانًا في L. |

## 5. بوابة الانتقال من L إلى A

لا يكفي مرور شهر. تتطلب بوابة التفعيل: إتمام السيناريوهات المختارة بلا فقد مسودة أو أثر مالي كاذب أو dead end حرج؛ Export/Restore موثقين؛ دليل أن مشكلة واحدة على الأقل تتكرر؛ فئة ومنطقة أوليتان معلومتان؛ والتزام طرف حقيقي واحد على الأقل بتجربة ضيقة. إن غاب أي شرط، تستمر التجربة أو تعدل/تلغي Slice ولا تضيف Cloud/Auth بسبب التقويم فقط.
