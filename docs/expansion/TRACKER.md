## 3. المرحلة L — تجربة منزلية Local-first بلا حسابات ولا Cloud

### L-00 — تثبيت سطح Micro قبل التوسعة

- [ ] **L-00.1:** تدمج G19 بعد قبول مستقل؛ لا فرع توسعة يمس Agreement أو Cost قبل ذلك.
- [ ] **L-00.2:** تدمج G20 ثم G21 ثم G22 ثم G23 بالترتيب، مع PR وقبول مستقلين.
- [ ] **L-00.3:** تثبت رأس `main` ونتائج `pnpm check` قبل أول فرع توسعة.
- [ ] **L-00.4:** تعتمد wireframe نصي للشاشات الأربع: Home مع سطر خدمات، خدمات فارغة، خدمات مع متابعات، وتفصيل متابعة واحدة.

### L-01 — Domain/Storage ومحاكي الدور

- [ ] **L-01.1:** تنشئ Domain مستقلًا لـ`network`/`services`، لا يختلط بدومين المال أو الطلبات أو المخزون.
- [ ] **L-01.2:** تضيف Use Cases وPorts، ثم `PrototypeLocalStore` وIndexedDB؛ لا Page أو React يصلان إلى IndexedDB مباشرة.
- [ ] **L-01.3:** أي تخزين جديد يحمل معرفًا وزمنًا وفاعلًا وidempotency حيث يلزم؛ أي تغيير schema/export يمر بقرار Migration/Export/Import مستقل واختبارات Restore.
- [ ] **L-01.4:** تضيف محاكي دور QA محليًا وداخل feature flag/route موثق فقط، بعنوان واضح «بيئة اختبار محلية — ليست حسابات محمية».
- [ ] **L-01.5:** تطبق سياسة الدور في Application حتى في المحاكي، وتختبر URL المباشر والخطأ الآمن؛ لا تدعي أن ذلك أمن بين مستخدمين.

### L-02 — Owner Services

- [ ] **L-02.1:** تجعل `الخدمات` وجهة ثابتة بعد استقرار UX؛ تنقل الإعدادات إلى هيدر/المزيد مع QA رجوع وعدم dead end.
- [ ] **L-02.2:** الحالة الفارغة تقول الحقيقة ثم تعرض `ابحث عن مورد` و`اطلب توصيلًا` كمدخلين هادئين.
- [ ] **L-02.3:** الحالة المعبأة تعرض حتى ثلاث متابعات: المصدر والشيء/المهمة وآخر تحديث وفعل واحد؛ ترتيبها قرار Owner ثم الموعد ثم الأحدث.
- [ ] **L-02.4:** Home يظهر سطر خدمات واحدًا فقط إذا لم ينافس أولوية مالية/تشغيلية أعلى. الإشعار مدخل إلى العمل وليس نسخة من اللوحة.
- [ ] **L-02.5:** كل انتقال يعيد إلى المصدر الصحيح مع حارس المسودة؛ لا تنشأ واقعة مالية أو مخزنية عند الفتح أو التنبيه.

### L-03 — Market محلي كامل للتجربة

- [ ] **L-03.1:** Owner ينشئ احتياجًا مسودة ويراجع البيانات التي ستظهر قبل النشر؛ لا سعر بيع أو ربح أو Snapshot أو معلومات عميل خارج اختياره.
- [ ] **L-03.2:** Supplier simulator يرسل ردًا/عرضًا وتظهر حالة معرفة صادقة؛ Owner يقبل/يرفض/يغلق تفاعلًا فقط.
- [ ] **L-03.3:** Listing/الوسائط تمر `draft → submitted → under_review → approved/rejected → paused/archived`، وAdmin simulator يكتب السبب.
- [ ] **L-03.4:** من رد مقبول يظهر فقط `سجل ما حدث في مشروعي` كخيار لاحق؛ لا شراء أو تكلفة أو مخزون تلقائي.
- [ ] **L-03.5:** لا Checkout أو دفع أو عمولة أو ratings/نجوم أو Chat مفتوح أو توفر لحظي مدعى.

### L-04 — Delivery محلي كامل للتجربة

- [ ] **L-04.1:** Owner ينشئ طلب حركة مسودة ويقر سياقه قبل الإرسال؛ لا ينسخ عنوانًا أو هاتف عميل أو مبلغًا افتراضيًا.
- [ ] **L-04.2:** Courier simulator يرسل عرضًا/توضيحًا ثم أحداث `dispatched / arrived / completed / failed / cancelled` بفاعل ووقت وسبب عند الاستثناء.
- [ ] **L-04.3:** `arrived`/`completed` تصف ما سجلته جهة التوصيل فقط؛ لا تعني استلام مخزون أو تسليم طلب أو تحصيل أو مصروف.
- [ ] **L-04.4:** لا live tracking أو dispatch أو Driver Portal أو تسعير تلقائي أو دفع/تسوية.

### L-05 — تجربة البيت 1–3 أشهر

- [ ] **L-05.1:** يستخدم Owner Micro يوميًا ويصنف كل ملاحظة: UX أو Domain أو Storage أو صلاحية مستقبلية أو فرضية تجارية.
- [ ] **L-05.2:** ينفذ Export أسبوعيًا وRestore في بيئة اختبار منفصلة كل أسبوعين؛ لا يتشارك export حساسًا.
- [ ] **L-05.3:** يختبر Offline/refresh/back/ضغط متكرر/رفض إدخال و360/390/430px وRTL وLight/Dark.
- [ ] **L-05.4:** يستكمل 12–20 سيناريو Owner بلا فقد مسودة أو أثر مالي كاذب أو dead end حرج.
- [ ] **L-05.5:** يسجل دليلًا أن Market أو Delivery يحلان ضررًا متكررًا؛ إذا لم يثبت ذلك، نراجع أو نحذف Slice ولا ننتقل إلى Cloud.

## 4. المرحلة A — تفعيل حقيقي متعدد الأطراف

لا يبدأ أي بند هنا قبل قرار مالك صريح بعد تجربة L. هذه ليست شاشة Login؛ إنها ضمان أن الشخص الصحيح يرى السجل الصحيح من جهاز مختلف.

- [ ] **A-01:** اختيار هوية طبقة الشبكة، مع فصلها عن Manage المحلي ومالية صاحب المشروع واشتراك SaaS.
- [ ] **A-02:** إنشاء identity/workspace/membership بدعوات منتهية الصلاحية وأدوار Owner/Supplier/Courier/Admin على الخادم وقاعدة البيانات والـAPI.
- [ ] **A-03:** كل سجل شبكة يحمل `workspace_id`/tenant key؛ كل endpoint وsearch/export/notification/file URL يتحقق من الجلسة والدور والعضوية.
- [ ] **A-04:** ترفع الوسائط خاصة، ولا تصبح قابلة للعرض العام قبل قرار Moderation؛ تستخدم URL موقعة قصيرة أو proxy متحقق الصلاحية.
- [ ] **A-05:** تختبر سلبيًا Owner A مقابل Owner B وSupplier مقابل مال Owner وCourier مقابل Listing منافس وAdmin مقابل Manage؛ يجب أن تفشل كلها بأمان.
- [ ] **A-06:** تضيف حالات network صريحة: محلي/مسودة، بانتظار الإرسال، متزامن، فشل/يحتاج مراجعة؛ retry وidempotency يمنعان التكرار والتعارض الصامت.
- [ ] **A-07:** يبقى `الخدمات` مصدر متابعة داخل التطبيق إن فشل push أو الخلفية؛ push تحسين لا مصدر حقيقة.

## 5. المرحلة B — Pilot محدود

- [ ] **B-01:** تختار فئة ومنطقة وOwner testers بحدود مكتوبة.
- [ ] **B-02:** تدعو موردين أو شريك توصيل مستعدين فعلًا لمسار واحد، لا تفترض العرض أو الالتزام.
- [ ] **B-03:** تنشر سياسة بيانات/خصوصية واتصال ومسؤوليات قبل جمع عنوان أو رقم أو صورة حقيقية.
- [ ] **B-04:** تشغّل Market أو Delivery بمسار واحد مع إلغاء واستعادة ودعم محدودين.
- [ ] **B-05:** تقيس وقت الرد، اكتمال التفاعل، سبب الإلغاء، فهم الحالة، وما إذا كان الحل وفر بحثًا/حركة حقيقيين؛ لا تعتمد GMV أو التسجيلات وحدها.
- [ ] **B-06:** تقرر توسعًا أو تعديلًا أو إيقافًا أو تأجيلًا كتابةً. لا تضيف دفعًا أو تقييمات أو تتبعًا حيًا بلا قرار/دليل جديدين.
