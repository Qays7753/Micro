# Expansion — سيناريوهات E-00 ومصفوفة القبول

**الحالة:** `CURRENT / E-00 / CONCEPT AND CONTRACT ACCEPTANCE`
**الحد:** لا تثبت هذه السيناريوهات سوقًا أو أمنًا ميدانيًا أو نية دفع؛ تثبت فقط وضوح القرار والعقد قبل الكود.

## Major Discussion Points

## 1. قاعدة القبول

كل سيناريو يختبر شخصًا وموقفًا وضررًا ونتيجة وفعلًا تاليًا، ثم يصرح بما لا يتغير ماليًا. لا نغير السيناريو ليبدو العقد ناجحًا؛ إذا لم نعرف الفاعل أو الإفصاح أو الحالة أو الفعل التالي، نعيد العقد ولا نبدأ UI أو Data Model.

## 2. سيناريوهات Owner والسوق والتوصيل

| المعرف | الموقف والضرر | النتيجة المطلوبة | الحارس |
|---|---|---|---|
| S-01 | Owner يفتح Micro ويريد موردًا فورًا ولا يريد إعداد مال. | يفتح `السوق` من BottomNav، ويرى `استكشف` أو يبدأ Need مسودة قبل النشر. | لا يختار «منتجًا» ولا يكشف بيانات Manage. |
| S-02 | Owner لديه رد مورد يحتاج قرارًا. | يراه في `احتياجاتي` داخل السوق، مع المصدر والوقت و«راجع الرد». | لا يظهر «تم الشراء» أو تكلفة. |
| S-03 | Owner يفتح السوق بلا Listing أو رد ضمن تغطيته/بحثه. | يرى Empty أو No-results صادقة وفعلًا واحدًا مناسبًا داخل السوق. | لا metrics أو Listings/Tasks وهمية ولا انتقال إلى Delivery. |
| S-04 | Owner قبل ردًا وحدث اتفاق خارجي. | يسجل قرار متابعة ويختار لاحقًا تسجيل واقع في Manage. | لا Purchase أو دين أو Inventory تلقائي. |
| S-05 | Owner يفتح رمز التوصيل أو يحتاج توصيل طلب عميل. | يرى مركز Delivery؛ يبدأ مسودة فقط عند فعل صريح ويعاين ما سيكشفه قبل الإرسال. | لا طلب سيارة أو هاتف/عنوان عميل أو قبض من دون موافقة. |
| S-06 | Courier سجل وصولًا أو فشلًا. | يقرأ Owner الفاعل والوقت والحالة وسبب الاستثناء داخل التوصيل. | لا يتحول Order المحلي إلى delivered أو settled. |
| S-06A | Owner يحتاج بيك أب أو تبريدًا. | يذكر متطلب وسيلة نقل بعد أن يحسمه Wedge، ويظهر لطرف التسعير في Scope اللازم فقط. | لا اختيار سيارة/سائق أو حجز أو توفر حي. |

## 3. سيناريوهات Supplier وCourier وAdmin

| المعرف | الموقف والضرر | النتيجة المطلوبة | الحارس |
|---|---|---|---|
| S-07 | Supplier يضيف Listing وصورة. | يبقى draft/submitted ولم يظهر للمالك قبل approve. | لا صورة عامة أو رفض بلا سبب. |
| S-08 | Supplier يرى Need منشورًا خارج نطاقه. | يقرأ فقط الحد الأدنى الذي تسمح السياسة بالرد عليه. | لا مال Owner أو عميل أو عروض منافسة. |
| S-09 | Courier يريد تسعير حركة. | يرى منطقة/نافذة/طرد ومتطلب وسيلة نقل إن وجد بالحد الأدنى، ثم يقدم Quote. | لا حجز أو Expense أو عنوان تفصيلي مبكر. |
| S-10 | Courier يحاول تحديث مهمة جهة أخرى. | يتلقى رفضًا آمنًا ولا يرى بيانات المهمة. | تطبيق policy في API/DB وليس الشاشة فقط. |
| S-11 | Admin يطلب تعديل Listing. | Supplier يرى سببًا وحالة قابلة للتصحيح. | Admin لا يختار Supplier أو يدير المال/التوصيل. |
| S-12 | يتكرر إرسال Response أو Status بعد ضعف اتصال. | تظهر نتيجة واحدة وسجل Event صحيح. | idempotency ولا آخر كتابة صامتة. |

## 4. سيناريوهات الفشل والاستعادة

| المعرف | الحالة | النتيجة المطلوبة |
|---|---|---|
| S-13 | انقطاع قبل تأكيد إرسال Need أو Delivery. | تبقى المسودة ويشرح النظام أنها لم تصل للطرف الآخر. |
| S-14 | يفشل رفع Media. | لا نشر جزئي؛ يحتفظ المستخدم بالمسودة ورسالة سبب/إعادة محاولة. |
| S-15 | يصل Status متأخر أو مخالف. | لا يعاد ترتيب الحقيقة؛ يظهر رفض أو `needs_review`. |
| S-15A | يصل Badge/Notification إلى رابط Market أو Delivery قديم أو مصدر خاطئ. | يعيد الفتح إلى السجل المملوك أو يرفض بأمان؛ لا يغير الحالة لمجرد الفتح. |
| S-16 | Owner يستعيد Export Manage محلي. | لا يدعي استعادة Network أو صلاحياتها، ولا يغير مالًا بسبب سياق خارجي. |
| S-17 | يفقد مستخدم جهازه عند A. | لا حذف تلقائي؛ يمر استعادة هوية/عضوية وسياسة معلنة. |
| S-18 | محاولة فتح URL/ملف/إشعار لشخص آخر. | لا يوجد كشف سجل أو metadata أو محتوى حساس. |

## 5. جدول أثر الحقيقة المالية

| الحدث | كاش | دين | ربح/تكلفة | مخزون | المطلوب بدل الأثر التلقائي |
|---|---|---|---|---|---|
| نشر Need أو Listing | لا تغيير | لا تغيير | لا تغيير | لا تغيير | متابعة شبكة فقط. |
| قبول Response | لا تغيير | لا تغيير | لا تغيير | لا تغيير | قرار Owner ثم فعل تسجيل واقع اختياري. |
| إنشاء/قبول Quote | لا تغيير | لا تغيير | لا تغيير | لا تغيير | مراجعة Owner لمسار مالية Manage منفصل إن دفع فعلًا. |
| `picked_up`/`arrived`/`completed` | لا تغيير | لا تغيير | لا تغيير | لا تغيير | Owner يقرر إن كانت الواقعة تعني استلام/تسليم ويسجلها بعقد Manage. |
| Moderation أو بلاغ | لا تغيير | لا تغيير | لا تغيير | لا تغيير | تعديل حالة نشر/وسيط وسجل تدقيق فقط. |

## 6. معيار قبول E-00

تقبل E-00 فقط عندما يستطيع مراجع مستقل الإجابة من العقود والمصفوفة على: من فعل هذا؟ ما الحالة السابقة والتالية؟ من يرى أي حقل؟ ما الذي لا يتغير في Manage؟ ما الفعل التالي عند فشل أو تكرار؟ ما الذي يثبت محليًا وما يتطلب A/Pilot؟

## Action Points

- [ ] تربط كل شريحة تنفيذية لاحقًا بمعرفات السيناريو المتأثرة، ولا تضيف سيناريو بديلًا خارج هذه المصفوفة بدل تحديثها.
- [ ] يضاف دليل Prototype أو Pilot بجانب كل سيناريو بعد التنفيذ؛ لا يؤشر عليه من اختبار وحدة فقط إذا كان يتطلب هاتفًا أو دورًا حقيقيًا.
- [ ] إذا فشل سيناريو أساسي، يتوقف الانتقال إلى الشريحة التالية حتى يسجل قرار تعديل/تأجيل/رفض.
