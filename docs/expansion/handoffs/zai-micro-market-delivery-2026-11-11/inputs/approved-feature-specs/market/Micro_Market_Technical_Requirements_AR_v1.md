## 1. المسار المرجعي المشروط للبروتوتايب المتصل

يبقى السوق جزءًا من تطبيق مايكرو الحالي وتبويبه الموجود `/market`. نبني له وحدة مستقلة منطقيًا داخل المشروع، وتُضاف عند التفعيل طبقة API وبيانات ووسائط وهوية شبكة. يبقى Manage المالي محليًا، ولا نحتاج نقله إلى السحابة لتشغيل السوق.

خط الأساس التاريخي الموثق: React/TypeScript/Vite/Wouter. ترجيح Modular Monolith وWorkers/D1/R2 توصية لا حالة تشغيل. اختيار D1 مقابل Postgres/RLS مشروط بإثبات العزل والملكية والأداء والتكلفة والتوافق مع Micro؛ لا نقل مالي لتسهيل المزود. زر Google عبر هوية Micro المشتركة؛ Supabase Auth Free هو Adapter مرجعي عند عدم وجود مزود شبكة أعلى معتمد. لا ينشأ مزود هوية آخر للسوق إذا اعتمد النظام واحدًا. بديل DB/هوية لا يختار منفصلًا عن قرارات النظام، وتبقى ضرورة إثبات العزل والتكلفة قبل التفعيل.

الأساس المطلوب: بيانات مشتركة حقيقية للمورّدين والمشترين، صلاحيات تُفحص على الخادم، مسودات محفوظة بصدق، وإعلانات وصور لا تُعرض قبل اعتمادها. لا نحتاج Microservices أو WebSocket أو تطبيق هاتف جديد أو محرك بحث خارجي منذ البداية.

## 2. سجل الفحص السابق — لا وصف متحقق للمستودع الحي الآن

| الموضوع | الدليل الذي قُرئ | أثره على التنفيذ |
|---|---|---|
| الواجهة الحالية React/TypeScript/Vite/Wouter | `package.json` و`apps/prototype-web/package.json` | نوسّع المشروع نفسه؛ لا نبدأ واجهة Next.js أو تطبيقًا موازيًا |
| السوق موجود كوجهة خامسة | `app/navigation.ts` و`components/layout/BottomNav.tsx` | نستخدم المقعد الحالي دون إضافة مقعد أو تعديل بقية الترتيب |
| `/market` صفحة قريبًا | `app/MicroRouter.tsx` و`pages/Market.tsx` | لا توجد وظيفة سوق عاملة في هذا الموضع يمكن الادعاء بإعادة استخدامها |
| هوية المالك المحلية لا تساوي Login شبكيًا | `app/PrototypeServicesContext.tsx` و`app/StartupGate.tsx` والعقد 18 | تسجيل الشبكة قدرة جديدة؛ لا ننسخ هوية الجهاز إلى حساب موثّق تلقائيًا |
| الدخول الحالي يمر بتهيئة المشروع المحلي | `StartupGate.tsx` | فتح السوق للزائر أو المورّد دون تهيئة مالية يحتاج فصلًا محددًا لبوابة السوق |
| المحتوى يُعاد تركيبه عند تغير الموقع | `MicroAppShell.tsx`: مفتاح `main` مبني على `location` | حفظ حالة السوق والمسودة خارج المكوّن المعاد تركيبه |
| الرجوع القانوني يستخدم `returnTo` | `app/navigationContract.ts` | نستخدم العقد الحالي؛ لا ننتج `from` أو نثق في عنوان خارجي |
| فصل سطح القراءة عن المحرر العميق | `app/routeClassifier.ts` | نحدد تصنيف السوق صراحة ونحمي مدخلاته دون شريط جديد |
| Manage محلي والتوسعة موثقة وغير مفعلة | `docs/operations/current-state.md` ووثائق `docs/expansion/` | لا نعامل الكتابة عن Auth/DB كأنها تنفيذ أو تفعيل |
| المال الشبكي الحالي معرف بدقة مختلفة | العقد 25 و`src/domain/shared/currency.ts` | تحتاج أسعار B2B وحساب الكمية عقدًا مخصصًا، لا إعادة استخدام عمياء لـMoneyMinor |

الفحص التاريخي قرأ ملفات محددة؛ لم يعد في مهمة Drive، وليس تشغيلًا إنتاجيًا أو مسحًا معماريًا شاملًا. لم تُختبر أجهزة أو خدمات سحابية في هذا التسليم. روابط الأدلة المثبتة موجودة في القسم 18.

|---|---|---|

## 4. حدود الطبقات والخدمات

| الطبقة | مسؤوليتها | الحد الفاصل |
|---|---|---|
| واجهات السوق | العرض وإدخال البيانات وحالة التنقل | لا SQL ولا مفاتيح خدمات ولا كتابة مالية |
| Application | إنشاء مسودة وتقديمها ومراجعتها وحفظها والتواصل | تنسق الحالات والصلاحيات والذرية |
| Market Domain | وحدات وكميات وتسعير وقواعد نشر وحالات | مستقل عن React وD1 وR2 ومزود الهوية |
| Ports | Repository، Identity، Media، Policy، Audit، Clock | عقود يمكن اختبارها بمحوّلات بديلة |
| Workers/API | جلسة وهوية وصلاحيات وتحقق ومدخلات واستجابات | البوابة الوحيدة للوصول المتصل للبيانات |
| Adapters | D1 وR2 ومزود الهوية ومعالج الصور | لا يغير أي Adapter سجل Manage |

تظل حسابات Manage ومساراته الحالية مستقلة عن أعطال السوق. لا تستورد خدمات السوق خدمات مشتريات أو محافظ أو مخزون لكتابة واقعة. الملف التعريفي للمورّد على الشبكة ليس سجل المورّد المحلي في الدفاتر، وإعلان المادة ليس مادة مخزون. أي ربط بينهما يُصمم لاحقًا كفعل صريح.

لا تُفرض شجرة `features/` أو إعادة هيكلة المستودع. تُختار مواقع الملفات وفق الحدود والحراس الحاليين. استخدام `market/` أسماءً في الوثيقة يعبّر عن ملكية الوظيفة، وليس أمرًا بنقل ملفات. تُحمّل واجهات السوق والهوية والمعالجة المتصلة عند الحاجة، ولا تُضاف إلى كومة إقلاع الرئيسية بلا قياس.

## 5. مقارنة مساري الاستضافة والهوية

| العنصر | Workers + D1 + R2 | Workers + Supabase/Postgres + R2 |
|---|---|---|
| بيانات السوق | SQL مبني على SQLite مع دعم FTS5 [S1] | Postgres مع إمكان سياسات RLS [S2] |
| العزل المقترح | Worker وسياسة موحدة واستعلامات Repository مقيدة وقيود علاقات | سياسة التطبيق مع سياسات RLS على الجداول |
| الصور | R2 خاص وقراءة محكومة | R2 بالطريقة نفسها؛ الصور لا تفرض اختيار قاعدة بعينها |
| الهوية | Google عبر هوية Micro المشتركة؛ Supabase Auth Free مرجع التنفيذ | نفس قرار الهوية المشتركة؛ لا حساب آخر للسوق |
| التشغيل | بيانات وملفات السوق على Cloudflare؛ الهوية قد تكون خدمة أخرى | مزود بيانات إضافي واتصال يجب قياسه واختباره |
| سبب تفضيله | مناسب لمسار Cloudflare المرجح وبداية محددة النطاق | أرجح إذا كان العزل المستقل داخل DB أو استعلامات Postgres شرطًا أساسيًا |

ترجيحي اختبار D1/R2 أولًا مشروط بإثبات العزل والملكية والأداء والتكلفة؛ لا اختيار نهائيًا قبل هذه الأدلة. لا أدعي أن إضافة `workspace_id` تحقق RLS مستقلًا في D1. إن كان العقد يتطلب منعًا مستقلًا في DB حتى عند خطأ استعلام الخادم، فالتوصية تتحول إلى Postgres/RLS بدل تسمية عزل التطبيق بما لا يفعله.

الاختبار الحاسم للمزود: جهتان وحسابان فعليان وقراءة/تعديل/ملف خاص ونشر وسحب واستعادة، مع اختبار حدود المجانية على الحساب. لا ينقل ذلك مالية مايكرو، ولا يحول بطاقة الدفع إلى موافقة على خطة مدفوعة. المصادقة المحاكاة ليست إثباتًا للتجربة المتصلة.

### دليل اختيار D1 مقابل Postgres/RLS

Cloudflare Workers/D1/R2 اتجاه مرجعي موثق ومقترح، لا اختيار قاعدة نهائيًا ولا وصفًا لخدمات مفعلة. React/TypeScript/Vite/Wouter سجل تقني تاريخي يحتاج فحص المستودع الحي. يستخدم Market مزود هوية Micro المعتمد؛ Supabase Auth مرشح Adapter فقط إذا لم يوجد مزود أعلى، ولا يفرض اختيار قاعدة Supabase لبيانات السوق.

| المسار | ما يقدمه | دليل اختياره المطلوب |
|---|---|---|
| Workers + D1 + R2 | API وخزن SQL بسمات SQLite وFTS5 ووسائط خاصة؛ عزل يطبقه الخادم وRepository وقيود العلاقات | CX عبر حسابين من الدور نفسه، معاملات ونسخ وفشل متزامن، سحب صلاحية وملفات وفهرس خاص؛ أداء البحث العربي والتسعير والاستعادة والتكلفة ضمن الخطة |
| Workers + Postgres/RLS + R2 | سياسات صفوف داخل DB فوق سياسة التطبيق، دون تغيير حدود المنتج | الأدلة نفسها، مع اختبار RLS بمستخدمين فعليين وأدوار غير متجاوزة للسياسات، وضبط grants/views/functions ومفاتيح الإدارة، وقياس الاتصال والتكلفة والاستعادة |

إذا اشترط عقد Micro حاجز RLS مستقلًا داخل قاعدة البيانات لا يسمى تقييد الاستعلامات في D1 تحقيقًا له. وإذا اختير Postgres فلا تنفذ كل طلبات المستخدم بمفتاح يتجاوز RLS ثم تدعي اختبارها. تجرى مقارنة متماثلة في الحالات والبيانات ومؤشرات الأداء، ويثبت ADR القرار وأسبابه وحدود الرجوع. فشل أحد الأدلة يفتح بديلًا موثقًا؛ لا يعدل MarketPrice أو صور السوق أو ينقل Manage لتسهيل المزود.

الأسماء D1 وbatch وFTS5 وحصص صفوف D1 في بقية المواصفة تصف المحول المرجعي عند اختياره؛ لا تجعل البديل ممنوعًا. عند ترجيح Postgres/RLS يثبت ADR مقابلات المعاملات والفهرسة والاستعادة والحصص ويصالح وثائق التنفيذ قبل الاعتماد عليه، مع بقاء عقود السوق والاختبارات والحدود المالية والصور كما هي.

الترشيح المهني الأولي: اختبار D1 مع R2 وWorker لأنه منسجم مع الاتجاه المكتوب، لا اعتماده دون القياس. يؤجل الحسم إلى إثبات البنية المتصل؛ لا يوقف إعداد العقود المحايدة للمزود وقواعد السوق.

## 6. الهوية والجلسات والصلاحيات

**الدخول المعتمد:** زر «المتابعة باستخدام Google» عبر OAuth/PKCE ومزود هوية الشبكة المشترك. لا Email OTP أو SMS أو كلمات مرور منفصلة للسوق. هاتف النشاط لا يتحقق من Google؛ المراجعة اليدوية في البروتوتايب تسجل طريقتها أو تعرضه غير متحقق دون شارة كاذبة. لا خدمات إرسال بريد أو رسائل مدفوعة مطلوبة في هذا الإصدار.

نفس الشخص يستطيع حمل دور مشتري ودور مورد، لكن كل طلب يستخدم سياق الجهة صراحة. نسخة البداية تسمح بنشاط مورّد واحد للشخص، مع نموذج عضويات لا يمنع التوسع لاحقًا. الأدوار التجارية والإدارية لا تأتي من قيمة يرسلها المتصفح أو `user_metadata` يمكنه تعديلها.

التصميم المفضل جلسة BFF على النطاق نفسه: Cookie آمنة `HttpOnly` و`Secure` و`SameSite`، مع حماية CSRF/Origin للأفعال الكتابية. تحفظ بيانات تجديد الجلسة اللازمة في مخزن خادمي محمي ومشفرة؛ لا داخل تخزين المتصفح أو السجلات. تُختبر دورة التجديد والخروج والإلغاء في Adapter الهوية المختار.

الـWorker يتحقق من توقيع JWT و`iss` و`aud` و`exp` والخوارزمية المسموحة. عند استخدام JWKS يلزم إعداد مفاتيح غير متماثلة؛ الوثائق توضح أن endpoint لا يعيد مفاتيح عند استخدام توقيع مشترك [S5]. بعد إثبات الهوية، تُقرأ العضوية وحالة الحساب من مصدر خادمي؛ صلاحية التوقيع وحدها لا تعني أن العضوية ما زالت نشطة.

| المورد المطلوب | من يقرأ؟ | من يغير؟ |
|---|---|---|
| نسخة مادة معتمدة للنشر | الزائر وكل أدوار المستخدمين | لا تعديل من القراءة العامة |
| مسودة أو نسخة تعديل | أعضاء جهة المورّد المخولون | نفس الجهة ضمن حالة مسموحة |
| ملف مورّد عام | الحقول المعتمدة فقط | تعديل مالكه ثم مراجعة ما يحتاج نشرًا |
| صور غير منشورة | مالكها؛ والمشرف عند تقديمها للمراجعة | إجراءات الرفع/الفحص المسموحة |
| محفوظات | صاحب الحساب نفسه | صاحبها فقط |
| بلاغ | صاحبه يرى تأكيده؛ والمشرف المخول يرى اللازم | قرار مسبب وفق الصلاحية |
| طابور مراجعة | مشرف/مدير مخول | ضمن تخصصه؛ لا إدارة مالية |
| Manage المحلي | مالك مشروعه المحلي | عقوده الحالية وحدها |

المورّد يستطيع رؤية مواد منافسيه **المنشورة للعامة**، وليس مسوداتهم أو اتصالاتهم أو أرقامهم الخاصة. العشوائية في المعرفات ليست أمانًا؛ رفض الوصول يطبق قبل إعادة السجل، مع استجابة لا تكشف وجود سجل خاص.

يحتاج المشرف MFA وصلاحيات محددة، ولا يعتمد إعلانًا يخص الجهة التي يمثلها. إنشاء عضويات إدارية يتم من مسار إدارة موثق، لا تسجيل ذاتي. الاستعادة تعيد الهوية والعضوية المثبتتين فقط؛ فقد الدخول الشبكي لا يحذف Manage، واستعادته لا تستعيد قاعدة Manage من هاتف آخر.

### مصفوفة بوابات السوق والملكية والنشر

هذه حالات شخص وملف ومحتوى متمايزة، وليست أنواع حسابات بديلة. حالة المورد وحالة الإعلان ومعالجة الصورة ومراجعتها والظهور العام محاور مستقلة.

| الحالة | ما يراه | ما يستطيع فعله | حالة الصور | من يملك قرار الإتاحة؟ |
|---|---|---|---|---|
| زائر | النسخ العامة المعتمدة والقنوات المسموحة | تصفح وبحث وتجهيز تواصل خارجي | صور معتمدة لمحتوى متاح فقط | لا يملك النشر |
| مستخدم Micro مسجل | العام ومحفوظاته وبلاغاته | الحفظ والبلاغ والحظر وبدء مسار البيع اختياريًا | لا يرى صور غيره الخاصة | التسجيل لا يعتمد موردًا |
| مقدم ملف مورد | ملفه المبدئي ومسوداته وحفظها | استكمال ملف وإنشاء مسودة ورفع صور خاصة وتقديم ما اكتمل | خاصة؛ ملكية وحصص وفحص حتى قبل اعتماد الملف | لا نشر ذاتي |
| ملف مورد قيد المراجعة | نسخته المقدمة وأسباب النقص وحالة إعلاناته | تحضير وتقديم الإعلان والصور بالتوازي؛ تعديل الملف بنسخة جديدة | يراها صاحبها؛ المشرف يرى المقدمة فقط | المشرف يراجع الملف؛ لا يتجاوز بوابة بقية الأجزاء |
| مورد معتمد | ملفه المعتمد ومساحة إعلاناته والسوق العام | تقديم مواد وإدارة بياناته ضمن الصلاحية | قبول الملف لا يقبل الصور أو الإعلانات تلقائيًا | لا نشر لإعلان لم يعتمد |
| مسودة إعلان | مالكها فقط | حفظ ناقص وتحرير ومعاينة ورفع خاص؛ تقديم النسخة المكتملة | معالجة خاصة؛ غير مقدمة لا تدخل طابور المشرف | لا قرار نشر على مسودة |
| إعلان مقدم للمراجعة | المالك والمشرف المخول، كل ضمن مهمته | قرار على النسخة المحددة أو سحب/تعديل وإعادة تقديم | الخاصة المقدمة للمشرف؛ المعالجة لا تساوي قبول المحتوى | المشرف يعتمد النسخة والصور؛ انتظار الملف يمنع النشر |
| إعلان منشور | النسخة العامة للجميع، والتعديل الخاص لمالكه | سعر/توفر/كمية معلنة/إيقاف مباشرة ضمن القيود؛ تعديل المحتوى بمراجعة | العامة المقبولة فقط؛ الصورة الجديدة خاصة حتى قبولها | خدمة نشر مخولة بعد الموافقات؛ لا PATCH عام للاعتماد |
| إعلان موقوف أو مخفي | الحالة والسبب المسموحان؛ لا محتوى محظور | المورد يوقف؛ يستأنف إيقافه فقط إن بقي الاعتماد والحداثة صالحين؛ التجديد بعد 60 بمراجعة | لا طلب جديد للصورة المعتمدة عند منع إتاحتها؛ لا كشف صورة خاصة | الإدارة لحظرها؛ المورد لا يرفعه، ولا يعيده تغيير السعر |
| مشرف محتوى | الملف والإعلان والصور المقدمة والبلاغات اللازمة | مراجعة مفسرة بصلاحية ونسخة وMFA، دون اعتماد إعلان جهته | المقدم ضمن اختصاصه فقط؛ لا مسودات غير مقدمة | ضمن سياسة المراجعة، دون تجاوز ملكية أو تعليق |
| مدير السوق | الإدارة المخولة والتصنيفات والسياسات | منح أدوار من مسار موثوق وتعديل القوالب وإجراءات نطاقه | لا وصول شامل مفترض لملفات خاصة غير لازمة | وفق صلاحياته وسجل قرار؛ لا وصول مالي تلقائي |

في الرفع المبكر تنشئ الخدمة سياق جهة مورد مبدئيًا مملوكًا للهوية، لا صفة مورد معتمد. تستمد الملكية من الجلسة وتتحقق من الارتباط على الخادم؛ لا تمنح اعتمادًا من قيمة role أو workspace يرسلها العميل. المستخدم المسجل قد يبقى مشتريًا فقط دون أي ملف مورد.

### مساحة المورد وحدود الأدوار والميزات المؤجلة

Micro هو المنتج؛ مساحة المورد جزء من Market وتبويبه الواحد. تجمع ملفي كمورد وإعلاناتي والمسودات والمراجعات وتنبيهات التوفر دون تطبيق أو تسجيل دخول آخر. لا إعداد محافظ أو ديون أو تهيئة مالية مطلوبة، ولا ظهور قسري لكل وظائف Micro. يراجع تركيب الإقلاع والقشرة حتى يعمل السوق عند غياب أو فشل مخزن Manage. لا تبني هذه المواصفة تدفق اختيار الوحدات أو إعداداتها عند أول تشغيل.

الهوية تخص الشخص، والجهة تخص نشاط العرض، وملف المورد بيانات ومراجعات ذلك النشاط، والعضوية تفويض لأفعال معينة. لا يستخدم حقل نوع مستخدم حصري يمنع تعدد الأدوار مستقبلًا. كل طلب يستخدم الهوية والملكية والسياق والحالة؛ لا اتحاد تلقائي لصلاحيات الجهات. إعداد مورد لا ينشئ مشروع Manage، ولا يربط بريدًا مشابهًا بمالية محلية أو يرفعها.

بوابة السائق المستقلة قرار يخص السائق؛ لا تُنسخ إلى المورد، ولا يدمج ملف المورد أو مراجعاته أو صلاحياته بملف السائق. إمكان اجتماع أدوار مستقبلًا لا يمنح دور سائق من ملف مورد أو العكس. طلب المورد Delivery أو الانتقال بين البوابتين يتبع قرار الخدمة المعنية لاحقًا؛ لا يبنى هذا الربط ولا ينشأ حجز من مادة أو نقرة تواصل في v1.

My Ask Micro ميزة مستقبلية خارج هذا التكليف؛ الأساس الوحيد المحفوظ لها الآن هو عدم تجاوز حدود الهوية والملكية والصلاحيات. لا شاشات أو أدوات أو API أو ميزانية تشغيل لها هنا، ولا تعطل قبول Market. اختيار الوحدات مؤجل أيضًا؛ فصل الإقلاع والاعتماديات هو الأساس اللازم فقط، دون بناء نظام اختيار مسبق.

## 7. نموذج البيانات المنطقي

أسماء الكيانات توصيفية. الحقول المتغيرة حسب الفئة تستخدم JSON ذا Schema محدد الإصدار؛ أما الملكية والحالة والفلاتر الأساسية فتظل حقولًا مفهرسة. لا يُحفظ الإعلان كله كنص حر، ولا تُنشأ قاعدة لكل مورد منذ البداية.

| الكيان | الحد الأدنى من البيانات والعلاقات |
|---|---|
| `network_identities` | معرف داخلي، مزود و`subject` فريدان، الحالة؛ دون كلمة مرور |
| `network_workspaces` و`memberships` | الجهة ونوعها؛ الهوية والدور وحالة العضوية؛ عدم دمج الصلاحيات |
| `supplier_profiles` ونسخ نشرها | مرجع الجهة، بيانات نشاط خاصة/مسودة، مرجع نسخة عامة معتمدة، قنوات الاتصال المقبولة وحالة مراجعتها والتحقق من ملكيتها ودليله إن وجد |
| `categories` و`attribute_definitions` | شجرة التصنيف، معرفات حقول وأنواعها ووحداتها وإلزامها وإصدارها |
| `units` و`regions` | نوع الوحدة ودقة الكسور؛ محافظة/منطقة بمعرفات ثابتة؛ التحويلات المسموحة فقط |
| `listings` | المورّد، المرجع العام، نسختا العمل والنشر، حالة الظهور، توفر مباشر، تواريخ وحداثة و`version` |
| `listing_revisions` | نسخة محتوى ثابتة عند التقديم: العنوان والمواصفات والخيارات وموقع العرض وإصدار Schema |
| `sale_terms` | مرتبطة بنسخة الإعلان؛ جاهز/مخصص، وحدة وعبوة وحد ومضاعف وخلط وتسعير وأوقات |
| `price_tiers` | شروط البيع، حد الشريحة، السعر وأساسه؛ ترتيب وقيود اتساق |
| `media_assets` و`revision_media` | مالك الملف ومفتاحه وحجمه وتجزئته وحالة معالجته ومراجعته؛ ترتيب الصور والغلاف في النسخة |
| `availability_events` | تغيير التوفر أو تأكيده، المرجع والفاعل ووقت الخادم؛ ارتباط خياراته بالنسخة المنشورة |
| `saved_items` | هوية صاحب الحفظ، نوع الهدف ومعرفه؛ قيد فريد يمنع تكراره |
| `reports` و`moderation_decisions` | هدف وسبب ومبلّغ؛ نسخة مراجعة وقرار وفاعل ووقت؛ هوية المبلّغ لا تدخل العرض العام |
| `audit_events` | أحداث كتابة وتغيير صلاحيات وقرارات؛ سجل محدود الإضافة دون أسرار |
| `operations` | مفتاح العملية وصاحبها ونوعها وتجزئة الطلب ونتيجته لمنع التكرار |
| `outbox` و`attention` | أعمال مشتقة قابلة لإعادة المحاولة؛ حالات مراجعة للمستلم داخل السوق |

كل سجل خاص يحمل ملكية جهة أو هوية مناسبة، ووقت خادم، ومعرف نسخة. العلاقات بين الآباء والأبناء تشمل الجهة لمنع إلحاق صورة أو شريحة بإعلان جهة أخرى. معرفات الحقول والخيارات مستقرة؛ لا تربط القيم بترتيب ظهورها فقط.

المصدر المعتمد للمحتوى `listing_revisions`؛ البحث يقرأ إسقاطًا للنسخة المنشورة فقط. تحديث الإسقاط والفهرس لا ينشئ حقيقة ثانية مستقلة. يمكن إعادة بنائه من النسخ وحالات النشر. قناة التواصل في ملف المورّد لها نسخة نشر أيضًا حتى لا ينشر تعديل غير مراجع مباشرة عبر جميع إعلاناته.

**الفهارس الأساسية:** جهة/حالة/وقت تحديث؛ تصنيف/ظهور/وقت نشر/معرف؛ مناطق الخدمة؛ المورّد/الإعلانات؛ هدف الحفظ/الهوية؛ طابور المراجعة؛ ومفتاح عمليات فريد. لا يُنسخ سجل بحث المشتري إلى ملف المورّد.

### ضبط بوابة الملف في نموذج البيانات

تضاف حالة مراجعة ملف المورد بصورة مستقلة عن ملكية الجهة المبدئية: إنشاء المسودة والصورة يحتاج هوية وملكية صالحين، لا اعتماد المورد. تقديم النسخة المكتملة مسموح والملف معلق؛ خدمة النشر وحدها تشترط قبول الملف ونسخة الإعلان والصور وعدم وجود مانع. الحالة تأتي من الخادم ولا يقبل role أو verified أو approved من المتصفح. لا يصبح الملف المبدئي عامًا ولا يتحول المشتري تلقائيًا إلى مورد معتمد.

## 8. حساب الكميات والأسعار بدقة

عقد MarketPrice ودقة الكميات محفوظان؛ تطبيقهما يحتاج إغلاق REC-02. التعارض مع عقد 25 مسجل في الفحص السابق ويعاد فحص نصه الحي، دون تقريب مالي أو تغيير MoneyMinor.

- كميات الإعلان تُخزن كمقادير صحيحة مضروبة في 1000، مع دقة الوحدة. `24` حبة = `24000`، و`0.5` كغم = `500`.
- السعر يحمل عددًا صحيحًا بوحدة `1/1,000,000` دينار مع كمية أساس السعر؛ `0.125` = `125000` من وحدات التسعير. يسمى نوعه `MarketPrice`، ولا يسمى `MoneyMinor` الخاص بـManage.
- أسعار العرض وأساسها لا تتحول إلى floats. تُرسل الكسور والنتائج في JSON كسلاسل عشرية مقيدة؛ ويحللها Domain بتحقق صريح. هذه سلاسل رقمية ذات صيغة محددة، وليست نصوص أموال حرة.
- كل قيمة مخزنة في D1 ضمن نطاق صحيح آمن في Adapter؛ الحسابات الوسيطة تستخدم BigInt أو حسابًا عشريًا دقيقًا. لا تُضرب قيم كبيرة في JavaScript Number ثم تُقرب بعد فقد الدقة.
- صالحية الكمية: تبلغ الحد الأدنى، وتنقسم على المضاعف، وعلى محتوى العبوة إذا كانت مغلقة. تستخدم القاعدة نفسها في الجاهز والتخصيص كلٌ بشروطه.
- الكمية التالية هي أصغر كمية تحقق القيود كلها. تختبر صيغة المضاعف المشترك للعبوة والزيادة، وتمنع إعدادًا غير متوافق عند النشر.
- يُحسب تقدير المادة = الكمية ÷ كمية أساس السعر × سعر الشريحة المختارة، ثم يُقرب مرة واحدة إلى 0.001 د.أ بالنصف إلى الأعلى. الشريحة تنطبق على كامل الكمية.
- `null` يعني غير معلن؛ لا يساوي صفرًا. لا رقم نهائي عند غياب سعر التخصيص أو تكلفة مطلوبة. تظل الضريبة والتوصيل وشروط حد التعامل ظاهرة.

أمثلة قبول: 30 حبة مع حد 24 ومضاعف/عبوة 12 تقترح 36 وقيمتها 4.500 بسعر 0.125؛ و2.3 كغم تقترح 2.5 وقيمتها 12.000 بسعر 4.800؛ و3.2 متر تقترح 3.5 وقيمتها 8.400 بسعر 2.400. المخصص 100/50 يقترح 150 لطلب 120 دون اختلاق سعر؛ والجاهز لا يورث شروطه إليه. 1.500 لكل 12 يساوي 0.125 للحبة. الخشب حسب المقاس يقبل الكمية الصحيحة ويطلب الأبعاد اللازمة، دون مجموع مجهول.

لا يحول تسجيل شراء لاحق هذه الأنواع إلى مال Manage بصبّ نوع أو تقريب صامت. تصميم جسر يقبل مراجعة مبلغ مستقل مؤجل، وتظل دقة السجلات التاريخية كما هي.

## 9. API والسلوك المتزامن

بادئة مقترحة `/api/market/v1` خلف Worker؛ ليست مسارات واجهة أو تبويبات. كل Endpoint له قائمة حقول قراءة وكتابة معلنة. العمليات لا تقبل `approved` أو `workspace_id` أو دورًا أعلى ضمن حقول تعديل عادية.

| المجموعة | العقود المطلوبة |
|---|---|
| الاكتشاف | `GET /categories` و`/regions` و`/units` و`/listings` مع فلاتر وcursor |
| المادة والمورّد | `GET /listings/:id` و`/suppliers/:id` و`/suppliers/:id/listings`؛ نسخة عامة فقط |
| تفاصيل التواصل | `GET /listings/:id/contact` بعد إعادة فحص النشر والقناة؛ لا يسجل حدوث محادثة |
| الحساب | `GET /me` يعيد الهوية والعضويات المسموحة لا حقول Manage |
| ملف النشاط | إنشاء جهة مورد مبدئية مملوكة واستكمال الملف وتقديمه؛ قبول الملف مستقل عن صلاحية تجهيز المادة |
| المسودات | إنشاء وحفظ نسخة وصور خاصة وتقديم المكتمل أثناء مراجعة الملف؛ معرف عملية وملكية جهة مبدئية و`If-Match` |
| التقديم | `POST /my/listings/:id/submit` لنسخة محددة ولو كان الملف معلقًا؛ لا يحول التقديم إلى نشر؛ يمنع التكرار |
| التوفر والظهور | إجراءات محددة لتأكيد التوفر أو تغييره أو الإيقاف أو الأرشفة أو إعادة التقديم |
| الصور | طلب رفع، تأكيد اكتماله، حالة معالجة، قراءة مخولة، ربط بترتيب وغلاف، إزالة من نسخة العمل |
| المحفوظات | `PUT/DELETE /me/saved/:type/:id` وقراءة قائمة خاصة؛ إجراءات idempotent |
| البلاغات | `POST /reports`؛ تحقق دخول وسبب وهدف؛ لا كشف بيانات المبلّغ |
| الإشراف | طابور مخول وقراءة نسخة مقدمة وقرار مسبب وربط القرار بمعرف النسخة |
| الأحداث | تسجيل محدود لتجهيز الاستفسار وفتح القناة؛ دون نص الرسالة أو بيانات مشتري غير لازمة |

**العقود المشتركة:**

1. `Idempotency-Key` للأفعال التي قد تتكرر؛ يربط بالخادم بالفاعل والجهة ونوع الفعل وتجزئة الطلب. المفتاح نفسه مع payload مختلف يعيد تعارضًا. لا يرى مستخدم نتيجة عملية غيره.
2. `version/ETag` و`If-Match` للتعديل والمراجعة. تعارض نسخة يعيد `409` ولا يستبدل تعديل جهاز آخر. يتيح الواجهة نسخ مدخلاتها أو مراجعة الفرق.
3. الحالات `401` للدخول و`403` لرفض فعل معلوم و`404` لإخفاء سجل خاص غير مخول و`422` لأخطاء الحقول و`429` للحدود؛ `5xx` لا تُعرض كنتيجة فارغة.
4. الاستجابة تحمل `request_id` و`code` و`field_errors` عند الحاجة. النص العربي يأتي من قاموس موحد؛ لا SQL أو مفاتيح أو stack trace للمستخدم.
5. تحقق Schema يرفض الحقول الزائدة أو المحمية، ويطبق على الخادم حتى لو نجح تحقق الواجهة. الاستعلامات SQL مُعلّمة المعاملات؛ الترتيب وأسماء الحقول بقائمة سماح.
6. عمليات الموافقة تحدّث قرار المراجعة ومرجع النسخة المنشورة والإسقاط وAudit/Outbox ذريًا. D1 batch توفر معاملات متراجعة عند فشل أحد أوامرها [S6]؛ اختيار الآلية يشمل تحقق النسخة داخل نفس المعاملة، لا check ثم update منفصلين.
7. تعاد قراءة الصلاحية قبل إعادة نتيجة عملية قديمة؛ إيصال العملية لا يكون منفذًا لبيانات فقد صاحبها حق الوصول إليها. مفاتيح الإنشاء تربط بمعرف مورد ثابت حتى بعد انتهاء تخزين إيصال العملية.

## 10. الصور والنشر الآمن

R2 مخزن خاص، ولا تُحفظ الصور في أعمدة D1 أو Base64 في الإعلان. حالة الصورة منفصلة عن حالة الإعلان. الأصل والنسخة المعالجة لهما مفاتيح غير قابلة للاستبدال في مكانها.

**التدفق:** إذن رفع من API بعد فحص الملكية والحصة ← رفع إلى مساحة مؤقتة ← تأكيد وفحص خادمي للحجم والنوع والملكية ← معالجة نسخة آمنة ← مراجعة ← إتاحة النسخة المعتمدة فقط مع الإعلان المعتمد.

رفع البروتوتايب يمر عبر Worker بإذن أحادي الاستهلاك وحجز حصة قبل R2، مع إعادة محاولة idempotent. لا يصدر رابط PUT مباشر قابلًا للتكرار خارج الحصة، لأن ذلك قد يجاوز ضوابط المجانية. ينتج staging ثم ملف معالج نهائي ثابت. روابط الرفع الموقعة تقنية توسعة مرجعية لاحقة وليست مسار البروتوتايب المعتمد.

حدود البروتوتايب: 6 صور، حتى 2 MB للصورة و20 مليون بكسل، JPEG/PNG/WebP. الفحص للبايتات والأبعاد وملكية الجهة؛ لا SVG أو HTML أو جلب URL خارجي. لا ينشر أصل إذا فشلت المعالجة أو نفدت الحصة، وتزال EXIF/الموقع من الصور التي ستعرض.

معالج خادمي مؤهل ينتج صورة بطاقة نحو 480px وصورة تفاصيل نحو 1440px ضمن الأبعاد الأصلية دون تكبير غير لازم. Cloudflare Images binding مرشح لمعالجة بايتات الصور وحفظ المشتقات [S8]. فشل المعالجة يترك المادة والمسودة محفوظتين وصورة غير صالحة للنشر قابلة لإعادة المحاولة.

قراءة الصور العامة تمر عبر Worker يعيد فحص نسخة الإعلان وحالة الملف؛ وصول المسودة للمالك أو المشرف المخول فقط. للبداية تُمنع ذاكرة HTTP المشتركة من خدمة صور مادة أوقفت للتو: `no-store` على استجابات البوابة، مع إمكانية تخزين البايتات داخليًا بعد فحص الإتاحة في كل طلب. إذا أضيف CDN عام لاحقًا، يلزم عقد سحب وإبطال cache؛ حذف R2 وحده قد لا يمحو نسخة cache [S9].

لا تُحذف صورة مرتبطة بإصدار منشور لأن المورّد حذفها من مسودة تعديل. تنظيف الرفع المتروك والملفات غير المرجعية مهمة قابلة للتكرار بعد مهلة تشغيلية، وتراجع المراجع والنسخ والبلاغات قبل الحذف.

## 11. البحث العربي والفلاتر والأداء

البداية: بحث D1 FTS5 في إسقاط عام للمحتوى المعتمد، مع فلاتر SQL مفهرسة [S1]. لا تُفهرس مسودات الموردين في فهرس الاكتشاف ولو كانت الواجهة تخفيها. العدادات والاقتراحات والتصنيفات لا تكشف محتوى غير منشور.

تُحفظ الكتابة الأصلية، ويُنشأ نص بحث منفصل: توحيد Unicode، إزالة التطويل والتشكيل لأغراض البحث، توحيد صور الألف، وضبط المسافات والأرقام. لا نساوي خامات مختلفة أو ندمج التاء المربوطة والهاء افتراضيًا. المرادفات حسب الفئة، وأوزان الصلة حتمية معلنة داخليًا. FTS لا يعوض اختبار البحث العربي؛ نختبر مفردات حقيقية ومقاسات وعبارات مختلطة ولا ندعي stemming عربيًا تلقائيًا [S10].

تقييد طول العبارة وعدد كلماتها، وتعقيم صيغة FTS، وإدخال قيم SQL بالربط يمنعان الانهيار والحقن. لا نستخدم `LIKE` مسحًا كاملًا لكل كلمة في كتالوج ينمو.

فلتر الكمية يتحقق من الوحدة والحد والزيادة والعبوة والجاهز/المخصص والخلط. عند وجود شرط لكل خيار يحتاج اختيارًا، يوضح ذلك أو يستبعد من المطابقة المؤكدة. الموقع والتوصيل فلتران مختلفان. ترتيب افتراضي ثابت مع فاصل تعادل بالمعرف؛ pagination بـcursor مرتبط بالفلاتر والنمط وإصدار النتائج لمنع خلط القوائم.

**ترتيب السعر:** يقارن أسعارًا قابلة للمقارنة عند الكمية والشروط المختارة، ولا يستخدم float لنسبة سعر العبوة. الحالة البسيطة بأساس تسعير موحد يمكن ترتيبها في SQL بأعداد صحيحة. عند اختلاف الأساس أو وجود شرائح، تجمع الخدمة جميع المرشحين المطابقين ضمن حد عمل معلن أولي 2000 إعلان، ثم تقارن الكسور بدقة وتُنشئ نتيجة مرتبة قصيرة العمر مع pagination. إذا تجاوزت المطابقة هذا الحد يُطلب تضييق الفلاتر ويظل ترتيب التاريخ متاحًا؛ لا يرتب أول 2000 ويقدمها كأرخص السوق كله. إيقاف مادة يُفحص أيضًا عند قراءة النتيجة المرتبة، ولا تسمح نتيجة قديمة بتسريبها. محرك خارجي يصبح خيارًا عند إخفاق قياسات حقيقية، لا قبلها.

أهداف اختبار أولية وليست نتائج أو SLA: استجابة بحث p95 خلال 1500ms وتفاصيل خلال 1000ms، على بيانات 10,000 إعلان و100 مورد وحمل 10 طلبات متزامنة في بيئة اختبار موصوفة. صفحة 20 نتيجة، بحد أقصى 50. تُقاس بايتات الصور وصفوف D1 المقروءة ووقت Worker، ويُضبط التطبيق بعد القياس دون رفع ميزانيات مايكرو القائمة بصمت.

## 12. المسودات والتنقل داخل التبويب

مسارات واجهة مقترحة: `/market`، `/market/listings/:id`، `/market/suppliers/:id`، `/market/saved`، `/market/my-listings`، `/market/editor/:draftId`، `/market/my-profile`؛ وللإدارة `/market/admin/*` عند السماح. هذه امتدادات للتبويب نفسه. تتقدم المسارات الثابتة على الديناميكية حيث يلزم، ويظل تنشيط BottomNav تحت `/market`.

تُدمج مع `returnTo` و`canonicalReturnFor` وعناوين التنقل وتصنيف المسارات وسجل التشخيص. الرجوع الافتراضي إلى السوق، ومن المحرر إلى إعلاناتي، دون `history.back()` غير مضبوط. يُقيد `returnTo` بقائمة المسارات الداخلية المتاحة للدور؛ ولا تكدس سلسلة مصادر متداخلة تتجاوز حد العقد. حالة الفلاتر الطويلة والتمرير تحفظ بمفتاح حالة داخلي، دون هاتف أو نص استفسار في URL.

المحرر متدرج داخل امتداد السوق، مع حارس التغييرات الحالي. يبقى التبويب مرجعًا واحدًا، ويُحسم تصنيف المحرر في سجل المسارات بدل استثناء CSS محلي. لا يُغير ذلك تصنيف المحررات المالية. نوافذ الفلاتر والصور والتواصل تدير التركيز والرجوع والإغلاق وتعيد المستخدم لموضعه.

وصف الفحص السابق أن بوابة التهيئة تسبق مسارات التطبيق؛ يعاد التحقق عند التنفيذ، و يلزم فصل مسارات السوق العامة عن طلب إنشاء مشروع محلي وعن فشل IndexedDB المالي، مع إبقاء حماية Manage كما هي. تعديل `StartupGate` وحده قد لا يكفي إذا كان Provider أو Shell يهيئ خدمات Manage قبلها؛ لذا يُراجع تركيب `App` وProvider والقشرة، وتُحصر هذه التهيئة حيث تحتاجها مسارات Manage. المورّد فقط لا يُدخل مالية ولا يحصل تلقائيًا على سياق Owner؛ دخول وظيفة Manage يبدأ إعدادها المحلي المعتاد إذا اختارها.

حالة السوق المستمرة تعيش خارج `main` المعاد تركيبه لكل `location`. المسودة المحلية تستخدم مخزنًا منفصلًا ذا إصدار تحت ملكية الشبكة، مفصولًا عن IndexedDB المالي وتصدير Manage؛ لا تتغير `localSchemaVersion/localExportVersion` لإنشاء مخزن سوق منفصل. تعرض الاستعادة بصدق أن ملف تصدير Manage لا يحتويه.

السوق Light Mode حسب مواصفات المنتج، وبهوية مايكرو الحالية وRTL وأرقام 0–9. تقييد مظهر السوق لا يغير إعدادًا محفوظًا لبقية التطبيق دون قرار. تُعاد الاستفادة من المكونات والأيقونات الفعلية حيث تطابق المطلوب، ولا تستبدل مكتبة أيقونات النظام كله ضمن هذه المهمة؛ أي فرق مع مواصفات الهوية يُحصر ويُراجع قبل إضافة اعتماد جديد.

الحفظ المحلي بعد إدخال مستقر نحو 800ms، والخادمي عندما يتوفر الاتصال والدخول الصحيح. الحالات المعروضة: غير محفوظ، محفوظ على الجهاز، محفوظ على الحساب، فشل الحفظ، أو تعارض نسخة. لا تظهر «محفوظ» بلا نجاح فعلي. مسودة مرتبطة بالهوية والجهة؛ لا تظهر للحساب التالي على الجهاز. عند الخروج تبقى النسخة المحلية معزولة ولا تُرسل إلا بعد إثبات الحساب نفسه؛ ويتاح حذفها من مسار بيانات السوق.

لا يوجد نشر أو قرار مراجعة أو تغيير عضوية Offline. إعادة حفظ مسودة لا تعني إعادة تنفيذ تقديم قديم أو طلب تواصل. لا تُرسل الخلفية نص رسالة المستخدم أو تنشر إعلانًا عند عودة الاتصال دون مراجعة نيته وحالة النسخة.

## 13. دورة النشر والمراجعة والمهام

طلب النشر يجمد نسخة للمراجعة. معلومات البائع والإعلان الجديد والصور وتغيير المادة أو الاتصال تحتاج مراجعة قيس؛ السعر العددي ضمن نمطه والتوفر والإيقاف تتحدث مباشرة بتحقق ونسخة/حدث موثق. يرى البائع حالة نسخة المحتوى وحالة التحديث المباشر مستقلة، ولا يعيد قرار مراجعة متأخر سعرًا أو توفرًا أقدم.

قبول المشرف يشترط النسخة المقدمة نفسها، والصور المقبولة، وحالة القناة والمورد، وإصدار التحديث المباشر الحالي. إذا تغيرت شروط الوحدة/المضاعف أو حالة الحساب يرفض القرار القديم بتعارض، أو تعاد مراجعة دمج المحتوى والتسعير المتوافق صراحة. إيقاف الإدارة لا يرفعه المورد. لا تستطيع مراجعة محتوى قديم إلغاء تحديث سعر أو توفر وقع بعدها.

تُنفذ مهام الحداثة والمراجعة والتنظيف كعمليات مجدولة قابلة للتكرار. سياسة 30/60 محسومة وتطبق عبر REC-04؛ لا تستخدم إشارة 90 يومًا التاريخية تشغيليًا، وتُعرض تواريخها وسببها للمورد. إعادة التجديد بعد انتهاء الظهور تدخل المراجعة؛ ولا تغير تاريخ النشر الأصلي.

توصية طابور المراجعة كما في العقد 20: هدف 48 ساعة عمل وتصعيد عند 7 أيام عمل أو أكثر من 20 عنصرًا، بعد تثبيت التقويم والمسؤول التشغيلي؛ لا يَعِد التطبيق المستخدم بها قبل تجهيز التشغيل. تظهر المدة الفعلية، ولا يظهر ترتيب انتظار دقيق إذا لم يكن طابورًا خطيًا.

يُكتب Audit وOutbox مع القرار في المعاملة نفسها؛ ثم تعالج الأعمال المشتقة بأمان. قد يكفي جدول Outbox ومهمة دورية في البداية. إضافة Queue لاحقًا لا تغير حقيقة القرار ولا تحل محلها. التنبيه داخل إعلاناتي/السوق، وليس صندوق خدمات مركزيًا أو Push مطلوبًا للنجاح.

### ترتيب قبول الملف والإعلان والصور

1. يبدأ المستخدم من أضف إعلانًا أو مساحة المورد. يستطيع تجهيز الملف والمسودة والصور الخاصة أثناء استكمال الملف ومراجعته، دون إعداد مالي.
2. الحفظ الناقص مسموح؛ عند التقديم يلزم اكتمال الحقول المناسبة للعنصر المقدم وفحص الملفات اللازمة. لا يشترط أن يكون قرار الملف قد صدر لتقديم الإعلان المكتمل.
3. تجمد نسخة ملف ونسخة إعلان ومراجع الصور للمراجعة. ترتيب مراجعة الأجزاء قابل للتوازي؛ لا ترتيب إلزاميًا يجعل بدء المحرر ينتظر اعتماد الملف.
4. قبول ملف المورد لا ينشر الإعلان أو الصور؛ قبول الإعلان والصور مع ملف معلق يعطي حالة «مقبول المحتوى — بانتظار اعتماد ملف المورد»، دون إتاحة عامة أو ظهور في بحث أو عداد أو رابط صورة.
5. النشر للإعلان يشترط قبول نسخة ملف المورد العامة المعنية ونسخة الإعلان المحددة وكل الصور المرتبطة بها، ونجاح المعالجة وصلاحية العضوية وعدم إيقاف المورد أو الإعلان أو انتهاء الحداثة. لا تعتمد الموافقة معرفًا مبهمًا لأحدث نسخة.
6. إغلاق آخر موافقة يعيد التحقق من جميع المراجع والحالات والنسخ في مسار نشر مخول؛ نية النشر هي التقديم الصريح، ولا يسوّي قبول إداري منفرد كل حقول الظهور. القرار والنشر والإسقاط والسجل متسقة ذريًا أو لا ينشر شيء.
7. التوصية التشغيلية المحافظة للمرة الأولى: يبقى ملف المورد بلا إعلان مكتمل الموافقات خاصًا حتى أول إتاحة مكتملة؛ لا ينشأ دليل عام لملفات قيد الاستكمال. هذه طريقة تطبيق للحماية، لا قرار مالك منسوب جديد. بعد الإتاحة لا يكشف الملف العام مادة أو صورة مخفية؛ لا يشترط بقاء إعلان نشط دائمًا لإظهار حقول ملف سبق اعتمادها ما لم توقف الإدارة الملف.
8. رفض الملف يمنع أول نشر ولو قبل المحتوى؛ يحتفظ المالك بمسوداته وتصحيحه. تغيير ملف مقبول سابقًا يبقي النسخة العامة السابقة إذا بقيت صالحة وغير موقوفة، والجديدة خاصة حتى قبولها. إيقاف المورد يمنع الإتاحة، وليس مجرد رفض تعديل مقترح.
9. حفظ أو معالجة صورة لا يساوي قبولها؛ لا ينشر الأصل عند فشل المعالجة. صورة جديدة لا تدخل نسخة عامة سابقة، وإلغاء قبول أو سحب صلاحية يسبق أي قراءة لاحقة. لا يمكن سحب بايتات سبق تنزيلها لجهاز.

اعتماد المورد يعني مراجعة معلوماته ضمن السياسة، لا شهادة جودة أو ضمان تعامل. قبول قناة الاتصال منفصل عن التحقق من ملكيتها، ويعرض نطاق التحقق ودليله بصدق.

الاستعادة تشمل بيانات السوق والصور والهوية والمراجعات، وليس D1 وحدها. D1 Time Travel مرتبط بالخطة: الصفحة الرسمية تذكر 7 أيام للخطة المجانية و30 للمدفوعة عند تاريخ المراجعة [S13]. لا يوضع وعد «30 يومًا دائمًا» بلا مطابقة الحساب.

توصية مبدئية: نسخة بيانات دورية مشفرة إلى نطاق صلاحيات منفصل، ونسخة صور/manifest قابلة للاستعادة، مع هدف RPO يوم وRTO يوم عمل يُختبران قبل الوعد بهما. مقاومة فقد الوسيط في R2 لا تمنع الحذف العرضي أو المقصود [S14]. لا نسخة احتياطية تُعلن قبل تجربة استعادة في بيئة معزولة والتحقق من مراجع الصور والصلاحيات.

تُعتمد مدة الاحتفاظ بالمرفوض والمحذوف والبلاغات وAudit وجلسات الهوية بسياسة خصوصية محلية قبل إدخال بيانات حقيقية. لا تفرض هذه الوثيقة مدة قانونية. يتطلب التفعيل مكان تخزين بيانات معلومًا، ومسار تصحيح/حذف/تصدير محدودًا بصاحبه، ومراجعة ما يُرسل لمزودي الهوية والرسائل.

لا يحتاج التواصل WhatsApp Business API في النسخة الأولى؛ يجهز نصًا ويراجعه المستخدم ويفتح قناة خارجية أو ينسخه. لا نقرأ الرسائل ولا نسجل حصول بيع أو سرعة رد. التقاط النقرات لا يخزن نصها ولا يخلطها بمبيعات.

**تكلفة البروتوتايب:** الهدف صفر رسوم تشغيل فعلية ضمن حصص مضبوطة، مع قبول وسيلة الدفع للتفعيل فقط. لا SMTP/SMS مدفوعين، ولا نسخ مثال 5.25 GB القديم كحجم مستهدف للتجربة. تُقاس السعة والعمليات على حساب Micro كاملًا ويخصص هامش للصور ونسخها والتحميل المتروك. ارتفاع الحمل يستدعي تقليل التجربة أو منع العملية لا ترقية أو خصمًا صامتًا؛ عقد المجانية المرفق محدد الضوابط.

### تتبع القبول بعد التوجيه الأحدث

MM-01–22 معايير مطلوبة لا نتائج. ملحق FA-01–17 في ملف التنفيذ على Drive يزامن القرارات؛ FA-13 لمساحة المورد، FA-14 لاعتماد الأجزاء، FA-15 للفصل والتأجيل، FA-16 للمسح والاعتماد البنيوي، FA-17 لاختيار المزود بالدليل. CX-01–12 يحدد أدلة البيئة المتصلة؛ لا نجاح محاكاة يحل محله.

## 17. ما يلزم توفيره للتنفيذ وحدود الجاهزية

**محدد في هذه الوثيقة:** البنية المرجحة وبديلها، الفجوة مع الكود، البيانات والعلاقات، الهوية والجلسات والعزل، دقة الكميات والأسعار المقترحة، API، الصور، البحث، المسودات، التنقل، التزامن، المراجعة، التشغيل والاستعادة، الاختبارات والتسلسل.

**متطلبات تنفيذ فعلية وليست قرارات منتج مفتوحة:** حسابات الخدمات وGoogle OAuth ومفاتيحها، المصالحات داخل المستودع، اختيار مشاركين من أي محافظة وقطاع، سياسة احتفاظ ومراجعتها النظامية، تجربة تكلفة صفر ضمن حصص فعلية، وخطة الفرع/Claim. لا يتطلب البروتوتايب SMTP أو مزود SMS أو تحديد محافظة وقطاع وحيدين.

لا نحتاج الآن شراء سيرفر دائم أو خدمة دفع أو WhatsApp API أو محرك بحث مدفوع أو نقل قاعدة المال أو إضافة تبويب. ولا تعني جاهزية هذه المواصفات أن تكاليف التشغيل أو الأداء أو سياسات المزودين قد اختبرت بحساب المستخدم.

**التوصية التنفيذية الأولى:** T0 ثم T1؛ وبالتوازي المنطقي فقط تحضير مقارنة المزود. أول دليل متصل مطلوب هو حلقة صغيرة: مورد A ينشئ مادة وصورة خاصة، مشرف يعتمد نسخة بعينها، زائر يرى النسخة العامة، ومورد B يفشل في فتح مسودة A أو تعديلها. إذا أوقفنا المادة تختفي من البحث والصور، وتبقى مالية مايكرو كما كانت. هذه الحلقة تكشف مخاطر الأساس قبل توسيع الواجهات.

### إدارة القطاعات والحقول المعتمدة

إدارة القطاعات والفروع والحقول امتداد داخل إدارة السوق تحت التبويب نفسه. تتيح لقيس: إضافة واسم وترتيب ونقل فرع، إخفاءه من التصفح، إيقاف استقبال إعلانات جديدة فيه، وضبط حقوله. النشر العام يبين «لا توجد إعلانات بعد» إذا كان القطاع خاليًا، ولا يدعي أن غياب النتائج يعني غياب الموردين. قوائم القطاعات قابلة للبحث ولا يلزم حشدها جميعًا في المشهد الأول.

أنواع الحقول المسموحة: نص قصير، نص طويل محدود، رقم مع وحدة، اختيار واحد، خيارات متعددة، نعم/لا. يتحكم المالك بالاسم والمساعدة والإلزام والخيارات والوحدة والحدود وظهوره كفلتر عندما يدعم نوعه الفلترة. حقول السعر والكمية والحالة والملكية أساسية محمية، ولا يعاد تعريفها كحقول قطاع. لا JavaScript أو SQL أو صيغ تنفيذية من لوحة الإدارة.

معرف الفئة والحقل ثابت؛ تعديلات القالب تصدر نسخة جديدة. إعادة التسمية لا تغير المعرف، وجعل الحقل مطلوبًا يسري على الجديد أو النسخة المقدمة لاحقًا، ولا يمسح أو يعيد تفسير إعلان مقبول قديمًا. حذف ما له مراجع يتحول إلى تعطيل/أرشفة أو نقل بخريطة مراجعة؛ لا حذف متسلسل للإعلانات. تعليق كل محتوى قطاع إجراء إداري منفصل بسبب وتأكيد، وليس نتيجة ضمنية لتعديل اسمه أو إخفائه من القائمة. كل تغيير مسجل، وتعاين الواجهة النموذج قبل تفعيل نسخة القالب.

### حالة المادة والفوائض والبقايا

يفصل النموذج بين `material_condition` = جديد / مستعمل صالح للاستخدام، و`stock_form` = توريد اعتيادي / فائض / بقايا أو قصاصات. كلاهما يختاره الناشر بوضوح؛ يمكن أن تكون المادة جديدة وفائضًا معًا. المطلوب صور ممثلة للحالة، ووصف العيوب أو التفاوت والمقاسات الفعلية التي تؤثر في الاستخدام. مستعمل غير صالح أو موصوف بأنه جديد خلاف حقيقته لا يُقبل.

عند عرض كمية محدودة يظهر `declared_available_quantity` ووحدتها أو «دفعة واحدة» بمحتوى موصوف، مع وسم إن كانت الكمية تقريبية. هذه إفادة بائع وليست مخزونًا محجوزًا أو لحظيًا؛ لا ينقصها مايكرو من اتصال أو رسالة. فلاتر الحالة وشكل المعروض مضافة، وعند معرفة كمية محدودة يستبعد فلتر المطابقة طلبًا يتجاوزها. إذا لم تعلن الكمية فالمطابقة تخص شروط البيع فقط ويحتاج التوفر تأكيدًا. يبقى الحد والعبوة والمضاعف والسعر مربوطين بالوحدة نفسها؛ الدفعة غير القابلة للتحويل لا تقارن بسعر حبة أو كغم.

### Google وهوية النظام المشتركة

تسجيل واحد بزر «المتابعة باستخدام Google» وتدفق OAuth/PKCE مع state وnonce/التحققات المناسبة للمكتبة الرسمية، وإعادة فحص الجلسة والعضوية على الخادم. لا تقييد تلقائي لـ`@gmail.com` لأن حساب Google قد يستخدم بريدًا آخر؛ لا مزود بريد مستقل أو Email OTP أو كلمة مرور خاصة بالسوق في v1. تُستخدم هوية النظام المعتمدة لتخدم السوق وبقية أجزاء الشبكة، بينما يبقى استعمال Manage المحلي وفق قراراته، دون نسخ بياناته أو ربطها بالبريد المتشابه.

هاتف البائع معلومة اتصال منفصلة؛ Google لا يحقق ملكيته. في البروتوتايب يمكن قيس مراجعة القناة باتصال تحقق يدوي متفق عليه وتسجيل الطريقة والوقت؛ إن لم يتحقق الهاتف يوسم «أدخله البائع — غير متحقق» ولا تظهر شارة تحقق كاذبة. يشترط لقبول ملف البائع وضوح معلوماته ووجود قناة اتصال مقبولة؛ البريد المتحقق من Google ينشر فقط إن اختار صاحبه نشره. لا KYC أو سجل تجاري إلزامي عام ولا SMS مدفوع في هذا المسار. أساليب التحقق الأوسع لاحقًا تتبع سياسة النظام المشتركة.

### سياسة المراجعة المعتمدة والتغييرات المباشرة

قيس مسؤول التشغيل الأول. تُراجع معلومات البائع قبل نشره الأول، والإعلان الجديد، والصور الجديدة، وتغيير هوية المادة أو وصفها أو فئتها أو حالتها أو شكلها أو موقعها أو قناة الاتصال. يحتفظ التعديل المعروض للمراجعة بالنسخة السابقة المقبولة حتى قبول الجديدة، مع توضيح ما يراه العامة وإمكانية إيقاف القديم فورًا.

السعر وحدوده وشرائحه العددية ضمن نمط التسعير نفسه، والتوفر، والكمية المحدودة المعلنة، والإيقاف أو تأكيد التوفر تُحدث مباشرة إذا نجح تحقق الشروط والدقة والملكية. لا يمر معها تغيير صورة أو مادة أو قناة أو وحدة أو حد/مضاعف أو نمط تسعير. يُحفظ revision/حدث وactor/time/سبب التغير حيث يلزم؛ ليس تعديلًا صامتًا للتاريخ. إذا كانت هناك نسخة محتوى معلقة، تبقى مستقلة عن النسخة العامة، وعند الموافقة تُدمج التغييرات المباشرة فقط إذا بقيت الوحدة والشروط متوافقة، وإلا يظهر تعارض يحتاج إعادة تقديم. قرار قديم لا يعيد السعر أو التوفر تلقائيًا.

تأكيد التوفر أو تغيير السعر لا يرفع حظر إدارة أو انتهاء ظهور؛ تجديد الإعلان بعد 60 يومًا يدخل المراجعة. هدف 48 ساعة عمل داخلي يقاس، ولا يكتب كوعد للمستخدم قبل توفر قدرة تشغيل تثبته. صلاحية نشر أسرع لبائع ملتزم لاحقًا تحتاج سياسة مسجلة؛ لا تُفعّل تلقائيًا في البروتوتايب. يظل إبلاغ المادة/الحساب، وحظر بائع داخل مايكرو وإخفاء إعلاناته عن الحساب الحاظر، وإلغاء الحظر متاحًا دون ادعاء إيقاف اتصالات خارج التطبيق. منع الإساءة والإيقاف الإداري لا يعتمدان على عدد البلاغات وحده.

### تأكيد حدود التوجيه الأحدث في الإضافات

قرارات OD-15–21 تسري على هذه التفاصيل أيضًا: مساحة المورد داخل Market بالحساب نفسه؛ تجهيز المسودة والصور الخاصة أثناء المراجعة؛ لا نشر قبل قبول الملف والنسخة والصور جميعًا. التسجيل والتقديم والاعتماد والنشر ليست مترادفات. بوابة السائق لا تنشئ بوابة مورد مماثلة أو تدمج ملفات الدورين. My Ask Micro واختيار الوحدات مؤجلان، ولا ينشأ Delivery أو شراء أو أثر Manage تلقائيًا. المراجعة ومنح أدوار الاختبار يدويًا مقبولان من مصدر خادمي موثوق فقط؛ لا محاكاة محلية بديلًا عن القبول المتصل. التقنيات والمزود وصف موثق مشروط، لا دليل تشغيل أو اختيار نهائي.

### عقد المجانية والتجربة المتصلة

المطلوب تشغيل محدود على خطط مجانية فعلية، لا نموذجًا محليًا بدل الشبكة. مرشح الإثبات Workers Free + D1 Free + R2 Standard وهوية Micro مع Google؛ Postgres/RLS بديل مقارنة قبل اختيار DB، ومعالجة صور R2 عبر Images Free ضمن حصة تحويل مجانية مثبتة، دون اختيار Hosted Images المدفوع. إذا كان للنظام مزود هوية مشترك معتمد يدعم Google يستخدمه السوق؛ لا يضاف مزود مستقل ثاني. Cloudflare اتجاه موثق؛ اختيار DB بعد دليل العزل والملكية والأداء والتكلفة والتوافق مع ADR Micro، دون افتراض تفعيل الخدمات. خدمات إرسال SMS والبريد والهواتف الآلية ليست متطلبات البروتوتايب.

إضافة وسيلة دفع مسموحة للتفعيل، لكن لا تفعل خطة مدفوعة أو overage عمدًا ولا ترقية آلية. الخطط المجانية ليست وعدًا باستخدام غير محدود أو جاهزية إنتاج. يفحص المنفذ شروط الحساب الفعلية ومجموع استعمال Micro والخدمات الأخرى عليه قبل التشغيل؛ ويستبعد خدمة لا يمكن تقييد تكلفتها، أو يكتب بديلًا مجانيًا متوافقًا. تجاوز سقف التجربة يوقف الإجراء المسبب ويظهر السبب بدل تكبد رسوم. لا يُعرض صفر تكلفة كحقيقة تشغيل قبل اختبار الضبط وبيان الخطط على الحساب.

ضوابط بداية هندسية وليست حصرًا لمنتج السوق: حتى 100 حساب مشارك و500 إعلان نشط في التجربة؛ كل مشارك مخول يستطيع التقديم؛ النشر بعد الموافقات، دون حصر جغرافي أو قطاعي. وسائط حتى 6 صور للإعلان وبحد رفع 2 MB للصورة؛ حتى 2 GB إجمالي مساحة R2 محسوبة مع staging والمشتقات والنسخ والاحتياطي المحجوز، أو أقل إذا كان الهامش المتبقي في حساب المالك أصغر. تحدد حصص عمليات R2 والتحويلات والمراقبة على مستوى النظام بهامش محافظ دون الحصة المجانية المتاحة الفعلية، لا لكل جزء كأنه يملك الحصة كلها. الوصول إلى 80% ينبه المسؤول، وبلوغ الحد الداخلي يمنع المزيد من العملية المسببة. تستمر القراءة المسموحة إن بقي لها هامش؛ لا يزال مخزون أو مالية Manage خارج هذه الحصص.

رفع البروتوتايب يمر عبر Worker بإذن رفع أحادي الاستهلاك وملكية وحصة محجوزة قبل استدعاء R2؛ لا يصدر رابط PUT مباشر قابلًا لإعادة الاستخدام خارج بوابة الحصة. تكرار العملية نفسها يعيد النتيجة دون كتابة R2 أخرى. يعالج الملف خادميًا بحدود CPU وخدمة الصور المجانية، وتفشل المعالجة بأمان دون نشر الأصل إذا استنفدت حصتها. الرفع المباشر الموقّع خيار توسعة لاحقة بعد عقد تكلفة وتكرار، وليس مطلوبًا الآن.

تختبر بوابة المجانية عدد الطلبات وأحجامها والاحتفاظ بالنسخ ومحاولات الإعادة والملفات المتروكة واستدعاءات الصور والرسوم المحتملة، وتوثق إعدادات المنع. اختبار 10,000 إعلان لقياس التوسع يستخدم بيانات اصطناعية محلية أو بيئة اختبار ضمن حصصها، ولا يعني فتح تجربة حية بهذا الحجم أو شراء خطة أعلى. رفع حصص التجربة مستقبلًا قرار تشغيل مبني على القياس وخطة تكلفة جديدة؛ قابلية التوسع تعني بنية يمكن تطويرها دون إعادة تعريف المنتج، لا وعد تشغيل غير محدود مجانًا.

### إضافات البيانات والـAPI والاختبارات بعد الاعتماد

تضاف `material_condition/stock_form/declared_available_quantity/quantity_is_estimate` مع نسخة المحتوى، و`blocked_sellers` مملوكة للهوية ولا تغيّر صلاحيات الوصول العام، ونسخ `category_schema` و`publication_updates` لضبط دمج تحديث السعر المباشر. إدارة الفئات والحقول بـendpoints مخولة للمدير وتحقق Schema مشترك؛ endpoints الحظر والإلغاء خاصة بصاحبها. تحديث السعر endpoint محدود الحقول لا يمرر صورة أو وحدة أو حالة اعتماد. ميزانية الاستخدام والحجز مشتركة على مستوى Micro، وإذن الرفع أحادي الاستهلاك مربوط بالفاعل والجهة والنسخة.

اختبارات إضافية: حساب Google صالح/مرفوض وعودة آمنة بلا Open Redirect؛ مستخدم غير محترف ينشر بعد مراجعة بطاقته؛ فائض جديد وبقايا ومستعمل بعيوب واضحة؛ عدم مطابقة كمية محدودة أصغر؛ قالب فئة جديد لا يفسد إعلانًا قديمًا؛ سعر مباشر لا يعود للخلف عند موافقة محتوى؛ حظر/إلغاء وإخفاء نتائج البائع للحاظر؛ امتلاء الحصة وحجز متزامن ورابط رفع لا يتجاوز العامل؛ وصفر بيانات مالية مرسلة للشبكة. آلية توفير الخدمة مستقبلًا داخل تطبيق موزع موضوع منفصل، ولا تختار هذه الوثيقة متجرًا أو Native أو ضيوفًا بطريقة جديدة.
### حدود الميزانية الأولية واختبارات القرارات النهائية

حصص تشغيل أولية داخلية مشتركة لكل Micro: 20,000 طلب Worker يوميًا، و500,000 صف D1 مقروء و20,000 صف مكتوب يوميًا محسوبة مع الفهارس وأعمال الحصص، و200,000 عملية R2 من فئة A و2,000,000 من فئة B شهريًا، و1000 تحويل صورة جديد شهريًا. تتقدم حدود الحساب المجانية الفعلية المتبقية إذا كانت أصغر، وتترك هوامش لاستدعاءات التحقق والنسخ والإعادة. ليست هذه حصص المزود الموعودة للمستخدم، ولا بديلًا عن قراءة خططه عند التفعيل. يراجع اختبار W2 دقة الحساب والاحتياط والأثر عند بلوغ كل حد؛ لا تُزاد تلقائيًا لأن الخدمة تقبل الدفع.

متطلبات اختبار مشتركة غير منفذة: Google وحده للدخول؛ مستخدم عادي يتحول إلى ناشر من الحساب نفسه؛ إدارة قيس للقطاعات والحقول دون إفساد الإعلانات؛ جديد/مستعمل مع فائض/بقايا وكمية معلنة؛ تحديث سعر مباشر لا يعكسه اعتماد محتوى أقدم؛ حظر وإلغاء حظر؛ ورفع Worker أحادي الاستهلاك مع بلوغ الحصة. المراجعة الإدارية تحتاج TOTP/MFA مجانيًا للمشرف في المسار المرجعي، لا SMS MFA مدفوعًا. تفاصيل إتاحة الخدمة في تطبيق موزع مستقبلًا تظل موضوعًا منفصلًا بقرار المالك؛ لا يحول البروتوتايب إلى مشروع Native جديد.

المراجع الرسمية المحددة لهذه القرارات (تحقق إعداداتها عند التشغيل): [Google OAuth](https://supabase.com/docs/guides/auth/social-sign-in/auth-google)، [TOTP MFA](https://supabase.com/docs/guides/auth/auth-mfa/totp)، [R2 pricing](https://developers.cloudflare.com/r2/pricing/)، [Images Free](https://developers.cloudflare.com/images/pricing/)، [D1 Free](https://developers.cloudflare.com/d1/platform/pricing/)، [Workers limits](https://developers.cloudflare.com/workers/platform/limits/). الأرقام الداخلية أعلاه ضوابط هندسية دون حصص المزود، وليست تصريح اشتراك أو نتيجة قياس فعلية.

التنفيذ يفصل `published_content_revision_id` عن `commercial_version` و`availability_version`، ويستخدم قارئًا واحدًا `effective_offer` لتكوين العرض العام. أحدث لقطة سعر مصرح بها مصدر السعر الحالي، وسجل التحديثات تاريخها لا مصدر منافس؛ النسخة المحتوائية المعلقة تحفظ الإصدار التجاري الذي بدأت منه. كل كتابة مباشرة تستخدم نسخة متوقعة، والموافقة تقارنها ثم تحمل آخر سعر فقط عند تطابق الوحدة والشروط، وإلا ترفض بتعارض. لا قرار مراجعة يجعل لقطة سعر سابقة حاكمة فوق تحديث أحدث.
