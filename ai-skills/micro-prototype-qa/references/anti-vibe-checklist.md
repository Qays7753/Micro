## الهدف

حوّل قرار المنتج إلى واجهة ذات سبب واضح لكل رقم ولون وبطاقة وفعل. لا يعني هذا إخفاء استخدام AI؛ بل منع الواجهة العامة والمنفصلة عن مهمة صاحب المشروع.

## قبل البدء

1. شاهد الشاشة الحية أو لقطة حقيقية. لا تحكم من وصف لفظي فقط.
2. حمّل حزمة القراءة (`QUALITY` وفق `AGENTS.md` §2) — لا قوائم قراءة مكررة هنا.
3. عند أي تغيير بصري، اقرأ كذلك `ai-skills/micro-design-system/SKILL.md` و`ai-skills/micro-web-native-ux/SKILL.md`.
4. لا تتعامل مع «لا يبدو جيدًا» كحكم نهائي؛ حوّله إلى عنصر محدد وقرار مستخدم ودليل مرئي وإصلاح مقترح.

## سير التدقيق

### 1. اختبار اللمحة

دوّن أول ثلاثة عناصر تقع عليها العين خلال نصف ثانية. قارنها بالفعل أو الرقم الأهم في الشاشة. إذا برزت صورة زخرفية أو بطاقة شرح قبل القرار، سجل خلل هرمية كبيرًا.

### 2. خريطة المعنى

لكل surface ظاهر، اكتب واحدًا فقط: **قرار، رقم موصوف، حالة، إدخال، أو فعل**. احذف أو ادمج ما لا يحمل واحدًا منها. لا تستخدم Card كغلاف افتراضي لكل فقرة.

### 3. تدقيق الطابع المولد

افحص قائمة الإشارات أدناه. ركز على التكرار البصري والنصوص العامة والألوان غير الدلالية والوعود التي لا يدعمها Domain والأصول الزخرفية التي تسبق المهمة.

### 4. تدقيق الثقة المالية

لا تعرض رقمًا بلا: الاسم المالي الصحيح، المصدر أو النطاق، الفترة إن وجدت، ودرجة المعرفة عند الحاجة. لا تسمِّ قبض الطلب كاشًا حاليًا، أو متبقيًا قبل التسليم دينًا، أو مؤشر طلبات مكتملة ربح المشروع.

### 5. تدقيق الإدخال والـRTL

اتبع قرار Micro الحالي: حقول الأرقام تقبل وتعرض **أرقامًا إنجليزية `0–9`**، وتبقى أسطر الرقم والعملة والتاريخ معزولة LTR داخل واجهة RTL. احتفظ بقيمة الإدخال كسلسلة مستقرة، وتحقق منها ثم حوّلها في Application عند الحفظ؛ لا تحوّل `Number(value) || 0` مع كل ضغطة. (الأصل التعاقدي: `docs/contracts/10-cash-continuity-prototype-contract.md`.)

### 6. تدقيق affordance

كل زر أو صف قابل للنقر يحتاج تسمية أو حاوية أو موضعًا أو سهمًا أو رمزًا يطابق سلوكه. كل بطاقة غير قابلة للنقر يجب ألا تحاكي حقلاً أو زرًا. لا تجعل اللون ذاته يعني علامة هوية وحالة مالية وقابل للنقر في الشاشة نفسها.

### 7. الإقرار

قبل قبول التغيير، تحقق حيًا من العربية RTL وLight/Dark وأحجام 360 و390 و430 والنص الطويل ولوحة المفاتيح والرجوع الآمن. راجع الكود: لا منطق مالي في React ولا وصول مباشر إلى IndexedDB.

## قواعد منع الأنماط العامة

| نمط يجب منعه | البديل المطلوب |
| --- | --- |
| hero أو texture عام يسبق الرقم أو الفعل | سطح قرار هادئ يبرز الفعل أو الرقم ثم التفاصيل عند الحاجة. |
| بطاقات مستديرة متشابهة لشرح وحالة ومدخل وفعل | سطح واحد لكل كتلة ذات معنى، مع فرق واضح بين input والحالة والفعل. |
| «قرار الآن/ما نعرفه/الخطوة التالية» مكرر في كل route | استخدم هذا النحو فقط حين يضيف قرارًا جديدًا؛ وإلا اكتب سياق الشاشة مباشرة. |
| نص حماية طويل ومتكرر | اعرض الجملة اللازمة بجانب لحظة الخطر، ثم ووفر تفصيلًا عند الطلب. |
| ألوان pastel متعددة من دون معنى مالي | اربط اللون بحالة دلالية واحدة، واستخدم التباين والحجم والتجميع للهرمية. |
| Dashboard بمؤشرات مشروع غير مدعومة | اعرض «صورة الطلبات المسجلة» بتعريف وحدود معرفة، أو لا تعرض الرقم. |

## معيار القبول

يقبل التغيير عندما يستطيع صاحب مشروع عربي أن يجيب في ثوانٍ: **ماذا حدث؟ ما الرقم الذي يهمني؟ ما درجة ثقته؟ ما فعلي التالي؟** ولا يمكن لأي عنصر بصري أن يعده بفعل أو دقة لا يوفرهما التطبيق.

## ممنوعات

لا تنسخ Dashboard من ERP أو POS أو Figma Kit. لا تغير ألوان Micro أو Domain Core لأن مشكلة الواجهة بصرية. لا تضف رسمًا بيانيًا أو KPI أو «ربح المشروع» لإضفاء طابع مالي بلا event model وفترة وسياسة معرفة داعمة.

## مصدر القرار (من القائمة القصيرة الأصلية)

| السؤال | علامة الفشل |
| --- | --- |
| هل للشاشة فعل أساسي واحد أو رقم واحد واضح؟ | كل العناوين والبطاقات متساوية الوزن. |
| هل لكل رقم معنى ونطاق ومعرفة؟ | رقم مزخرف أو label فضفاض مثل «الإجمالي». |
| هل كل بطاقة إدخال أو حالة أو فعل بوضوح؟ | بطاقة ثابتة تشبه input، أو card قابل للنقر لا يبدو زرًا. |
| هل النص يصف واقع المستخدم لا فلسفة المنتج؟ | «لنرتب»، «لا تقلق»، «الفهم قبل الرقم» يحل محل معلومة أو فعل. |
| هل اللون يؤدي معنى واحدًا؟ | لون الهوية نفسه للزر والحالة والتحذير والوسم الثابت. |

## إشارات التصميم المولد التي تتطلب تدقيقًا

1. surface مستدير وظل خفيف لكل عنصر بلا فرق وظيفي.
2. صورة أو texture أو icon tile يلفت الانتباه قبل المهمة.
3. ثلاث بطاقات معلوماتية ملونة متجاورة بلا اختلاف في القرار أو الأولوية.
4. CTA صغير أسفل شرح طويل أو فعل أساسي مخفي خلف scroll.
5. لغة مطمئنة متكررة بدل مصطلح مالي صحيح ومحدد.
6. رقم يعرض عملة/موقعًا/دقة بطريقة متعارضة مع العقد أو لا توضح مصدره.
7. عدم وجود focus أو pressed أو سبب لحالة disabled.

## مراجع مهنية

- NN/g، [Visual Hierarchy](https://www.nngroup.com/articles/visual-hierarchy-ux-definition/): استخدم اللون والحجم والتجميع لتوجيه الانتباه نحو الأهم، لا لتلوين كل سطح.
- MDN، [`inputmode`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/inputmode): اعتبره تلميح لوحة مفاتيح فقط، لا تحققًا للرقم.
- Boldare، [Design system for vibe coding teams](https://www.boldare.com/blog/vibe-coding-design-system/): افهم التوكنات ووثائق المكونات وبوابات المراجعة كممارسات قابلة للتكييف، لا كمعيار ملزم.
