# Micro Web Native UX

> **التسجيل (WS-204 — 2026-10-01):** المالك: مالك المنتج · آخر مراجعة: 2026-10-01 · الحالة: CURRENT/OPERATIONAL · مسجلة في `ai-skills/README.ar.md` و`docs/00-document-index.md`.
> **السلطة:** هذه المهارة تشغيلية فقط ولا تعلو فوق عقود Micro ووثائقها canonical؛ عند أي تعارض يُوقف التنفيذ ويُسجَّل التعارض بدل حسمه داخل المهارة.
> **التفعيل:** بناء أو مراجعة App Shell والتنقل والشاشات وBottom Sheets والنماذج والرجوع ولوحة المفاتيح وRTL وSafe Areas وPWA UX وحالات الواجهة.
> **عدم التفعيل:** تغيير قيم الهوية والتوكنات (لمهارة micro-design-system ومجموعة docs/architecture/) أو حسم معنى مالي؛ سلطتها سلوك تجربة الويب.

## الغرض

طبّق تجربة Web App تبدو كتطبيق Android حديث من حيث السلوك واللمس والطبقات، مع إبقاء Micro تطبيق ويب فعليًا. لا تغيّر الهوية البصرية المثبتة أو النطاق المالي أو عقود Domain.

## اقرأ قبل التنفيذ — حزمة واحدة

حمّل حزمة القراءة `UI` وفق `AGENTS.md` §2 (النواة + الحزمة) — لا قوائم قراءة مكررة هنا.
## قواعد التجربة

1. ابنِ Web App بملء الشاشة مع App Shell واضح، لا صفحة Website ولا Dashboard مكتظًا.
2. اجعل RTL والعربية معيار الاختبار الأول، مع دعم النصوص الطويلة والأرقام والتواريخ دون قص أو انعكاس خاطئ.
3. استخدم الهوية والتوكنات من مرجع UI/UX. لا تضع Hex أو قياسًا خامًا داخل مكوّن إذا كان له Semantic Token معتمد.
4. استخدم Bottom Sheet للمحتوى الثانوي أو الإجراء القصير فقط. اجعل الإغلاق بالرجوع وEscape آمنًا، واحفظ المسودة قبل الإغلاق، ولا تجعل الطبقة تخفي زر الحفظ مع لوحة المفاتيح.
5. اجعل لكل شاشة فعلًا أساسيًا واحدًا واضحًا. لا تضع الحذف أو الإلغاء بجوار الحفظ دون فصل بصري وتأكيد مناسب.
6. أظهر الحالات الأربع على الأقل: loading، empty، no-results، error. لا تستخدم empty عندما فشل التحميل، ولا تعرض نجاحًا قبل تأكيد الحفظ.
7. اجعل الحالة المالية نصية وصريحة. لا تجعل اللون وحده يقرر الربح أو الخسارة، ولا تعرض نتيجة نهائية إذا كانت التكلفة ناقصة.
8. صمّم العرض الأساسي لأحجام الهاتف المعتمدة في المرجع، ثم عالج العرض الأوسع دون تحويله إلى تجربة Desktop مختلفة.
9. طبّق focus واضحًا، أهداف لمس مناسبة، ترتيب Tab منطقيًا، تسميات عربية، ورسائل خطأ مرتبطة بالحقل وقابلة للفهم.
10. اجعل PWA وOffline UX طبقة تشغيل: لا تغيّر معنى الحدث المالي ولا توحي بأن البيانات متزامنة مركزيًا في Prototype المحلي.

## سير العمل

ابدأ بتعريف هدف الشاشة، الحالة التي تدخلها، البيانات التي تعرضها، القرار الذي تساعد عليه، والفعل التالي. حدّد قبل الكود ما إذا كانت الشاشة صفحة كاملة، Sheet، Dialog، أو جزءًا من App Shell.

اربط كل عنصر تفاعلي بعقد Application/Use Case. لا تستخرج نتيجة مالية في المكوّن، ولا تحفظ مباشرة في IndexedDB من الواجهة. اختبر المسار الطبيعي ثم المسودة والرجوع ولوحة المفاتيح وفشل الحفظ والتكرار.

عند استخدام مكوّن أو نمط من Material 3 أو Figma أو مكتبة خارجية، خذ السلوك أو البنية فقط، وأعد تنفيذه ضمن هوية Micro. افحص الترخيص قبل نسخ أصول أو كود.

## معيار القبول

اعتبر التغيير مقبولًا فقط إذا كان قابلًا للاستخدام بالعربية RTL، يعمل في Light وDark، لا يسبب dead end، يحافظ على المسودة عند الرجوع الآمن، يوضح loading/empty/error/no-results، ويقود المستخدم إلى قرار مفهوم. أرفق لقطات أو خطوات إعادة الاختبار عند تغييرات الواجهة المهمة.

## ممنوعات

لا تضف POS أو Inventory أو Ledger أو Auth أو Sync أو Billing بحجة تحسين UX. لا تنقل Material 3 كهوية كاملة. لا تخلط صفحة Web مع Native runtime داخل نفس القرار. لا تغيّر لون Micro أو الخط أو المسافات المعتمدة دون قرار Canonical جديد.
