# Micro Anti-Vibe Interface Audit

## الهدف

حوّل قرار المنتج إلى واجهة ذات سبب واضح لكل رقم ولون وبطاقة وفعل. لا يعني هذا إخفاء استخدام AI؛ بل منع الواجهة العامة والمنفصلة عن مهمة صاحب المشروع.

## قبل البدء

1. شاهد الشاشة الحية أو لقطة حقيقية. لا تحكم من وصف لفظي فقط.
2. اقرأ `docs/product/mobile-ui-ux-reference-v1.md` و`docs/product/financial-operating-model-v1.md` و`docs/contracts/05-financial-p0-policies.md` من جذر Micro.
3. عند أي تغيير بصري، اقرأ كذلك `ai-skills/micro-design-system/SKILL.md` و`ai-skills/micro-web-native-ux/SKILL.md`.
4. لا تتعامل مع «لا يبدو جيدًا» كحكم نهائي؛ حوّله إلى عنصر محدد وقرار مستخدم ودليل مرئي وإصلاح مقترح.

## سير التدقيق

### 1. اختبار اللمحة

دوّن أول ثلاثة عناصر تقع عليها العين خلال نصف ثانية. قارنها بالفعل أو الرقم الأهم في الشاشة. إذا برزت صورة زخرفية أو بطاقة شرح قبل القرار، سجل خلل هرمية كبيرًا.

### 2. خريطة المعنى

لكل surface ظاهر، اكتب واحدًا فقط: **قرار، رقم موصوف، حالة، إدخال، أو فعل**. احذف أو ادمج ما لا يحمل واحدًا منها. لا تستخدم Card كغلاف افتراضي لكل فقرة.

### 3. تدقيق الطابع المولد

افحص قائمة [`references/checklist.md`](references/checklist.md). ركز على التكرار البصري والنصوص العامة والألوان غير الدلالية والوعود التي لا يدعمها Domain والأصول الزخرفية التي تسبق المهمة.

### 4. تدقيق الثقة المالية

لا تعرض رقمًا بلا: الاسم المالي الصحيح، المصدر أو النطاق، الفترة إن وجدت، ودرجة المعرفة عند الحاجة. لا تسمِّ قبض الطلب كاشًا حاليًا، أو متبقيًا قبل التسليم دينًا، أو مؤشر طلبات مكتملة ربح المشروع.

### 5. تدقيق الإدخال والـRTL

اتبع قرار Micro الحالي: حقول الأرقام تقبل وتعرض **أرقامًا إنجليزية `0–9`**، وتبقى أسطر الرقم والعملة والتاريخ معزولة LTR داخل واجهة RTL. احتفظ بقيمة الإدخال كسلسلة مستقرة، وتحقق منها ثم حوّلها في Application عند الحفظ؛ لا تحوّل `Number(value) || 0` مع كل ضغطة.

### 6. تدقيق affordance

كل زر أو صف قابل للنقر يحتاج تسمية أو حاوية أو موضعًا أو سهمًا أو رمزًا يطابق سلوكه. كل بطاقة غير قابلة للنقر يجب ألا تحاكي حقلاً أو زرًا. لا تجعل اللون ذاته يعني علامة هوية وحالة مالية وقابل للنقر في الشاشة نفسها.

### 7. الإقرار

قبل قبول التغيير، تحقق حيًا من العربية RTL وLight/Dark وأحجام 360 و390 و430 والنص الطويل ولوحة المفاتيح والرجوع الآمن. راجع الكود: لا منطق مالي في React ولا وصول مباشر إلى IndexedDB.

## قواعد منع الأنماط العامة

| نمط يجب منعه | البديل المطلوب |
| --- | --- |
| hero أو texture عام يسبق الرقم أو الفعل | سطح قرار هادئ يبرز الفعل أو الرقم ثم التفاصيل عند الحاجة. |
| بطاقات مستديرة متشابهة لشرح وحالة ومدخل وفعل | سطح واحد لكل كتلة ذات معنى، مع فرق واضح بين input والحالة والفعل. |
| «قرار الآن/ما نعرفه/الخطوة التالية» مكرر في كل route | استخدم هذا النحو فقط حين يضيف قرارًا جديدًا؛ وإلا اكتب سياق الشاشة مباشرة. |
| نص حماية طويل ومتكرر | اعرض الجملة اللازمة بجانب لحظة الخطر، ثم وفر تفصيلًا عند الطلب. |
| ألوان pastel متعددة من دون معنى مالي | اربط اللون بحالة دلالية واحدة، واستخدم التباين والحجم والتجميع للهرمية. |
| Dashboard بمؤشرات مشروع غير مدعومة | اعرض «صورة الطلبات المسجلة» بتعريف وحدود معرفة، أو لا تعرض الرقم. |

## معيار القبول

يقبل التغيير عندما يستطيع صاحب مشروع عربي أن يجيب في ثوانٍ: **ماذا حدث؟ ما الرقم الذي يهمني؟ ما درجة ثقته؟ ما فعلي التالي؟** ولا يمكن لأي عنصر بصري أن يعده بفعل أو دقة لا يوفرهما التطبيق.

## ممنوعات

لا تنسخ Dashboard من ERP أو POS أو Figma Kit. لا تغير ألوان Micro أو Domain Core لأن مشكلة الواجهة بصرية. لا تضف رسمًا بيانيًا أو KPI أو «ربح المشروع» لإضفاء طابع مالي بلا event model وفترة وسياسة معرفة داعمة.
